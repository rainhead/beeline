# Browsing: scope, filters, sort

Part of Beeline's architecture notes; the index is [README.md](README.md).

Browsing lives at `/samples` and `/specimens` (`src/app/listings.ts` + `src/app/views/listings.tsx`, beeline-2c3.21): the same paged table at two grains, with scope, filters, search, sort and page all in the query string so a filtered listing is a shareable URL, and one download of exactly what the filters select: a CSV on `/samples`, and on `/specimens` the Excel file for editing specimens (beeline-kgyd.5, Peter, 2026-11-17: the specimens CSV was dropped, so that the Excel file is that listing's one download; a program reads the same columns from the API's specimen rows, and the exports page has the files). Its columns are in Darwin Core terms wherever one exists (the pin's number is `fieldNumber` and `catalogNumber` the museum's, filled only where Ecdysis has reported it, per ADR 0008's amendment and gh-98; the sample number is `fieldNumber` on the samples CSV and `sampleNumber` among the specimen columns). The samples CSV is UTF-8 with a BOM, `\n` line endings, and streamed whole a page at a time, so it has no cap and no line that is not a record; a numeric cell is never formula-guarded, since a guarded longitude is `'-123.26`, text. Reshaped with Peter and Nora on the sandbox (2026-09-16): each column heading opens a menu holding that column's two sort orders and its filter — a listing *describes* its columns as `TableColumn` specs and `DataTable` draws them, through the one `ColumnMenu` in the component library (the header's `<details class="menu">` with the panel fixed so the wrapper's sideways scroll cannot clip it), so every menu wears the same chevron, the order in force is a separate arrow with `aria-sort` on the heading cell, and no screen can draw a heading differently from the next; it was written out twice at first, for the listings and for People, and the two had drifted within a day (Peter, 2026-09-17) — whose form carries the rest of the query as hidden inputs (`listingParams` is the one place the query becomes a query string, so hidden inputs and hrefs agree); what is in force reads off a row of dismissable pills, not off ten controls. Above the table sit the search box and a three-way toggle — my records, my atlas's (from `person_membership`), all — with every other program and "At large" reached through the Atlas column and shown as a pill. There is no season filter: the dashboard's link to settled seasons names a date, the day before `season.active_since`. A record's number is a pill, the iNaturalist link is the wordmark, the host plant is a column on both listings (with its common name after it, and a filter that matches the name as observed, what iNaturalist calls the plant now, or its common name, which downloads carry as four columns after all the others: [plant-taxa.md](plant-taxa.md#what-a-host-is-today), beeline-rfkj.4), the samples listing says whether each sample was netted or trapped — a Method column, the sample page's word, with a filter and no order, since sorting two values only puts one first; the filter (`kind`) narrows specimens too, by the sample they came from — whether labels are on paper is a filter (`labels`, beeline-3v33) in the Specimens column's menu on samples and the Field number column's on specimens: a sample is waiting on labels while any specimen of an active season has none on paper, held back by a flag or in a run not yet printed (`sample_labels_waiting`, `schema/155`), and its count is written beside the specimens; a specimen asks of its own label (`specimen_on_paper`, `schema/101`, the per-specimen test `printed_sample` is now read from, so the filter and the rule that stops a printed sample following iNaturalist cannot disagree) — the samples listing's Flags cell names each kind of flag on the row in a word or two (beeline-ik0d, Peter 2026-11-04; the words in `listings.status.flag`, held to `qc_rule` by a test), a missing field naming the field and a hold showing its reason, coloured for whether it blocks printing and opening, as a `details.menu`, onto the rule's instruction and a link to the sample, since a phone has no hover; the kinds of flag are gathered in the pass that counts them, which costs nothing more, but what the findings say is not, because building every sample's details for the aggregate added about a third to the page and asking for the page's afterwards rebuilt the whole union of rules, so only the two chips made from a finding read their rule's own view for the page's samples (`findingWords`) and the rest leave their details to the sample page; colour is not the only signal, the severity being in each chip's accessible name and at the head of its panel, with blocking flags first, and a symbol for it waits on the domain icon set (beeline-2c3.14); three show and the rest are a link to the sample; and the column's menu filters to one kind (`flag`) beside the severity filter, which on specimens narrows by their sample's flags, as the severity filter does — the specimens listing also carries the date the determination of record was made — an order and no filter, since "what came back from the taxonomist this winter" is asked by sorting, and a dash where the source gave no date, which is most legacy determinations — and on a wide screen the heading row is sticky — which needs the wrapper to stop being a scroll container, since sticky positions against the nearest one, so `main > .table-scroll` is `overflow: visible` from 64rem up. A session is keyed by `inat_user_id`, never by `person.entity_id`: that is a per-store sequence draw a rebuild or `db:reseed` redraws, so a session holding one resolved to whoever inherited the number and a volunteer browsed as somebody else under the `mine` scope forced for them (beeline-ten). The person is resolved through `inat_account` per request, which also makes unbinding an account end its sessions and rebinding move them. Resolution failing is not revocation: an unbound session stops sliding its `last_seen_at` so the idle cutoff never reaches it, and rebinding that iNat user would revive every cookie ever issued for it as whoever now holds the account — so `endSessionsFor` runs on both sides of an account change and the idle purge collects orphans. Scope is `mine` (where everyone starts), one program, `outside` (collected where no member atlas reaches, called "At large" on the pages), or all of them. The Atlas column's menu lists every program, because an atlas is one kind of program (beeline-t0rh, Peter, 2026-11-18): the atlases, the National Wildlife Refuges (`NWR`) and the BLM surveys, with "At large" last; "My records" is not a program and is the scope toggle's first position, not a menu choice. A program with no states assigned has no atlas to read a sample's by, so `NWR` is the samples whose true point lies inside a refuge area (`sample_area_current`, kind `refuge`), found only where the reader may see the location, as the place filter is, and a refuge sample stays its atlas's as well, so `OBA` still finds it; `BLM` has no samples to find yet (beeline-8zlh will link the refuge program to its refuges, and the programs' own events will say which program a sample was collected for). `MM` is accepted as another name for `outside`, since the catch-all program is today exactly the samples no atlas covers, and is not offered in the menu beside it. `scopePrograms` lists the menu's programs, and the API takes the same codes as `scope`. Every scope is open to everyone: a volunteer sees every record, at minimum what iNaturalist already shows them (Peter, 2026-10-23, beeline-20w3). Until then `mine` was forced for volunteers at parse time, and the scope picker, the collector filter and the `member` filter were staff's. Scope asks where a sample fell; the `member` filter asks where its collector belongs, and the two genuinely disagree — most records from outside the atlases are members travelling (beeline-lcl). **What a reader may not see is a location**: where a sample's observation is obscured or private on iNaturalist (`sample.geoprivacy` or `taxon_geoprivacy`), or the sample cites an observation no sync has read, so that nobody here knows whether it is (1,537 legacy-linked samples on the dev store until the nightly began reading them by id, and the 404 whose observation iNaturalist no longer has after), and the reader is neither staff nor one of its collectors — a co-collector counts, and so does whoever acts for one, since a delegate reads a household's records as the household does — the row carries no coordinates, uncertainty, elevation or locality, and no county either where the observation is private, which is what iNaturalist shows them. iNaturalist's own shifted point is not offered instead; nobody has a use for it (Peter). The rule is `withheld` in `src/app/listings.ts`, applied in the query rather than the view — the location join yields nothing and the place columns read through a CASE — so the place filter, the place sort and the CSV all see the hidden values, and a search cannot find a record by a locality it would not show; the record pages reuse it, and drop with it the observation's place guess, the overrides, the history of where the sample was and what its findings quote. The observer's notes stay, as iNaturalist shows them to everyone, though they are where a volunteer writes the spot: iNaturalist's own handling is half-hearted and nobody has a better rule (Peter, 2026-10-23). Downloads carry coordinates otherwise, with their provenance and geoprivacy beside them: the open per-atlas question ([docs/questions.md](../questions.md)) is about revealing taxon-obscured coordinates *downstream* — on labels, to Ecdysis and GBIF — not about showing a participant their own data, and CONTEXT.md's stance is that anyone trusted with this store is trusted with them. Dashboards scope to the active seasons: the current one, and last season until 1 March, when it settles (`season`/`settled_sample`, CONTEXT.md's **Season**), still flagged and still fixable but no longer asking.

On `/samples` the Place cell of a sample whose locality the reader may change carries a pencil (beeline-7ywr, Peter, 2026-11-04): it opens, in the cell, a combobox of iNaturalist's own locality and the names suggested from the coordinates, each with why in a word or two ("nearby town", "park") and listed with the sample's county and state as the column writes the place but saved as the locality alone (a choice's `label`, which the island shows in place of its value), free for staff to write one in, and Save posts to `/samples/:id/place`, which works out from the name alone what to write (empty or iNaturalist's name follows iNaturalist again, a suggested name is adopted, anything else is written in), then returns to the same listing, or to the sample's page where the editor was opened there. The editor is `PlaceEdit` (`src/app/views/components/place-edit.tsx`), shared with the sample page's Place row, on the general `InlineEdit` (beeline-8w8n). Staff are offered it on a printed sample too, to correct the record before a reprint, with a line saying the labels keep the old name; nobody else is, and nobody on a printed sample entered in Beeline, whose own form refuses it. It is a `<details>`, so it opens without scripting, where the combobox is a text box with a `<datalist>`. The status filter's sixth value, `locality` ("Locality missing or unusable"), lists the samples it is for. Immediately above the table sits a row of what can be done with its rows (Peter, 2026-10-31): a Download menu on both listings, holding the CSV and what it contains, with room for other forms (a KML has been mentioned), and on `/specimens` the bulk actions staff have. Bulk actions are chosen first: a button names the action, and pressing it puts the listing in that action's mode (`act` in the query, carried by `listingHref` like any filter, and kept by Clear), with tick boxes only on the rows it can take (beeline-1kb.23). Marking labels for reprint is the only one so far; [Printing](printing.md) describes it.

The filtered selection a listing reads is built once, by `filteredSamples` and `filteredSpecimens` in `src/app/listings.ts`, and used by `listSamples`, `listSpecimens` and the counts the API makes (`countSamples`, `countSpecimens`, optionally by season, atlas or kind), so a count cannot come from a second copy of the filters (beeline-pnqr.2, [The API and its keys](the-api-and-its-keys.md)). `ExactLookup` adds whole-value matches on a sample number, field number, catalogue number or observation id for the API; no page uses them.

**The specimens download ends with four columns for loading an edited copy back, and is an Excel file only** (beeline-kgyd, Peter, 2026-11-16: people will edit the download in a spreadsheet and upload it, mostly to give determinations, and staff to correct a sample's method, dates and place; the preview of an upload is built, applying one is not: [Loading an edited download](loading-an-edited-download.md)). `/specimens.xlsx` takes the listing's query, reads and pages it as the listing does, and writes the specimen columns' values with every cell stored as text; it is the file to edit and upload back, since a CSV is rewritten by a spreadsheet and cannot be compared exactly. Everyone may download it. There was a `/specimens.csv` too, until beeline-kgyd.5 removed it: it is now an unknown address, with no redirect. The page offers the Excel file as a single button with its note beside it, where `/samples` offers its CSV in a menu. Its `specimens` tab holds a few of the specimen columns (those that help recognise the bee, then identification and disposition, in the order `SPECIMENS_LAYOUT` gives); it also carries three small tabs built when the file is asked for (`names` and `identifiers` to look names up in, and `about` saying what the file is), grey columns Beeline does not read, and warnings on the columns that take a few words (`src/app/specimen-workbook.ts`, [what the spreadsheet offers](loading-an-edited-download.md#what-the-spreadsheet-itself-offers)). The full set of specimen columns, `SPECIMEN_CSV_HEADER` with `specimenCsvRow`, is still the definition that the API's specimen rows, the Darwin Core archive and the upload's comparison are built on, with the four columns here after every column that was there before, as the host columns did. A program that wants every column reads them from the API's specimen rows, or the files on the exports page. `caste` is the determination of record's, which the download never carried, so that renaming a worker does not lose that it is one. The other three are `ROUND_TRIP_COLUMNS` in `src/app/listings.ts`, and are Beeline's bookkeeping:

- `specimenId` is the specimen's own id. A row will be found by it and not by `fieldNumber`, which is not unique, may be absent, and is the cell a spreadsheet is likeliest to damage (a dropped leading zero).
- `specimenVersion` is `s` and the first twelve hex digits of a SHA-256 over the specimen's own changeable cells as the row writes them (name, qualifier, sex, caste, determiner, date identified, disposition, remarks) and the id of the determination they were read from (`specimenVersion`). If it is not the specimen's now when the file comes back, the row was edited against something Beeline no longer says, and its determination and disposition are held. It replaced the determination's id, which was the first design: an id does not change when a loader updates a determination in place (Ecdysis fills a sex or a caste, a worksheet fills a date) or when a joined name is corrected (a person's or a taxon's), so a stale file looked current. The id is still on `SpecimenRow`, since the hash reads it, but no column carries it.
- `sampleVersion` does the same for the sample's cells that staff may change. It is `v` and the first twelve hex digits of a SHA-256 of the collecting dates, method, locality and point as the reader was given them (`sampleVersion`), so a reader whose location is withheld gets a code that says nothing about the true one. The `v` is there because a spreadsheet reads a run of digits, or digits around an `e`, as a number and rewrites it.

The Darwin Core archive leaves all four out (`NOT_IN_ARCHIVE`, `src/app/dwc-archive.ts`): the three mean nothing to a museum database, and whether the archive should publish caste, and under which term, is undecided. The API's specimen rows carry them, since its rows are the download's.
