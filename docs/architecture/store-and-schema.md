# Store and schema

Part of Beeline's architecture notes; the index is [README.md](README.md).

The schema **is** the `schema/*.sql` files, applied in filename order (0xx tables, 1xx derived views). Databases are blown away and rebuilt before cutover ([docs/roadmap.md](../roadmap.md)); the ones that can't be — the sandbox, production later — catch up through `migrations/NNNN-slug.sql` and `pnpm db:migrate`, recorded in `schema_migration` and stamped (never run) on a fresh build ([ADR 0006](../adr/0006-migrations-for-deployed-stores.md)). `pnpm db:migrate --check` compares names and comments against a fresh build, never a view's stored text, which depends on the DuckDB version that wrote it (the ADR's 2026-11-22 amendment). A change that migrations cannot carry, to the promotion rules or to a table others reference, was answered by `pnpm db:reseed` and a fresh promotion. Both now refuse a store that holds any print run or minted field number (`src/registry-guard.ts`, beeline-83b8.13), because a reseed leaves them behind and the new store's next run would issue those numbers again. `db:build` and `db:reseed` also refuse to delete a target that holds any. What answers such a change on production is not decided (beeline-131s). QC rules, printability, and determination-of-record are SQL views, not app code. Engine: DuckDB behind dialect-neutral SQL — [ADR 0001](../adr/0001-duckdb-first-with-portable-sql.md).

Every DuckDB the project opens goes through `src/db.ts`, which states the memory and thread budgets, pins the session time zone to UTC, and turns off one planner default of DuckDB 2.0, `delim_join_as_cte`. With it on, 2.0 copies the outer side of a correlated subquery into each subquery rather than sharing it, and the name-parsing views hide such a subquery in each alias macro (`ingest/parse-names.sql`): a legacy promotion on the test fixture took 100 s against 3.5 s on 1.5, and most pages on a copy of production's store ran 8–30% slower. `test/duckdb-openers.test.ts` holds that nothing opens DuckDB any other way, and that the `duckdb` command on the image (for maintenance mode) is the same version as the library.

**What the QC findings cost** (beeline-poon). The findings are views, so every page that shows a flag computes them: a sample or specimen page for its one sample, and a listing, the front page and printability for every sample. Two rules keep the first of these cheap. Every finding names its sample in `sample_id`, one about a single specimen included, so that a filter on one sample is handed down to each rule's own tables (`schema/130`): with that, one sample's findings take 23 ms on production's store of 2026-11-17 (2 threads), where they took 177 ms while `sample_qc_finding` looked the sample up through the specimen. Since #425 they take 48 ms (store of 2026-11-22): the second arm of the host rule, for a host staff set, builds the whole taxon chain under `sample_host` whichever sample is asked about, though production has no such host (beeline-amdt.3). And a new rule view should start from the sample, or from a table keyed by it, and join outward, since a rule that first counts or groups over every sample does that work even when asked about one. The findings for every sample take about 100 ms, a samples listing asks for them once for its rows and again for its total only when a status filter is set (`samplesCountQuery` in `src/app/listings.ts`, which asks `needsRollup` in the same file; beeline-amdt.1), and the specimens listing, whose rows show no flags, asks for them once and only with a status filter (`specimenListingBase`), and rewriting the rules does not change that much: the cost is spread over four rules, three of which read all 400,000 specimens. `qc_rule_observation_missing_upstream` also reads all of `observation_seen`, to which every weekly sweep adds about 14,000 rows; the nightly and the sweep therefore delete each sighting that a later run of the same source has repeated (`pruneSightings`, `src/sync-inat.ts`, beeline-amdt), which changes no finding, since the rule asks only which sources have returned an observation and when any last did. Measure a change to any rule with the app's own planner settings (`src/db.ts`), not a bare `duckdb` shell: DuckDB 2.0 chooses different plans under each, and the same view has measured 15 ms and 78 ms depending on the query around it.

**A row another table refers to cannot have a key column updated** (checked on `@duckdb/node-api` 2.0.0-r.1, beeline-stoi). `UPDATE animal SET parent_id` fails on any node a determination or a child refers to, and succeeds on one nothing refers to. So `animal.parent_id` is the parent at creation and never changes. A node that Ecdysis files elsewhere gets a row in `animal_filing`, a table with no foreign key that nothing refers to, written with `MERGE ... IS DISTINCT FROM`; the view `animal_tree` (`schema/117`) gives each node's parent in effect as `filed_under_id`, a name that cannot be taken for the column. The rest is in [Determinations and names](determinations-and-names.md).

**A sample's method** (beeline-ni5m.15, `schema/031_methods.sql`, `schema/121_views_method.sql`, migration 0123). How a sample's bees were caught is a controlled list. `method` holds the eight methods with the word a label prints and whether the device is a trap; `sample_method` gives each sample one of them, with a trap count; `method_text` says which method each wording in `sample.protocol` means, matched on the exact text. All three are tables beside `sample` and not columns of it, because DuckDB refuses to add a NOT NULL, CHECKed or foreign-keyed column to a table that other tables reference, or to rename or drop one, and `sample` has seventeen such tables. So `sample.protocol` and `sample.kind` stay for good, and a method that is changed is changed in the two places together: `sample.protocol` is the method as written and is never parsed, and `sample_method` is the method. Every writer of one writes the other in the same transaction, with `INSERT ... ON CONFLICT (sample_id) DO UPDATE` and never delete and insert: legacy promotion and the carry-over of held-back records and minting (`ingest/promote-legacy.sql`, `src/carry-over-legacy.ts`, `ingest/mint-samples.sql`), the trap form and a samples file's new rows (`src/trap-sample.ts`), the Method form and a samples file's changes (`src/app/sample-method.ts`), the collector's edit (`src/app/sample-edit.ts`) and the trap count (`src/app/sample-corrections.ts`); deleting an entered sample removes the row too (`DELETED_WITH_SAMPLE`). The test fixture `insertCleanSample` writes the row as the migration does. A code is permanent, since the other two tables refer to it. Three views follow: `sample_without_method` is a worklist (a sample whose words are empty or not listed; one on production), `sample_method_out_of_step` is always empty and the nightly fails when it is not (`src/check-sample-methods.ts`, the last step of the nightly's tail, naming the count and never the samples), and `sample_kind_method_mismatch` says where the kind disagrees with the method (976 on production, all settled), which nothing yet acts on. **The trap count has one home**, `sample_method.trap_count`: nothing reads a count from anywhere else, and it is null for a method that is not a trap. Every write of the method row and the count is `setSampleMethodRow` (`src/sample-method-row.ts`), which also writes the old `sample.sampling_effort` column from the stored count and method ("6 vane traps"), for no purpose but to keep that column filled until it is retired; the API's read of a sample and the change log are what read it (the sample page shows the count and no longer shows the effort). `sample_method_out_of_step` states the invariant by three clauses, each named in its rows: *method* (the stored method is the one `method_text` gives the method as written, and no row where the text is not listed), *count* (no count on a method that is not a trap) and *effort* (the old column is what the one writer would write for the stored count and method, which the view spells in SQL and `test/sample-method-row.test.ts` holds to `trapEffort`). Migration 0123 is the last place a count is read from text: the count an effort states in the form `trapEffort` writes, else the count the method as written states, for a trap. When a sample's method changes (`changeSampleMethod` in `src/app/sample-method.ts`) its count is kept for a method that is a trap and cleared for one that is not. A development rebuild by promotion reads a count from the method as written only, so a count a person changed on an old-record sample is lost by a rebuild; production is never rebuilt. A reseed carries no `sample_method` row, as it carries no sample: promotion and minting write it again with the sample. The label's word, the plant relationship, the listings, the exports and the kind read the words as written, not the method.
