# Files people send, and expert determination sheets

Part of Beeline's architecture notes; the index is [README.md](README.md).

**Every file someone sends Beeline is stored before anything reads it** (Peter, 2026-11-09: "we'll continue to get spreadsheets for things from various people"). A taxonomist's determinations, a staff inventory or an atlas lead's corrections usually arrives as an email attachment. `pnpm received:store <file> --from "<who sent it>" --sent <instant> [--note …]` (`src/received-files.ts`) uploads it, unconverted, into the "Beeline received files" folder on the program's shared drive (`RECEIVED_FOLDER`). It sets Drive's modified time to when the file was sent and writes the sender into the file's description, where anyone browsing the folder sees it. From then on the Drive id is the file's name. `pnpm received:fetch <id>` downloads it into `data/received/<id>/`, the file under its own name with `file.json` beside it, and a loader reads that directory. A loader keeps the Drive id as provenance, so a value in the store can be traced back to the file that said it, and the file opened again when a question comes up. Both commands act as Beeline's service account, the one the nightly backup uploads as, not as whoever is signed in to gcloud (Peter, 2026-11-09). The drive is the program's rather than a person's, and the account's `drive.file` scope lets it read back exactly the files it stored and nothing else. So the production machine, which holds the key as `BEELINE_DRIVE_KEY`, fetches a file itself, and a workstation reads the same key from `data/secrets/drive-key.json`, copied from the machine with `fly ssh console -C 'printenv BEELINE_DRIVE_KEY'`. The folder sits in Bee Line, beside databaseBackups. The account could not create it, because it was then a member of databaseBackups alone, so Peter made it, and Andony, who manages the drive, added the account to Bee Line (2026-11-09). Under `drive.file` the account cannot even look up a folder it did not create, databaseBackups included, so only an upload shows whether it can write to one. `data/` is gitignored, and fetched files stay there, since most of them name people. A loader writes what it could not place into the same directory.

`pnpm determinations:load data/received/<id> [db] [--sheet …] [--dry-run]` (`src/load-determination-sheet.ts`, beeline-t8zv) reads an expert's own sheet of determinations, one row per specimen, with Darwin Core headers. `fieldNumber`, `genus` and `identifiedBy` are required; `family`, `specificEpithet` and `sex` are read when present. The first was the Idaho Bee Atlas's sheet of November 2026: 2,140 rows from Karleen Davis, three quarters of them determined by Skyler Burrows. Its determinations are `worksheet_import` with `is_expert` true, and their provenance is a row in `worksheet_determination`: the Drive id, the tab and the row. A new channel value was not possible, because DuckDB cannot change the CHECK on a deployed store's `determination.channel` (ADR 0006, still true of 2.0 on 2026-11-09). A determination sheet is what that channel already names, and the volunteer worksheet loader's own skip rule ignores expert rows, so the two do not read each other's.

The loader records what the sheet says and guesses nothing, so it holds a row rather than placing it doubtfully. Each reason is listed in `held.csv`, and the counts come back split by season:

- **The number.** A field number typed into a sheet is the likeliest thing in it to be wrong, so `recordedBy` or `lastName`, and `eventDate` or `verbatimEventDate`, confirm it when present. A row is held when its collector is none of the specimen's collectors, compared as letters only (O'Loughlin is OLoughlin), or when its date falls outside the sample's. Dates arrive as Excel day numbers (a date cell read as text), ISO dates, m/d/yyyy, or the collectors' Roman-numeral month (VIII/25/2024). A number no specimen carries, or more than one does, or that appears twice in the sheet, is held.
- **The name.** The name is the genus and the epithet, run through `ingest/taxon-aliases.csv` for spelling, and kept as written in `verbatim_identification`. An epithet of `sp.` or `spp.` makes it a determination to genus. A name the tree lacks and Ecdysis accepts is adopted, as the Ecdysis loader does (`src/adopt-ecdysis.ts`). Any other name is held, because naming a species is a taxonomist's decision: Idaho's held 16 rows, among them *Osmia penstemonis* and *Andrena melanochlora*. A gender ending that differs from Ecdysis's (*hudsoniella* for *hudsoniellum*) is a decision too, not a spelling, so it is held as well. A row whose family is not the one the tree files its name under is held.
- **The determiner.** `identifiedBy` goes through `ingest/determiner-aliases.csv`, as legacy promotion's does. A person that file names who is not in the store yet is created, as promotion creates them; that is how Skyler Burrows arrived. A spelling the file lacks is held, because who determined a bee is a fact somebody has to state. A blank one is recorded with no determiner, because the sheet's author vouches that every row is an expert's.

A specimen whose determination of record already says the same thing is skipped: the same name, the same determiner, and the same sex where the sheet gives one. On Idaho's sheet that was 308 rows the old system already held. Anything else is recorded now, and so supersedes what stood before, an earlier expert's determination included. The result lists each of those, because a reader should see them. On Idaho's sheet there were two, both corrections Karleen called out: she had found that 2420587 and 2420591 carried another bee's determination. Loading the same file again records nothing (`already_loaded`, by file, tab and row). A reseed does not carry what the loader recorded, as with the other import channels, so run it again after one.

**Held rows become a bead** (Peter, 2026-11-09). Nothing in the store or the app records a held row: `held.csv` on the machine's disk is all there is. So whoever runs a load files a bead that lists the held rows, says who has been asked about them, and gives the commands to load the same file again. Every load judges every row afresh, so once the cause is fixed — a name decided with `pnpm taxon:decide`, a spelling added to an alias file, or a corrected sheet stored as a new file — rerunning the load records only what was held. Idaho's 17 are beeline-fwhs. This holds while an engineer runs each load by hand; a load the nightly runs would need a held-rows view in the app instead.
