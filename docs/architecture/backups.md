# Backups

Part of Beeline's architecture notes; the index is in [AGENTS.md](../../AGENTS.md#architecture-overview).

The `store-backup` job (`src/store-backup.ts`, beeline-elf, 3am Pacific, ahead of the Sunday sweep so it cannot be pushed past 5am) puts one archive a night in the Bee Line folder on the OSU shared drive, as a service account scoped to `drive.file`: copies of both stores — the private one still encrypted with the store's own key, so the key's copies off the server are what make it restorable — the authored CSVs, and a manifest of table counts and hashes. The copy is taken inside the app (ADR 0005) and is not `COPY FROM DATABASE`, which inserts tables in name order and so fails on the first foreign key; `src/store-snapshot.ts` copies the schema with `(SCHEMA)`, which carries the sequence's position, and fills tables parents first, a self-referencing table (`animal`) a level at a time, in one transaction per store. Nothing is trusted: the copies are reopened and their rows and schema counted against the store, Drive's MD5 of what it stored must match (an upload that does not is binned before the run fails), and only then does retention — two weeks of nights, the first copy of each month for a year — move old copies to the bin. Unconfigured outside development, the job fails rather than succeeding at nothing. Restoring and the drill are [the runbook's](../runbooks/deploy-fly.md#backups).
