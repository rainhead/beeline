# Printing

Part of Beeline's architecture notes; the index is in [AGENTS.md](../../AGENTS.md#architecture-overview).

A print run (`schema/035`, its meaning in `schema/155`, the writers in `src/print-run.ts`, beeline-1kb.2) is the batch act of printing and the moment specimens come to exist: **preparing a run is the freeze**. It takes every pending sample in scope — `pending_print_sample`, which never holds a sample from a settled season, because nothing from one is printed (Peter, 2026-10-14: a full sync of the sandbox minted 818 samples from observations the old system never recorded, 441 of them from 2018, and nobody pins a bee eight years later), then narrowed to `print_scope_sample` for an unscoped run, which means every atlas without an `atlas_printing` row plus samples outside any atlas, since Oregon prints for the whole program — and a run scoped to one atlas is refused unless that atlas has the row, since the rest are the program's to print (Peter, 2026-09-21; the flag is a satellite row, like `person_admin`, because DuckDB cannot add a NOT NULL column to a referenced table by migration) — creates their specimen rows, mints a field number for each — and no `occurrenceID`, which the museum database assigns ([ADR 0008](../adr/0008-specimen-identity.md), second amendment; beeline-1kb.15) — composes the six label strings (`src/label-text.ts`, the reference implementation's formats so a Beeline label reads like every label already pinned, the collector line included: `P.Abrahamsen`, set tight with no space after the initial, as every label in the drawers reads — decided in the room on 2026-09-18, screens keep `labelName()`'s `P. Abrahamsen` — and both names for a pair, `M.&D.O'Loughlin`; a county prints as its name alone, never with iNaturalist's `, US, WA` suffix, which `countyName` refuses even if the store still held one, since 172 labels in the first run anyone prepared said `Franklin County, US, WACo`, beeline-gr7; a BC regional district prints as the province abbreviates it, CAPRD for Capital, since the old system's CRD is the province's Cariboo, beeline-313x, and the county itself is the one Beeline wrote from the coordinates, [Areas](areas.md)) and lays them out in sheet order — the collector line, then the primary collector's id to keep two people whose lines read the same apart, then date, sample number (natural order) and specimen number — a blank cell between collectors, 250 to a sheet, so one collector's numbers run together. A taxon-obscured sample, one whose host plant iNaturalist hides because it is rare, is pending only where its atlas has said its labels may carry the true point (`atlas_taxon_obscured_printing`, Oregon alone so far, on Arthur's answer to gh-13 of 2026-10-21); everywhere else, a sample outside every atlas included, `taxon_obscured_awaiting_atlas` blocks it until the atlas answers, printed or not, since an imported label may carry iNaturalist's stand-in point and a further label would then be the first to print the true one. A pending sample with no single primary collector stops the run rather than being skipped by the join (`sample_primary_collector_invalid` is checked first, as the location row is checked after). The snapshot is `printed_label`, one row per label per run: the six strings *and* the values they were rendered from, so the sheet re-renders byte-identical and beeline-1kb.17 can compare an iNaturalist edit against what actually printed. The mint is the INSERT into `minted_field_number`, whose PRIMARY KEY is the uniqueness guarantee (ADR 0008 §5); `specimen.field_number` is written beside it because it is the column every read uses, and `specimen_field_number_stale` asserts the two agree. The number continues the eight-digit `YY` form, seeded one past the highest eight-digit number in the **imported corpus and the registry together**, floored at `YY000001` — the registry alone would have started a rebuilt 2026 store at `26000001`, inside the imported block whose ceiling is `26072091` (`minted_field_number_collision` is the check). State is derived from timestamps, never a column: prepared → approved → printed → mailed, or canceled while unprinted, each a guarded UPDATE behind one in-process lock, and the freeze runs on a connection of its own because the app's shared connection cannot hold two transactions at once. Two runs can be open together and cannot collide: the freeze is what takes a sample out of pending. **Printed is the moment that matters, not the freeze** (Peter, 2026-09-14): `printed_sample` — a specimen with a label in a printed run, or an imported specimen with no run at all, since the legacy labels are on pins too — is what `promote-observations.sql` and `mint-samples.sql` read to stop the coordinates and the locality following iNaturalist; dates never followed. The one exception is an imported point that is a stand-in, the point iNaturalist publishes to hide an obscured observation's real one, which the old system stored and printed: `sample_location_standin` (`schema/106`) names it, 100 m or more from the observation's true point, and promotion takes the true point anyway, because Arthur ruled that the record's accuracy outranks agreeing with the pin (2026-10-14, beeline-b34). **Cancelling destroys nothing**, and not by preference: DuckDB will not delete a referenced row in the transaction that removed its references, and a cancel that half-succeeded leaves specimens no run holds, which read as printed. So the labels stay as the record of what was prepared, the specimens keep their rows with the number cleared, the numbers stay burned (`specimen_id` NULL), `individuated_specimen` (`schema/117`) takes those rows out of the count that `pending_print_sample` and `qc_rule_count_below_printed` read, and the next freeze re-adopts them — same row, a fresh number. Every author column after `prepared_by` is a plain INTEGER, because a foreign key is an index and an indexed column on a row the labels reference could never be updated (duckdb/duckdb#20246). `db:reseed` carries none of it and says how much it left behind: the sandbox is the only store that reseeds, and a deployed store is migrated (ADR 0006). The sheets are `src/label-pdf.ts` (beeline-1kb.4): pdf-lib, the reference implementation's geometry verbatim — 25×10 on US Letter, 0.666"×0.311" labels, its six text boxes and shrink-to-fit rule, an 8×18 DataMatrix of the digits stood on end — because Arthur asked that the new sheet match the old one, and the vendored Oxygen Mono (`assets/fonts/`, OFL). Rendered from `printed_label` rows only, with the document dates set to `prepared_at` and no object streams, so two renders of a run are byte-identical (a test hashes them; `print_run.pdf_sha256` will record the first). The DataMatrix is vector: filled rectangles, one per run of dark modules, from bwip-js's module matrix. It was a 1-bit image first and came out blurry, because viewers and print drivers smooth a tiny bitmap when they scale it whatever its Interpolate flag says. Fits are remembered per render and found by bisection, since a sheet repeats the same strings down a column; with the freeze writing its three tables in multi-row statements rather than three statements a label, a 5,411-label run freezes in 1.6 s and renders in 2.9 s on a workstation, where the first version took 7.6 s and 7.2 s and minutes on the sandbox's two shared threads. A scanner reads the number, not a string, since only the digits are encoded, as the reference did. The render runs on a **worker thread** (`src/label-pdf-worker.ts`, beeline-1kb.19), because it is CPU-bound from end to end and Node would otherwise run it on the thread that serves every request — during the first demonstration Fly's health check failed mid-render, not at a deploy, the process alive and answering nothing. Measured on the production shape (`node --import tsx`, 5,000 labels): `/healthz` answered 2 probes at worst 3,996 ms while the sheets rendered in process, and 47 at worst 36 ms — its idle latency — with the worker, for about 7% more wall clock. The boundary is what makes it the cheap fix rather than rendering at approve time as a job: plain rows in, bytes out, nothing in between touching the store, and the renderer itself untouched so the sheets stay byte-identical. `runPdf` coalesces concurrent requests for one run's sheets, since two admins opening an unrendered run would otherwise start two workers on the same input. The freeze's own TypeScript half is the same shape of work and stays on the main thread: it runs inside the freeze's transaction, which cannot cross a thread. The screens are `/print-runs` (`src/app/print-runs.ts` + `src/app/views/print-runs.tsx`), admin-gated like `/jobs`: the list with a Prepare form whose scope picker says how many labels and samples each scope would take before anyone presses it, and the run page — the six strings per label in sheet order as the proofing surface, the labels to look at listed first, one button for the state's next step with a note, Cancel while unprinted, and the sheets at `/print-runs/:id/labels.pdf`, rendered on first request into `data/print-runs/` (config `printRunsDir`) with the hash recorded — and a cached file is served only when it hashes to what the run recorded, since a reseeded sandbox restarts ids while that directory survives; a canceled run serves no sheets at all, its numbers being burned. The writes go through the print connection (`printConn`, opened in `main.ts` beside the scheduler's) and refuse impersonation. What a volunteer sees: their front page keeps a sample until its labels are **mailed**, not until a run is prepared — the freeze takes a sample out of `pending_print_sample` at once, and the page listed only what was pending, so in the first demonstration a sample vanished from its collector's dashboard days before any envelope existed; `sample_label_in_progress` (`schema/155`) is what holds it there, reading "3 labels are being printed" and then "printed Sep 18, not mailed yet". Then a Label column on the sample page's specimen list — printing, printed, mailed, run canceled, or printed before Beeline, never blank — and a Labels block on the specimen page, one row per run with the number as it printed, which is also the proofing lookup's other half: a number that matches twice shows each specimen's labels beside their runs. A specimen with no number is two stories, told apart by whether it has a label row (beeline-1kb.21): one a canceled run had numbered reads "awaiting a number" on the listing and the sample page and names the burned number on its own page, since the registry has let go of it and `printed_label` is where it survives; one with no label row at all predates field numbering, and only that one says so.

**Reprints** (gh-218, beeline-1kb.5.1) are a second label for a specimen that already has a number. An admin asks for one from the specimen page's Labels block, or for every specimen in a sample from the sample page, with an optional reason (never received, damaged or lost, record corrected) and note; the row is `reprint_request` (`schema/035`), and the writers are `requestReprint` and `withdrawReprint` in `src/print-run.ts`, behind the print-run lock on the print connection. A request is refused for a specimen with no field number, one already asked for, or one a run that has not printed yet holds, since that run is about to print it; for a sample, the specimens that qualify are asked for and the rest are left alone. Whether a request has been answered is derived, never written: `pending_reprint` (`schema/155`) is the requests not withdrawn that no uncanceled run prepared since holds a label for, so a canceled run puts its reprints back by itself. The freeze takes `print_scope_reprint` (or `printable_reprint` for one atlas) beside the pending samples, and a reprint is held only by the flags in `qc_rule_unwaivable` — a hold, a missing required field, a point that is hidden or not yet cleared to print — not by printability as a whole, because an imported sample can carry flags that were never anybody's to fix and the label is already on a pin. A settled season is no bar either: a person asked for this one. The reprint is composed from the record as it stands, like a new label (Peter, 2026-10-30): for a lost label that is what printed, since a printed sample stops following iNaturalist, and for a corrected record it is the correction, as Arthur answered on gh-17. Where its text differs from the specimen's last Beeline label, `warnings` names the lines (`reprint differs from its last label: location`), which puts it among the labels to look at; an imported specimen has no label to compare against. On the sheets the reprints follow the new labels in the same order, set off by one blank cell, the gap between two collectors (Peter, 2026-10-30), and they mint nothing: a reprint is told from a first print by having no `minted_field_number` row in its run (`printed_label_reprint`, `schema/101`), never by a flag. That same test is why `printed_sample` and `individuated_specimen` ask whether a run *minted* the specimen's number rather than whether it has any label: an imported specimen can have a label now, and its reprint waiting in an unprinted run must not unlock a sample whose labels have been on pins for years, nor a canceled reprint take it out of the count. Everyone sees a waiting request on the specimen page and "reprint requested" on the sample's specimen list; the Labels block marks each reprint and says who asked and why. Staff can also tick specimens on `/specimens` and mark them all at once (beeline-1kb.23), which is how Arthur works through a collector's recent labels with the listing's own filters: a tick box per row belongs to one form under the table, so without scripting it marks what is ticked on the page in view, and the `bulk-select` island (`src/app/islands/bulk-select.ts`) keeps the ticks in the tab's sessionStorage across pages and filters, ticks a whole page, counts, and hides the bar until something is ticked. Ticks are cleared when the listing comes back from a marking, not on submit, so a refused request leaves them for another try. The writer takes the list as one bound parameter, never as SQL text; the listing marks each specimen whose reprint is waiting.

A sample staff hold (beeline-plu) is not printable, so no later freeze takes it. One held after its run was prepared is not taken out: `loadRun` names it on the run page while the run is prepared or approved, and the printer decides whether to cancel and prepare again, which leaves it out — proofing pulls, the per-label alternative, were decided against (beeline-1kb.3). A past season's held sample is not named, since its labels print with the run regardless (Peter, 2026-10-25).
