# Errors and logs

Part of Beeline's architecture notes; the index is in [AGENTS.md](../../AGENTS.md#architecture-overview).

With `SENTRY_DSN` set, the app reports to Sentry (`src/app/error-reporting.ts`, beeline-8w6.1): a failed request with its route pattern and the signed-in login, a failed job with its name, the console as searchable logs, and every job run as a cron check-in built from its `Schedule`; unset, it reports nothing and behaves the same. The rule is `/healthz/jobs`'s — say which thing went wrong, never the record it went wrong on — so the SDK collects no request body, query string, cookie or local variable, and every message is passed through `redact`, which blanks anything quoted, any decimal of four or more places, tokens and email addresses. Two consequences for new code: log a string, never an object, since the log integration sends an object as JSON whose every quoted key is blanked; and put the value an error is about in quotes, as DuckDB already does, so redaction finds it. Listing requests are also counted, as the application metric `listing.view` (`src/app/usage.ts`), to see how people browse: the listing, the scope, the sort and whether it was changed, a page band, and which filters are in use — each free-text filter reduced to whether it was used, since a listing search is how somebody finds a person or a place — with the viewer's role and never their identity. Every request's latency is the metric `request.duration` by route pattern, method and status, and one over a second also logs a `[request] slow:` line naming the route and the login (`src/app/request-timing.ts`, the outermost middleware): until it, a page that answered in eight seconds was invisible except to the person waiting. A listing's CSV does its work after its response has gone, so `csvStream` reports its pages' time in the store separately, as `csv.generation`. Neither writes anything to the store. The runbook's section is [Errors, logs and job check-ins](../runbooks/deploy-fly.md#errors-logs-and-job-check-ins). The `resource-budget` job (`src/fly-usage.ts`) reads the last day of the machine's CPU, memory, swap and disk from Fly's metrics and fails when a limit was crossed, the CPU burst balance being the one heavy batch work actually reaches; Fly counts CPU in clock ticks, not seconds ([the machine's budget](../runbooks/deploy-fly.md#the-machines-budget)).

What the person sees is a page, never bare text (`errorResponse` in `src/app/server.tsx`, `src/app/views/error-page.tsx`, beeline-0kj): a thrown error and an address nothing answers both render inside the ordinary layout, so the header, the menu and Send feedback survive, with a way back to the same-site page that linked there and a way home. A failure gets an eight-hex-digit **reference** (`reportAppError`), in the log line and as a Sentry tag, and the feedback email the page starts carries it — so "it broke" arrives with what finds it. It never says *what* failed, since DuckDB's errors quote the values they choke on; development alone shows the error, with a hint where it reads like a store behind its migrations. Not-found is one page however it is reached — a record that does not exist, by any address — identical but for the feedback email's note of the address asked for, and a test holds them to it; since every record is open to everyone signed in, there is no longer a record that exists and is not the person's to see. A page that knows more and leaks nothing by saying it — the taxonomy, print runs, people — passes its own sentence. Signed out, everything is still the sign-in page. A caller that asked for JSON gets `{error, reference}`, and if the layout itself cannot render, a static page that depends on nothing answers instead. **New code answers a 404 with `errorResponse(c, "notFound")`, not `c.text`.**
