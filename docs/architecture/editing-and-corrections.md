# Editing and corrections

Part of Beeline's architecture notes; the index is [README.md](README.md).

Non-iNat samples are edited in-app (`/samples/:id/edit`, collector-gated): each save updates the live sample row and records correction events keyed by staging Mongo `_id` in `data/corrections.csv` (`src/corrections.ts` — outside the blow-away path), which legacy promotion reads union the git-curated `ingest/legacy-corrections.csv`, app rows winning ([ADR 0004](../adr/0004-correction-overlay.md), beeline-2c3.8). Staff set a sample's **locality** from its page (`/samples/:id`, admin-gated, refused while impersonating; `src/app/locality-override.ts`, beeline-649), because an unprinted iNat-linked sample's locality follows its observation on every promotion and nobody could edit one in the app, so a place name the observation cannot yield had nowhere to go. One form, two durable stores, since the two kinds of sample are named by different things a rebuild reproduces: a sample with an observation goes to `data/sample-overlay.csv` (`src/sample-overlay.ts`, the person overlay's shape plus a `base_value`, keyed `inat:<observation id>` — the link is the sample's identity, and `entity_id` is a per-store draw), applied as the satellite `sample_locality_override` (schema/030) by `src/apply-sample-overlay.ts` at the end of observation promotion and at once from the page; a sample with none goes through the corrections overlay as the collector's own edit would. The follow rule in `ingest/mint-samples.sql` skips overridden samples, `sample_locality_override_stale` asserts the row and the sample agree, and `sample_locality_override_diverged` (schema/175) names an observation that has since moved to a third value, which the page shows beside the override rather than resolving: a deliberate assertion beats an unreviewed upstream edit (ADR 0004). Removing the override hands an unprinted sample back to its observation at once; a printed one keeps what the label says. Promotion reads the file only when given its path, so a scratch promotion never reads the deployed store's decisions; the nightly reports rows that name no sample in the run's detail and goes on. The coordinates take the same form (beeline-942): a second field in the same file, `coordinates`, valued `<latitude> <longitude> [uncertainty m]`, applied as `sample_location_override` with `sample_location` written beside it as `staff_entry`, the provenance every read already carries — and the location upgrade in `ingest/promote-observations.sql`, which used to rewrite `sample_location` unconditionally and so erased a staff point on the next nightly, skips overridden samples. The base it records is the `sample_location` row as it stood, whatever its source, so removal hands an unprinted sample back exactly what it had, an imported point included, and a sample that had none goes back to none; the elevation is left for `sample_elevation_stale` to notice, never cleared by the writer. The observation's believed-true point is now the view `observation_location` (schema/105), which promotion's candidate table reads and the diverged view compares against, with `sample_elevation_stale`'s 5e-5° tolerance. The form appears on the coordinates block even where the sample has none, because that is the case it exists for: an obscured observation with no trusted access yields no coordinates and cannot print, and only a person can put the true point in. Offered only on samples with an observation: the corrections overlay would land an imported sample's point as `legacy_import`, misstating who said so. A staff point carries the county, state and country of where it lies, printed or not ([Areas](areas.md)).

**Where the rules for a correction live** (beeline-pnqr.8). The routes for the collector's edit, `/suggested-locality`, `/place`, `/coordinates`, `/take-observation-location`, `/hold` and `/waiver` only read the form, call one function in `src/app/sample-corrections.ts` and turn its result into a response. The function (`editSample`, `adoptLocality`, `setPlace`, `setCoordinates`, `takeLocation`, `holdSample`, `waiveFlag`) takes who is acting (an `Actor`, made by `actorFor`, which never yields staff while impersonating), the sample and the input, and holds every rule: refusing while impersonating, the staff gate, a locality somebody else set standing, a printed sample, only an offered name unless staff, refusing while a sync job runs, deriving elevation and county after a point moves (`deriveMovedPoint`), and recording the change under its author. The input is a value or a function that reads it; a page passes a function that parses the form, and the correction calls it only after the rules that do not depend on the form have passed, and before it takes its turn of the per-sample queue (next paragraph), so a refused request's body is never read. It returns `{ ok: true, ... }` or `{ ok: false, refusal }` with a named refusal, which the route turns into the message and status it has always answered with (each route's switch ends in `unreachable`, so a refusal left unhandled fails the typecheck), so the API calls the same function and maps the refusals to its own errors ([the API](the-api-and-its-keys.md), beeline-pnqr.6). The API passes the input as a value, and adds two things the pages do not use: an `outcome` on every success (`saved`, `removed` or `unchanged`, as the writer reported it) and, for the collector's edit, a `dryRun` option that plans the edit in the same queue turn and writes nothing. The actor's `via` says which door the request came through, and is recorded as the history entry's source (`app` for a page, `api` for the API). The two reasons a correction writes for itself, for an adopted locality and for taking the observation's location, are built in `src/app/correction-reasons.ts` from the message catalogue, so a page and the API store the same words. Every one of them runs one at a time for its sample (next paragraph). `/method` still has its rules in the route, and takes its own turn of the same queue. The collector's edit is split into `planSampleEdit` (the events and column values, no writes) and `writeSampleEdit` (the overlay file, then the store), which `applySampleEdit` composes; a dry run needs the first alone. `writeSampleEdit` is not exported, because a plan is only valid inside the queue turn that made it: writing an older plan after a newer save would overwrite that save. Still no retry on a write conflict, for the reason in [ingestion jobs](ingestion-jobs-and-elevation.md). `test/sample-corrections.test.ts` pins the refusals and the saves without a page, and `test/sample-corrections-routes.test.ts` the author when acting for someone, impersonation through the pages, and that a refused request with an unreadable form still gets its refusal.

**One correction at a time for a sample** (beeline-4ksk). Every one of those functions runs in the same shape (`correct` in `src/app/sample-corrections.ts`). The rules that do not depend on the form are asked first, so a request that will be refused is refused without its form being read. The form is then read, outside the sample's queue, so a slow upload holds up nobody else's save. Then one turn of the per-sample queue (`src/app/sample-queue.ts`) asks those rules again, of the sample as it stands now, checks what depends on the form, writes, derives what follows from the write, and records the change in the sample's history. The second asking is the one the write relies on. Because the whole of that is one turn, two corrections to one sample cannot interleave: neither writes between the other's check and its write, the localities a collector may adopt are the ones offered in that turn and not when the request arrived, and each history entry is taken before the next correction begins, under its own author. Until this, only the collector's edit and the place editor took a turn. The other five did not, and the history is recorded from the sample's state after the fact (ADR 0007), so a collector adopting a locality while staff held the same sample could have both changes entered under one of their names, and a collector could replace a locality staff had saved a moment earlier. A turn is taken once the input is in hand. A caller that already holds it, as the API does, skips the first asking and takes its turn in the same tick it was called, so a program that sends one correction and then another without waiting has them applied in that order. A page's form has to arrive first, so two page requests within a few tens of milliseconds of each other may be applied in either order. A staff point is entered in the history straight after it is written and again after its elevation and county are derived: deriving waits for "Check iNaturalist now" if one is running, and that check ends with a pass over every sample's history under no author, which would otherwise take the staff point for its own. (A check that ends in the instant between the write and that first entry can still take it: the history is read from state after the fact, so that window can be made small and not closed.) The edit form of a sample entered in Beeline takes a turn of the same queue for its write and history entry. Nothing a turn calls may take a turn for the same sample itself, since the queue does not nest.

**How a sample from the old Beeline was collected** (beeline-p8y1). Staff correct a sample's method and the day collecting ended from a pencil on its Method row (`POST /samples/:id/method`, `src/app/sample-method.ts`, admin-gated, refused while impersonating), offered on any sample built from the old Beeline's records, with an iNaturalist observation or without. The collector's form refuses a sample with an observation because a correction has to name an old record and an observation-only sample has none; a sample built from old records has them whether or not it was linked, and the nightly sync never rewrites a linked sample's method or dates, so the correction stays. A save is the collector's edit in shape: one event per old record and field in `data/corrections.csv` (`samplingProtocol`, and `day2`/`month2`/`year2` for the end), written before the live sample changes, then a pass of the sample change log credited to whoever saved. The kind is not a field of its own: promotion makes a sample a trap sample exactly when its records give an end date, so an end date given here makes it one and none makes it a net sample collected on its start day, what a rebuild would make of the corrected records. The start date is not offered, since promotion groups records into samples by it. A save from either form also writes its events into the store's own correction tables (`src/app/correction-store.ts`), which promotion builds from the files and `legacy_occurrence_corrected` reads the old records through: production is never promoted again, and the legacy-format export and the copy into old Beeline write each record's own method and end date where a sample's records disagree, so without it a correction reached the page and never the export (the independent review of #314). Saves to one sample run one at a time across the collector's form, the staff place editor and this one, each with its entry in the change log (`src/app/sample-queue.ts`). Two effects matter only on a recent sample, not on the imported ones this was made for: widening a sample's dates widens the range `sample_mint_pending` refuses to mint a later observation of the same collector and number into, as any trap sample's does, and a label in a prepared, unprinted run is not marked out of date by a change of method alone. It was made for Pat Wheeler's six trap samples of 2021, which Beeline published as netted on one day because the copy promotion kept was the one the old Beeline printed from the observation, with its default "aerial net" ([the legacy-format export](the-legacy-format-export.md)).

**A printed sample whose pin moved** (beeline-1kb.17.1, GitHub #298). Once labels print, the point stops following iNaturalist, so a collector who moves the pin afterwards leaves the record agreeing with a label that may be wrong. `sample_location_label_diverged` (schema/175) names a sample Beeline printed a label for, with no staff point, whose observation now lies more than 100 m from it (the label's three decimals, the distance beeline-1kb.17 settled on). On the sample page staff see where iNaturalist puts it now and one button, "Use iNaturalist's location" (`POST /samples/:id/take-observation-location`, `takeObservationLocation`), which is the staff coordinates write with the observation's point as its value, read from the store rather than the form. The labels on paper are untouched and a reprint is asked for as any other. Samples whose labels the old Beeline printed are left out: on the store of 2026-11-10 the same test found 542 of them, all imported points a median 3 km from their observations and some an ocean away, which say the old system held a different point or linked the wrong observation rather than that someone moved a pin. Showing those, and the volunteer's side, is still beeline-1kb.17. The country, state and county come from `observation_place` only for the line on the page, in a second query made when the view finds something, because joined into the view it cost every printed sample's page 140 ms.

Staff **holds** and **waivers** (beeline-plu, beeline-1kb.9; *Hold* and *Waiver* in [CONTEXT.md](../../CONTEXT.md)) are two more fields in the same file, set from the flags card on `/samples/:id` (`src/app/qc-decisions.ts`, admin-gated, refused while impersonating) and applied by the same applier: `hold`, valued `held`, becomes a `sample_hold` row, and `waiver:<rule>`, valued `waived`, becomes a `sample_qc_waiver` row whose `base_value` is what the flag said when it was waived — the thing the waiver is tied to, as a locality override's base is what the observation said (schema/050). A reason is required for both, and the applier refuses a standing one without, rather than inserting a row the CHECK would fail the whole promotion over; it refuses a waiver on an unknown, non-blocking or unwaivable flag the same way, and `sample_qc_finding` ignores one on an unwaivable flag even if it reaches the table. A hold is a finding (`qc_rule_staff_hold`), so printability, the front page and the listings need nothing of their own; a waiver takes its finding out of `sample_qc_finding` while it is in force — the flag still says what it said when waived — which the applier settles each time it runs (`refreshWaivers`, after every promotion and every staff decision) and stores as `in_force`, because comparing the text in the view made every finding build its text and printability 80% slower with no waivers at all. `observation_missing_upstream` says when the observation was last returned rather than counting the runs that missed it, so a waiver on it does not lapse at the next sync. Waivers are also rechecked at the end of every sync and every person-overlay application, since a completed run and a moved iNaturalist account both change what a flag says before any promotion; and `qc_rule_sample_number` joins its two cases into one finding per sample, because a waiver names a flag by its sample and rule. Only samples with an observation take either, since the overlay names a sample by it and every sample still waiting to print has one.
