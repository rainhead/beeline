# The API and its keys

Part of Beeline's architecture notes; the index is [README.md](README.md).

Beeline has an API under `/api/v1/` for programs: a script, an AI assistant, an agent working on the code (`src/app/api.ts`, beeline-pnqr). Every request carries a **personal API key** as a bearer header, and every answer is JSON, errors included. The first endpoint is `GET /api/v1/me`, which says whose key it is and what it may do.

**A key** (`src/app/api-keys.ts`, the `api_key` table in `schema/012`) is made by a person on their own page, `/keys`, reached from the account menu. They name it, choose what it may do and how long it lasts, and see it once: the store keeps only its SHA-256, as it does for a session, so a copy of the table lets nobody in. The key starts with `beeline_` so that one pasted in the wrong place can be recognised. Its first 12 hex digits of the hash are its reference, which the person's list shows and which is safe to record. Like a session, a key is held against the iNat user and resolved through `inat_account` on every request.

**What a key may do** is chosen when it is made, and is a ceiling, not a grant: `read` sees what its person sees, `edit` will also correct its person's own samples, and `staff` does what its person may do as staff. The scopes a person may give are decided in one place (`offeredScopes`) for both the form and the check on what it posts: `staff` only for someone who is staff now, and `edit` not at all until something accepts it, so no key gains a power later that its maker was never offered. A person may have ten working keys. A staff key acts as one only while its person holds a `person_admin` row, which is asked on every request, so taking the rights away stops the key at once. A key acts as its own person and nobody else: there is no acting for someone and no impersonation through one, and a key cannot be made or revoked while acting for someone, because a key signs its holder in as its owner and a delegation does not hand that over.

**A key stops working** when it expires (7, 30 or 90 days, the longest being the most a session can last; a key has no idle limit and no signing out), when its person or a staff member revokes it, or when their iNat account is unlinked: the unlink on `/people` revokes the account's keys where it ends its sessions (as soon as the store has changed, before the change log is written, so a failure after that cannot leave them standing; a key is also made inside the queue that runs account changes one at a time, and only if the person's account is still the iNat user their session was issued to, so none can be made between an unlink and its revocation or by a session the change ended; saving an account without changing it revokes nothing), and the nightly `session-purge` job revokes the keys of an account that went some other way. Without that, linking the account to a different person would bring the key back as them. A row is kept after its key stops working, so what the key did can still be traced to it.

**Two credentials, two places.** The API is mounted ahead of the session gate and never calls it, so a session cookie means nothing under `/api/v1/`; no page reads a bearer header, so a key means nothing anywhere else. `test/api-keys.test.ts` holds both. The CSRF check does not apply to the API for the same reason: it protects a credential a browser sends by itself.

**The old Beeline's redirect.** Until the old Beeline closes, `/api/*` is redirected to it ([the app process](the-app-process-and-its-gate.md)). `/api/v1/` is registered ahead of that, and a request that carries an `Authorization` header to any other address those redirects answer, the old interface's pages included, is answered 401 and not redirected, because some HTTP clients resend that header when a redirect stays within the site, and one mistyped path would hand the key to another server.

**Limits.** One key may make 120 requests a minute, counted in memory and before the key is looked up, so a key over its limit costs the store nothing; past that it is answered 429 with `Retry-After`. The machine's CPU allowance is small, and a script in a loop should be slowed before the pages are. The last-used time is written at most every five minutes and is allowed to lose a write conflict, as a session's slide is.

**Jobs** (beeline-pnqr.5). A staff key can do what the Jobs page shows staff and its Run button does:

| Request | Answer |
| --- | --- |
| `GET /api/v1/jobs` | every registered job with its schedule and latest run, and which job is running |
| `GET /api/v1/jobs/runs?job=<name>&limit=<n>` | recent runs, newest first |
| `GET /api/v1/jobs/runs/<id>` | one run: its status, its detail, and the steps a night job recorded |
| `POST /api/v1/jobs/<name>` | starts the job now; 202 with the run to watch, as soon as the run is recorded |

Starting a job takes no arguments: it is the registered job, run now, as the button runs it. One job runs at a time ([Ingestion, jobs, and elevation](ingestion-jobs-and-elevation.md)), so a start while another runs is answered 409 naming what is running, and a name nobody registered 404; the scheduler's `startRun` tells the two apart and returns the run's id, which the page's `start` never needed. A run's status is `succeeded` or `failed` as recorded, `running` for the one run the scheduler has in hand, and `unfinished` for a run the process stopped under, which nothing will complete. A program may treat `unfinished` as final, so the answer has to be right at the moment a run ends: the scheduler names the run it has in hand by id (`runningRun`), set as the run's row is inserted and cleared only after its outcome is written, the API asks it on both sides of reading the rows, and a run with no outcome that neither answer names is read once more before it is called unfinished. These are for staff keys only, as the page is for staff only: a run's detail is whatever the job or its error said, and that can name people. Who started a run is written to the log (`[api] <login> started job ...`), since `job_run` has no column for it yet (beeline-pnqr.7). The commands that still need maintenance mode are not jobs and cannot be started this way; moving them is beeline-pnqr.7.

**Who can see and revoke which keys** (beeline-pnqr.9). Anyone signed in may open `/keys`, see their own keys and revoke them, so that someone who has lost their staff rights can still end a key that goes on working for reading. Making a key is staff only for now: the page tells anyone else, in plain words, that it is not open to them yet and shows no form, and `POST /keys` answers 403. The account menu links to `/keys` for staff and for anyone who has made a key; whether a non-staff person has one is a single `hasKeys` lookup on the iNat user the gate already read from the session row, made only when a page is rendered for someone who is not staff (no index, since the table holds a handful of keys per person and an index would add a second structure to a table whose rows are updated on use). While viewing Beeline as someone else `/keys` is refused and the link is not shown; while acting for someone under a grant the list is still the signed-in person's and nothing can be changed. Staff also see another person's keys on that person's page, `/people/:id`, only when they have made one: name, what it allows, made, expires, last used, reference and whether it is revoked or expired, never the key. Each working key has a Revoke button posting to `/people/:id/keys/:ref/revoke`, staff only and refused while viewing as someone. The person in the URL must be the key's owner, so a reference taken from another page revokes nothing. Only a working key (not revoked and not expired) is touched, so a second revoke changes nothing and keeps the first one's record. The page lists the keys of the person's account in two parts, under separate headings. The first is the keys made while the account has stayed with this person, with a Revoke button on each working one. The second, "Made before this account was linked to this person", is the keys made before the account was unlinked or moved, with no buttons, since all of them have ended, and with who revoked them and why. Staff see those names because they may need to trace a key, and the heading says plainly that they are not this person's.

**What is recorded when a key is revoked.** Three columns on `api_key`: `revoked_by`, the iNat login of whoever did it (the owner's own login when the owner did), and `revoked_reason`, one of `owner` (on `/keys`, or staff ending their own key from their own page), `staff` (on the person's page), `account_changed` (staff unlinked or changed the account on `/people`; `revoked_by` is that staff member) and `account_gone` (the nightly `session-purge` job; `revoked_by` is empty). A key revoked before the columns existed has both empty. The third column, `account_changed_at`, says whose keys these are: when staff unlink an account or link it to someone else (`revokeKeysFor`), or the nightly job finds it linked to nobody (`revokeOrphanedKeys`), every key of the account that is not yet marked is stamped with that moment, whether it was working, revoked or expired. Only the working ones are revoked and given a reason, so an expired or already revoked key keeps its own story. A stamped key belongs to whoever held the account before: the account's new holder does not see it on `/keys`, the account menu does not offer them the link because of it (`hasKeys` and the owner's list read only keys with no stamp), and the person page shows it to staff under the separate heading. A person unlinked and then linked again to the same account therefore starts with no keys of their own on `/keys`, and the keys they had made show to staff under that heading; a key made after the relink is theirs. Revoking by staff is refused while acting for someone as well as while viewing as someone, as on `/keys`. The owner's list says who and why only when it was not the owner ("Revoked 12 Nov by samstaff", "Revoked 12 Nov by samstaff: the iNaturalist account changed"); the staff list on the person's page always says who, "by its owner" included. A key with neither column set says only the date. Staff revoking a key is not written to the person change log ([ADR 0007](../adr/0007-authored-changes-are-events.md), `src/person-change.ts`): that log records differences in a person's state, a key is not part of that state, and an entry would have to pretend otherwise. The two columns are the record.

**Making keys is staff only for now.** A collector's key would have nothing to read until the read endpoints exist (beeline-pnqr.2). What comes next under the same gate: the sample corrections the pages allow (beeline-pnqr.6). Asking the store a question in SQL is deliberately not part of the API (Peter, 2026-11-13): it is a command on the machine, `pnpm store:query`, over `fly ssh` ([Backups](backups.md), beeline-pnqr.4), because a server that accepts SQL from the internet has one key between a stranger and a copy of everything, and the only people who need it already have a shell there.
