# Registrations, from Ideal Logic

Part of Beeline's architecture notes; the index is [README.md](README.md).

People register for Master Melittology in Ideal Logic, the registration platform OSU Extension uses. Since 2026-11-18 Ideal Logic gives Beeline one HTTP endpoint that returns every registrant: a name, an email address, a home address, the atlases they said they belong to, and an iNaturalist handle they typed. Beeline reads it for three things (epic beeline-w8ab): to find collectors it does not know, with their atlas; to look up where a collector's labels are mailed, at the moment staff download a print run's addresses; and, later, to email people. This reverses the decision of 2026-09-11 that Beeline would keep mailing addresses itself ([gh-34](https://github.com/rainhead/beeline/issues/34)).

## The rule: addresses never reach the disk

An address or an email address is never written to Beeline's disk (Peter, 2026-11-18). It is fetched when it is needed and dropped when the request that needed it ends. What Beeline keeps of a registration is the link from a person to it, and through that link the address is looked up each time.

The rule shapes the code in places a reader might otherwise tidy away:

- **Errors from the client carry fixed text**: a status or a count, never a piece of the response and never Ideal Logic's own message (`IdealLogicError`, `src/ideal-logic.ts`). The job framework writes an error's message into `job_run.detail`, which is in the store and every backup, and logs its stack. `JSON.parse` quotes the text it failed on, and here that text is somebody's record. A test feeds the client a response cut off in the middle of a street.
- **Neither table has a column for an address or an email address** (`schema/014`), and `src/registrations.ts` does not read those fields at all.
- **Evidence is recorded by its kind**, never by the value: `register_email`, not the address that matched.
- **Nothing is cached** between requests.

## The API

`GET https://apps.ideal-logic.com/api/f36e9b6c.json` with the key as a bearer token returns everybody in one list (826 people on 2026-11-18). The header `X-NumResults` says how many there are, and the client refuses a list of a different length, so that a change in Ideal Logic's default paging cannot make registrants look gone. It also refuses an answer whose header is missing, empty or not a number, since without it the list cannot be checked. Every failure is a 404.

The request and the reading of its body together have 60 seconds (`REQUEST_TIMEOUT_MS`, which `createIdealLogicClient` lets a test shorten), combined with the caller's own abort signal. A stalled response would otherwise hold the night's job; when the deadline passes, the client throws the same fixed "could not be reached" error as for a network failure.

Ideal Logic allows **100 requests a day**. The list is fetched whole, never per person. The client counts its own attempts for the Pacific day and refuses the one that would pass 60 (`RequestBudget`), which leaves the rest for a person working by hand. The count is in memory; nothing fetches at boot, so a machine restarting in a loop makes no requests. The app holds one client (`config.idealLogic`), so the nightly job and the downloads draw on one count. The key is the secret `IDEAL_LOGIC_KEY`; without it the job fetches nothing and says so.

The province of a Canadian address is read off the first letter of its postal code (`provinceFromPostalCode`; X is shared by two territories and names neither). Ideal Logic added province and country fields on 2026-11-18 at our request (beeline-w8ab.5), and Beeline does not read them, because the postal code is the better source. Both are typed by the registrant. The province was filled for 67 of 92 Canadian addresses, spelled several ways ("BC", "British Columbia", "BC - British Columbia"), and once named a different province from the postal code. The country was filled for 31 of the 92. The feed also gained a county and a BC regional district, which nothing needs yet. It has no registration date, which Beeline does not need: `first_seen_at` is the night Beeline first saw a registration, and that tells a new registrant from then on.

## Which registration is whose

`person_registration_event` (`schema/014`) holds decisions, and the latest one about a person is the answer (`person_registration`, `schema/104`). They are events so that a link that mailed labels to the wrong home can be traced to who made it and on what evidence.

- **Several people can share a registration.** A couple registered once, under the first name "Pete and Gretchen".
- **The link is not in the person overlay.** The overlay exists to replay decisions onto a rebuilt store, and production is no longer rebuilt. It also cannot name a person who shares a name and has no account, and its curated copy is in this public repository.
- **An id names a person's record**, which Ideal Logic keeps as they update their details, so a link goes on finding their current address. A person can have two records under two email addresses: five names had two on 2026-11-18. The nightly job links neither of a person's two records; staff choose.
- **Not everyone registered is a collector.** Ideal Logic also holds people who signed up only for a workshop, which is why the nightly job keeps a registration only when Beeline has a use for it.

The handle a registrant types is the weakest evidence there is: of 142, seven were not the login Beeline holds for that person (typing slips, a display name, the word "yes"). So nothing links on a handle alone, and nothing links on a name alone, since 386 registrants have no relation to Beeline and any of them may share a collector's name. Three ways a link is made:

1. **The old register's email addresses**, once, by hand (`pnpm ideal-logic:link-register`, `src/link-register-emails.ts`). The registration's email address must be in the old Beeline's register against exactly one login, exactly one person must hold that login, and the full name must agree. It linked 259 of 593 people on 2026-11-18. It runs on a machine that holds the register and sends each link through the API, addressing the person by iNaturalist login (a store id can change when a store is rebuilt, a login cannot) and sending it again, up to five tries, when the API answers 429 (too many requests); it is not part of the nightly job, because the register is a frozen file that holds addresses.
2. **The nightly job**, where the typed handle is the login of exactly one person and the full name is that person's (20 more people). It never links a person a decision has already been made about, so a person staff unlinked stays unlinked, and it never links a registration that is already linked to somebody. Staff can still link a second person to it, since a household shares one registration.
3. **Staff**, for everybody else, on the `/registrations` page ([below](#the-registrations-page)), or through `POST /api/v1/people/<id>/registration` ([The API and its keys](the-api-and-its-keys.md)).

The full name must agree, and not only the family name, because of households: two people who registered separately can share one login, which only one of them holds.

The server checks that again for `register_email` evidence (`decideRegistration`, `src/registrations.ts`). The command-line tool matched on names from an exported file, and a login may have moved to another person since, so the server compares the registration's name with the person's display name as it is now, and refuses with `name_differs` if they disagree. The API answers 422 without repeating either name, and the link is left for staff to decide. Evidence of kind `staff` is not checked, since a person has already looked.

## The registrations page

`/registrations` (`src/app/registrations.ts`, `src/app/views/registrations.tsx`, beeline-w8ab.2) is where staff place the people the nightly job could not. It is for admins, and its writes are refused while staff are viewing Beeline as someone else, like every staff write. It reads only what Beeline keeps, so it shows no address and no email address and makes no request to Ideal Logic.

It has two sections, each with a count in its heading.

- **Collectors with no registration** lists everyone who is the primary collector of a sample and has no row at all in `person_registration_event`: nobody has linked them and nobody has said they have none. People with labels waiting to print (`pending_print_sample`) come first, then people with labels in a print run that has been prepared but not mailed, then the rest by their latest sample. The order follows the work: a collector whose labels are about to be mailed needs an address first. For each person it suggests the registrants whose whole name folds the same as theirs (`namesAgree`), whose family name folds the same, or whose typed handle is their iNaturalist login without regard to case. A suggestion says why it was made and names anyone already linked to that registration, since a household shares one. Each has a **Link** button. **No registration** records that the person has none, which also stops the nightly job from linking them later. A small form takes an Ideal Logic id for a registration no suggestion found, and shows `decideRegistration`'s refusal when Beeline has not seen the id.
- **Registered, not in Beeline** lists registrants that nobody is linked to and that named an atlas or typed a handle, newest `first_seen_at` first, with no actions. A handle that is the login of an observer waiting on `/unclaimed` links to that observer's page, because that is where such a person becomes a collector when they first collect.

A decision is made by `POST /registrations/:id/link`, `/none` or `/unlink`, which takes its turn in `oneDecisionAtATime` with every other decision about a person and records evidence `staff` with the signed-in staff member's login. It redirects back to the page with the outcome in the address (`?saved=`), and a refusal shows on the page with status 422. A person's own page (`/people/:id`) shows the registration, who decided and when, with an **Unlink** button that returns to that page.

## The nightly job

`ideal-logic-registrants` runs at 1am (`src/app/jobs/registry.ts`). It makes one request and keeps a row in `ideal_logic_registrant` for each registration Beeline has a use for: one linked to a person, one that names an atlas or a handle, or one whose name is a person's. The rest have no relation to Beeline, and their names do not belong in every backup. A registration that has left Ideal Logic keeps its row, and its `last_seen_at` falls behind.

A failed run is retried every 15 minutes until 5am, like every night job, which is about a dozen requests at worst.

## The download of a print run's addresses

Staff cut a run's sheets apart and mail each collector their labels, so the run's page has a button that downloads a CSV of the collectors' mailing addresses for a mail merge (beeline-w8ab.3, `POST /print-runs/:id/addresses.csv`, `src/app/print-run-addresses.ts`). It is a POST so that a browser prefetch cannot spend one of the day's requests, and the button shows only where `config.idealLogic` holds a client. The request makes its cheap checks first: the caller is an admin, a client is configured, and the run exists and is not canceled. It then asks the store whether any primary collector of the run is linked to a registration, and if none is, it does not call Ideal Logic at all. Otherwise it calls `fetchRegistrants()`, which can take up to a minute. Only after the answer arrives does it reload the run, refusing with 409 if the run was canceled meanwhile, and read the collectors, their label counts, the printed collector lines and their registration links together in one transaction, so a link corrected during the wait is used and the reads cannot disagree. It matches each collector to a registrant, builds the file in memory and sends it with `Cache-Control: no-store`. The client shares a fetch that is still under way with any call that arrives meanwhile, so a double click or a download during the night's job costs one request, and it forgets the answer the moment the fetch settles. Nothing is written to disk, and the one log line says who downloaded which run and how many rows had an address, never a name or an address.

The file has one row per home, not per person, so a household gets one envelope. Collectors linked to the same registration always share a row, with or without a street: two collectors on a registration that has no street get one row with both names, their labels added up and the no-address note. A collector with no registration gets a row of their own. Collectors linked to different registrations share a row only when the street, city, state or province, postal code and country all agree, and never when the postal code is empty, because the same street name in two towns is two homes. The street and city are compared in lower case with each run of characters that are not letters or digits read as one space, so "12 Oak St." and "12 oak st" agree but "12-14 Oak St" and "1214 Oak St" do not. The postal code is compared as letters and digits only, so "V8W 1P6" and "v8w1p6" agree. A label counts towards a collector only when its sample has exactly one primary collector; labels of any other sample are reported in the last row, which is never negative. The rows come in four groups: complete addresses, then incomplete ones, then collectors with no address, then at most one row for labels that are not in the file. An incomplete address is one with no city, no postal code, no state or province (a Canadian postal code starting with X names none), or a country that is neither a US state nor a Canadian postal code. Its row keeps the parts that are present and says what is missing, so staff can finish it by hand. A collector with no linked registration, whose registration has no street, or whose registration was not in Ideal Logic's answer or could not be read, still gets a row with empty address columns and a note saying which.

A pair's labels are mailed to the primary collector, the first in the sample's collector list, and to nobody else (Peter, 2026-11-18). So the file has a row for the primary collector of each sample and none for a second collector, whose name appears only in the collector line as printed.

A printed label records the collector line as printed and no person, and the freeze keeps nothing else about who the primary collector was (`printed_label`, `schema/035`). So the file follows each sample's primary collector as it is now. A row says so when a label of that collector was printed with a collector line that differs from what the sample would print today. A label whose sample has no primary collector now, or has another, can drop out of its first collector's row, so the file adds up the labels it holds against the run's own count and, if they differ, ends with a row that has no names or address and says how many labels are not in it. When the client throws an `IdealLogicError`, the answer is the standard error page with status 429 for a spent budget and 503 for anything else, carrying the error's fixed text and the requests left today, and never a partial file. A canceled run gets the same page with status 409. The page's hint warns that opening the file in Excel before the merge can drop the leading zero of a ZIP code.
