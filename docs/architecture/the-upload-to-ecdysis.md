# The upload to Ecdysis

Part of Beeline's architecture notes; the index is [README.md](README.md).

`src/app/ecdysis-upload.ts` (beeline-8dx9.12) writes the two files a person uploads to Ecdysis by hand, one Ecdysis collection at a time, and only a collection Beeline reads whole (`ECDYSIS_COLLECTIONS`: British Columbia's collection 196 for the program BC; Washington's dataset 44 is not). The page is a section of the program's Data tab, `/programs/<code>/data` (`src/app/views/program-data.tsx`; it was the last section of `/exports` until beeline-q8di), and the archive is asked for with a `POST` to `/programs/<code>/data/ecdysis/<year>-upload.zip` (a form on the page; GET answers 405) and the associations file is a `GET` of `/programs/<code>/data/ecdysis/downloads/<download id>/associations.csv`. Who may open the tab, and so every one of these routes, is stated once in [programs.md](programs.md) (leads of the program, and admins). Each route takes the program from the address, and the download a request names must be that program's own, so a lead cannot fetch another program's file by guessing an id. The plan behind them is [publishing-to-ecdysis-and-gbif.md](../research/publishing-to-ecdysis-and-gbif.md), what Symbiota does with them is measured in [symbiota-import-test-2026-11-20.md](../research/symbiota-import-test-2026-11-20.md), and the two files Joel Gardner made by hand before are specified in [ecdysis-upload-files.md](../research/ecdysis-upload-files.md).

These are not the program archives (`src/app/dwc-archive.ts`, written nightly, never uploaded anywhere). They share that file's stream and its cell functions (`csvCellsOf` reads the staff download's cells by name; `specimenArchiveStream` takes an `ArchiveLayout`, which is the program archives' by default), and they have a column list of their own.

## Which collections, which specimens, and when

**Only a collection Beeline reads whole is offered files.** Beeline reads British Columbia as Ecdysis's collection 196 (`collectionId` in `ECDYSIS_COLLECTIONS`) and Washington as dataset 44, a subset of WSU's collection 164 (`datasetId`). A Symbiota upload adds no record to a dataset, and Symbiota matches a catalog number across the whole collection, so the day after an upload to Washington the same specimens would be offered again, and a record in the collection but outside the dataset would be replaced. The page shows Washington with a sentence saying so and the route answers 409. When Beeline reads Washington by the collection, the rule lets it in without a change here.

**A specimen is eligible on its own account.** A specimen is in an archive when it

1. belongs to the collection's program, by the scope `programArchives` gives it;
2. has a label on paper (`specimen_on_paper`, through the listing's own `labels=printed`) and a label number of digits only (a label number that is a collector's name and a number is counted, and never shown);
3. has no `specimen_disposition` row whose disposition is anything but "in collection" (a missing pin, or a remark that old Beeline recorded the specimen twice, which may be a second record for one bee);
4. has no row in `specimen_catalog_number` (the listing's `ecdysis=not`), **and** its would-be catalog number, the collection's prefix and the label number, is not in the archive Beeline last downloaded from Ecdysis, **and** its label number is on no other specimen and its catalog number fits Symbiota's 32 characters;
5. unless the downloader chooses otherwise, has no obscured coordinates, of two kinds counted apart: the specimen was collected from a plant whose location iNaturalist obscures (a protected plant; `nullif(sample.taxon_geoprivacy, 'open') IS NOT NULL`), private included (the observation is of the plant the bee was collected from, so this is about the plant and never about the bee being rare), or the observer obscured or hid their own observation (`sample.geoprivacy`).Peter decided on 2026-10-23 that the judgment on these records is the taxonomist's, made before upload, so the downloader chooses for each kind (`includeTaxonObscured=1`, `includeObserverObscured=1`, two checkboxes in a form) and the page says that including them puts their true coordinates in Ecdysis, where anyone can see them. A specimen in both kinds goes only when both are chosen. The choice is kept in the record of the download. Everything else is written as a staff reader sees it, with true coordinates, as the program archives are;
6. is not one whose sample is in `sample_geoprivacy_stale` (schema/105: the sample's copy of its observation's flags disagrees with the observation's). Which flags are true is not known, so the downloader's choice cannot be applied to it; it is left out, counted as its own line, and never offered as a choice. It is eligible again at the next sync that corrects the copy.

Nothing about the specimen's year, or about what else of that year Ecdysis holds, makes it ineligible. After an upload and a new read, the same year therefore offers whatever is still eligible: what was left out earlier, and what was labelled later. That is intended.

**Which years a collection offers is a setting in code.** `UPLOAD_CONSTANTS[program].years`, beside the collection's other fixed values, lists them. British Columbia offers 2026 only, by Peter's decision of 2026-11-21: its older years wait on beeline-2afe, and Washington's on GitHub #420. Adding a year is therefore a code change, made when that is settled, so that no one uploads a year by accident. Years with eligible specimens that are not listed show on the page as not offered, with their counts and a link to the Specimens listing for the program, the year, `ecdysis=not` and `labels=printed`, which are the filters the counts use, and the route refuses them with 409. (The tests set the setting to the seasons their fixtures are dated in; one test pins what the code says.)

The fourth rule has two parts because the store keeps only the Ecdysis records the loader matched to a specimen: `specimen_catalog_number` holds those, and the loader counts the rest and keeps five as a sample (`unmatchedSample`). A record Ecdysis holds that Beeline could not match, say because its label number is on two specimens (beeline-1kb.14), would look new, and uploading its catalog number again would make Symbiota replace that record whole. So `catalogNumbersInArchive` reads every catalog number out of the cached archive file the nightly read keeps (`cachedArchivePath`, `data/ecdysis/collection-196.zip`), with DuckDB as the loader reads it, comparing without regard to case because Symbiota's column does (`utf8_general_ci`; confirmed on the test database, not on Ecdysis's). It unpacks the occurrences file into a folder of its own under `BEELINE_ECDYSIS`, which the app's store is allowed to read (`storeFiles`; `test/store-file-limit.test.ts` runs it under that limit), and removes it. Each unpack is chained, at the moment it is asked for, onto the one before it, so one cannot clear the leftover folders while another is using its own; leftovers from an unpack cut short are removed first; two first views share one unpack; and the answer is kept in memory while the zip's size and time stay the same.

**Narrowing within a year is deliberately not offered.** An archive request takes the collection, the year and the two choices about obscured specimens, and nothing else: a query parameter or any other form field is a 400. An earlier version passed the Specimens listing's filters through. It cost more than it gave: the archive became a POST form, whose address carries no filters, so a person could not follow the instruction to add them; the listing's parser is forgiving on purpose, so a filter had to be validated again (an empty place, LIKE wildcards in text filters, which the listing does not escape); and each page had to be rechecked against the filters, and the filters recorded. British Columbia uploads a whole year, so the feature went. The `filters` column was dropped from the unmerged schema with it.

## When an archive may be built

The read must have downloaded the archive. The fetch's probe asks Ecdysis's API for the collection's record count and the number of records modified since the last download, and reloads the kept archive when both are unchanged; a second change to a record that was already modified leaves both as they were, so the upload does not rest on a reload. The marker says which it was (`source`), and a marker whose source is a reload gets its own refusal (`reloaded`) telling the person to press "Read Ecdysis now". That button runs a second job, `ecdysis-read-now` (`src/app/jobs/registry.ts`, on demand, never by the clock), which is the same read as the nightly one with `force`: a collection read whole is downloaded whatever the probe says (`fetchEcdysis`'s `force` option); a dataset is left to the probe. The nightly job is unchanged. The probe is still taken in a forced read, for the baseline the nightly run compares with, but decides nothing.

No archive is written, and the page and the route say so in plain words (the route shows its refusal as a page with the sentence and a link back to the Data tab, because it is shown at the address of the POST, where reloading would repeat it), unless the last read of Ecdysis for the collection began under two hours ago. Symbiota replaces a record it matches whole, so an archive made from an old read could replace a record someone added since, and a person must read Ecdysis again just before downloading. The page has a button for that, which posts to `/programs/<code>/data/check-ecdysis`. That route starts the `ecdysis-read-now` job through the same runner the Jobs page's Run button uses (`JobsDep.start`), unless a read of Ecdysis (`ecdysis-read-now` or the nightly `ecdysis-fetch`) is already running, or the last check, failed or not, ended less than five minutes ago (`ECDYSIS_CHECK_MIN_INTERVAL_MS`; the redirect carries `?check=recent` and the tab says when Ecdysis was last checked, or that the check did not work), and then redirects back to the tab. The interval is there because the job reads every collection and replaces every collection's marker: a lead of one program pressing the button repeatedly would make another program's specimens file, being made at that moment, start again (its marker is replaced, so the file is thrown away), and would download Ecdysis's whole collections each time. A failed check counts too, because it can fail for one collection after refreshing another, and an immediate retry would download everything again; the Jobs page, which only admins use, is not limited. A lead cannot open Jobs, so the tab says in its own words whether a check is running (`JobsDep.running`, the job the scheduler has in hand), or when the last one finished or that it failed (the latest finished `job_run` of either job, `ecdysisCheckOf`), and never shows why it failed. If another job is running and the check could not start, the redirect carries `?check=busy` and the tab says Beeline is busy. Like every other action under the tab, it is refused while impersonating.

The source is a marker the fetch writes beside the cached archive after every successful read, whether it downloaded or found the archive unchanged (`<collection>.read.json`, `ReadMarker` in `src/fetch-ecdysis.ts`): when the read began, which zip it loaded (size and modification time) and how many occurrence rows the archive itself has. That count is made from the archive's own file, as the upload code counts it again from the zip. It is not the loader's `occurrences`, which counts a join to specimens and so counts an Ecdysis record twice when its label number is on two Beeline specimens (beeline-1kb.14): British Columbia's real zip has 9,452 occurrence rows against 9,438 specimens with a stored catalog number, so the figures do differ in production, and a comparison with the loader's count would refuse for good. The fetch also checks, when Ecdysis says nothing moved, that the kept zip is still the one the marker describes (size and time) before reloading it, and downloads again if not; a store with no marker downloads once. The upload code, for its part, compares the file's size and time with the marker's immediately before and after reading its catalog numbers, and refuses if either differs; it also compares them before returning a kept or in-flight answer. The archive's own file time is not used, since it changes only when an archive is downloaded. An archive is refused when the marker is missing, the zip is missing or cannot be read, the zip is not the marker's (size, time), the zip has a different number of occurrence rows than the marker's record count, or a catalog number the read recorded in `specimen_catalog_number` is not in the zip. That last test uses `loaded_at`: the loader writes it with the read's own start time for every specimen matched at that read, so those catalog numbers must be in that read's zip. It does not compare with every catalog number in the store: `src/load-ecdysis.ts` never removes a `specimen_catalog_number` row (an occurrence missing from a later archive leaves its row as it was, by design, since a flat export need not be the whole collection), so a record Ecdysis has since deleted keeps a catalog number the zip lacks, and a check against all of them would refuse for good.

## One archive for each read

Three tables (`schema/177`, migration 0116), because rows are never updated here (ADR 0007). `ecdysis_upload_download` is the start of a download: who, when, the collection, the year, the choice about obscured specimens, the planned count and the time of the read it rested on. A download is an identity (the associations file is asked for by its id, and its specimens refer to it), so its key is an `entity_id` (ADR 0002; a log row nothing refers to would take a key of another name, as `event_change` has `change_id`). `ecdysis_upload_download_completed` is its end, a facet keyed by the download's id, with the number of specimens actually written; `ecdysis_upload_download_specimen` is the specimens the archive held, about 8,000 rows an upload, each with `catalog_number`, the catalog number it was written under. The associations file names its subject by that saved number, and the page compares it with `specimen_catalog_number` and the cached collection, so a label number corrected after the archive was prepared changes neither; a recorded specimen that no longer exists counts as not known to be in Ecdysis, never as held. The count is one SQL statement grouped by download (the cached collection's catalog numbers go into a temporary table on the transaction's connection for it), not a load of every recorded specimen. None has a foreign key, because DuckDB would then refuse to update a referenced row, and a key to `specimen` would stop specimens being edited.

An archive is refused for a collection when any download for it, started or finished, began after the last successful read began. So a second archive, whatever the year or the filters, needs a new read. A download without a completion that began under 15 minutes ago is shown as being prepared; an older one as not prepared; both block. An abandoned or failed download keeps its start and gets no completion, and still blocks until the next read: the person may hold a partial file, and a read is cheap. A zip that was cut short cannot be uploaded, so the cost of this is a read. A read that began before a download and finished after it also blocks, because the download began after the read's recorded start.

The decision and the start are written in one transaction (`startDownload`). DuckDB works on snapshots, so two requests that each see no download can both pass a check, and the check is not what keeps them apart. The table's `UNIQUE (collection, read_at)` is: DuckDB refuses a second row with the same key, so at most one archive can be started for a read. The loser's transaction is rolled back (its own rollback may fail too and hide the cause, so the loser asks again what is on record and answers "an archive was just started"). A test sends two requests together.

**The archive is built whole before anything is answered.** It is generated in memory (`buildArchive`: British Columbia's is about 145 KB, and a bound of 50 MB refuses a larger one with a clear error), the completion is then recorded with the specimens actually written, and only then is the archive sent, under a file name that carries the number actually written. So "completed" means "Beeline finished writing it", which is the boundary that matters, because the person may have the file from the moment it is sent; and the planned count can no longer differ from the name. A client that goes away after that leaves a completed download on the page, which is correct. A failure while building, or an archive over the bound (413), leaves the start and no completion, and it still blocks until the next read; the 413 says so, and that a new read is needed before asking again. While building, the read marker on disk is looked at before each page and at the end; if it is no longer the one the plan rested on (a newer read finished), the build stops, nothing is recorded as completed, and the answer says to start again (tested with the marker replaced mid-build). The archive is asked for with POST, as the print-run address download is, because asking records a start and uses up the read; the app's origin check covers it. HEAD is refused for the associations route too, since Hono runs the GET handler for HEAD and drops the body.

**Known gap.** Two requests that rest on two different reads finishing within the same instant have different `read_at` and so different keys, and both can start. Symbiota's report would then show the second upload as updates, which the instructions say to stop at.

**The page lists prepared archives whatever the state of the read** (`downloadViewsOf`): the most recent ten per collection, newest first, each with who, when, how many specimens and whether Ecdysis now holds them ("all in Ecdysis since the last read") or how many it does not hold yet, with its associations link; and any older finished download that still has specimens absent from Ecdysis, so the list is not cut before the outstanding ones are found. A specimen counts as in Ecdysis when it has a `specimen_catalog_number` row or, where the cached archive is in hand, its catalog number is in it. An unfinished download is listed while it blocks. The freshness check governs only starting a new archive. A sentence says an older archive must be deleted, not uploaded. A download is looked up by id in one query (`downloadById`).

The id of each archive row (the specimen's `entity_id`) and each identification's `sourceIdentifier` (the determination's `entity_id`) are entity ids and rest on production never being reseeded, which ADR 0006 states: a reseed renumbers them, and Symbiota would then update the wrong identifications in place. The same holds for the recorded specimens of a download.

## The associations file belongs to a download

The associations file is built from a finished download, by its id (`/programs/<code>/data/ecdysis/downloads/<id>/associations.csv`), for exactly the specimens that archive held (the third table), and takes no filters or choices of its own. It stays available after later reads for as long as the record does, because loading it twice adds nothing (Symbiota rejects each row as a duplicate; tested 2026-11-20). The page offers it beside each finished download, not beside the checkboxes. A download that did not finish has none. A trap sample has no row at all, decided by the sample's `kind` and not by the word "trap" in the free-text protocol: Symbiota applies one relationship, `hasHost`, to the whole file, and the plant near a trap is not a host. The specimens file carries no host at all (see below). Places that still decide by protocol text (`methodNamesTrap`, `methodNamesTrapSql`, `plantRelationship`): `src/legacy-export.ts`, `src/app/your-bees.ts`, `src/app/determine.ts`, the program archives' and downloads' `associatedTaxa` in `src/app/listings.ts`, and the two listing views and the record view.

## The rules hold when the archive is written

The plan is made from the store at one moment and the archive is written later, a page at a time. So each page asks again (`eligibleNow`, the same rules as the plan, and also the collection year: a sample whose date was corrected to another year since the plan belongs to another year's archive) which of its specimens may still go, and reads the specimens and their identifications in one transaction (`db.transaction()`, as `runCollectors` reads), so a page is one moment of the store: a specimen that has become obscured, been marked missing or held in Ecdysis since the plan is not written, and a determination added meanwhile is in its specimen's page or not at all. The specimens actually written are collected and recorded as the download's. `pagedStream` was given an optional `last` on a page, since a page can be shorter than a full one without being the last, and a fix: a page whose bytes the compressor held back wrote nothing, and a stream that returned without writing was never asked for the next page. The real archive is two pages of 5,000 specimens; the tests make the page size small.

## The archive's columns

`occurrence.txt` and `meta.xml` declare each column under the term Symbiota maps. Every term was checked three ways: Symbiota's source (`SpecUploadDwca.php` 273-276 takes the last part of a term's address as the header; `SpecUploadBase.php` `echoFieldMapTable`, 344-440, lower-cases it, drops `_ . ( )` and spaces, applies a small translation map, and maps it where `uploadspectemp` has a column of that name), the importer's own mapping page (auto-mapped with no change by hand), and a live import (the stored value in the named column equals the archive's cell, for every cell of 31 records). Constants are real columns because whether Symbiota honours a `default` in `meta.xml` is untested, and they are each collection's own (`UPLOAD_CONSTANTS`): Washington's records carry `labelProject` "Washington Bee Atlas" (what Joel's files write; Symbiota's `labelProject` column maps by name, which was read from the source and not imported live), and British Columbia's file has no such column until BC says what its records carry. There is no `occurrenceID`: Washington's collection ignores an uploaded one (test B2). The `id` of each row is the specimen's `entity_id`; Symbiota keeps it in `dbpk` only for a record it inserts.

The last seven rows' cells (name, authorship, qualifier, determiner, date, sex, caste) are filled only where the determination of record is an expert's. Where it is a volunteer's, or there is none, they are empty and the record is created with no name, so that Ecdysis's own experts name it (Peter, 2026-11-20). The determination of record is the newest expert's, else the newest volunteer's (`determination_of_record`).

**The specimens file carries no host.** Ecdysis holds a specimen's host plant in two places: the association row, loaded from the associations file, and the `associatedTaxa` text on the specimen record itself. Loading the associations file again later can correct the association row but never the text on the specimen record, so the two would disagree after a plant is renamed (tested on a local Symbiota, beeline-8dx9.15). Peter decided on 2026-11-22 that the specimens file writes no `associatedTaxa` column, so the host reaches Ecdysis only as the association. The cost is known: a trap sample has no association row (see the associations file), so a plant recorded near a trap is not recorded in Ecdysis at all, and British Columbia's 2026 file has no trap sample. The program archives and downloads keep the field.

**The hand-made file's columns this file does not write.** Joel's Washington file has `verbatimElevation` (the same number as `minimumElevationInMeters`, so a duplicate), `verbatimEventDate` (the date reformatted as text; Symbiota keeps the original text of a date only when it must convert one, and Beeline's `eventDate` is already ISO), `georeferenceSource` or `georeferenceSources` ("label": Beeline's `location_source` is a different thing and must not be written there), `municipality` and `habitat` (Beeline holds neither: it has no town boundaries and no habitat, and Joel types them by hand; beeline-8dx9.2). The helper columns that feed the associations upload (`relationshipOfResource`, `associationType`, `relatedResourceID`, `relationshipRemarks`, `url`) belong to the associations file, not the archive.

## The identifications

`identification.txt` holds every determination of every specimen in the file, as history, with `https://symbiota.org/terms/identificationIsCurrent` 1 only on the determination of record when it is an expert's and 0 on every other, so a specimen with only volunteers' determinations has history and no current name (test A5). Its columns map as follows: `scientificName` to `sciname`; `scientificNameAuthorship`, `identificationQualifier`, `identifiedBy`, `dateIdentified` by name; `identificationIsCurrent` to `iscurrent` (translation map, SUB 389); and `sourceIdentifier`.

Symbiota's unique key on a determination is (record, `dateIdentified`, `identifiedBy`, `sciname`), and it keeps only the first of two rows that agree on all four, whatever their flags (test A6). `uploadIdentificationRows` therefore writes determinations of one specimen that have the same name, determiner and date (or lack of one) as one row, current if any of them is, with the current one's other cells; the comparison is `symbiotaKey`: without accents or case, with runs of white space as one, as Symbiota's columns compare. Two determinations that agree in everything but the qualifier or the sex are therefore written as one, and the later detail is lost in Ecdysis.

`sourceIdentifier` is the determination's own `entity_id`. Symbiota's importer maps the header `sourceIdentifier` to the column of that name (SUB 1405-1418): a determination already on the record with the same one is updated in place instead of added again, so loading the same file twice duplicates nothing. Darwin Core's own `identificationID` would be the right term, but the importer has no mapping for it. Patch 3.1 of Symbiota's schema marks the column "deprecated" and copies it to `instanceID`; this importer still reads and writes it, and a later Symbiota that dropped it would leave the header unmapped, which is harmless.

## The associations file

`associationsCsv` writes, for the specimens a finished download held, one row for each whose sample has an iNaturalist observation that still exists (`observationGone` is left out: no page to send anyone to) and is not a trap sample, with exactly `subject identifier: catalogNumber`, `resourceUrl` (`https://www.inaturalist.org/observations/<id>`) and `verbatimSciname` (the host as the observation named it, at the rank Beeline holds, empty where there is none): the headers Symbiota's "Extended Data Import" page (titled "Extended Data Importer") maps for an external link (`OccurrenceImport.php` 440-485). It has no `objectID`, so Symbiota's export shows the observation's address as the related resource, which GloBI recognises, and no `occurrenceID`, so the subject is found by catalog number alone, in one round of uploads. UTF-8, quoted by RFC 4180, with no byte order mark and no formula guard: the program's CSV downloads have both for spreadsheets, but this file is read by Symbiota, which loaded it the same with and without a mark, and a guard would write an apostrophe into a name that begins with `-`, `=`, `+` or `@`. A person loads it with the association type "Occurrence - External Link" and the relationship "hasHost", the only fitting choice the page offers today ("visits flowers of", which GloBI reads as a flower visit, is not on its list).

## What a person is told, and why

The page (`m.programData.ecdysis`) gives ten steps, each one thing to do on one screen (the design page's rule for `Steps`: a step that moves to another screen is two steps), and the note "Good to know" under the list. In order: (1) read Ecdysis now (the button posts to the tab's own check route, described above, and the tab shows the state of the check beneath it); (2) download the specimens file and upload it once, today, then delete it, because uploading it again later would replace identifications made in Ecdysis since (Symbiota overwrites a matched record whole and never compares dates), and the first file of a year need not be the last, since what is left out is offered again after the next read; (3) open the collection to upload into, named under the collection's heading; (4) open the collection's "DwC-Archive Import" link (the page is headed "Manual DwC-Archive Import: Identify Data Source"), choose the file and press "Analyze File"; (5) make sure "Match on Catalog Number" (ticked by default, `specuploadmap.php` 449) and "Import Identification History" are ticked, then press "Start Upload"; (6) stop at the "Pending Data Transfer Report" unless it says "Records to be updated: 0", the new records are the number in the file's name, and it shows no line "Records matching on catalog number that will be appended" (`specuploadprocessor.php` 168, from `SpecUploadBase.php` 815-846, with the warning "This will result in records with duplicate catalog numbers"; it appears when the switch is off), and otherwise press "Transfer Records to Central Specimen Table"; (7) download the associations file of that file; (8) open "Extended Data Import", choose the file, set the import type to "Associations" and the association type to "Occurrence - External Link", and press "Initialize Import"; (9) leave the field mapping, choose the relationship "hasHost" and press "Import Data"; (10) read Ecdysis again, because the counts do not change and no second file is offered until it has. Localities are as the labels have them (the note).

The archive's file name carries the collection, the year, the number of specimens and the Pacific date and time written (`uploadFileName`), so an old one is recognised and thrown away and the number the pre-transfer report must show is in the name. Responses carry `cache-control: no-store`.

## Verified against a real Symbiota (2026-11-20)

A synthetic store of invented people and places (32 specimens in the file: an expert's determination of record, volunteers' only, none, two identical undated determinations, a trap sample with a range of dates, a host at genus and at family rank, no observation, a disposition and remark, quotes, semicolons, an accent) was imported through Symbiota's own upload pages into a live-managed collection that already held four other records. Every cell of every record landed in the column above. The four earlier records were byte-for-byte unchanged afterwards (hashed). Names and current flags were as specified, and the end date was in `eventDate2` with `endDayOfYear`. A second import of the same archive duplicated nothing and changed no value, but it moved every record's `dateLastModified`: Symbiota's update first blanks `countryCode` and `continent`, then fills them again, and the blanking is a change to the row. The 29 associations loaded through "Extended Data Import". Symbiota's own Darwin Core export then showed the record, its identifications and the association.

What the guards exist for, also measured: after an expert named a volunteer-only record in Symbiota's editor, importing the same archive again with matching on blanked the record's name, determiner and date and moved its `dateLastModified`, while the determination history kept the expert's current row, so the record and its history disagreed. Three identifications differing only by an accent, case or spacing in the determiner collapsed to the first row in the file, and the one flagged current was lost. "Extended Data Import" skips a catalog number the collection does not hold and shows no "create new records" box for associations; a request that carries that field by hand creates a blank record. Symbiota's "skeletal" upload type creates new records for catalog numbers the collection lacks, with the CSV's fields, `basisOfRecord` PreservedSpecimen and an "undetermined" determination by "unknown" dated "s.d.", the pattern seen on Washington's records. The pre-transfer report reads "Records to be updated: 0" and "New records: N" for a new-only archive, and "Records to be updated: N" followed by "Caution:   incoming records will replace existing records" for one that matches; the record count is unchanged until the button "Transfer Records to Central Specimen Table" is pressed. The scripts are not kept in the repository.

## Rehearsed with real records (2026-11-21)

A rehearsal on a local copy of Symbiota used British Columbia's real records. Its 9,452 existing records were loaded into a live-managed collection whose GUID source is the catalog number. The 2026 specimens file (8,085 specimens, with 369 identifications as history, none current, and no record with a name, because none has an expert determination) was then uploaded through Symbiota's own pages. The "Pending Data Transfer Report" read "Records to be updated: 0" and "New records: 8085". Stopping at the report changed nothing in the collection, so it works as a dry run. It left the upload staged, which the next upload for the collection replaces (`SpecUploadBase.php` 562-572) and which no visitor, editor or export sees. Pressing "Transfer Records to Central Specimen Table" added 8,085 records in about 12 seconds, and every record and determination that was already there was unchanged, byte for byte. All 8,085 new records matched the file in every mapped column. The associations file created 8,082 associations with none skipped, and loading it again added nothing. Uploading the specimens file a second time gave the report "Records to be updated: 8085 Caution: incoming records will replace existing records" and "New records: 0".

One caution came out of it: Symbiota's transfer writes whatever is staged for the collection at that moment, not the upload that a particular report page was shown for, so a report page left open should not be used later. For the same reason the page's note under the steps tells people that only one person should upload to a collection at a time: a second person's staged upload would be written by the first person's transfer. One limit remains: no trap sample and no expert determination were among the real 2026 specimens, so those paths rest on the earlier test with made-up records.
