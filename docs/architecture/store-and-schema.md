# Store and schema

Part of Beeline's architecture notes; the index is [README.md](README.md).

The schema **is** the `schema/*.sql` files, applied in filename order (0xx tables, 1xx derived views). Databases are blown away and rebuilt before cutover ([docs/roadmap.md](../roadmap.md)); the ones that can't be — the sandbox, production later — catch up through `migrations/NNNN-slug.sql` and `pnpm db:migrate`, recorded in `schema_migration` and stamped (never run) on a fresh build ([ADR 0006](../adr/0006-migrations-for-deployed-stores.md)). A change that migrations cannot carry, to the promotion rules or to a table others reference, was answered by `pnpm db:reseed` and a fresh promotion. Both now refuse a store that holds any print run or minted field number (`src/registry-guard.ts`, beeline-83b8.13), because a reseed leaves them behind and the new store's next run would issue those numbers again. `db:build` and `db:reseed` also refuse to delete a target that holds any. What answers such a change on production is not decided (beeline-131s). QC rules, printability, and determination-of-record are SQL views, not app code. Engine: DuckDB behind dialect-neutral SQL — [ADR 0001](../adr/0001-duckdb-first-with-portable-sql.md).

Every DuckDB the project opens goes through `src/db.ts`, which states the memory and thread budgets, pins the session time zone to UTC, and turns off one planner default of DuckDB 2.0, `delim_join_as_cte`. With it on, 2.0 copies the outer side of a correlated subquery into each subquery rather than sharing it, and the name-parsing views hide such a subquery in each alias macro (`ingest/parse-names.sql`): a legacy promotion on the test fixture took 100 s against 3.5 s on 1.5, and most pages on a copy of production's store ran 8–30% slower. `test/duckdb-openers.test.ts` holds that nothing opens DuckDB any other way, and that the `duckdb` command on the image (for maintenance mode) is the same version as the library.

**What the QC findings cost** (beeline-poon). The findings are views, so every page that shows a flag computes them: a sample or specimen page for its one sample, and a listing, the front page and printability for every sample. Two rules keep the first of these cheap. Every finding names its sample in `sample_id`, one about a single specimen included, so that a filter on one sample is handed down to each rule's own tables (`schema/130`): with that, one sample's findings take 23 ms on production's store of 2026-11-17 (2 threads), where they took 177 ms while `sample_qc_finding` looked the sample up through the specimen. Since #425 they take 48 ms (store of 2026-11-22): the second arm of the host rule, for a host staff set, builds the whole taxon chain under `sample_host` whichever sample is asked about, though production has no such host (beeline-amdt.3). And a new rule view should start from the sample, or from a table keyed by it, and join outward, since a rule that first counts or groups over every sample does that work even when asked about one. The findings for every sample take about 100 ms, a samples listing asks for them once for its rows and again for its total only when a status filter is set (`samplesCountQuery` in `src/app/listings.ts`, which asks `needsRollup` in the same file; beeline-amdt.1), and the specimens listing, whose rows show no flags, asks for them once and only with a status filter (`specimenListingBase`), and rewriting the rules does not change that much: the cost is spread over four rules, three of which read all 400,000 specimens. `qc_rule_observation_missing_upstream` also reads all of `observation_seen`, to which every weekly sweep adds about 14,000 rows; the nightly and the sweep therefore delete each sighting that a later run of the same source has repeated (`pruneSightings`, `src/sync-inat.ts`, beeline-amdt), which changes no finding, since the rule asks only which sources have returned an observation and when any last did. Measure a change to any rule with the app's own planner settings (`src/db.ts`), not a bare `duckdb` shell: DuckDB 2.0 chooses different plans under each, and the same view has measured 15 ms and 78 ms depending on the query around it.
