# Store and schema

Part of Beeline's architecture notes; the index is [README.md](README.md).

The schema **is** the `schema/*.sql` files, applied in filename order (0xx tables, 1xx derived views). Databases are blown away and rebuilt before cutover ([docs/roadmap.md](../roadmap.md)); the ones that can't be — the sandbox, production later — catch up through `migrations/NNNN-slug.sql` and `pnpm db:migrate`, recorded in `schema_migration` and stamped (never run) on a fresh build ([ADR 0006](../adr/0006-migrations-for-deployed-stores.md)). A change that migrations cannot carry, to the promotion rules or to a table others reference, was answered by `pnpm db:reseed` and a fresh promotion. Both now refuse a store that holds any print run or minted field number (`src/registry-guard.ts`, beeline-83b8.13), because a reseed leaves them behind and the new store's next run would issue those numbers again. `db:build` and `db:reseed` also refuse to delete a target that holds any. What answers such a change on production is not decided (beeline-131s). QC rules, printability, and determination-of-record are SQL views, not app code. Engine: DuckDB behind dialect-neutral SQL — [ADR 0001](../adr/0001-duckdb-first-with-portable-sql.md).
