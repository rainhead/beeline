# Backups

Part of Beeline's architecture notes; the index is [README.md](README.md).

The `store-backup` job (`src/store-backup.ts`, beeline-elf, 3am Pacific, ahead of the Sunday sweep so it cannot be pushed past 5am) puts one archive a night in the Bee Line folder on the OSU shared drive, as a service account scoped to `drive.file`: a copy of the store, the authored CSVs, and a manifest of table counts and hashes. Until 2026-11-05 it also carried the private store, encrypted with that store's key; the store was retired then (beeline-4tdh), and `checkBackup` still reads archives from before, opening that copy only when given the key, since retention keeps a year of monthly copies. The copy is taken inside the app (ADR 0005) and is not `COPY FROM DATABASE`, which inserts tables in name order and so fails on the first foreign key; `src/store-snapshot.ts` copies the schema with `(SCHEMA)`, which carries the sequence's position, and fills tables parents first, a self-referencing table (`animal`) a level at a time, in one transaction. Nothing is trusted: the copies are reopened and their rows and schema counted against the store, Drive's MD5 of what it stored must match (an upload that does not is binned before the run fails), and only then does retention — two weeks of nights, the first copy of each month for a year — move old copies to the bin. Unconfigured in production, the job fails rather than succeeding at nothing; the sandbox, which gives production its folder at cutover because two apps' retention in one folder would bin each other's copies, says it backed nothing up (beeline-83b8.8). Restoring and the drill are [the runbook's](../runbooks/deploy-fly.md#backups).

**The copy kept for queries** (beeline-pnqr.4). After the snapshot is verified, and before the upload, the job also leaves that same copy at `BEELINE_QUERY_COPY`, by default `query-copy.duckdb` in the store's own folder (`queryCopyPath` in `src/app/config.ts`; the file written is `keepQueryCopy` in `src/store-backup.ts`). It is a plain, unencrypted DuckDB file whatever the archive around the Drive upload is, and there is exactly one: each night's replaces the last by writing `query-copy.duckdb.partial` beside it and renaming, so a reader never opens half a file. It is about as large as the store (the snapshot is rebuilt compactly, so a little smaller than a store that has seen many updates), and for a moment during the replacement the volume holds the store, two copies, and the work directory's copy, so it needs room for those. `src/query-copy.ts` runs one SQL statement a time against it, and not against the live store, because a SELECT on the live store can call `nextval` (a sequence does not go back when the statement is rolled back, so a query could use up the 32-bit `entity_id` sequence of a store that is never reseeded) and a write inside a WITH clause is typed SELECT. The instance it opens is separate, read-only, locked against `SET`, without file or extension access, on one thread and 256 MB, and has no temporary directory it can create: a query that needs more memory than that fails with an error rather than spilling, because DuckDB 2.0.0 does not enforce `max_temp_directory_size` on a read-only instance (a 1 MB limit let one query write 1 GB beside the copy). One quirk: the open file is itself readable through `read_text`, which shows nothing a SELECT on its tables does not. The data is up to a day old, since the copy is made at 3am Pacific; a copy that has not been made yet is a `no-copy` error, not a crash.
