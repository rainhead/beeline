# Printing

Part of Beeline's architecture notes; the index is [README.md](README.md).

A print run (`schema/035`, its meaning in `schema/155`, the writers in `src/print-run.ts`, beeline-1kb.2) is the batch act of printing and the moment specimens come to exist: **preparing a run is the freeze**. It takes every pending sample in scope — `pending_print_sample`, which holds a sample from a settled season only once staff have released it (below), because nothing else from one is printed (Peter, 2026-10-14: a full sync of the sandbox minted 818 samples from observations the old system never recorded, 441 of them from 2018, and nobody pins a bee eight years later), then narrowed to `print_scope_sample` for an unscoped run, which means every atlas without an `atlas_printing` row plus samples outside any atlas, since Oregon prints for the whole program — and a run scoped to one atlas is refused unless that atlas has the row, since the rest are the program's to print (Peter, 2026-09-21; the flag is a satellite row, like `person_admin`, because DuckDB cannot add a NOT NULL column to a referenced table by migration) — creates their specimen rows, mints a field number for each — and no `occurrenceID`, which the museum database assigns ([ADR 0008](../adr/0008-specimen-identity.md), second amendment; beeline-1kb.15) — composes the six label strings (`src/label-text.ts`, the reference implementation's formats so a Beeline label reads like every label already pinned, the collector line included: `P.Abrahamsen`, set tight with no space after the initial, as every label in the drawers reads — decided in the room on 2026-09-18, screens keep `labelName()`'s `P. Abrahamsen` — and both names for a pair, `M.&D.O'Loughlin`; a county prints as its name alone, never with iNaturalist's `, US, WA` suffix, which `countyName` refuses even if the store still held one, since 172 labels in the first run anyone prepared said `Franklin County, US, WACo`, beeline-gr7; a BC regional district prints as the province abbreviates it, CAPRD for Capital, since the old system's CRD is the province's Cariboo, beeline-313x, and the county itself is the one Beeline wrote from the coordinates, [Areas](areas.md)) and lays them out in sheet order — the collector line, then the primary collector's id to keep two people whose lines read the same apart, then date, sample number (natural order) and specimen number — a blank cell between collectors, 250 to a sheet, so one collector's numbers run together. A taxon-obscured sample, one whose host plant iNaturalist hides because it is rare, is pending like any other once Beeline holds its true point, and its label carries that point: how a rare plant's location is handled is a question for export, not for printing (Peter, 2026-11-20, who removed the rule `taxon_obscured_awaiting_atlas`; labels and every export carry true coordinates until an atlas says otherwise, and Oregon's answer on gh-13 of 2026-10-21 agrees, beeline-pnag). A pending sample with no single primary collector stops the run rather than being skipped by the join (`sample_primary_collector_invalid` is checked first, as the location row is checked after). The snapshot is `printed_label`, one row per label per run: the six strings *and* the values they were rendered from, so the sheet re-renders byte-identical and beeline-1kb.17 can compare an iNaturalist edit against what actually printed. The mint is the INSERT into `minted_field_number`, whose PRIMARY KEY is the uniqueness guarantee (ADR 0008 §5); `specimen.field_number` is written beside it because it is the column every read uses, and `specimen_field_number_stale` asserts the two agree. The number continues the eight-digit `YY` form, seeded one past the highest eight-digit number in the **imported corpus and the registry together**, floored at `YY000001` — the registry alone would have started a rebuilt 2026 store at `26000001`, inside the imported block whose ceiling is `26072091` (`minted_field_number_collision` is the check). State is derived from timestamps, never a column: prepared → approved → printed → mailed, or canceled while unprinted, each a guarded UPDATE behind one in-process lock, and the freeze runs on a connection of its own because the app's shared connection cannot hold two transactions at once. Two runs can be open together and cannot collide: the freeze is what takes a sample out of pending. **Printed is the moment that matters, not the freeze** (Peter, 2026-09-14): `printed_sample` — a specimen with a label in a printed run, or an imported specimen with no run at all, since the legacy labels are on pins too — is what `promote-observations.sql` and `mint-samples.sql` read to stop the coordinates and the locality following iNaturalist; dates never followed. The one exception is an imported point that is a stand-in, the point iNaturalist publishes to hide an obscured observation's real one, which the old system stored and printed: `sample_location_standin` (`schema/106`) names it, 100 m or more from the observation's true point, and promotion takes the true point anyway, because Arthur ruled that the record's accuracy outranks agreeing with the pin (2026-10-14, beeline-b34). **Cancelling destroys nothing**, and not by preference: DuckDB will not delete a referenced row in the transaction that removed its references, and a cancel that half-succeeded leaves specimens no run holds, which read as printed. So the labels stay as the record of what was prepared, the specimens keep their rows with the number cleared, the numbers stay burned (`specimen_id` NULL), `individuated_specimen` (`schema/117`) takes those rows out of the count that `pending_print_sample` and `qc_rule_count_below_printed` read, and the next freeze re-adopts them — same row, a fresh number. Every author column after `prepared_by` is a plain INTEGER, because a foreign key is an index and an indexed column on a row the labels reference could never be updated (duckdb/duckdb#20246). `db:reseed` carries none of it, so it refuses a source that holds any print run or minted number, and it and `db:build` refuse to delete a target that holds any; `legacy:promote` refuses such a store too (`src/registry-guard.ts`, beeline-83b8.13). None of those sees a store moved into place by hand, which brings its own registry, so the deployment keeps a count outside the store: `data/registry-mark.json` (config `registryMarkPath`, `src/registry-mark.ts`, beeline-l3w7) holds how many print runs and minted numbers the store has held and the highest number minted, raised at every boot and inside each run's transaction before it commits (so a mark that cannot be written refuses the run, and a crash leaves the mark ahead rather than behind), and the app refuses to boot on a store that holds less of any of the three, since none goes down in a healthy store. The highest number catches a different store that happens to hold as many rows, such as a sandbox copy with rehearsal runs. A mark file that cannot be read is refused too, never taken for no mark. It is deliberately not in the nightly backup: it records what this volume has seen, and a backup restored over a store that printed since is the loss it exists to catch. Development warns and starts it again instead. A deployed store is migrated (ADR 0006), and how a promotion-rule change reaches one that has printed is not decided (beeline-131s). The sheets are `src/label-pdf.ts` (beeline-1kb.4): pdf-lib, the reference implementation's geometry verbatim — 25×10 on US Letter, 0.666"×0.311" labels, its six text boxes and shrink-to-fit rule, an 8×18 DataMatrix of the digits stood on end — because Arthur asked that the new sheet match the old one, and the vendored Oxygen Mono (`assets/fonts/`, OFL). Rendered from `printed_label` rows only, with the document dates set to `prepared_at` and no object streams, so two renders of a run are byte-identical (a test hashes them; `print_run.pdf_sha256` will record the first). The DataMatrix is vector: filled rectangles, one per run of dark modules, from bwip-js's module matrix. It was a 1-bit image first and came out blurry, because viewers and print drivers smooth a tiny bitmap when they scale it whatever its Interpolate flag says. Fits are remembered per render and found by bisection, since a sheet repeats the same strings down a column; with the freeze writing its three tables in multi-row statements rather than three statements a label, a 5,411-label run freezes in 1.6 s and renders in 2.9 s on a workstation, where the first version took 7.6 s and 7.2 s and minutes on the sandbox's two shared threads. A scanner reads the number, not a string, since only the digits are encoded, as the reference did. The render runs on a **worker thread** (`src/label-pdf-worker.ts`, beeline-1kb.19), because it is CPU-bound from end to end and Node would otherwise run it on the thread that serves every request — during the first demonstration Fly's health check failed mid-render, not at a deploy, the process alive and answering nothing. Measured on the production shape (`node --import tsx`, 5,000 labels): `/healthz` answered 2 probes at worst 3,996 ms while the sheets rendered in process, and 47 at worst 36 ms — its idle latency — with the worker, for about 7% more wall clock. The boundary is what makes it the cheap fix rather than rendering at approve time as a job: plain rows in, bytes out, nothing in between touching the store, and the renderer itself untouched so the sheets stay byte-identical. `runPdf` coalesces concurrent requests for one run's sheets, since two admins opening an unrendered run would otherwise start two workers on the same input. The freeze's own TypeScript half is the same shape of work and stays on the main thread: it runs inside the freeze's transaction, which cannot cross a thread. The screens are `/print-runs` (`src/app/print-runs.ts` + `src/app/views/print-runs.tsx`), admin-gated like `/jobs`: the list with a Prepare form whose scope picker says how many labels and samples each scope would take before anyone presses it, and the run page — the six strings per label in sheet order as the proofing surface, the labels to look at listed first, and until it prints, the samples that have changed since it was prepared — `printed_label_out_of_date` (`schema/155`, beeline-fq3j) compares the values each label was made from with the sample's now, because a prepared run's samples still follow iNaturalist and still take edits, and on the first production run localities were corrected during proofing with nothing saying which labels the edits left behind; the collector line is not compared, since a label keeps only its text —, one button for the state's next step with a note, Cancel while unprinted, and the sheets at `/print-runs/:id/labels.pdf`, rendered on first request into `data/print-runs/` (config `printRunsDir`; the files people upload are kept beside it, in `data/uploads/`, [Loading an edited download](loading-an-edited-download.md)) with the hash recorded — and a cached file is served only when it hashes to what the run recorded, since a reseeded sandbox restarts ids while that directory survives; a canceled run serves no sheets at all, its numbers being burned. The writes go through the print connection (`printConn`, opened in `main.ts` beside the scheduler's) and refuse impersonation. What a volunteer sees: their front page keeps a sample until its labels are **mailed**, not until a run is prepared — the freeze takes a sample out of `pending_print_sample` at once, and the page listed only what was pending, so in the first demonstration a sample vanished from its collector's dashboard days before any envelope existed; `sample_label_in_progress` (`schema/155`) is what holds it there, reading "3 labels are being printed" and then "printed Sep 18, not mailed yet". Then a Label column on the sample page's specimen list — printing, printed, mailed, run canceled, or printed before Beeline, never blank — and a Labels block on the specimen page, one row per run with the number as it printed, which is also the proofing lookup's other half: a number that matches twice shows each specimen's labels beside their runs. A specimen with no number is two stories, told apart by whether it has a label row (beeline-1kb.21): one a canceled run had numbered reads "awaiting a number" on the listing and the sample page and names the burned number on its own page, since the registry has let go of it and `printed_label` is where it survives; one with no label row at all predates field numbering, and only that one says so.

**Reprints** (gh-218, beeline-1kb.5.1) are a second label for a specimen that already has a number. An admin asks for one from the specimen page's Labels block, or for several by ticking them on `/specimens` (below), with an optional reason (never received, damaged or lost, record corrected) and note; the row is `reprint_request` (`schema/035`), and the writers are `requestReprint` and `withdrawReprint` in `src/print-run.ts`, behind the print-run lock on the print connection. A request is refused for a specimen with no field number, one already asked for, or one a run that has not printed yet holds, since that run is about to print it; for a list, the specimens that qualify are asked for and the rest are left alone. Reprinting is specimen by specimen (Peter, 2026-11-06): the sample page's "every label in this sample" form and its route are gone, and a whole sample is asked for by ticking its specimens. Whether a request has been answered is derived, never written: `pending_reprint` (`schema/155`) is the requests not withdrawn that no uncanceled run prepared since holds a label for, so a canceled run puts its reprints back by itself. The freeze takes `print_scope_reprint` (or `printable_reprint` for one atlas) beside the pending samples, and a reprint is held only by the flags in `qc_rule_unwaivable` — a hold, a missing required field, a point that is hidden or not yet cleared to print — not by printability as a whole, because an imported sample can carry flags that were never anybody's to fix and the label is already on a pin. A settled season is no bar either: a person asked for this one. The reprint is composed from the record as it stands, like a new label (Peter, 2026-10-30): for a lost label that is what printed, since a printed sample stops following iNaturalist, and for a corrected record it is the correction, as Arthur answered on gh-17. Where its text differs from the specimen's last Beeline label, `warnings` names the lines (`reprint differs from its last label: location`), which puts it among the labels to look at; an imported specimen has no label to compare against. On the sheets the reprints follow the new labels in the same order, set off by one blank cell, the gap between two collectors (Peter, 2026-10-30), and they mint nothing: a reprint is told from a first print by having no `minted_field_number` row in its run (`printed_label_reprint`, `schema/101`), never by a flag. That same test is why `printed_sample` and `individuated_specimen` ask whether a run *minted* the specimen's number rather than whether it has any label: an imported specimen can have a label now, and its reprint waiting in an unprinted run must not unlock a sample whose labels have been on pins for years, nor a canceled reprint take it out of the count. Everyone sees a waiting request on the specimen page and "reprint requested" on the sample's specimen list; the Labels block marks each reprint and says who asked and why. Staff can also mark many at once from `/specimens` (beeline-1kb.23), which is how Arthur works through a collector's recent labels with the listing's own filters. A bulk action is chosen **first** (Peter, 2026-10-31): the plain listing has no tick boxes, only a button naming the action, and pressing it puts the listing in that action's mode, `act=reprint` in the query, so paging, sorting and clearing filters keep it. In the mode a row that can be marked gets a tick box and a row that cannot says why instead — no number, already waiting, or in an unprinted run — and the form is held at the foot of the window from the start, so what ticking is for is said before anything is ticked. Which rows qualify is one SQL expression, `REPRINT_BLOCKER` in `src/print-run.ts`, read by the writer, the specimen page and the listing, so a box is offered exactly where marking would work. Each tick box belongs to the form by its `form` attribute, so without scripting the form marks what is ticked on the page in view; the `bulk-select` island (`src/app/islands/bulk-select.ts`) keeps the ticks in the tab's sessionStorage, keyed by the action and the signed-in login, across pages and filters, ticks a whole page, counts, and holds the button until something is ticked. Ticks are cleared when the listing comes back from a marking, not on submit, so a refused request leaves them for another try. The writer takes the list as one bound parameter, never as SQL text, and the listing marks each specimen whose reprint is waiting. A volunteer's counterpart is not this action but a ticket (beeline-l7ui), which will offer its own action in the same mode.

A sample staff hold (beeline-plu) is not printable, so no later freeze takes it. One held after its run was prepared is not taken out: `loadRun` names it on the run page while the run is prepared or approved, and the printer decides whether to cancel and prepare again, which leaves it out — proofing pulls, the per-label alternative, were decided against (beeline-1kb.3). Every held sample is named except one from a settled season that staff have not released for printing (Peter, 2026-10-25): a withdrawal is refused while a sample's labels are in a prepared run, so such a sample is in a run only when the run was prepared while its season was still active, as a run prepared in February can hold last season's samples that settle on 1 March, and its labels print with the run regardless. A released one is named, since staff decided it prints. (It was every sample of the current season, which hid a hold on last season's samples in January and February.)

**A settled season's labels are released, not assumed** (beeline-3vs.7, Peter, 2026-11-19). Trap bottles are pinned years after they were collected, so a trap sample staff entered or recounted in Beeline needs labels whatever its season; a count copied from iNaturalist for a settled season does not (908 such samples on production stay unprinted). A release is a row of its own in `sample_print_release_event` (`schema/050`): who, when, an optional reason, and whether it is a release or a withdrawal. Rows are only added, never changed, with an id from the global sequence (ADR 0002, as `minted_field_number.entity_id`), so the order the rows were written in is their order by id and not by `decided_at`; a sample's standing is its latest event, the one with the highest id, which the view `sample_print_release` (`schema/102`) gives for the samples whose latest event is a release. `settled_unreleased_sample` is the settled samples without one, and it is what `pending_print_sample`, `sample_labels_waiting`, `sample_coordinate_limit` and the county stamp (`followsPointSql`, which reads the view `sample_follows_point`, [Areas](areas.md)) read where they used to read `settled_sample`. A release is written by four acts, all plain writes. The first three write one in any season, unless one stands: in an active season it changes nothing yet, but a sample not printed before its season settles on 1 March would otherwise stop printing, and a count staff set prints whatever its season. They are staff changing a trap sample's specimen count (`setSpecimenCount`, with the count in one transaction; a count equal to the one it has writes nothing); staff changing the count on the trap form (`/samples/:id/trap`); staff entering a trap sample on that form, whose settled dates show a note saying so (an edit's note says only that a new count releases); and the explicit act, `releaseLabels` (`POST /api/v1/samples/:id/release-labels`, and the sample page's "Release labels for printing" button). A trapper's entry writes none: nothing in it says the bottle is unlabelled. The form's writes are inside `createTrapSample` and `updateTrapSample`'s own transactions, the old count read under their lock. Entry in Beeline alone is not a release, and the 16 settled samples entered before this change were not backfilled by the migration: staff release them one at a time once they confirm the bottles hold no labels (GitHub #407). Releasing a sample already released, and withdrawing one that is not, write nothing. A release is allowed in any season: in January and February last season is still active, and staff may release a sample ahead of 1 March, when it would otherwise stop printing. It is refused for one whose count still follows its iNaturalist observation (an observation and no label on paper): a settled season's count copied from iNaturalist does not print, and staff cannot correct that count either, so there is nothing for them to vouch for. The check and the write run under the promotion lock (`withPromotionLock`), because observation promotion could otherwise link an observation onto the sample between the two. `setSpecimenCount` takes the same lock for the same reason. **Lock order**, everywhere: the sample's turn in the queue (`onSample`), then the promotion lock, then the print runs' lock, because a promotion's county stamp takes the print runs' lock inside the promotion lock. The page offers the release on any sample with no standing release whose count is above the specimens already individuated, except where the count follows an observation; for an active season's sample it says its labels print anyway and the release keeps them printing after 1 March. A released sample is held to the 100 m coordinate limit like an active one, since it will print. **A released settled sample that follows its point is placed before it prints.** Where it has an observation or was entered in Beeline and no label is on paper, or staff set its point, its county, state and country follow its point (the view `sample_follows_point`, `schema/150`, which the stamp and `sample_awaiting_place` both read, so that no sample prints before the stamp has looked at one it would write), which the nightly's stamp writes; a label made before would carry what was typed, and a printed label is permanent. So `sample_awaiting_place` (`schema/150`) holds it out of `pending_print_sample` until the stamp has looked at it, at its present point, after the release: the stamp records that in `sample_place_stamped` (`schema/038`). The store cannot say it from the sample's county alone, because the county's name is the gazetteer's and is not in the store, and `sample_place_disagreement` leaves out points near a county's edge. A sample that does not follow its point (old records with neither an observation, an entry nor a staff point, and printed ones) needs no stamp and is pending at once. Any write that rewrites a released sample's country, state, county or point deletes its `sample_place_stamped` row in the same transaction (the trap form's save, the staff place correction and any edit of those fields, and a staff point that moves it or is taken away; a point set again to where it already is leaves the row), so a retyped county waits for the stamp as the nightly rewrites it. The sample page tells staff which it is waiting for, one sentence for its actual state: the nightly update where it has a point, coordinates where it has none, the next print run otherwise. If the nightly's areas step cannot run (no gazetteer, or one that predates areas), released samples wait for ever, so the Prepare page counts them (`ScopeCounts.awaiting_place`) and says they print once the nightly update has worked out their county and state. The answers of `setSpecimenCount` and `releaseLabels` carry `released` (this request wrote a release) and `awaiting_place`; a `pending` of 0 means the sample is not released, is waiting for the stamp, or is held back by a flag. Withdrawing is refused while the sample's labels are in a print run that has not printed (`labels_in_run`): cancel the run first, or let it print. Nothing before the refusal could tell the printer a run's samples had been withdrawn, and a run's labels are permanent once printed. The check and the write are under the print runs' lock. Minting never links an observation to a sample entered in Beeline or to one with a standing release (`sample_mint_free_link`, `schema/108`), which would make its number, count and place follow iNaturalist, and the count a promotion follows skips a sample with a standing release. On a collector's front page a released sample is asked about like an active one: its flags show, since a flag blocks labels its collector is waiting for.

**No label carries an elevation read at another point, or goes without one it should have** (beeline-trl9, Peter, 2026-11-21). When a sample's point moves, its elevation is left for `sample_elevation_stale` (`schema/170`) to flag and the nightly to read again, and every promotion (the nightly, a volunteer's "Check iNaturalist now", connecting a collector) empties the stale ones it finds, so a run prepared in between could print the old point's elevation (sample 797063 would have printed 478 m, a California point's, under Oregon coordinates) or, after a promotion, none. So `prepareRun` first lists the samples of its scope, new labels and reprints, that are in `sample_elevation_pending` (empty or stale, and not too vague to deserve an elevation) and passes them to `readElevations`. The app's version runs `deriveElevations` on only those samples, from the tiles in `data/dem`, on the promotion connection behind the promotion lock and not while the nightly or the weekly sweep runs, as the staff coordinates routes do (`deriveMovedPoint`). An app built without a promotion connection of its own reads nothing, so such samples are held: the read keeps a transaction open across tile reads, and on a connection other writers share, their writes would land inside it. This is done in its own step before the print-run lock is taken for the freeze, because it reads files and runs a transaction of its own, because the promotion lock is taken before the print-run lock elsewhere and so cannot be taken inside it, and so the print-run lock is not held across tile reads. The freeze then asks `sample_elevation_pending` again over the samples in the run, and holds out of the run every sample still in it, whatever the reason (no tile on disk, a void cell, an unreadable tile, the nightly running, a point or an elevation that changed meanwhile); a held sample stays pending for the next run. A sample stale only because its point is too vague for an elevation (`elevation_derivation_limit`; the nightly never reads it) is not held: it prints no elevation, and the run page does not call that label out of date for it. If every sample is held the run is refused (`awaiting_elevation`) rather than reported as nothing waiting; otherwise the run's page says how many were left out (`?held=` on the redirect), and the Print runs list says how many samples have no current elevation (`scopeCounts().stale_elevation`), the most a run can leave out. It is done in code, not in `pending_print_sample` as `sample_awaiting_place` is, because a view cannot read tiles and the list would count samples preparing a run would have fixed. Known cost: a point where the tile has a void cell (water) is read again on every Prepare and held for good, since the nightly leaves it empty too.

**A label is out of date in its own terms** (`printed_label_out_of_date`, `schema/155`, beeline-fq3j, beeline-5rqm). The run page lists the labels of a run that has not printed whose sample no longer has the values they were rendered from: locality, county, state, country, coordinates, elevation and dates, each compared with the column `printed_label` kept at freeze time, never with the label text. The method is the one field compared as a printed word: a label says `net`, `trap` or `nest` (`methodText`, `src/label-text.ts`: `nest` where the protocol contains "nest" in any case, otherwise the sample's kind), and the view compares `printed_label.method_text` with the same rule in SQL. So a save that changes a sample's kind or protocol lists its labels only when the word would change; renaming `aerial net` to `net` does not, and a nest sample made a trap sample still says `nest`. The rule is written twice, in `methodText` and in the view, and `test/label-out-of-date-method.test.ts` holds them equal over every kind and a range of protocols. Staff cannot change a method while the sample's labels are in a prepared run (`in_print_run`), so the view is the safety net for a change that arrives some other way, such as the nightly.

**Mailing addresses.** The run's page also offers a CSV of its collectors' mailing addresses, for a mail merge onto address labels (beeline-w8ab.3, `POST /print-runs/:id/addresses.csv`, `src/app/print-run-addresses.ts`). The addresses are fetched from Ideal Logic while the request is answered and are never stored, logged or cached; how the file is built, and what happens when Ideal Logic cannot answer, is in [Registrations, from Ideal Logic](ideal-logic.md#the-download-of-a-print-runs-addresses). The route is a POST because each download spends one of Ideal Logic's daily requests, and it refuses a canceled run, whose labels will never be mailed, both before it asks Ideal Logic and again after the answer arrives, since the wait can be long. It reads the collectors only after the answer, so the file reflects the store as it is then. Labels carry no person, so the file follows each sample's primary collector as it is now, notes where the collector line on the run's labels differs from what the sample would print today, and ends with a row counting any labels it could not place. A collector whose labels staff have said are kept in the lab (the "Labels" card on the person's page) gets a row saying so in place of an address, and is not looked up in Ideal Logic.
