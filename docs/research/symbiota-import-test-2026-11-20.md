# Symbiota DwC-A import against a live-managed collection: measured behaviour

Environment: Symbiota commit 4491b791c (copy; schema 3.0 plus patches 3.1 to 3.4), PHP 8.2.36 + Apache, MariaDB 10.11, one admin user.
Two live-managed collections: collid 1 (GUID source Symbiota-generated) and collid 2 (GUID source occurrenceID). All data invented.
Driven through the real pages with a logged-in session: specuploadmap.php (analyze, automap), specuploadprocessor.php (Start Upload, then the "Transfer Records" form),
importextended.php, collections/editor/occurrenceeditor.php (to create "entered in Symbiota" records and determinations), collections/download/downloadhandler.php (export),
and collections/admin/uploadhandler.php from the command line. SQL was used only to look at rows.
MEASURED = ran it and read the rows. READ = from source only. Line numbers are in the current checkout.
Scripts: h.py (harness), t.py, a*.py, b*.py, c*.py (one per question). Logs of every upload: logs/*.txt.

Short answers: see the report in the conversation; this file keeps the same tables.

All file names below are under classes/ unless stated. "SUB" = SpecUploadBase.php, "SUD" = SpecUploadDwca.php.

## How one import works (READ, then confirmed by every test)
1. SUD::uploadData (475-) loads core rows into the staging table uploadspectemp and identification rows into uploaddetermtemp.
2. SUB::cleanUpload (593-) matches staged rows to existing records. In a Live Data collection only catalog-number matching runs (612-625). The dbpk match at 595-599 is for Snapshot and Aggregate collections only.
3. SUB::transferOccurrences (955-): UPDATE every matched record with ALL columns that exist in both uploadspectemp and omoccurrences (976-989, `o.field = u.field`), then INSERT IGNORE the unmatched rows (1021). The only columns excluded are dbpk, observeruid, dateentered, initialtimestamp, occid, collid (getTransferFieldArr, 1159-1187).
4. SUB::transferIdentificationHistory (1385-1442) adds identification rows.

## Surprises and what did not run
1. Absent and blank core columns wipe the existing record. Any automated archive must carry every column that the portal's staff may have edited, or those edits are lost (B3).
2. The importer never clears the old current flag, so two current determinations is the normal result of A1 (A1, A2, A3b, A7).
3. The occurrence row is always overwritten from the core row, whatever the identification dates say, so an old archive restores an old name (A7).
4. Live collections never update by dbpk; the UUID core id is dropped on matched records, so only catalog number or other catalog numbers can match (B1).
5. Same name + same determiner + no date collapses to the first row; the unique key ignores the flag, so a flag-1 row can vanish (A6).
6. Associations cannot come in through the DwC-A importer; the separate Import extended data page does it, one relationship per run (C2).
7. eventDate ranges lose the end date unless sent as eventDate2 (C1).
8. Symbiota's own exporter writes comma-separated .tab extension files that disagree with its meta.xml (C2).
9. uploadhandler.php exits 0 on failure and its switches are not part of the profile (C4).
10. A spreadsheet upload rewrites the current determination in place (extra under A).
Not run or not done: MySQL (only MariaDB 10.11 was used); the Laravel api/ endpoints; images; taxonomic thesaurus (taxa table empty, so tidInterpreted was not exercised); non-admin roles; the real Ecdysis versions of PHP, MySQL or Symbiota. Schema install quirks: two benign errors in patches 3.1 and 3.2 (ALTER on tables that do not exist in the 3.0 baseline); web pages show harmless "ob_flush" notices. Nothing blocked the work.
Cleanup: containers symtest-db, symtest-web, symtest-files, volume symtest-dbdata, network symtest_default and image symtest-web removed. Left on the machine (shared, pulled for this run): images mariadb:10.11, nginx:alpine, php:8.2-apache.

## D3 New records only
MEASURED. There is no setting that adds only new records. With "match on catalog number" ticked, a file holding only new catalog numbers changes nothing else: a hash over all existing rows and all existing determinations was identical before and after (19 records), and only the new records (and their determinations) appeared. With the match box UNticked, a file row whose catalog number already exists is not matched; it is inserted as a second record with the same catalog number (the page warns "Records matching on catalog number that will be appended ... duplicate catalog numbers"), the existing record stays untouched, and its determinations gain a second current row. Why: SUB 612-625 (matching only when ticked), SUB 1022 (insert of unmatched rows), SUB 1421.. staged rows only (setDeterminations is limited to the staged rows).

## D4 occurrenceID in a CSV (both GUID settings)
MEASURED. Same as the archive path (SpecUpload.php 316-324, SUB 626-632). Collection with Symbiota-generated GUIDs: the occurrenceID column is ignored on new records (occurrenceID NULL, recordID generated) and on matched records the existing occurrenceID is kept whether the file's differs, is blank or the column is absent. Collection with occurrenceID as GUID source: stored on a new record; a different incoming value REPLACES the existing one; blank or absent keeps the existing one.

## D5 Matching and duplicates
MEASURED. (i) Catalog number twice in the file and not in the collection: two new records with the same catalog number are created. (ii) Twice in the file and once in the collection: only the first file row is applied; the second is ignored (the report still counts it as matched). (iii) Twice in the collection and once in the file: only the record with the lowest occid was updated, the other copy was left alone, and no warning was shown. (MySQL does not define which joined row an UPDATE uses, so treat (ii) and (iii) as observed, not guaranteed.) Matching on otherCatalogNumbers is exact text equality and overwrote the catalogNumber (archive-path result, SUB 2477-2505).

## D7 Import extended data (associations)
MEASURED unless marked.
- Page fields: file, import type (1 = associations), association type (resource, internalOccurrence, externalOccurrence, observational), then a mapping page. The relationship is chosen ONCE per file on the mapping page (not a column), and association type and relationship are both required; if either is missing nothing is loaded and no error is shown (OccurrenceImport.php 201-210). A "replace matching" box updates existing rows (see C2).
- Column headers that auto-map (matched on the lower-cased header, getTranslation in UtilitiesFileImport.php; headers with spaces such as "catalog number" were also recognised): subject: catalogNumber, otherCatalogNumbers, occurrenceID, occid. Association columns for all types: relationshipID, objectID, basisOfRecord, establishedDate, notes, accordingTo; resourceUrl for resource and externalOccurrence; verbatimSciname for externalOccurrence and observational; object-catalogNumber, object-occurrenceID and occid-style object columns for internalOccurrence (OccurrenceImport.php 471-485). A header that is not a target name (for example "plant") is left unmapped and silently ignored; my file with such a plant column loaded nothing.
- External URL to an iNaturalist observation: headers catalogNumber (or occurrenceID), resourceUrl, optionally objectID, relationshipID, notes; association type externalOccurrence. Observational association to a plant: catalogNumber, verbatimSciname; association type observational.
- Relationship list shown on the page, from the table ctcontrolvocabterm (cvID rows for omoccurassociations.relationship, seeded in config/schema/3.0/db_schema-3.0.sql 3847; the page reads them in OccurrenceImport::getControlledVocabulary 570-591): analyticalStandardOf, derivedFromSameIndividual, ecologicallyOccursWith, hasAnalyticalStandard, hasHost, hostOf, originatingSampleOf, partOf, sharesOriginatingSample, siblingOf, subsampleOf (plus fieldNotes and genericResource defined for the "resource" type). "visitsFlowersOf" and "visits flowers of" are not on the list, so a person cannot pick them on the page. The server does not check the value, though: when I posted the form with those strings by hand they were stored as given (and exported). So the controlled list is enforced only by the page's drop-down. A portal manager can add terms to ctcontrolvocabterm (a table edit, not tested).
- Subject by occurrenceID: yes; a row with occurrenceID matched (also matches recordID). It matches on occid, occurrenceID or recordID, catalogNumber, or otherCatalogNumbers (OccurrenceImport.php 364-400). A catalog number that exists twice gets the association on BOTH records (OccurrenceImport.php 201, loop over every matched occid). A row with no match is skipped with "SKIPPED: Unable to find record matching any provided identifier(s)".
