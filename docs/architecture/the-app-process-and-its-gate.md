# The app process, and its gate

Part of Beeline's architecture notes; the index is [README.md](README.md).

The web app (`src/app/`) is the process that owns the database — [ADR 0005](../adr/0005-app-process-owns-the-store.md): Hono with `hono/jsx` SSR views, Lit light-DOM islands built by Vite, MD3 color tokens generated from a seed (`src/app/theme/tokens.ts`), every route session-gated by construction — and the gate remembers the URL it refused, so signing in lands you on the page you asked for rather than home (same-site GET paths only, carried in a short-lived cookie beside the OAuth state, beeline-2c3.31); `/design` is the design system (component library in `src/app/views/components/`, among them the one combobox every field offering known values uses — `Combobox` for a server-drawn field, the `beeline-combobox` island behind it with its rules in `src/app/islands/combobox-model.ts`, and the taxon picker on Identify specimens built on it with the taxonomy as its search (beeline-wn2) — stylesheets split `elements`/`layout`/`components` under `src/app/static/`, every section rendering live from the real tokens), offered only to admins but not gated — it reads no records, so walling a curious volunteer out of it protects nothing; the reason it is not offered to them is that it is not their tool — and `/glossary` is its volunteer-facing counterpart. The header nav carries only the records people work through, `/samples` and `/specimens`; everything else a person can open — the glossary, the taxonomy, the staff tools — lives in the menu left of the brand, grouped by what it is for rather than by who may use it, and each item is shown only to whoever may open it (beeline-45v.5); on a phone the records collapse into it too. Beside it, in the header itself and never in a menu, is "Send feedback": a mailto to `BEELINE_FEEDBACK_EMAIL` (no address, no link) pre-filled with the page, the time, the browser and the session — the session as the first 12 hex digits of its id's SHA-256, since the id is the bearer credential and an email carrying it would let whoever read it sign in; the session table keeps only that SHA-256, so those digits are the start of the row's key. The account menu is for the person signed in and their own things — signing out, acting for someone, and later their mailing address — and never a place to find pages. Every response carries a Content-Security-Policy and its companion headers from one middleware registered first (`src/app/security-headers.ts`, beeline-m9o): same-origin scripts, styles, fetches and forms, iNaturalist's static host for the avatar, no framing, and inline `style=` attributes allowed while inline `<style>` and script are not; the Referrer-Policy keeps a same-origin referrer because the error page's way back reads it. Right after that middleware, a request whose Host is the www form of the origin's host (`www.melittologist.org`) is answered with a 301 to the same path and query on the origin, because the CSRF check and the OAuth redirect both name that one origin, so a form submitted from www would be refused; the app's `.fly.dev` name is not redirected, since it is how a deploy is tried before DNS points at it (beeline-83b8.14). Auth is iNat OAuth; sessions, sign-in records (`inat_sign_in`, which held volunteers' OAuth tokens until those were dropped and is kept with no purge, beeline-cj6/zg4), last visits and the impersonation log are ordinary tables in the store (`schema/012`). They lived in a separate, encrypted private store until 2026-11-05 ([ADR 0003](../adr/0003-private-data-store.md), retired by beeline-4tdh): once a session is kept as the SHA-256 of its cookie and never the cookie (beeline-5l84), a copy of those tables signs nobody in, and nothing else in them is worth a second file and a key that has to survive off the server. `absorbPrivateStore` (`src/app/db.ts`) carries a deployed private store's rows across at the first boot that finds one, all but its sessions, which no browser could use again once the cookie was renamed, and renames the file to `private.duckdb.retired`; it goes, with `BEELINE_PRIVATE_DB_KEY`, once production has done that. A session ends 30 days after its last request and 90 after it began however often it is used (beeline-jpau), so a stolen cookie does not work forever. Every cookie the app sets goes through `cookieJar` (`src/app/cookies.ts`, beeline-73c9): the whole site's path, HttpOnly, SameSite=Lax, Secure on an https origin, and then named with the `__Host-` prefix, which a browser lets no other host set. That matters here because the domain's subdomains reach servers Beeline does not run (old Beeline's on `old.` and the wildcard, a separate host on `member.`), and any of them could otherwise plant a session or an OAuth state cookie for the whole domain. The session cookie's name from before the prefix is not read at all, not even for a transition, since any subdomain can set it: everyone signed in once more after the rename.

Until the old Beeline closes, after February, the paths of its interface (`/volunteerLogin`, `/dashboard`, `/admin` and the rest, and `/api/`) are answered ahead of the gate with a redirect to the same path on old.melittologist.org, where it runs from cutover, and the sign-in page says it moved there; `/determinations` is this app's own page and is not redirected (`src/app/old-beeline.ts`, beeline-83b8.12). All of it is temporary and goes with the old Beeline.
