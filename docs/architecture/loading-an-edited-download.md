# Loading an edited download

Part of Beeline's architecture notes; the index is [README.md](README.md).

People download the specimens listing as an Excel file from `/specimens`, edit cells in a spreadsheet, and will upload the edited copy (beeline-kgyd, Peter, 2026-11-16). **There are two uploads, by what a row is** (Peter, 2026-11-17): specimens, and later samples. The **specimens file**, built here, is for whatever is edited on a specimen: mostly determinations, and a disposition with its remarks (what became of the pin). It carries a few of the specimen columns, not all 46 ("why is identifiedByID useful? A number of these columns seem arguably extraneous"). A sample's dates, method, locality and coordinates are not edited from it. They are edited in the **samples file** (beeline-kgyd.4.9, below), which has one row for each sample and a tab named `samples`, and is meant to become the main way trap samples are created and updated. Its download, its preview and applying its new rows as trap samples (beeline-kgyd.4.10) are built; applying a change to an existing sample is not. The comparison's rules for those groups of cells (`UNIT_RULES` in `src/app/upload-plan.ts`) are shared with it. Beeline shows every difference and, in a later slice, records the changes.

**Three slices exist.** Staff upload a file at `/uploads` (`src/app/views/uploads.tsx`, the routes in `src/app/server.tsx`) and read at `/uploads/:id` how many rows differ from what Beeline says now and how many it cannot use, with **the file handed back with a note on each row** (below), under a line saying that **Beeline doesn't change any record from a staff upload of the specimens file yet**. (The samples file's new rows can be applied, below; its differences on existing samples are shown only.) **Anyone else uploads their own identifications and saves them** to Identify specimens (beeline-kgyd.7, below). The routes are open to anyone signed in and refused while impersonating, as the other writes are. The link is on `/specimens` beside the download, for everyone, and on `/exports` for staff. **Staff may also upload the samples file** (below), which this page tells from the specimens file by its headings, and the staff member who uploaded it can apply its new rows.

## Why an Excel file with text cells, and not the CSV

The first design uploaded the CSV. Four rounds of review kept finding the same thing: a spreadsheet rewrites CSV cells that nobody edited, and each rule added to forgive one rewrite hid a real edit somewhere else.

- A longitude of `-123.45678901234567` comes back from a spreadsheet as `-123.4567890123`, cut to ten digits. The comparison first tolerated differences of 1e-9 so that rewrites would pass, and so offered a longitude that nobody had touched as a change, and at the same time could not tell it from a person correcting the sixth digit.
- A corrected collecting date typed as `3/4/2025` (3 April) was read both month first and day first and counted as unchanged if either reading was what Beeline said. A person who meant 3 April and a spreadsheet that made it 4 March gave the same file, and the correction was hidden.
- Leading zeros of a field number, a month such as `2025-07` read as `Jul-25`, an upper-case `TRUE`, composed and decomposed accents and non-breaking spaces were each tolerated in turn.

The owner's decision (Peter, 2026-11-16): the file people edit is an Excel file in which **every cell is stored as text, with the Text number format** (`@`, built-in format 49). A spreadsheet does not reformat a text cell, and does not convert what a person types into a cell formatted as text, so the comparison can be exact and every tolerance rule goes. `GET /specimens.xlsx` takes the listing's query and shares its reader, paging and host-name handling (`specimenDownload` in `src/app/server.tsx`); it writes the columns of the specimens layout (below) with the values `specimenCsvRow` gives for those headings (then `textCell` in `src/app/listings.ts`, the row's cell text without a CSV's formula guard), a main sheet named `specimens`, the header in row 1, and Beeline's own tabs after it. A null is an empty cell that carries the Text style of its own, and the Text format is also the default style of every column, so a program that ignores the column's style still has what somebody types there as text. A cell over 32,767 characters or a sheet past 1,048,576 rows, Excel's own limits, is not written: the writer throws, and since the download is already streaming by then the download stops with an error and the failure is reported, which is the honest result rather than a file Excel cannot open. The specimens listing has no CSV any more (beeline-kgyd.5, Peter, 2026-11-17: "let's drop the CSV download option"): a program reads the same columns, with the four extra ones, from the API's specimen rows, and the exports page has the files. A CSV upload is refused with words telling the person to download the Excel file and edit that.

**A leading `=` needs no guard in an Excel text cell.** The CSV guard (a quote before `=`, `+`, `-`, `@`) exists because a spreadsheet opening a CSV decides for itself what a cell is. In an `.xlsx`, a string cell is a string: only a cell with an `<f>` element is a formula, and the writer never writes one. The guard would also change what the person sees and what the upload compares, so the Excel file has none and the reader un-guards nothing. A test asserts the writer's output has no `<f>` element, and openpyxl, a second program, reads a cell beginning `=` from the writer's file as a string and keeps it one when it saves the file again. Excel itself, LibreOffice Calc and Google Sheets have not been tried: that they treat a string cell as a string is what the file format defines, not something checked here.

## The writer is ours, the reader is SheetJS

**The writer is hand-written and small.** `src/app/xlsx.ts` writes the workbook the download is, and knows nothing of Beeline. An `.xlsx` is a zip of a few XML parts, and the repository already has `fflate`, which `src/app/dwc-archive.ts` uses to stream a zip, so the writer needed no dependency. It streams the sheet a page of rows at a time as the CSV download does, escaping XML properly: characters that XML 1.0 cannot carry, and lone surrogates, are written as the spreadsheet escape `_xHHHH_` and a literal `_x0041_` as `_x005F_x0041_`, so any string survives. The same module holds the types of what the reader returns.

**The reader is [SheetJS](https://sheetjs.com) 0.20.3, in `src/app/xlsx-reader.ts`.** A hand-written zip and XML reader was written first and then thrown away (Peter, 2026-11-17). Three rounds of review kept finding ways for a crafted file to stall it (a zip that unpacks to far more than its size, entries that share one payload, XML that never closes), each fixed by more code to be reviewed in its turn, and it had never met a file that Excel or Google Sheets had saved. SheetJS has been read against Excel's and Sheets' own files for years. What Beeline keeps is a thin adapter that says of each cell its text and its kind, and what stands in front of the library:

- **The adapter** (`readXlsxHere`). A cell with a formula is `formula` whatever its cached value, and so is every other cell inside the range an array formula covers (the library gives the formula and the range, `F`, to the first cell only, and the rest would read as numbers somebody typed; a shared formula gives each cell its own `f`); a string is `text`; `t: "b"` is `boolean`; `t: "e"` is `error` (its words come from Excel's fixed error codes, since asking the library for text costs a format for every cell); a number is `date` when its number format is one by the library's own test (`SSF.is_date`) and `number` otherwise. A number's text is `String(v)`: the number it is, not the digits the file stores it in. A date's text is the ISO day from the library's `SSF.parse_date_code`, given the workbook's `date1904` flag: SheetJS leaves a 1904 workbook's serials as they are and reports the flag, and the library does the arithmetic, which a test checks for both systems. Beeline decides nothing about which number formats are dates: `0*m`, for instance, is a date to the library. The sheet rule is the one below: the tab named `specimens`, else the only tab, else a refusal naming the tabs, and the other tabs are listed as not read. The library is asked for the sheet names first (`bookSheets`), then for that sheet alone, with `sheetRows` just above the row limit, no styles, no macros, no formatted text, dense cells, `cellNF` and `cellFormula` on and `cellDates` off.
- **The cheap refusals come first, before the library sees a byte.** A file over 20 MB (`too_large`); a file that is not a zip (`not_a_zip`), which matters because SheetJS reads a CSV as a one-sheet workbook and would accept what the upload exists to refuse, and the page tells the person to download the Excel file from Specimens and edit that; an OLE file (`protected_file`: an older `.xls`, and also what Excel makes of a workbook that is encrypted or carries a sensitivity label). After the library: no sheets (`not_a_workbook`), more than 20,000 data rows (`too_many_rows`), a row of more than 500 cells (`too_wide`; the download has under 60 columns), a workbook with several tabs and none named `specimens` (`no_such_sheet`). Anything the library throws is `unreadable`; nothing escapes the route as an exception.
- **A worker thread, with a time limit and a memory limit.** Parsing happens off the request thread (the way `src/label-pdf-worker.ts` runs, one file with the spawner and the worker body, started from its own module URL with the loader the app already runs under), because older SheetJS versions had a regex denial of service and a prototype pollution bug, and because a zip can unpack to far more than its size, and none of that should be able to stall the server or reach its objects. The worker gets the bytes and returns plain data (rows of text and kind, the sheet names) or a named refusal. It has 30 seconds (`took_too_long`, from a timer that terminates the worker) and a 768 MB heap (`resourceLimits`; running out is `too_large_unpacked`); both are parameters, which the tests set tiny. **The memory limit is the heap's only.** A zip unpacks into buffers outside the heap, which `resourceLimits` does not count: a probe unpacked a 200 MB sheet in a worker limited to 48 MB in four seconds. So what bounds a decompression bomb is the 20 MB file limit and the time limit, not the memory limit, and the worker keeps a bomb off the request thread rather than keeping it small. Every preview re-reads the kept file, so each view starts a worker; two at once work, and a test shows it.
- **Installing it.** SheetJS is not published to npm past 0.18.5, which has known vulnerabilities, and the `xlsx` package there is that old one. Fixed versions are tarballs on the vendor's CDN, so `package.json` names the tarball by URL (`https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`) and `pnpm-lock.yaml` records the tarball's integrity hash, which every install verifies: the build fetches from `cdn.sheetjs.com` and fails if what arrives is not what was locked. Never add the npm package. 0.20.3 was the newest version on https://cdn.sheetjs.com and the vendor's tags (https://git.sheetjs.com/sheetjs/sheetjs/tags) on 2026-11-17. To upgrade, find the newest version there, run `pnpm add https://cdn.sheetjs.com/xlsx-<v>/xlsx-<v>.tgz`, read the changelog for the options this file uses (`cellNF`, `cellFormula`, `dense`, `sheetRows`, `sheets`, `bookSheets`, `SSF`), and run the reader tests. The licence is Apache-2.0.
- **What was set aside.** ExcelJS reports types well but has had no release since October 2023. hucre has no dependencies and documented limits, but it is eight months old and has one author. DuckDB's Excel extension infers a type for each column and does not report a cell's stored type, which is the thing this needs. read-excel-file returns values, not cell types.

**Which sheet is read.** The sheet named `specimens`, the name the writer gives it, or `samples` for the samples file. If there is no such sheet and the workbook has exactly one, that one; if it has several and none is named either, the file is refused (`no_such_sheet`) and the page names the tabs and says to keep the edited rows on a tab named `specimens` (or `samples`). When it read one sheet of several, the plan lists the names of the others and the page says they were not read, since a person who duplicates the tab and edits the copy would otherwise be told nothing differs. The tabs Beeline puts in the download itself (`names`, `identifiers`, `collectors`, `about`: `REFERENCE_TABS` in `upload-plan.ts`) are not listed, and a change to one changes nothing, since none is read.

## What the spreadsheet itself offers

The Excel download does more than hold the rows (beeline-kgyd.2, Peter, 2026-11-17: checks embedded in the spreadsheet wherever a vocabulary is constrained, which "needn't prevent edits", and tabs to look values up in, "just for lookup/autocomplete; we'll see if that's enough to avoid typos"). It is all built when the file is asked for, from the store, by `src/app/specimen-workbook.ts`, and none of it is in the API's rows. **Nothing in the spreadsheet is relied on**: a person can paste over a validation, a program may ignore one, and the upload checks every cell again by the rules below.

- **Which columns, and in what order** (`SPECIMENS_LAYOUT` in `src/app/upload-plan.ts`, beside the comparison's rules, and the one place that says; a volunteer's file is `VOLUNTEER_LAYOUT`, below). To recognise the bee, grey and not read: `fieldNumber`, `sampleNumber`, `specimenNumber`, `recordedBy`, `eventDate`, `locality`, `county`, `stateProvince`, `associatedTaxa`. The determination, white and read: `scientificName`, `identificationQualifier`, `sex`, `caste`, `identifiedBy`, `dateIdentified`. Then white and read: `disposition`, `occurrenceRemarks`. Last, grey and not to be edited: `specimenId`, `specimenVersion`. The full columns' `sampleVersion` is not in the file: it says what a sample's cells were when the file was written, only a sample's groups of cells use it, and the specimens file reads none of those (the samples file carries its own `sampleVersion`, below). A file that still has other columns under their headings (an older download with all 46, or the CSV's columns pasted in) loads: the comparison finds columns by heading, and what differs in any column the file does not read is listed under "Differences in columns Beeline does not read from this file", so a person who edited a grey cell is told it was ignored. The column lists exist at load as a check: a column the layout reads must be one the comparison has a rule for.
- **Warnings, not refusals.** `disposition`, `identificationQualifier`, `sex` and `caste` take one of a few words, the lists the comparison holds a cell to (`SPECIMEN_CHOICES`). The words are on a tab, `words`, a column for each, and each column of the main sheet takes its list from its column there, from the first word to the last and no further. A word that is not on the list brings a warning (`errorStyle="warning"`), which the person may dismiss and keep. Its title and message come from the message catalogue (`workbook.warning`) and name the column; the writer limits them to Excel's 32 and 255 characters. **The words are on a tab because a list written into the check itself is not read the same way everywhere.** That form is one quoted string, `"gyne,worker,drone"`, which Excel and Google Sheets split at the commas and Gnumeric offers whole, as a single choice (Peter, 2026-11-17, in Gnumeric; confirmed by having Gnumeric read the file with `ssconvert` and looking at the check it kept). A list that points at cells is read as those cells by all of them.
- **Suggestions, for `scientificName` only.** It takes its list from the `names` tab: a list that points at that tab's first column, with `showErrorMessage="0"`, which in Excel offers the words and refuses and warns of nothing. A tab with no rows gives no list. **No spreadsheet format has a list that only suggests, so what a person sees depends on the program** (found 2026-11-17): Google Sheets has two kinds of list, one that refuses and one that marks the cell, and reads this one as the second, so a name not on the tab is marked "Invalid: input must fall within specified range" and kept; Gnumeric drops a list that shows no message, so it offers nothing. For a scientific name that mark is fair: a name the tree lacks is one Beeline will ask about. **`identifiedBy` has no list for that reason.** It had one, from the `identifiers` tab, and Peter typing his own name into Google Sheets got the "Invalid" mark; an identifier Beeline has not met is ordinary, since staff paste in what experts send, so the tab is for checking a spelling and nothing is tied to it. A name that is not offered is simply typed, and nothing in the comparison treats an unknown identifier as a fault.
- **Two tabs to look names up in, after `specimens`.** *names*: every name in Beeline's tree that the Identify specimens picker offers (`entryTaxa`, `src/app/determine.ts`: every node but kingdom, phylum and class), with its rank and family, sorted by name. The tree has no retired names, so none is left out, and a synonym the program keeps is in it, as it is in the picker; what Ecdysis holds and the tree does not is not ("names in our tree, not everything in Ecdysis"). The picker also carries how often a name is used and whether it takes castes, which the tab does not need. *identifiers*: people who identified a specimen in the last five years, written as the `identifiedBy` column writes one (the person's display name, else the name text of the determination), once each, sorted. A determination counts if it is dated (`determined_on`) in the window, or has no date and was recorded in the window by any channel but the old system's import, or is of a specimen collected in the window (the sample's last day of collecting). The last clause and the exception are there because the old Beeline kept no determination dates, so every determination of its own was recorded on the day it was imported, and that day says nothing about when the person identified anything; counting it would put every old identifier on the list. This differs from the owner's wording, which counted a recorded day for every channel. Five years because an identifier stays in the program's work for years and the list of everyone who ever did is the list the owner wants to avoid. The window is counted back from today in Oregon (`src/oregon-today.ts`, the one definition of that day). **There is no collectors tab**: the owner first asked for one (people who collected in the last 24 months), but `recordedBy` is read by nothing, so no column could take suggestions from it, and the file is for editing specimens; the query went with it. **Cost,** measured on 2026-11-17 on a copy of production's store from that night's backup (398,612 specimens, 334,970 determinations, 3,652 names), on the workstation while it was busy (load 28), median of seven runs: the names tab's rows take 12 milliseconds and come to 3,649 rows and about 135 KB of text; the identifiers tab's rows take 30 milliseconds and come to 147 names. Both are read once for each download, before its first row is written. Production's machine is smaller and nothing here was measured on it.
- **Who may see these names.** Whoever may download the specimens listing, which is everyone signed in (the session gate covers every route). Every signed-in person can already list every specimen's determiner at scope `all`, since only locations are withheld from a listing (`withheld`), and the record page of any specimen shows every determination in its history with the determiner's name (`determinationHistory`, `src/app/record.ts`). The tab shows those same display names and name texts and nothing more: no email, login or ORCID iD.
- **Shading, not locking** (Peter, 2026-11-17: "make clear which columns we will ingest and which we won't, perhaps by locking ones we won't"). Every cell of a grey column is filled light grey, `FFD9D9D9`, a plain RGB colour that shows the same in Excel and Google Sheets and is legible with black text, and the heading of each column Beeline reads that a person may edit is bold. The grey and bold sets are the layout's own lists, so the file cannot say a column is read that the comparison ignores. Sheet protection was not used: Excel refuses to sort a range that holds a locked cell, and sorting and filtering are how staff will work in these files; Google Sheets and Numbers each treat an imported protection differently, and none of it would hold against a person who wanted to edit anyway, since the upload checks again. Locking could be added on top, but a person who sorts by name would then be refused in every sheet that has a locked cell in the range.
- **The `about` tab**, last: what the file is for, what happens when it is uploaded, what white and grey mean, the two columns to leave alone, a row for each of the eight columns Beeline reads with what it takes (the vocabularies from `SPECIMEN_CHOICES`, and the upload page's own words for dates), and what the other tabs are. All words are in `workbook.about` in `src/app/messages/en.ts`. The line for `identifiedBy` says a name not on the identifiers tab is fine.
- **Wrapped columns and widths** (beeline-kgyd.11, Karla Salp, 2026-11-18). A spreadsheet draws an unwrapped text cell's overflow across the empty cell beside it, and an empty cell does not stop it. On a row with no determination the grey `associatedTaxa` text (`"visits flowers of":"Astereae"`) ran across the empty `scientificName` and read as the bee's name; `identifiedBy` ran over an empty `dateIdentified`, and a name with a subgenus over an empty `identificationQualifier`. A width cannot stop it, since a host is free text of any length. So the writer wraps the columns whose text can be long (`wrappedColumns`, listed in `WRAPPED_COLUMNS` in `src/app/specimen-workbook.ts`: `recordedBy`, `locality`, `county`, `associatedTaxa`, `scientificName`, `identifiedBy`, `occurrenceRemarks`), as two more cell styles (the Text format wrapped, and on grey wrapped). A wrapped cell never overflows. The rows carry no height of their own, so a long value makes its row taller in Excel and Google Sheets, and Gnumeric keeps the wrapping (checked with `ssconvert` on 2026-11-18: its output has the wrapped styles and sets no row height). Widths (`widths`, default 16, `COLUMN_WIDTHS` beside the list) are set so that most rows stay one line; a non-positive width is refused. The rows are streamed, so the writer cannot measure them and the caller says what fits. A clearer `associatedTaxa` heading is a separate question: the upload recognises columns by heading.
- **Who is on the link.** `/specimens` offers one download, a button "Download the Excel file for editing specimens" with its short note beside it, for everyone, and beside it the link to the upload page. Its note says the file holds what the page's filters select, so people filter first (beeline-kgyd.9); a volunteer's note says the file holds their own identifications and that an upload saves them as drafts when they choose.

**What has been tried in a real spreadsheet program, and what has not** (2026-11-17). Peter opened the file in Google Sheets and in Gnumeric: the dropdowns of the four vocabularies work in Google Sheets, and in Gnumeric after the lists moved to the `words` tab (checked by `ssconvert`, and then by Peter by eye: "gnumeric looks good"). The suggestion list on `scientificName` marks an unlisted name in Google Sheets and is absent in Gnumeric, as above. The plain text cells came back unchanged from Google Sheets and Numbers (see the tests paragraph below). **Gnumeric is also the one real spreadsheet program the tests run**, where it is installed (it is on Hostess; it is not in CI, where the test is skipped): `test/upload-plan.test.ts` has its converter, `ssconvert`, open the file Beeline wrote and save it again as an Excel file, and the copy, which is Gnumeric's own file and not Beeline's bytes, compares as no difference with no stray tab. Not tried: Excel itself, LibreOffice Calc, how the grey columns and bold headings look anywhere but Google Sheets and Gnumeric, and a date pasted from another sheet. What the tests check of the rest is the file: SheetJS reads every sheet, openpyxl reads each validation and fill back as written, and every cell is text in the Text format. That Excel offers a list drawn from another sheet from a validation written in this form, that a warning dismisses as intended, and that Google Sheets does the same on import, is what the format says and is not checked here.

**For the slice that applies determinations:** the preview should list each distinct `identifiedBy` Beeline does not know and offer to add them as new people who are experts (Peter, 2026-11-16). Nothing creates a person before that.

## The comparison

`src/app/upload-plan.ts` is a function of the store and the file's bytes that returns a plan (`planUpload`, or `parseUpload` then `comparePlan`). A row is found by `specimenId`, never by field number, which is not unique and may be absent; the field number column is still read, as a check on the row's identity, and **it is exact text**: a cell that is not the specimen's number holds the row (`number_disagrees`), and `12345` for `00012345` is a disagreement now, since the file no longer loses leading zeros. What "now" is comes from the download itself, `listSpecimens` through `specimenCsvRow` and `textCell`, so the two are written by the same code. **The comparison reads as the uploader's own download did** (`Viewpoint`): staff's file as staff, with every location shown and the identification of record; a volunteer's file with their reader, so the locations withheld from them are blank on both sides, and with their own identification in place of the record's. Columns are found by name in any order. A column the file lacks is never a difference. In an `.xlsx` an absent cell and an empty cell are the same thing: blank.

For each compared column, in this order:

1. If the file's cell text equals Beeline's text for that cell, it is unchanged, whatever type the cell is. Both are trimmed, and a line break inside a cell is compared as a line feed on both sides, since a spreadsheet may save one as CRLF or as a lone CR. Trimming means an edit that only adds or removes spaces at the start or end of a cell is not seen anywhere; that is deliberate, and not a thing the page says.
2. Otherwise the cell is read by the column's kind, strictly. A number column (latitude, longitude, uncertainty) takes a `text` or `number` cell that is a plain decimal number and is equal if numerically equal to Beeline's (an exponent is accepted only in a number cell, where the spreadsheet wrote it). Excel keeps a number to 15 significant digits, so converting `-123.27891540527344` to a number, or pasting it, stores `-123.278915405273`: a cell of type `number`, and only one, is unchanged when it equals Beeline's number rounded to 15 significant digits. A text cell is exact. A number cell's text is the number it is (`String(Number(v))`), not the digits the file stores it in. `eventDate` takes `YYYY-MM-DD` or `YYYY-MM-DD/YYYY-MM-DD`, real calendar days with the end not before the start, and a single day equals the same day written as a range. `dateIdentified` takes `YYYY-MM-DD`, `YYYY-MM` or `YYYY`. Sex, caste, the qualifier and `identifiedByExpert` are compared ignoring case. Anything else is text, and a different text is a difference.
3. Otherwise a cell that differs and is a `boolean`, `formula` or `error` cell, a `date` cell in a column that is not a date column, or a date column's cell not in the forms above, is held with a reason that says what to do: the spreadsheet turned the cell into a date (`converted_to_date`), it holds a formula (`holds_formula`), it is something else that is not text (`converted_other`), or it is not a date Beeline reads (`date_unreadable`, `number_unreadable`). The words tell the person to format the cell as text and type the value as `YYYY-MM-DD`.

   **A real date cell in `dateIdentified` or `eventDate` (a column of the samples file) is read as that day** (Peter, 2026-11-17), compared and checked as typed `YYYY-MM-DD` is, with day precision. The first version held every such cell as `converted_to_date`, which was written before anyone said that staff would fill the file by pasting rows from other experts' sheets, and a paste brings the other sheet's cell types with it: every pasted date would have been held. A date cell is not ambiguous the way typed text is, because the file stores a serial number and the workbook's own date system, and the reader turns those into the day (both systems are tested). A date cell that also holds a time of day other than midnight is not a day and is held (`holds_time`, with words saying the cell holds a time as well as a date). A date cell in any other column, and a formula in any column, is held as before.

   **A name Beeline has never seen is not a fault.** Nothing here checks `identifiedBy` against the people Beeline knows: a determiner it does not know is listed as a difference like any other, and no hold reason fires for it (a test says so).

Dates are worked out from the serial by the library, with the workbook's own date system, so a serial in the 1904 system is the day it is.

Beeline's own side is read from its own numbers and not by reading its text the way a person's text is read: the download writes a latitude of 0.0000001 as `1e-7`, which is that number and not text, so a coordinates difference carries numbers where numbers belong. The strict reading stays for the file's text cells.

Each cell of a plan carries the value as read beside its text (`CellValue`: the number, the day or range of days, the date with its precision, the lower-cased word), and a specimen's difference carries its sample's id and the id of the determination of record, so that a later step applies what was read and re-derives nothing from the file.

## Units, and when one is complete

A fact is held or listed whole. The units are a specimen's identification (name, qualifier, sex, caste, determiner, date identified), a specimen's disposition and remarks, and for a sample its dates and method, its locality, and its coordinates (latitude, longitude, uncertainty). **Only the two specimen units are read from a file today** (the layout's `read` list). The sample's three units are read by the samples file's own comparison (`src/app/samples-upload-plan.ts`, below), which shares their rules; the specimens file reads none of them, and the specimen-grain comparison's tests of them give it a parsed upload whose layout names their columns as read. A sample's cells in an older download are listed as columns not read from this file. A unit that differs is listed as a difference only if it is complete; if it is not, every cell of it that differs is held, with the cell that makes it incomplete, and the page shows each with what Beeline says and what the file says, so a new name is seen held together with the date that was damaged. A sample's cells are repeated on every row of its specimens, so a sample's difference is one difference however many rows say it; if its rows do not say the same thing it is held (`rows_disagree`); and a cell that cannot be used on any row holds the unit for the whole sample.

**What complete means is `UNIT_RULES` in `upload-plan.ts` and nothing else decides it.** Where the schema has a CHECK, the rule is the CHECK, from the constants beside the model types (`DETERMINATION_SEXES`, `DETERMINATION_CASTES`, `DETERMINATION_QUALIFIERS` in `src/model.ts`; a test reads `schema/040` and fails if they drift; `DISPOSITIONS` in `src/load-dispositions.ts`):

- **Identification:** a name; a qualifier, sex and caste that are blank or in the vocabulary; a caste that fits the sex (a drone is male and a male is a drone, where both are said, as the CHECK has it); a date identified that is not after today (a year or month that has begun is not in the future).
- **Disposition:** a disposition that is blank or in the vocabulary, and a remark, because `specimen_disposition.remarks` is not null and not empty and the store could not take a row without one.
- **Dates and method:** a collecting date, readable and not after today.
- **Coordinates:** latitude and longitude both given, or all three cells blank (an uncertainty belongs to a point); latitude within -90 to 90 and longitude within -180 to 180; an uncertainty blank or a positive whole number no larger than 2,147,483,647 (the column is a 32-bit INTEGER, `schema/030`). A file that has only one of the two columns holds the unit (`column_missing`).
- **Locality:** any text, blank included. A blank locality means the sample follows iNaturalist's locality again (`setPlace` in `src/app/sample-corrections.ts`), and the page says so.

Today is read in Oregon, as everywhere else in the app.

**A file edited against something Beeline no longer says is held.** A specimen's units are held (`specimen_changed_since`) when the row's `specimenVersion` is not the specimen's now, and a sample's units (`sample_changed_since`) when its `sampleVersion` is not the sample's now. A file lacking the column cannot say what it was edited against, so its units are held as `column_missing`. The specimen's version is a hash of its changeable cells and not the determination's id, because an id does not change when a row is updated in place or a joined name is corrected. It also hashes the specimen's own id, and the sample's version the sample's id: without them every specimen with no determination and no disposition shared one version, and so did two samples that said the same things, so a file whose `specimenId` cells had been shifted (fill-drag increments them; one column sorted alone) and whose field numbers were blank would have listed a new name against the wrong specimen. **A file downloaded by someone who is not staff and uploaded by staff** carries the person's own identifications and a `specimenVersion` that starts with `o` where staff's starts with `s`, so every specimen unit in it is held as `specimen_changed_since`, and nothing in it is taken as the record. (Before beeline-kgyd.7, such a file had staff's columns with the locations withheld from its downloader blanked, and its sample units were held as `sample_changed_since`, whose words still say both possible causes.)

**`identifiedByExpert` is never read from a file.** The determination of record ranks expert determinations first (`schema/110`), so a flipped cell would outrank every other determination for good. It, the authorship, the rank and the host columns are listed apart, in a collapsed section, as differences Beeline does not take from a file.

**Columns it did not read are named on the page, in one line.** A heading that is not a column of the download is not read, and the page says so; one that matches a download column except for case or spaces is named as probably that column. A heading padded with spaces is that heading. A heading twice refuses the file (`repeated_column`), since which one is meant cannot be told.

**A row is held and the rest of the file goes on; a whole file is refused only when it cannot be read**, for the reasons above or for no `specimenId` column or no data rows. A held row contributes no differences. Counts are split by active and settled season with `settled_sample` ([CONTEXT.md](../../CONTEXT.md), Season); a row naming no specimen has no season and is counted apart.

## The page, and the file with notes

**The page is a few counts and two actions, never a list of rows** (Peter, 2026-11-18: "this page makes sense if they have like ten ids to input ... Karla has hundreds (at least) of 2025 bees, and this page will be huge. Errors should maybe just come back as a column on the file, in a download", and "nobody knows wtf held means"). For a volunteer: how many rows, how many identifications are ready to save, how many can't be saved, how many are the same as Beeline has, and how many have changes in grey columns, each line only when its count is not zero; then "Save N identifications" and "Download your file with notes", each only when it would do something. For staff: how many rows differ, how many have something Beeline can't use, how many are the same, and how many changed only columns not read from this file, under the line that nothing is changed yet, and the download. Columns and tabs that were not read get a line each, only when there are any. Nothing on the page explains how the comparison works.

**The file with notes** (`GET /uploads/:id/notes`, `src/app/upload-notes.ts`) is **the person's exact file with one column added** (Peter, 2026-11-18): their own tabs, cells past the last heading, formulas, dates, formatting and checks all come back as they uploaded them. It is not rewritten with a library, which would drop the formatting and the checks; `src/app/xlsx-annotate.ts` patches the original instead. Only the XML of the sheet that was read changes: a cell on each row in a new column after the last column the sheet uses, headed `Beeline's note` (`NOTE_COLUMN`), as an inline string (text written in the cell itself, which needs no change to the workbook's shared table of strings); the sheet's stated extent; a column width where no column definition covers or follows it; and each changed row's `spans`, a hint of the columns it uses, which is dropped. Being after the last column, the new cells move no cell, formula, merge, check, conditional format, defined name or table. Every other part of the zip comes back with the same contents. Patching unpacks every part on the request thread, where the reader read only the sheet, in a worker; a zip that says its parts unpack to more than 200 MB (`MAX_UNPACKED_BYTES`) is not unpacked, and gets the copy. The patched file is read again before it is handed back and must give every row the cells it gave before. A file it cannot patch safely (one it cannot unzip or find the sheet in, a sheet with a table, whose range could take in the new column, a row or cell that does not say where it is, a namespace prefix it does not expect, or a patched file that does not read back the same) gets a copy instead, rebuilt from the rows with Beeline's own tabs and the note column after the last (`notesCopy`), and the page says the download is a copy without the person's own tabs, formatting and formulas. For a volunteer a note is blank where the identification will be saved or nothing changed, "Not saved: " and a reason with what to do (`m.uploads.notes.reason`, one for every reason the comparison or the drafts can hold a row for) where it cannot be, and a line saying grey columns are not saved where only those changed. An identification another volunteer has already given counts as the same and has no note. For staff a note says "Differs: column was X, file says Y", "Can't use: " and the reason, and "Not read from this file: " with the cells, as the row has them. The plan's lists of rows stop at ten for a page; the notes use every row (`everyRow` on a held item and a sample's difference). **The file uploads again cleanly**: `parseUpload` skips a heading of `Beeline's note`, neither reading it nor naming it as a column it did not read, so a volunteer can fix the rows in the file with notes and upload that, and a note column already in a file is written into, not repeated. It is worked out again each time it is asked for, so after saving, the rows saved read as the same as Beeline has and the rest keep their notes. None of the words a person reads, on the page, in the notes or in the volunteer's about tab, says held, draft, plan, unit, reader or layout; a test checks.

## A volunteer's file: their own identifications, saved to Identify specimens

Anyone who is not staff downloads a file of their own (beeline-kgyd.7, Peter, 2026-11-18: "Volunteers should download their own latest identification only", and that volunteers get different columns in the download itself). **Its columns are `VOLUNTEER_LAYOUT`**: the same grey columns to recognise the bee, then only `scientificName`, `sex` and `caste`, then `specimenId` and `specimenVersion`. Nothing a volunteer may not change is in it: no qualifier, date identified, disposition or remark. Nor is `identifiedBy`, since every row is the person's own identification and a draft is credited to whoever is signed in, so the column would say nothing. **The three white cells are the person's own identification** (`src/app/own-identification.ts`): the draft they have on Identify specimens, else their newest determination that is not an expert's, else blank; never the identification of record and never an expert's, so an expert's name cannot reach their file and come back as theirs. Its `specimenVersion` is a hash of those three cells and the specimen's id, starting with `o`, so it does not change when the overnight commit turns a draft into the same determination or when someone else identifies the bee. The tabs follow the columns: no identifiers tab, the words tab lists only `sex` (female and male, which is what a draft takes) and `caste`, and the about tab says the cells are the person's own and how drafts and the 1am commit work. A file with any of staff's other columns is refused whole (`staff_file`, the layout's `refuses` list), with words telling the person to download their own: its names are the record's, an expert's among them. Karla Salp's copy from before this slice is that file.

**Whose identification, for a delegate.** The cells are the determiner's, who is the person signed in, as on Identify specimens; while staff look as someone else (impersonation) they are that person's, so the view is theirs. A delegate acting for a household downloads the household's specimens (scope `mine` follows the switch) with the delegate's own identifications in them, which is blank where only the person they act for has named a bee. That differs from Identify specimens, which shows the newest volunteer identification whoever made it. Peter's rule was "their own", so the file follows it.

**The comparison is as the uploader**, as above, and then `src/app/upload-drafts.ts` works out each identification that differs as a draft, or holds it. Reach is Identify specimens' own (`entryRowsFor` in `src/app/determine.ts`, the person acted for while the switch is on): a row for a specimen the page would not let the person name is held as `not_yours` if it differs and only counted if it does not. **saveDrafts would quietly fix what it is given, so each such case is held instead**, with words saying what to write: a name not in Beeline's tree (`name_not_in_tree`; a name from Ecdysis is given on Identify specimens, not in a file), a name the tree holds at more than one rank (`name_ambiguous`), a sex other than female or male (`sex_not_draft`), a caste on a bee whose kind has none (`caste_not_taken`), a caste with no sex (`caste_no_sex`), and a male of a bee with castes whose caste is not written as drone (`drone_unsaid`). A file missing one of the three columns holds every identification it changes (`column_missing`), since the part left out would come from whatever the store has, which may be another volunteer's. One that says what the newest volunteer identification already says, where the person has no draft, is held as `already_said`: saving would change nothing and the file would show the same difference next time. Where the person has a draft, the same identification is held as `matches_another` (CodeRabbit): saveDrafts would remove the draft rather than keep one that agrees with another volunteer, and the person's own identification would fall back to an older one of theirs; the note says to clear the bee on Identify specimens to do that. Each write gives the name, sex and caste whole, so saveDrafts takes no part from the store. A changed name must be a node of the tree by its exact spelling, at any rank but kingdom, phylum and class, as the picker offers; an unchanged one is the person's own, a draft's name from Ecdysis included.

**Saving** (`POST /uploads/:id/apply`, only by the uploader, only for a file that is not staff's). The page's "Save N identifications" form carries a digest of what saving would write. Saving reads the file again and works the plan out again **before** the drafts' turn, and refuses (showing the page as things stand, with a line saying something changed) if the digest is not the one the form carried. Working the plan out takes seconds to tens of seconds for a file of 20,000 rows, the upload's limit (measured on 2026-11-18 on a copy of production's store of 16 November, the busiest volunteer's first 20,000 rows on the workstation: comparePlan 7.4 s and draftPlan 1.4 s with the machine's load near 20, and 33 s and 5 s with it near 55; 500 rows took 0.3 s), and the turn (`inDraftTurn`, the queue saveDrafts uses) holds every save on Identify specimens, so only a quick re-check runs inside it: whether the upload was already saved, and `draftState`, a hash of what the plan reads about every specimen the file names (whether the person can still name each, their draft, the newest volunteer identification, their own identification). It is read **before** the plan is worked out and again in the turn, and nothing is saved unless the two agree, so a change made on Identify specimens while the plan was being worked out is never overwritten, whichever row it is on (an independent review: read at the end of the plan, it could miss a change made while the comparison ran). A second submission of the same page whose plan was worked out after the first had saved finds a plan that changed; before telling the person nothing was saved, it looks whether the upload was saved and, if so, shows what was. A test can act between reading the state and working the plan out through `uploadApplyPause`, which only tests pass. The drafts (`saveDraftsInTurn`, given the transaction) and a row in `upload_applied` (`schema/047`, one per upload, with how many) go in one transaction, so a second submission waiting behind the first finds the row and saves nothing. Where the person's file left a name as their own draft had it, the write leaves the name out and saveDrafts keeps the draft's, as the page does when only the sex is changed; a draft naming a taxon from Ecdysis that Ecdysis no longer offers would otherwise be refused on every attempt. Once saved, the page says how many were saved, that they are on Identify specimens and can be undone there until 1am Pacific (Identify specimens' own words), and still counts the rows that can't be saved, whose notes the file still carries. Staff looking at a delegate's upload see it as the uploader alone, without the switch, so the household's specimens count as someone else's there: shown only, never saved. The overnight commit (`src/commit-determinations.ts`) records the drafts as the person's own `in_app` determinations, never expert ones. Staff see a volunteer's upload as the volunteer alone would, without the delegation switch, and cannot save it: staff applying a file, Ecdysis names, qualifiers and the request field for volunteers are not built. A volunteer sees only their own uploads; another's answers 404.

## The samples file

`GET /samples.xlsx` (beeline-kgyd.4.9, Peter, 2026-11-19) is the Excel download of the samples listing, **staff's alone for now** (anyone else gets 403, and a samples file uploaded by someone who is not staff is refused with a sentence saying so). It takes the `/samples` listing's query as `/specimens.xlsx` takes the specimens listing's, writes every kind of sample, net and trap, streams through `xlsxStream`, and stops at 20,000 rows, the upload's limit (`MAX_ROWS`): a file the upload refused whole would be worse than one that stops short, and the note beside the button on `/samples` says "at most 20,000 samples". The specimens download has no such stop today.

**Columns** (`SAMPLES_LAYOUT` in `src/app/upload-plan.ts`; the row is `samplesFileRow` in `src/app/sample-workbook.ts`, which takes each value from `sampleCsvRow` wherever the samples CSV has the column, so the comparison and the download cannot drift). White and read: `fieldNumber` (the sample's number), `recordedBy` (the collectors in order, joined by ` | `), `eventDate`, `samplingProtocol`, `trapCount` (the leading number of `sample.sampling_effort`, by `trapCountOf`; blank for a net sample or an effort in other words), `specimenCount`, `decimalLatitude`, `decimalLongitude`, `coordinateUncertaintyInMeters`, `countryCode` (alpha-2 as the CSV writes it), `stateProvince`, `county`, `locality`. Grey: `sampleId`, which finds the row, and `sampleVersion`. Every cell is text, long-text columns wrap, white headings are bold, as in the specimens file. **The file's `sampleVersion` is a hash of its own**, over the sample's id and the text of every white cell as written (prefix `f`; `s`, `v` and `o` are the specimens file's, the samples listing's and a volunteer's), so a change to any cell the file carries since the download shows. The listing's `sampleVersion` in `listings.ts`, which the API and the specimens comparison use, is untouched. Tabs: `collectors` (everyone who collected a sample whose last day of collecting is in the last 24 months, Oregon's today, by display name, once, sorted, for looking a spelling up; `recordedBy` takes no list, for the reason `identifiedBy` does not, a spreadsheet marking an unlisted name "Invalid") and `about` (what the file is for, white and grey, a line for each white column, and that a blank `sampleId` will become a new trap sample, which is not built yet). The words are in `workbook.samples` in `src/app/messages/en.ts`.

**Which file an upload is comes from the file, every time it is read; nothing is stored about it.** `parseAnyUpload` reads the tab named `specimens` or `samples` (else the only tab); a `sampleId` heading with no `specimenId` heading, or a tab named `samples` with no `specimenId`, is a samples file (the second so that a samples file whose `sampleId` heading is mistyped is told what is missing, not that a specimen column is). A file with neither refuses as before. The kept file and its copy in Drive are exactly as for a specimens file. `Layout` says which kind it is, and `kind` decides the comparison and the page.

**The comparison** (`src/app/samples-upload-plan.ts`, `planSamples`) is at the grain of a sample. It reuses `evaluateAs`, `UNIT_RULES` (dates and method, place, coordinates) and the strict reading of a cell from `upload-plan.ts`, and adds the rules for the other groups. What Beeline says now is what the download would write for the sample now, read as staff, through the same row function.
- **An existing row** (`sampleId` given) cannot be used when the id is not a positive whole number, when the id is on another row too, when no sample has it, or when `fieldNumber` is not exactly the sample's number. The number is the row's identity check and is never a change.
- **Groups of cells**, each listed whole or held whole: `method_dates` (`eventDate`, `samplingProtocol`), `trap_count` (blank, or a whole number from 1), `specimen_count` (a whole number from 0, not blank), `collectors` (`recordedBy` split at `|`, names trimmed and blanks dropped, at least one, compared as a list so `A|B` equals `A | B`), `area` (`countryCode`, `stateProvince`, `county`: country and state not blank, a two-letter country mapped back to the store's alpha-3 by the inverse of the download's own table, a three-letter one taken as it is, anything else cannot be used; the country is compared without case), `place` and `coordinates`. A complete group that differs is held as `sample_changed_since` when the row's `sampleVersion` is not the sample's now, and as `column_missing` when the file has no such column.
- **A new row** (blank `sampleId`) would become a new trap sample, and is judged by the trap form's own `checkTrapSample` (`src/trap-sample.ts`) given the row mapped onto the form, so the preview and a later write judge a row alike, together with the comparison's rules for a future collecting date and the bounds of a point; where both find fault with one field, it is said once. A blank `specimenCount` is 0 on a new row, as on the form. Two new rows with one number cannot be used (`new_number_repeated`), and a number another trap sample has is the form's own problem.
- **Collectors** in a new row, or in a changed list on an existing one, are matched by `matchCollectors` (`src/collector-match.ts`), the rule the trap form and staff's collector correction use, so the preview predicts what a write will do. A batch shares one read of the people (`readPeople`, passed in), which the file needs because a list per row would read them 1,600 times. A row whose names do not all match one person each cannot be used, and the plan lists each distinct name that matched nobody, or several people, once with how many rows name it.
- **Counts are split by season** (`SeasonSplit`): an existing sample by `settled_sample`, a new row by its first day against the store's `season.active_since`, and a row with neither (no such sample, no readable date) as not placed.

**The page and the file with notes** are as for the specimens file (`samplesNotes` in `src/app/upload-notes.ts`, `notesFile` unchanged): a few counts (new trap samples that could be created, rows that cannot be used, existing samples that differ, the same as Beeline), each with its season split, then the collector names Beeline does not know, the one short list on the page because staff act on each name, a line saying nothing has been changed yet (and that changes to existing samples are not applied), and "Download the file with notes". Notes read "Differs: column was X, file says Y", "Can't use: " and a reason with what to do, "New trap sample, ready to be created when you apply the file", "New trap sample, can't use: ", or, after applying, "Created OBAS-01234", "Not created: <why>" and "Waiting to be applied". The reasons the samples file shares with the specimens file are in `uploads.notes.reason`; those only it has are `uploads.notes.sampleReason`, except two whose sentence comes from the check that found them (`collector_unknown`, `new_row_problem`). A test checks that no sentence on the page, in a note or in the about tab says held, draft, plan, unit, reader or layout. The note column is skipped on reading, so the file with notes uploads again cleanly.

### Applying the new rows (beeline-kgyd.4.10)

The preview of a staff member's own samples file offers **Apply** when a new row is ready (`POST /uploads/:id/apply-samples`; `src/app/samples-upload-apply.ts`). Only the uploader, if still staff, can press it: not another staff member, not while viewing as somebody else, and not while the nightly or the weekly sweep runs (`syncJobRunning`, which the API refuses on too; the apply job itself is not one of them). Existing rows that differ are still shown as differences and are not applied; the page says so.

**The button carries a digest** of what the page offered: for every new row that could be made, its row number and every value making it would write, the people its collectors came to included, and for a held row the sample it looks like. The request works the plan out again and, if the digest differs, writes nothing and shows the page as it stands with a line saying the comparison changed. The ticks of "create anyway" are the person's own answer and are not in the digest, which departs from the plan, where the digest covered them: they cannot be, because they exist only after the page was shown. What they chose is recorded as the rows queued.

**Applying is a claim and a job.** In one transaction the request inserts the upload into `upload_applied` (its key stops a second submission; `draft_count` is how many rows were queued) and one `upload_sample_outcome` row (`schema/047`) per row: `pending`, with the row's payload (the trap form's fields with the collectors as person ids), or `skipped` for a held row nobody ticked, with the sentence saying why. Then it starts the `apply-uploads` job. The job (`applyPending`) takes pending rows in upload and file order, one at a time, each a framework step, so a shutdown stops it between rows. It is registered with the new `onDemand` schedule: never due by the clock, never overdue, no Sentry monitor, started by a request, and started by the scheduler's own tick whenever `job.waiting` says a row is pending. That tick is how it waits out the nightly (one job at a time is the scheduler's rule, and the apply job holds it while it works, so the nightly waits for it in turn) and how a deploy that interrupted it resumes it, with nothing to do at boot. `scheduler.stop` waits for it like any running job (it is `inFlight`). A row is recorded `refused` only for a problem the code recognises (the trap form's checks, a number taken, a look-alike, the number's shape). **An error nobody foresaw is not stepped over** (Peter, 2026-11-19): the row stays `pending`, the upload is marked stopped at that row (`upload_applied.stopped_at`, `stopped_row`; no error text is kept, since a database error can quote values), the log line names the upload and row, the job goes on with other uploads and at the end throws the error, so the run fails and is reported to Sentry. `applyWaiting` and the job leave a stopped upload alone, and its page says applying stopped at row N because something went wrong and was reported, with a staff **Try again** button that clears the mark and starts the job. A shutdown is not an error: only the job's abort signal being set, or `JobInterrupted`, counts, and it leaves the row pending and unmarked, so the next tick resumes it; a run ended that way is not reported. A queued payload that is not the shape the job writes from (not JSON, no form) is refused at once with a diagnostic. **Stopping:** the job starts no creation once its signal is set (checked just before `createTrapSample`) and stops at row boundaries. A creation already begun is not cut off: it runs on the print connection, which `scheduler.stop` does not interrupt, because that connection is shared with the print runs and the trap form, and interrupting it could cut off somebody's freeze. The worst case for a shutdown is therefore one creation waiting behind the print runs' lock, which a freeze holds for seconds (a 5,000-label run freezes in about 1.6 s), well inside the machine's shutdown budget. The tick also asks `stopping` again after `waiting` answers, and `stop()` waits for a tick in progress, so no run starts once a stop began and the store is not closed under a tick. The job writes on the print connection, which `main.ts` now opens before the jobs and passes to `buildJobs`.

**Making a row.** The job runs `checkTrapSample` again on the payload (the collectors are ids, which `matchCollectors` takes as ids), looks for a look-alike again unless the row was ticked, and calls `createTrapSample(printWriter, sample, uploaderPersonId, within)`. `within` runs `UPDATE upload_sample_outcome SET outcome = 'created', sample_id = …` in the sample's own transaction, so a crash cannot leave a sample that no upload row names, and a row whose sample was made always says `created`: a sample made and a row still pending cannot both be true, which a test shows by failing `within` and finding no sample. A number taken since the page is `refused` with the trap form's sentence. The new sample's queue turn is taken inside its creating transaction, before anyone can see the sample, and held until its history entry is written, so no edit can land in the gap and be recorded as the upload's; the batch's pass runs while those turns are held, and they are let go when it ends. The history entry has `created: true`, the new source `upload` (`SAMPLE_CHANGE_SOURCES`, `Actor.via`, the record page's label "an uploaded file"), the applying staff member's iNaturalist login as author (empty if they have none) and the reason "From upload N". A crash between the commit and the history entry leaves the entry to the next full pass, which writes it under `reconcile`. A new row's note after applying says that a row looking like an existing sample was not created and to upload it again (ticking create anyway) or enter it on the trap form, since nothing can be ticked once the file is applied; pressing Apply when every new row is held and none is ticked says so, and is not told the file changed.

**A new row that looks like an existing sample is held** (Peter): the same first collector, collecting days that overlap, and a point within 100 metres (`LOOKALIKE_METRES`, `findLookalikes` in `src/trap-sample.ts`, one rule used by the preview and the job; a net sample counts as well as a trap). The page lists these rows, the one list besides the names Beeline does not know, with a link to the sample each looks like and a tick, "create anyway". Unticked, the row is not created and its note says to put that sample's id in `sampleId` to change it, or to tick create anyway. A tick counts only for a row that has a look-alike, so a stale or made-up one cannot switch off the job's check for another row. A reader who is not staff (staff who lost the role, reopening their upload) is told a row is held but not which sample it looks like, since the sample's location may be withheld from them. The job looks again, so a sample made since the page held the row; but it does not count the samples the same upload has just made, since two traps at one site on the same days are two samples a file may mean. The query uses a bounding box on the point first and the great-circle distance after, over `sample_collector` first collectors, and was measured on a copy of production (below).

**The series' numbers wait for a person** (Peter, 2026-11-19). `OBAS-` numbers must be five digits (`seriesNumberProblem`), and nothing else about their size is checked: production's highest is OBAS-20214, a block of 2025, while the main series ends near OBAS-01204, so "highest plus a margin" guarded nothing, and the earlier margin guard is gone. New rows whose number starts `OBAS-`, and rows with no number, are held unless the one box "I've checked these OBAS numbers" is ticked on the page, beside a line giving how many and the lowest and highest. The tick is posted with Apply like the look-alike ticks and is not in the digest; unticked, the rows are `skipped` with a note saying to tick it. **A blank number takes the next in the series**: the job gives the row `nextSampleNumber` inside `createTrapSample`'s lock (`autoNumber`), so consecutive rows get consecutive numbers; the form is checked with a stand-in (`AUTO_NUMBER_PLACEHOLDER`), the payload keeps the number blank, and the outcome row and the notes say the number given. The preview says how many rows have no number and the one they would start from. **A series number that any other sample has, of any kind** (letters, a hyphen: `OBAS-`, `WBAS-`; the old Beeline holds some trap bottles as net samples), cannot be used: the note names that sample and says to put its sampleId in the row. The preview asks, and the job asks again under the lock (`createTrapSample`'s `anyKind`; the trap form still counts trap samples only). The Apply page also says how many of the samples to be made are in an active season with specimens, since their labels are ready to print as soon as they are made, and a print run would give their bees permanent numbers and end the chance to delete them.

**The page** shows progress while rows are pending ("Applying: 3 of 40 rows done", refreshing every five seconds through a `Refresh` header) and, when done, how many were created and how many not. Counts then cover only the rows without an outcome, since a created row reads as a number Beeline already has. The file with notes reads the outcome rows.

**Deleting a sample made by mistake** is [Entering trap samples](entering-trap-samples.md#deleting-a-trap-sample). `upload_sample_outcome` has no foreign key to `sample`, so a deleted sample's record stands.

**Deleting everything an upload made** (Peter, 2026-11-19): on a samples upload's page, staff (not while viewing as someone else, and not while the job is still working on the upload) get "Delete the samples this upload made", a confirmation page, then every created sample that the single delete still allows is deleted, each in its own queue turn and recorded in `sample_deletion` with the reason "Undo of upload N". The page says how many were deleted and lists those that could not be with why (printed, in a print run, has specimens). The outcome rows stay, and read "Created OBAS-x, since deleted" in the notes, and the page's count says how many were since deleted.

**Not built:** applying a corrected group to a sample (beeline-kgyd.4.11; the job dispatches on `unit`, and any unit it does not know is refused), adding the collectors a file names (beeline-kgyd.4.13), trappers (beeline-kgyd.4.14), trappers uploading their own samples, and the overlay resolver's respelling suggestions for a name. The specimen-grain sample groups still in `upload-plan.ts` (`sampleDifferences`) are now unused by any file and are to go in a separate change.

## What is kept

**The upload is kept before anything reads it.** `upload` (`schema/047`, an entity, never updated) says who sent the file, when, its name, its SHA-256, its size and how many rows it holds, and an optional `reference`: the request behind the file, an email's message id or an issue link, so that a later change can be traced to who asked for it (never an address or a name). The bytes go to `<uploadsDir>/<upload id>/upload.xlsx` (config `uploadsDir`, `BEELINE_UPLOADS`, default `data/uploads`; declared and refused under Vitest like `printRunsDir`). A file that is refused is deleted again and no row is written. The preview reads the kept file and works the plan out again each time, so it always compares with what Beeline says now. **A second copy goes to the Drive folder of received files** (beeline-kgyd.1, Peter, 2026-11-18: "keep each uploaded file in the Drive folder of received files ... not in the nightly archive"), the folder where files people send by email are kept ([Files people send](files-people-send-and-expert-sheets.md)), and `upload.drive_file_id` says where it is. The file on the volume is not in the nightly backup, which holds the store and the authored CSVs; the copy in Drive is the one a store put back from a backup can still find. The order is fixed: the file is written to disk and read, a file that is refused is deleted and never reaches Drive, then it is stored in Drive, and only then is its row written. If Drive does not take it, the upload is refused (`not_kept`) and the copy on disk is deleted; if the row cannot be written after Drive took it, the copy in Drive is moved to the bin, so no copy names an upload that does not exist. Drive can also take the file and the answer be lost on the way back; then the upload is refused, and the app looks in the folder for a copy carrying that attempt's own mark (a random `attempt` app property, not the upload id, which a store put back from a backup can hand out again) and bins it. Both clean-ups are best effort: every failed keep logs its attempt mark and whether a copy was found and binned, and if a clean-up fails the log line says which copy is left (the Drive id, or the attempt to search the folder for), for staff to bin by hand. The request waits at most a minute for Drive (`KEEP_TIMEOUT_MS` in `src/app/upload-archive.ts`). The copy is named `upload <id> <login> <day> <file name>`, so a person browsing the folder finds it by the upload's id or by who sent it, and its description and Drive app properties say the same. The app keeps it as Beeline's service account, with the key it already reads for the nightly backup (`driveBackup.key` in `src/app/config.ts`), which the server passes to `createApp` as `uploadArchive`, in production only (`serverUploadArchive`): a workstation or the sandbox given the key to rehearse the backup keeps uploads on disk, since the folder is production's. A workstation without that key, and every test, has no archive and keeps the file on disk only: nothing on this path falls back to `data/secrets/drive-key.json`, as `pnpm received:store` does, because a developer's upload or a test's would then land in production's folder, and `driveUploadArchive` refuses to be made under Vitest. The tests give the app a fake archive. The preview links staff to the copy. Reading the file back from Drive when the disk copy is gone is not built: the preview still says that the kept file is missing.

**The route enforces the 20 MB limit on the bytes it reads** (Hono's `bodyLimit`, a little over the file's size for the form around it), not on a declared length, which a client can leave out or lie about. The upload's own folder is made without `recursive`, so an id that an earlier upload already used (a store put back to an earlier copy can draw it again) fails the upload with the generic failure page and a log line, writing no row and touching no file. The file is kept as `upload.xlsx` whatever it was called, so a name never reaches the file system, and the preview checks the kept file's SHA-256 before reading it and shows a failure page if it differs. `upload` carries CHECKs (`byte_size > 0`, `row_count > 0`, a 64-character hash) because a deployed store can never gain one (ADR 0006).

## What the applying slices must enforce

The comparison cannot see these, and they are not built here. Each is something an existing correction refuses, so a later slice that applies a difference must go through that correction's function and report what it refuses, not write around it:

- A changed collecting start date on a sample that has an iNaturalist observation, a method change on a sample with no old records, and a blank method on a sample entered in Beeline are refused by `src/app/sample-method.ts`.
- Coordinates on a sample with neither an observation, old records nor an entry in Beeline are refused by `setCoordinates`; on one of the last two they are kept under the sample's first old record, or in the store (beeline-kgyd.4.2, [Editing and corrections](editing-and-corrections.md)). A point is refused as a removal on any sample with no observation, whatever it has instead (so an all-blank coordinates unit cannot be applied as one there: staff set the right point), and as any change while a print run that has not printed holds the sample (`in_print_run`); the applying slice has to say both.
- A blank locality on a sample with no observation changes nothing (`setPlace` in `src/app/sample-corrections.ts`); on a sample with an observation it makes the sample follow iNaturalist's locality again. The page's note says both.
- A blank `identifiedBy`, and a determination dated before the collecting date, are refused by the sheet loader.

The staff page for the specimens file says that Beeline doesn't change any record from it yet; the samples file's page says that nothing has been changed until its new rows are applied, and that changes to existing samples aren't applied yet.

## Not checked yet, not built yet

Nothing checks that a scientific name is in the taxonomy, that a determiner is a person Beeline knows, or that a locality is one iNaturalist would give, nor any of the rules above, for staff's specimens file and for the existing samples of a samples file: the page says it changes nothing (of the new rows of a samples file, only applying changes anything), and a note says a row "differs", never that it is "offered". Not built: applying a change to an existing sample, the request field on what an upload writes (the outcome rows name the upload, whose `reference` holds it), and the determination and sample paths a plan would feed. The plan's `differences`, `sampleDifferences` and `held` are what those slices will read.

**Tests** (`test/xlsx.test.ts`, `test/upload-plan.test.ts`, `test/uploads-app.test.ts`, `test/volunteer-uploads.test.ts`, `test/samples-upload.test.ts` (the samples file, edited by its `sampleId`), and the `/specimens.xlsx` tests in `test/listings.test.ts`) build their input from the app's own `/specimens.xlsx?scope=all` and edit its cells with `test/workbook.ts`, which writes a workbook independently of the app's writer and can make any kind of cell a spreadsheet can. An unedited file compares as no differences at all. Every comparison in `upload-plan.test.ts` is given a `today` of its own, so the July days of the fixtures are never in the future; the future-date rule has tests that name their day. The reader's tests are of the adapter's decisions, not of SheetJS: each kind of cell, a date by its number format, both date systems, the sheet rule, each refusal, the worker (the same answer as in this thread, two at once, a workbook past a small memory limit refused with the app still answering, a one-millisecond time limit refused). The library is also tested against `test/fixtures/openpyxl-resaved.xlsx`: **written by Beeline's writer and saved again by openpyxl**, after one cell was typed over and one empty cell filled (the script that makes it, with the commands, is `test/fixtures/make-openpyxl-resaved.py`). It was **not** written by Excel, LibreOffice Calc, Google Sheets or Numbers. **Two of those have been tried by hand, once** (Peter, 2026-11-17, with the download as #371 wrote it: 46 columns, no tabs, no checks): a copy opened, edited and saved in Google Sheets, and one in Numbers, each came back with every cell still text in the Text format, values typed into cells included, and the only cells that differed from the original were the ones edited. Numbers pads the sheet to 1,000 rows, all empty, which the upload skips. Neither file is kept in the repository. Excel itself and LibreOffice Calc remain untried, and so does what any of them does to cells pasted in from another sheet. A round trip through LibreOffice (`soffice --headless --convert-to xlsx`) is written and skipped where Calc is not installed, which is the case on Hostess (LibreOffice there has Writer and no Calc) and in CI, so it has not been run. If a file saved by one of those programs turns out to differ from what the tests expect, the file is the evidence and the tests should change to match it. Hand-built XML in the tests needs `[Content_Types].xml` overrides for the workbook, styles and sheets, since SheetJS finds the parts by them.

**How the upload tests stay fast** (beeline-kgyd.6). Before, each test built its own store from the schema (0.4 s) and read each workbook in a worker thread (0.1 s to start), and the two files took about 110 s of test time. Now `uploadFixture` (`test/upload-fixture.ts`) builds the fixture store once for each file and copies it for each test; tests that only read share one copy (`sharedUploadFixture`); the tests read workbooks in the test's own thread (`ReadLimits.inThread`, which only tests set); and each group of tests runs its tests at the same time, DuckDB working on its own threads. The worker is still tested where it is the subject: the time and memory limits in `test/uploads-app.test.ts`, and one test that plans a file both ways and compares. A test that writes to the store must use `uploadFixture`, never the shared one.
