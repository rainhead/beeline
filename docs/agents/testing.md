# Writing tests

Read this before writing or changing a test, a test helper, or a fixture that builds a store. Moved out of AGENTS.md, which points here.

Tests run against in-memory DuckDB built from the real `schema/*.sql` (`createMemoryDb`), so a schema mistake fails a test rather than a review — the load-bearing half being *from the real schema*, not *in memory*. The schema is built once per run, and `createMemoryDb` in `test/helpers.ts` hands each caller a copy of it, a store of its own (`test/store-template.ts`): a build takes about 0.4 s and a copy 0.1 s, and a run makes some 1,700 stores (beeline-tl4q). `test/store-template.test.ts` holds that copy equal to a store built from scratch, in every catalog entry with its comment, every row and the next entity id, and in the connection's settings, loaded extensions and temporary tables, so whatever a copy cannot carry fails there before it changes what another test means. A test of building the schema itself takes `createMemoryDb` from `src/schema.ts` instead. A test must not depend on the order the tests run in: check a file with `pnpm vitest run <file> --sequence.shuffle --sequence.seed=<n>` for a few seeds before relying on it, and where tests build on one another, give each its own store rather than marking the file `describe.sequential` (beeline-zhry). A test shares a store with another only where every test that shares it writes nothing, because a test on a shared store can keep passing while it no longer tests what it did; `sharedUploadFixture` (`test/upload-fixture.ts`), for upload plans, which only read, is the one such store. Where being file-backed is itself what is under test, `createFileDb` (`test/helpers.ts`) applies the same schema to a file: the default catalog is then named after the file rather than `memory`, which is where beeline-d34 lived, invisible to a suite in which every test paired a file-backed private store (since retired) with an in-memory main one. It is slower, and reaching for it anywhere else is a mistake. `insertCleanSample` (`test/helpers.ts`) is the fixture that makes a sample nothing is wrong with, and a test that wants something wrong says which. A test that wants the store promotion leaves behind, and is not testing promotion itself, takes its own in-memory copy with `promotedStore` (`test/promoted-store.ts`): promoting costs about 5 s however small the fixture, so each kind of promoted store is built once per run and copied in about 0.2 s (beeline-vwn4). Promotion hands out entity ids in no fixed order, so two promotions of one fixture can number the same specimen differently. `insertCleanSample`'s sample collects on 14 July of the current season: a fixture that should be asked about or printed is dated with `CURRENT_SEASON` or `currentSeasonDate` from the same file, never with a year written into the test, because a written year settles on the 1 March after it ends and every test that expected it to be active fails (beeline-a0lj). A fixture that should have settled is dated in `SETTLED_SEASON`, not `CURRENT_SEASON - 1`, which is still active in January and February. A test that builds the app spreads `scratchPaths()` into it: the files the app writes default to the developer's own under `data/`, a test that fell back to one wrote fake history into them, and under Vitest the fallback now throws (`src/deployment-path.ts`, beeline-yq65). Temporary files are the run's to remove, not the test's: `test/global-setup.ts` points `TMPDIR` at one folder per run and deletes it when the run ends, so a test makes its folder with `mkdtemp(join(tmpdir(), …))` and leaves it. Until it did, nothing removed them, and on Hostess, where `/tmp` is held in memory, a week of runs left over 5 GB there (beeline-qqcg). Assert against strings the source actually produced rather than invented ones — `test/legacy-name-parse.test.ts` is the pattern, its corpus lifted from production staging and its few synthetic cases labelled as such, because a parser tested only on strings we wrote is a parser tested on our assumptions.
