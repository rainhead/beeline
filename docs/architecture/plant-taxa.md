# Plant taxa

Part of Beeline's architecture notes; the index is [README.md](README.md).

A floral host is stored as an iNaturalist taxon id, with the name and rank as they were observed. On its own that tells nothing about the plant: not its genus or family, not its common name, and not whether iNaturalist has since retired the taxon. The taxon cache is how the store comes to know. The plan and its decisions are in beeline-rfkj; this file covers the taxon cache (beeline-rfkj.1), old Beeline's plant list with the common names it gives (beeline-rfkj.2), what a host is today, with its common name, on the record pages (beeline-rfkj.3), and the lookups that match a host with a name and no id to a taxon (beeline-rfkj.5). The listings, their host filter, the CSV, the API's rows and record, and the Darwin Core archive's host id, current name and family (the archive carries the family too, by the default Peter's reviewer asked for; beeline-rfkj.4) are described at the end of [What a host is today](#what-a-host-is-today); what else the exports say about a host is beeline-rfkj.8's.

**iNaturalist's taxonomy is the plant taxonomy** (Peter, 2026-11-13). The store holds only taxa that something has referred to, plus their ancestors and the taxa that replaced them, each fetched by id from the API. It never loads iNaturalist's monthly taxonomy download. **Stored ids and names are never rewritten to follow iNaturalist's taxonomy.** A sample's host does change when its observation does: promotion copies the observation's taxon id, name and rank whenever the observation carries a taxon ([ingestion-jobs-and-elevation.md](ingestion-jobs-and-elevation.md)), and that is how most retirements reach a sample, since iNaturalist re-identifies the observations of a taxon it retires. What nothing does is replace a stored id because iNaturalist retired it. A sample whose host no observation will update keeps the id it has, and [What a host is today](#what-a-host-is-today) reads that taxon's current replacement when a page needs it.

## What is stored

`schema/066_inat_taxa.sql` holds four tables, each documented with `COMMENT ON`:

- `inat_taxon`: the id, name, rank as iNaturalist writes it (species, subspecies, variety, section, hybrid and so on), the rank's number, the parent, whether the taxon is active, iNaturalist's preferred English name for Oregon, and when the row was read. Varieties and subspecies are kept at the rank observed, because some protected populations are identified at that rank.
- `inat_taxon_ancestor`: every taxon above a taxon, **and the taxon itself at depth 0**. The two places that carry a lineage disagree about this (the taxa endpoint's `ancestor_ids` leaves the taxon out, an observation's `taxon.ancestor_ids` includes it), so the table always includes the taxon and a reader never has to know which source a row came from.
- `inat_taxon_replacement`: what a retired taxon was replaced by. A split is several rows, and a reader cannot pick one.
- `inat_taxon_absent`: ids iNaturalist was asked for and did not return, on the terms of `inat_place_absent` except that the verdict lasts 30 days. After that the id is asked for again, and any response that shows the taxon (as a result or as an ancestor, including one already stored) deletes the row at once.

Nothing leaves the cache: a taxon that no sample names any more stays. There are no foreign keys: an ancestor or replacement is recorded before the taxon it names has been read.

**A retired taxon's own lineage is stale.** Aster chilensis adscendens (322554) is a subspecies that iNaturalist replaced with Symphyotrichum ascendens (79294), a different species from the one its parent still names (56861). Anything that needs a host's genus or family must read the current taxon's lineage, never the retired taxon's.

## The worklist

`inat_taxon_uncached` (`schema/112_views_inat_taxon.sql`) is the one definition of what is missing: the ids named by `sample.host_inat_taxon_id` and by `observation_field.host_taxon_id` (the dashboard shows the hosts of observations not yet minted), and the ancestors and replacements already stored, with no `inat_taxon` row and not recorded absent. Fetching a taxon can add to the list, so the fetcher reads the view again after every batch until it is empty. The taxa that iNaturalist's answers to the old plant list's names came to are one more branch of that view: it reads `plant_name_hit_current`, every exact hit of every name and the taxa a retired hit was replaced by, not only the taxon a name resolved to (`plant_list_entry_taxon`, below), so each is read with its ancestors.

## The fetcher

`src/fetch-inat-taxa.ts` is modelled on `src/fetch-places.ts`, with two differences: taxa are refreshed, where places are fetched once, and the worklist grows as it is worked.

It uses iNaturalist's **v2 API** with an explicit `fields` list. v2 returns retired taxa with `current_synonymous_taxon_ids`, each taxon's ancestors with name, rank, parent and common name in the same response, and the Oregon common name when asked with `preferred_place_id=10` and `locale=en`. v1 returns whole records: 512 KB for ten taxa, where a v2 response for thirty is a few tens of kilobytes. Requests carry up to 30 ids, no more than one every 1.1 seconds, and no token.

Two things the response does not do, found by calling it. `ancestor_ids` leaves out the taxon itself, so the self row is added here. The `ancestors` array leaves out the root, Life (48460), though `ancestor_ids` names it, so Life is fetched by id like any other missing taxon. Ancestors in a response are stored as taxa, so a lineage costs no requests of its own, but only active ones that are not yet stored: an ancestor in a response carries no replacements, so a retired one goes through the worklist and is fetched itself. Nothing is taken from the response of a retired taxon, whose lineage is stale, nor for an ancestor that its `ancestor_ids` does not list, which would be stored with only its own row.

Each fetch of a taxon deletes and re-inserts its ancestor and replacement rows in one transaction with the batch, so a reinstated or re-split taxon leaves nothing stale and an interrupted run keeps the batches it finished.

**Refresh.** After the worklist, each run reads again two sets of stored taxa, both defined as views in `schema/112_views_inat_taxon.sql` and both leaving out a taxon read within the last 12 hours, so a cold fill does not read everything twice and a nightly run, about a day after the last, always finds a taxon due. `inat_taxon_recheck` is the stored replacements of retired taxa. It is what follows a chain: a replacement that iNaturalist later retires is noticed the night after, when it is read again, and what replaced it joins the worklist. A chain already formed when a taxon is first fetched is followed in that same run. `inat_taxon_stalest` is the stalest thirtieth of what is stored, so every taxon is read again within about a month. A stored taxon that a refresh no longer gets back keeps its row and is recorded absent, which also stops the refresh choosing it every night until the verdict is 30 days old.

**When the API refuses a batch.** A single unknown id answers 404 with an empty list, and several ids answer 200 with the ones iNaturalist holds (checked 2026-11-13), so a deleted taxon is not an error. A batch that is refused for another reason is asked again in halves, down to single ids, so that one id the API cannot answer costs only itself: it is reported as failed, not recorded absent, and asked again next run. Three single ids in a row failing means the API is down, and that phase stops; the refresh phase still runs when the worklist phase failed. The result says what went wrong (`errors`, `failed`) instead of throwing.

## Old Beeline's plant list

Old Beeline kept a hand-made list of plants, with each one's scientific name, a synonym and common names. It is [ingest/old-beeline-plant-list.csv](../../ingest/old-beeline-plant-list.csv), 1,405 rows, taken from the old server's `/app/shared/data/plantList.csv` on 2026-11-13. **It holds only five of the file's thirty-two columns: Rank, Family, Scientific_name, Synonym and Common_name.** The others are descriptions, traits (bloom, lifecycle, height, noxious or weedy) and two that come from OregonFlora (`PlantURL`, `OF_RecommendedPlants`). OregonFlora asks that its data not be redistributed without permission, the file does not say which columns are theirs, and nobody has confirmed that the program may publish them (Peter, 2026-11-14), so they stay out of this public repository until someone does. Rows are as the file wrote them, with the byte order mark and the old line endings gone. One row has no Scientific_name and files the family in the Family column (`Family,Ericaceae,,,heath`); the load takes the Family as its name when the Rank is Family, so it is loaded as Ericaceae. A row with no name by either route is skipped, since nothing can key it (none is left). The file's text is UTF-8: a curly apostrophe that had been read as three other characters (Jacob’s-ladder) was repaired.

**What is kept and what is worked out.** `schema/067_plant_list.sql` holds the list (`plant_list`, with the hash of the file it was loaded from) and its entries (`plant_list_entry`, keyed by list and by scientific name as written, never by row number), and what iNaturalist said about each name (`plant_name_lookup` and its hits). Rows keep what their source said. The matching and the common names are views in `schema/111_views_plant_list.sql`, so a taxon swap upstream, or a better lookup later (beeline-rfkj.6), changes the answer without a repair.

**Loading.** `loadPlantList` (`src/load-plant-list.ts`) runs at every boot of the app and by hand as `pnpm plant:load [db]`. On production the app holds the store alone (ADR 0005), so a CLI cannot write it, and a deploy is the only thing that changes the file, so boot is the first moment the store can read a new one. It needs no network. A SHA-256 of the loader's version (`PLANT_LIST_LOADER_VERSION`, raised with any change to how the file is read) and the file's bytes is kept with the list, so a change to the parsing reloads a list whose file did not change; the same hash changes nothing, and a different one replaces the list's entries in one transaction. A malformed file is refused and the old entries stay, including one with a quote that is never closed, which would otherwise swallow the rows after it and replace the list with a short one (the parser is strict about quoting here and lenient elsewhere); at boot that is reported and the boot goes on, because a missing list costs common names and nothing else. At boot it also logs how many of the list's names iNaturalist has not been asked about. `db:build` and `db:reseed` load the list too, since it is a file in git and needs no network, so a rebuilt or reseeded store has its common names, and a reseeded store's carried lookups read as answers, without starting the app; the next boot finds the file unchanged. The migration that brings a deployed store forward is `migrations/0093-plant-list.sql`, which mirrors `schema/067`, `schema/111`, the changed view in `schema/112`, `schema/114` as first written (`migrations/0094-host-current-taxon.sql` makes it again over `inat_taxon_current`, and `migrations/0095-plant-names-in-sentence-case.sql` over the sentence-case names) and the new comment on `inat_taxon` in `schema/066` (the cache now also holds the taxa the list's names came to).

**One name normalisation**, in `plant_name_normal` and applied to the list's names, the hosts' names (see [Hosts with a name and no iNaturalist id](#hosts-with-a-name-and-no-inaturalist-id)) and what iNaturalist matched alike: case ignored, the hybrid sign dropped (the list writes `Mentha piperita` where iNaturalist writes `Mentha × piperita`), and with it the sign as mangled by being read in the wrong character set (`Ã—`), `var.`, `ssp.` and `subsp.` dropped (iNaturalist writes a trinomial without them), any whitespace collapsed to one space. The rank is inferred from the shape of the name and not from the Rank column, which files families and tribes as genera and genera as species: one word is above species, told apart by its ending (-aceae family, -oideae subfamily, -eae tribe, -inae subtribe, -ales order, anything else a genus), two words a species or hybrid, more a subspecies, variety or form (`plant_name_shape`, which `plant_list_entry_name` reads). Of the 1,404 named rows, the column agrees with the shape on 1,368; the rest are the cases above.

**Looking names up.** `src/fetch-plant-names.ts` asks iNaturalist's taxa search once per name and expected rank, and records the answer whatever it is, so a name with no match is asked once. The endpoint is **API v1** `/v1/taxa?q=<name>&taxon_id=47126&is_active=any&rank=<ranks>`, found by calling both versions on 2026-11-14. v2 gives the same `matched_term` and `current_synonymous_taxon_ids` in a smaller answer, but it refuses `is_active=any` (422) and without it returns no retired taxon, so a name iNaturalist has since renamed finds nothing; v1 is a few kilobytes a name. `matched_term` is what makes a retired name findable. A page is 30 hits, and every page is read until the results run out, because a second taxon of the name on a later page is what makes the name ambiguous and the views judge only the hits stored (one lookup of the 1,404, Aster, had more than 30 results). Reading stops at ten pages; a lookup cut short there is recorded with `read_in_full` false, so it is not asked again every night, and its name reads as `too many results` and gets no taxon rather than be judged on part of the answer. None of the list's names comes near the cap.

**Which hits are the name** (`plant_name_hit_current`): the hit's own name is the name after the same normalisation, or its `matched_term` is, at an iNaturalist rank the shape allows. Both are read because `matched_term` is only one of the terms that matched: asked for Salix lasiolepis, iNaturalist returned that taxon with `matched_term` "Salix lasiolepis lasiolepis", and reading `matched_term` alone left 22 current names unmatched. A `matched_term` counts only when it is written as a scientific name (a capital first letter), because iNaturalist also puts common names there; 35 of the hits in the 1,404 first lookups have a lower-case `matched_term` and none of them was taken for a name, while every name that matched through an older name alone (Aster chilensis, now Symphyotrichum chilense; Fragaria vesca, once Potentilla vesca) was a scientific one, so this guards against a case not yet seen. A one-word name may also be a section, subgenus or supertribe (Salicaster and Simiolus are sections, Brassicodae a supertribe), but only when it has no hit at genus rank, so a genus such as Rubus does not become two taxa.

**Which taxon a name is** (`plant_name_resolution`), in this order. An active hit whose own name is the name wins outright: Abelia is the genus Abelia, whatever a retired Abelia points at. Otherwise every exact hit must come to one current taxon (a retired hit stands for what its answer said replaced it): three hits for Peritoma serrulata that name one taxon are one answer, two taxa are none (**ambiguous**), and a retired hit with no replacement is a dead end that makes the name ambiguous, since the name might have meant it, and when every hit is a dead end the outcome is "retired, no replacement". The outcome of every name is `plant_list_entry_taxon`'s `outcome`. A replacement that is itself retired is not followed here, one step is as far as `plant_name_hit_current` goes: what an entry covers is worked out from its taxon through `inat_taxon_current`, which follows the chain to its end (see [Common names](#common-names)). A name whose taxon the taxon cache later reads as retired is asked again (`plant_name_unlooked`), so the change is noticed. The new answer replaces the old one only when it arrives: a re-ask that fails for a transient reason, is rate limited (429) or is cut off by the cap or a shutdown leaves the old answer standing; one iNaturalist refuses (400, 414 or 422) replaces it with the refusal, since the old answer points at a retired taxon. If the re-ask comes back to a taxon that is still retired, the name is asked again the next time the cache reads that taxon, not every night.

**What it came to** (a copy of production's store from 2026-11-14, filled by the code as it now stands): of 1,405 named entries, 1,404 matched one taxon and 1 has no match (Brassicoidae, which the list spells differently from iNaturalist's Brassicodae). The first version of the rule left 9 ambiguous (Abelia, Escallonia, Hieracium, Ulex, Zygophyllum, Centaurea moncktonii, Crocus neapolitanus, Malus domestica, Veronica peregrina xalapensis), and each had one active taxon of that name beside a retired one or an older-name hit, which is what the first rule now settles. The rule makes no name newly ambiguous. No two entries reach one taxon.

**When it runs.** The `plant-names` job (`refreshPlantNames`, `src/app/jobs/registry.ts`) at 1am, 300 names a night, then the taxon cache's worklist for the taxa they led to (not its rolling refresh, which the pipeline does an hour later). It starts about 1:02, after the volunteer import (1 minute, at most 1:03 in the 30 days to 2026-11-14) and the commit of determinations (under a second). Its names deadline is 15 minutes and the taxa step's 8, so it ends by about 1:25 at the latest, 35 minutes before the 2am pipeline. Measured on a copy of production's store on 2026-11-14, the 1,404 names took about 29 minutes (1.2 seconds a request), so at 300 a night the first fill takes five nights, or staff start the job from `/jobs` as often as it takes. It never fails the run, but any request error marks the names step failed (as the taxa step does) and is logged as it happens; three in a row, a 429 or a shutdown stop the run, and after a 429 the job makes no call to iNaturalist for taxa either. **A name iNaturalist refuses** is iNaturalist's answer about it. A request refused with a 400, 414 or 422 (measured 2026-11-14: a query of 3,000 characters gets 422, one of 9,000 gets 414, and short strings holding a NUL byte or an ellipsis were answered 200) is recorded at once with `answered = false`: its outcome is `could not be asked`, it shows in `plant_list_entry_unmatched`, it does not fail the step, and it is asked again after 30 days (`plant_name_lookup.answered`); refused again, it is recorded again with a new `looked_up_at` and waits another 30 days. A 5xx, a network error or a timeout may pass, so nothing is recorded: the name keeps any answer it had, the step is marked failed, and the name is asked again next run. For a name already waiting to be re-asked that is one request each run, never a retry within a run, until iNaturalist answers; the run summary says how many names were recorded as could not be asked. `pnpm inat:fetch-plant-names [db]` does all of it at once by hand. Reading the taxa the names led to took 64 requests (1,916 taxa and 699 ancestors, 101 seconds), a little over the nightly cap of 60, because every exact hit's taxon is read and not only the resolved one; the second night finishes it.

**What a person works from.** `plant_list_entry_unmatched` (entries with no taxon, with the outcome and the synonym), `plant_list_taxon_shared` (two entries reaching one taxon, usually a name and its synonym), and `plant_name_unlooked` (what has not been asked).

## Hosts with a name and no iNaturalist id

Most samples from before iNaturalist carried the host have its name and no id: old Beeline's `speciesPlant` columns, promoted as genus and epithet (beeline-32ow). On production's store of 2026-11-15 that is 3,159 samples (7 of the active seasons, 3,152 settled), and 862 distinct names. They are matched to iNaturalist taxa by name, the same way as the plant list's names and by the same lookups (beeline-rfkj.5). **The id is never written into the sample** (Peter, 2026-11-13): the sample keeps the name it was given, and which taxon that name is gets worked out when read, so a better lookup or a taxon swap upstream changes the answer without a repair. The lookups are below; how a page, a listing and a download then read the host is under [Reading a host by its name](#reading-a-host-by-its-name).

**One question for both sources.** `plant_name_wanted` (`schema/111`) is the names to match: the list's scientific names, and the host name of every sample that has a name and no host id. A sample with an id is not in it, since its id is its host. `plant_name_shape` gives each of them its normalised name and the rank its shape implies, which is the one rule for both (`plant_list_entry_name` reads it). `plant_name_resolution` and `plant_name_unlooked` read every shaped name, so a name the list and a host both hold is asked once and resolved once, and the plant-names job's worklist takes the hosts' names without a change to the job. The job asks the list's names first, so a new entry of the curated list does not wait behind the hosts', and its summary, like the boot's log line, counts the names waiting on the plant list apart from those only hosts hold. A host name whose sample later gains an id leaves `plant_name_wanted`, but its lookup stays and its hits stay on the taxon cache's worklist: a few taxa read for nothing, which is harmless.

**What the host names need from the normalisation.** One name holds a line break between genus and epithet, and one a hybrid sign mangled by being read in the wrong character set (`Reynoutria Ã— bohemica`, the UTF-8 bytes of × read as Windows-1252), so the normalisation collapses any whitespace and reads `Ã—` as the hybrid sign. Neither changes any key of the list's names (a test holds this for the real file). A sample's `host_rank` is not read, for the same reason as the list's Rank column: it agrees with the shape on every id-less host but one, `Grass cover crop`, filed as an order and no name at any rank. A doubtful or open name keeps its tail: `Salix sp.`, `Salix cf. scouleri` and `Salix?` never equal the name of a hit, so they come to no match, for a person to decide, rather than be read as the name they qualify. No list name or host has such a tail today.

**A match through `matched_term` alone.** `plant_name_resolution.by_own_name` says, for a matched name, whether a hit whose own name is the name gave the taxon, or only a hit's `matched_term` did. The second is how an older name finds its taxon, but iNaturalist also puts a common name there, written with a capital first letter (asked for "oregon grape", it returned Berberis aquifolium with `matched_term` "Oregon grape"), so the capital-letter test does not keep out a common name typed where a scientific name belongs. Such a name comes to its plant when only one plant has it (`Dull Oregon-grape`, Berberis nervosa) and is ambiguous when two do (`Oregon grape`). The list's names were curated and a host was typed by a volunteer, so these are the matches to look over before a host is read through them.

**What it came to** (a copy of production's store of 2026-11-15, its lookups completed from iNaturalist the same day: 1,524 names in 30 minutes, 411 of them names that only hosts hold, so on production the hosts add two nights of the job). Of the 3,159 samples, 3,137 have a host name that matched one taxon (6 active, 3,131 settled; 850 names), and every one of those taxa is a current vascular plant. Two of the matched names matched only through `matched_term`, both older scientific names and both right: `Aster subspicatus` (6 samples, now Symphyotrichum subspicatum) and `Leontodon nudicaulis` (1, now Leontodon crispus). 21 samples have a name that matched nothing (1 active, 20 settled, 10 names: misspellings such as `Helianthus maximilani` and `Ribes sanguinium`, a family misspelt `Caprifoliacaea`, `Grass cover crop`, `Life`, a bee genus, `Homo sapiens`) and 1 settled sample's name is ambiguous (`Potentilla glandulosa`). Checked once against the samples that do have an id: of the id-less names that also appear on samples with an id, 684 (2,528 samples) resolve to the current taxon those samples carry, 33 (366 samples) to one of the several they carry, and 1 to another: `Solanum umbelliferum`, where the sample with an id was identified as iNaturalist's species complex of that name and the lookup, asked for a species, gives the species inside it. 140 names (261 samples) appear on no sample with an id, and 3 are unresolved. The 2018 `Aster` resolves to the genus Aster that the samples with an id carry. Reading every name's resolution costs about the same as before, 51 milliseconds before and 58 after on the same filled store, and the common names 271 and 278, on a busy machine.

## Common names

`plant_taxon_common_name` (`schema/114_views_plant_common_name.sql`, after the cache's worklist and `inat_taxon_current`; [What a host is today](#what-a-host-is-today) composes on top of it) gives each cached taxon its name: **the first common name of the list's entry for the taxon itself; otherwise iNaturalist's name for Oregon; otherwise the first common name of the nearest coarser list entry that covers it** (Peter, 2026-11-14; the list's names are preferred, but only for the plant they name). An entry covers a taxon when the entry's taxon is that taxon or one of its ancestors in `inat_taxon_ancestor`, **both taken as iNaturalist has them today**: the entry's stored taxon, and each ancestor, are resolved through `inat_taxon_current` first. An entry whose taxon iNaturalist replaced covers what lies beneath the replacement; an entry whose taxon was split, or is retired with nothing to replace it, or is pending or absent, covers nothing; a retired genus in a lineage matches the entry for the genus that replaced it. (A taxon that is not in the cache at all has nothing to resolve and stands for itself.) The nearest, the lowest depth, wins, so a variety with its own entry takes its own name, and a variety without one takes iNaturalist's name for the variety before its species' entry. At one depth, an entry written for the current taxon itself comes before one that reaches it only through a replacement, so a list holding both an older synonym and the current name gives the current name's entry. Where a species' (or lower) cell lists several names, commas or semicolons separate them and the first is shown. `source`, `list_entry` and `list_entry_depth` say where a name came from and how far above the taxon its entry sits.

**Common names are set in sentence case** (beeline-rfkj.9). iNaturalist writes many Oregon names in title case ("Western Water Hemlock"), the old list writes some 60 of its own that way ("Common Fiddleneck", "Western Lily of the Valley"), and the style guide at `/design/names` wants capitals only for proper nouns. So the name a taxon is shown with comes from `plant_name_sentence_case` (`schema/114`), for iNaturalist's names (through `plant_inat_common_name`) and for the list's alike; `inat_taxon.preferred_common_name` and `plant_list_entry.common_name` keep what the sources said. The conversion is in SQL, in the views, and not in the TypeScript that refreshes the cache: then `plant_common_name_stale`, which compares the cache with the views, still judges the name a page shows, and `plant_common_name_cache` stores the converted name, so a reader pays nothing. A name is cut into words (letters and apostrophes, so a hyphen ends a word and each part is judged alone) and the **first word loses its capital like any other**; every word is lower-cased unless it keeps its capital by one of four rules: (1) it is in a phrase of `ingest/plant-proper-nouns.csv` marked `keep` (Great Basin, Rocky Mountain, Willamette Valley); (2) it is a word that file marks `keep` (Oregon, Chinese, Utah, Pacific); (3) it is a possessive, a word ending in 's or in s' (Nuttall's, Douglas'), which keeps its capital because it is nearly always an eponym, unless the file marks it `lower` (Shepherd's, Lady's); a word ending in a bare apostrophe after another letter ("O'" in Jack-O'-Lantern) is not a possessive; (4) it is St or Mt followed by a period or by a single space (St. John's wort, St John's wort; not the st of 1st), or it is Saint or a Roman numeral, which the file holds. The file is the whole behaviour: **nothing is learned from the data**, so the names do not move when iNaturalist's answers or the list change, and a diff of the file is what changes a name. It holds a few hundred rows, each with a reason (`SELECT treatment, count(*) FROM plant_proper_noun GROUP BY 1` counts them as loaded), and is loaded with the list (`plant_proper_noun`; its bytes are part of the list's hash). `parseProperNouns` refuses a row that could never match or could not do what it says: letters and apostrophes, single ordinary spaces or a single hyphen between two words (Trans-Pecos), a period after a word inside a phrase (Mount St. Helens), a `keep` row that has a capital letter (`oregon,keep` would keep nothing), and a `lower` row only for a possessive; an error names the line the row is on, blank lines counted. Both the file and the names are compared with the curly apostrophe read as the straight one, and a word or phrase of the file is set with the apostrophe the name wrote at that place, so the displayed text keeps the source's character. **Phrases:** a row is a phrase when it is more than one word as the view cuts a name, so "Trans-Pecos" is one (the hyphen is part of it). A phrase is matched on whole consecutive words, in any case, wherever it occurs in the name (every occurrence), and set as the file spells it; it is not found next to a hyphen that is not part of it, so "Blue Mountain-heath" is not a place (the compound is a plant) and "Rocky Mountain-ash" gives "rocky mountain-ash"; a plural is a row of its own (Rocky Mountains, Siskiyou Mountains); of two phrases that overlap, the one that begins earlier spells the shared word, then the one first in alphabetical order, so the answer does not move between runs. A phrase beats a `lower` row for a word inside it. A word that is usually a common noun (Sound, Queen, Mount, New) is not a row of its own, only inside phrases (Puget Sound, Mount Hood, New Mexico). A few single words that are nearly always a place here are rows (Cape, Cascade, Rogue), knowing they would also capitalise the rare common-noun use. A taxon at section, subsection, subgenus, series or subseries rank, whose "common name" is a scientific one ("Allium Subg. Cepa"), a name that holds the abbreviation of a rank ("Acer ser. Acer", the name iNaturalist gives a taxon of rank complex), and a name equal to the taxon's own scientific name are left as written. **Limits that remain:** a proper noun that is in no row is lower-cased (a place that no name has met yet, a genus inside a common name), and so is an eponym that iNaturalist wrote in lower case until the file has a `keep` row for it; a possessive that is not a person's and is not yet a `lower` row keeps its capital (none is left in the cached names); a name that was written wrongly stays wrong; a place with a hyphen inside it is judged one part at a time unless the file has it as a phrase, so "Trans-Pecos" is a row and a new such place is not kept until it has one. Measured on a copy of production's store of 2026-11-14 with the list's names looked up (the cache then holds 3,307 iNaturalist names and 1,795 list ones): 1,655 of the iNaturalist names change, 1,209 of them in more than the capital of the first word, and 136 of the list's 1,049 distinct shown names change, 62 of them beyond the first word (counted on `plant_common_name_cache` against the names the sources wrote).

**Fixing a wrong name.** When a name shows a capital it should not have, or lacks one it should, do not change the name in iNaturalist's cache or in the list: add a row to `ingest/plant-proper-nouns.csv` with a reason. `keep` and the word as it is to be written (`Korean,keep`, or a phrase such as `Trans-Pecos,keep`) gives a word its capital; `lower` and a possessive (`Miner's,lower`) takes the capital that a possessive would otherwise keep. The file is read when the app boots, so the change takes effect at the next deploy's boot: the changed bytes make the loader replace the rows, and the same load refreshes `plant_common_name_cache`. Run `pnpm plant:load [db]` to see the result in a store by hand.

**A placeholder is not a name.** 202 rows have a placeholder where a common name belongs ("Abelia Species" on the genus rows, `tribe Cardamineae`, `Genus pieris`), and 35 have none. They are left out (`plant_list_entry_common_name`), so they cover nothing; a placeholder is the entry's own name with "Species" after it or a rank word before it, in any case, or the name written with its capital. `magnolia`, `iris` and `yucca` are names and are kept. This is a departure from the plain rule: without it a genus page would be headed "Abelia Species".

**Several names above species are no name** (Peter, 2026-11-14). For a taxon at genus rank or above the list often writes several names, or the members of a group, where one name belongs: "Plums, cherries, and allies" for Prunus, "cucumber, gourd family" for Cucurbitaceae, "penstemon, beardtongue" for Penstemon, "forget-me-not or borage" for Boraginaceae. Cut at the first separator it shows one of them as if it were the taxon's name, so such an entry gives no name at all, a host under it takes iNaturalist's name for Oregon, and the entry does not name the hosts beneath it as a coarser entry either. The rule is one view, `plant_list_entry_several_names`, so it is changed in one place: the entry's expected rank (the one `plant_list_entry_name` infers from the name's shape, the same rule that matches it to a taxon) is genus or above and the cell holds more than one name, separated by a comma, a semicolon, " or " or " and ". It applies to 87 entries. At species rank and below the cell lists synonyms and the first is shown ("butter and eggs, common toadflax" shows "butter and eggs"; a species' cell is cut at commas and semicolons only, so "stinging nettle or burning nettle" is shown whole). It replaces an earlier rule that caught 33 entries by " and " in the cell or a cell ending in " family" or " tribe"; that rule never applied at species rank, and of the cells it caught only four are single names that the new rule leaves as names (Apiaceae "carrot family", Hypericaceae "St. John's wort family", Iridaceae "iris family", Lamiaceae "mint family"). On the copy of production's store the change moves 3,453 of the 60,427 samples with a host from the list to iNaturalist's name (917 active, 2,536 settled), or to none where iNaturalist has none (61 active, 266 settled), and a few the other way (20 active and 99 settled, taxa under the four family cells now named by them). Before it, 995 active and 2,940 settled samples got their name from a genus-or-above cell with several names, and 2,559 active and 11,812 settled from a species-or-lower cell (unchanged).

**A coarser entry's name is the last resort, not the first.** The rule first written gave the nearest entry's name ahead of iNaturalist's, and on the copy of production's store it named 16,053 of 60,427 samples with a host (3,824 of the active seasons' 12,697) from a genus or family entry, though iNaturalist had a name for the plant itself for 15,074 of them: Sisymbrium altissimum became "mustard" where iNaturalist says "Tall Tumblemustard", and the genus Amsinckia "forget-me-not or borage" where iNaturalist says "Fiddlenecks". So a coarser entry now names a taxon only where iNaturalist has no name for it (Peter, 2026-11-14).

**Cost, and what it led to** (beeline-rfkj.3, measured 2026-11-14 on a copy of production's store with the plant list loaded and the cache filled: 5,686 taxa, 1,405 names looked up). `SELECT * FROM plant_taxon_common_name WHERE inat_taxon_id = 51884` takes about 27 milliseconds, the same as reading the whole view (an earlier measurement here, on another machine, was 90 to 125 milliseconds, again as long as the whole view). The earlier reading of that was that DuckDB does not apply the filter below the window function over every ancestor row, and that a query shaped to filter first would be cheap. The measurement says it would not: what takes the time is working out which taxon each of the list's 1,405 names is (`plant_name_resolution` alone takes about 17 milliseconds, and `plant_list_entry_taxon` 19), which no filter on the host's taxon can skip. A record page's own query takes about 127 milliseconds on that copy (the median of 36 reads of 12 current-season samples with a host), and joining the view for the one host added 57 more.

So the rows of the view are kept in a table, `plant_common_name_cache` (`schema/068_plant_common_name_cache.sql`, beside the list's own tables because it depends on no view; `plant_common_name_stale` is in `schema/115_view_plant_common_name_stale.sql`, after the view it checks), and a page reads one taxon's name there in about half a millisecond (the record page then costs about 12 to 20 milliseconds more than before, almost all of it `inat_taxon_current`). Everything that changes what the view says refreshes the table when it finishes, through `refreshPlantCommonNames` (`src/plant-common-names.ts`): the load of the list (`loadPlantList`, whether or not the list changed: a load that stored the list and then failed to refresh leaves the copy behind, and the retry with the same file finds the same hash, so it is the retry that puts the copy right; the boot refreshes once, through it), the plant-names fetch (`fetchPlantNames`, so the job and the CLI), the taxa fetch (`fetchInatTaxa`, so the nightly step and the CLI, and also when a run stopped at its cap or deadline, for the batches it had stored), and `db:reseed`. A refresh takes about 75 milliseconds and swaps the rows in one transaction. The migration creates the table empty and does not fill it: the boot, which loads the list and so refreshes the copy before the app serves anything, comes seconds after the migration and nothing reads the table in between, and a failure in the migration stops the deploy where a failure of the refresh at boot is reported and costs only the common names until the next refresh (the names job and the nightly step both refresh). The cost of this choice is that the table is only as fresh as the last refresh: something that writes the list, the lookups or the cache by another route and does not refresh leaves a page showing yesterday's name. `plant_common_name_stale` lists any taxon where the table and the view disagree (it reads the whole view, so a test or a person runs it, never a page), and `test/plant-list.test.ts` and `test/fetch-inat-taxa.test.ts` hold that each writer leaves it empty.

### Reading a host by its name

A sample whose host has a name and no id is read through the taxon its name comes to, everywhere a host with an id is read: the common name in the scientific name's tooltip on the record pages and in both listings, "now *X* on iNaturalist", the host filter's match on the current and the common name, and the current name, family and common name in the downloads and the API (Peter, 2026-11-15). **The id is never written into the sample** (Peter, 2026-11-13), so `hostInatTaxonId` stays empty for such a host: it is the id the sample holds, its identification on iNaturalist, and a name lookup is not one. `associatedTaxa` keeps the name as observed.

**Only a match through a hit's own name is read.** A name whose taxon came only through `matched_term` (`by_own_name` false) is an older name, which is fine, or a common name a volunteer typed as a host, which no rule here can tell from it, so it is not read and waits for a person with the other names that resolve to nothing (`sample_host_unresolved`, beeline-rfkj.6). On production's store of 2026-11-15 that holds back 2 names and 7 samples, both older scientific names (`Aster subspicatus`, `Leontodon nudicaulis`).

**A stored copy, as for the common names.** Working out which taxon each name is (`plant_name_resolution`) resolves every name, about 60 milliseconds whatever is asked for, too much for a page. `host_name_taxon` (`schema/116`) is the definition, and `host_name_taxon_cache` (`schema/068`) its copy, keyed by the host name exactly as the sample holds it, so a reader joins on the sample's own column and normalises nothing. It is refreshed with the common names by `refreshPlantCommonNames`, in the same transaction, after each writer of what it depends on: the boot load of the plant list, the plant-names job, the taxa fetch, and legacy promotion, the only writer of a host name with no id (minting always writes an id with the name). `host_name_taxon_stale` lists where the copy and its definition part, for tests and a person checking.

**`sample_host` has one row for each sample whose host the cache holds**, found by its id or, with none, through the copy, and `resolved_by` says which (`id` or `name`). It stays so that a reader that must not trust a name lookup as it trusts an identification can tell them apart: the rule that withholds the locations of sensitive plants (beeline-85m.6) must fail closed. The taxon id is looked up first and the cache's view joined once, so a page pays for `inat_taxon_current_named` once whichever way the host was found.

**The listings** carry the taxon a name comes to beside the stored id (`host_name_taxon_id`, one lookup in the copy by the sample's name), never in its place: `nameHosts` names a row's host through its id or, with none, that taxon, and the host filter matches `coalesce(host_inat_taxon_id, host_name_taxon_id)` against the current and common names. The CSV's `hostInatTaxonId` is still the stored id. The taxon comes from a join on the copy's key in both listings' queries; written first as a correlated subquery, it cost the host filter 70 to 85 milliseconds. Measured with `pnpm bench:pages` on a copy of production's store of 2026-11-15 with every name looked up, before and after run alternately twice on the workstation, the medians in milliseconds before and after: samples by host name 322 and 338 against 332 and 327; samples by host common name 320 and 333 against 332 and 326; specimens by host common name 260 and 270 against 267 and 270; specimens, all, 402 and 406 against 432 and 415; the sample pages 251 to 262 either way.

**"now *X* on iNaturalist"** compares the name as observed with the current name as the lookups compare names (`plantNameKey`, `src/plant-name-key.ts`, the page's copy of `plant_name_normal`'s rule, which `test/host-name-taxon.test.ts` holds to the view's answers), so `Mentha piperita` under *Mentha × piperita*, a line break or a difference of case is no new name. For a host with an id that changes nothing: its name as observed is iNaturalist's own.

**What is left for a person** is `sample_host_unresolved`, the worklist for hand decisions (beeline-rfkj.6). **Its guarantee:** every sample with a host name and no id is either read through a current vascular plant and not listed, or listed, and `test/host-name-taxon.test.ts` asserts it over every case. Each row says whether a page reads the host through a taxon that has a current one (`read`), why it is listed (`outcome`, the first that applies), the taxon a match came to, the taxa the lookup's other hits stand for today (`other_taxa`, what a person weighs: each part of a split, and a taxon the cache has not read by its id), its season and whether it has settled (the store's `sample_season` and `settled_sample`). The outcomes:

- **no name:** the name normalises to nothing.
- **The lookup's own outcome** (not looked up, no match, ambiguous and the rest): not read, unless a failed refresh left an older answer in the copy, which `read` then shows.
- **matched by another name:** not read (above).
- **not copied yet:** the name resolves, but the copy a page reads does not hold it, or holds an older answer, because a refresh failed or has not run since. The app's boot runs one.
- **taxon not read yet:** the name came to a taxon the taxon cache has not read. Not read until the nightly taxa step has.
- **taxon no longer current:** iNaturalist has retired the taxon with nothing after it, split it, or no longer has it. For a retired or split taxon the page says so under the volunteer's name ("no longer used", "split"); for one iNaturalist no longer has, it says nothing. Asking the name again need not change the answer, since a lookup names one replacement.
- **lineage not read:** read, but the cache holds no lineage for the taxon, so nothing says it is a vascular plant, and a reader that must fail closed is not alone in doubting it.
- **not a vascular plant:** read. The lookups search plants only, so a name can never come to an animal, and none is a moss on production.
- **other taxa had this name:** read through the active taxon of that name, but a retired or older-name hit of the same lookup stands for another taxon today, so a name written years ago may have meant that one. Both sides are followed to what they are now, and a hit that is a dead end names no other plant. This comes from the rule that picks the active taxon of a name (`plant_name_resolution`, above), which suits a curated list better than a volunteer's name of 2018.
- A sample not read for a reason none of these names is listed with no outcome.

On the copy of production's store of 2026-11-15, "other taxa had this name" covers 9 names and 28 samples: for 5 of them (*Malus domestica*, *Erythranthe lewisii*, *Escallonia*, *Abelia*, *Rhus trilobata*) the samples that have an id and the same name carry the same taxon, and for *Mimulus*, on 6 samples, there is nothing to compare with; iNaturalist has since split the genus, and an Oregon *Mimulus* of 2018 most likely means a plant now in *Erythranthe* or *Diplacus*. On that copy, with every name looked up, and after #352 had cleared the one name-only host that was Homo sapiens (which leaves 3,158 samples with a name and no id, where the measurements of the lookups above, taken before it, count 3,159 and 21 that matched nothing), 28 samples, all settled, are not read: 20 whose name matched nothing, 7 matched by another name and 1 ambiguous. The other 3,130 samples with a name and no id (6 of the active seasons, 3,124 settled) are read through their taxon, every one a current vascular plant whose lineage the cache holds, and 28 of those, all settled, are listed as well because other taxa had the name.

## What a host is today

`plant_taxon_common_name` reads the taxon's own stored lineage, which for a retired taxon is stale (see above), so it is only right for a taxon iNaturalist has not retired. A retired host is resolved to its current taxon first, and the name is read for that one, whose lineage is current.

A sample keeps the host id its observation gave it and the name as observed. `schema/113_views_inat_taxon_current.sql` says what iNaturalist calls that taxon now, when somebody reads it, and stores nothing. It comes before the common names (`schema/114`) because they read it, to follow a list entry's taxon to its current one; it reads only the cache's tables, never the plant list or `plant_taxon_common_name`, because `inat_taxon_uncached` reads `plant_name_hit_current`.

`inat_taxon_replacement_end` follows each retired taxon's replacements to the end of the chain, one row per end, and says what the end is (`end_kind`): `active` (a taxon iNaturalist has not retired), `retired` (a retired taxon nothing replaced: a dead end), `absent` (a taxon iNaturalist was asked for and did not return, whether or not the cache holds a row for it: also a dead end, and the walk goes no further through it) or `unread` (not in the cache yet). The walk keeps each pair it has reached once, so a chain that loops back on itself stops and has no end, and a diamond (two branches that come to one taxon) gives that taxon once.

`inat_taxon_current` has one row per cached taxon and its **standing**, worked out from the ends and never from whether a row exists:

- `current`: iNaturalist has not retired it. It is its own current taxon.
- `replaced`: retired, and every chain ends at one active taxon, which is the current taxon.
- `split`: replaced by **more than one** active taxon (a dead end beside them does not change that). There is no current taxon and nothing is picked. The genus, or the family, that every active taxon shares is given, so a count by genus can still use it, except when a dead end sits beside them, since it may be another half.
- `retired`: retired, with no active taxon at the end of any chain, or with one and a dead end beside it. The dead end might be the other half of a split, so nothing is picked.
- `pending`: a chain reaches a taxon the cache has not read, so what it comes to is not known until the nightly step has read it. Nothing is said.
- `absent`: iNaturalist was asked for the taxon and answered without it (`inat_taxon_absent`), though its row stays active.

**An absent taxon stays absent until a fetch returns it.** `inat_taxon_known_absent` (schema/112) lapses after 30 days, and that rule says when the fetcher asks again, not that iNaturalist changed its answer. Between the lapse and the next fetch, which can be most of a month for a taxon the rolling refresh reaches late, the last answer is the best there is, so `inat_taxon_current` reads the table itself, and the fetcher's removal of the row on a successful read is what makes the taxon current again. A replacement that is absent is a dead end for the same reason, cached or not: a retired taxon whose replacements are all absent is `retired`, not `pending` (nothing is left to read) and not `current`.

The current taxon's id, name and rank are those of the end of the chain, and italics follow its rank (a species replaced by a family is set upright). The genus and the family are the current taxon's, never the stored taxon's own stale ancestry (see above), and the taxon itself where it is a genus or a family. **An ancestor that is itself retired is resolved the same way:** replaced by what it came to when that is one taxon of the same rank, and no genus or family otherwise (a genus replaced by two genera, or by a section, gives none), so a genus or a family given here is never a retired taxon. `is_plant` and `is_vascular` say whether the lineage reaches Plantae (47126) and Tracheophyta (211194), for a split whether every taxon it came to does, and are null where there is no current taxon or the cache holds no lineage. These two views read only the cache's tables.

`schema/116_view_sample_host.sql` adds the common name and puts the sample on top. `inat_taxon_current_named` is the per-taxon view joined by id: it is `inat_taxon_current` with the cache's name for the **current** taxon, so a host that was replaced is named for the plant it now is, and a split, a retired, a pending and an absent one have no name. `sample_host` is a thin layer, one row for each sample whose host the cache holds: by its id, or, for a sample with a host name and no id, through the taxon its name comes to, with `resolved_by` saying which ([Reading a host by its name](#reading-a-host-by-its-name)). A sample whose host is neither has no row, and the page shows the name as observed.

**Measured on a copy of production's store of 2026-11-14** (the cache filled from iNaturalist the same day: 5,686 taxa and all 1,405 names looked up; see below for what each fix changed, which on this copy is nothing, since nothing here is yet in the cases the fixes are for):

- All 1,404 list entries that have a taxon reach a `current` one, so an entry following its taxon's replacement changes no name yet. The whole cache is 5,562 `current`, 106 `replaced`, 14 `retired` and 4 `split` (Ulex, Mimulus, Zygophyllum and Hieracium, each within one family), and none `pending` or `absent`; `inat_taxon_absent` is empty, so no replacement ends in it.
- Of the 106 replaced taxa, 48 have the name of their replacement exactly (a retired taxon replaced by another with the same name: 889607 and 47436 are both Lotus, 779132 and 72195 both Isatis, 745997 and 50638 both Plantaginaceae). "now X" under X would say nothing, which is why the page keys on the name and not on the standing.
- Every host (12,697 samples of the active seasons, 47,730 of the settled) is `current`, and none has a name that differs from the name as observed, ignoring case: nothing in this store is renamed under the same id.
- No current taxon has a retired genus or family in its stored lineage, so lineage through current resolution gives the same genus and family as before for all of them.
- `is_plant` and `is_vascular`: 5,242 current taxa are vascular plants, 14 more are plants that are not (mosses and the like), 306 are neither (Life, and the other kingdoms between it and Plantae). All 106 replaced taxa and all 4 splits are vascular plants.
- iNaturalist's v2 `current_synonymous_taxon_ids` gives the **last** replacement, not the first: asked on 2026-11-14 for 888235, a hybrid retired three times over (888235, then 1723119, then 1723125, then the active 1723128), it answered 1723128, and so did the answers for 1723119 and 1723125. - Cost: `inat_taxon_current` for the whole cache takes about 18 milliseconds and for one taxon about 12, `sample_host` for one sample about 18 to 20 (the earlier measure was about 9 for the page's read before lineage went through current resolution and `is_plant` and `is_vascular` were added), and a refresh of the copy of the names takes about 75 milliseconds.

The replaced, split and retired standings occur in the cache only for the taxa the list's names came to (the whole cache: 5,562 current, 106 replaced, 14 retired, 4 split), and they will meet a host only where a sample keeps the id its import stated and no observation will ever update it. They are tested, and a page shows them, but nothing on production exercises them today. Of the 106 replaced taxa, 90 have a different common name when read through the current taxon than through the retired one's own stale lineage.

Read through `sample_host`, the 60,427 samples with a host split by source exactly as in the table above (active seasons 7,452, 5,177 and 68; settled 31,139, 16,262 and 329, by the store's `season` and `settled_sample`), as they must when every host taxon is current.

**The record page** (`HostValue` in `src/app/views/record.tsx`, both the sample's and the specimen's, which read the same columns) shows the name as observed, as before, with the host's common name in the name's tooltip, and under it, in this order:

1. "now *Current name* on iNaturalist", whenever the current taxon's name differs from the name as observed, ignoring case, and whatever the standing. Keyed on the name and not on the standing, because a taxon can be renamed under the same id (standing `current`) and a replacement can carry the same name as the taxon it replaced, where "now X" under X says nothing. It sits directly under the first line, whose tooltip carries the common name, so that the page says first what Beeline recorded and then what iNaturalist calls it. The name is set from the current taxon's rank.
2. Where there is no current taxon: for a split, "split into several names on iNaturalist" and, when they share a genus or a family and no dead end sits beside them, "all in the genus *X*" (the family is set upright, the genus in italics, through `TaxonName` from the rank the view returns with the name); for a retired taxon, "no longer used on iNaturalist". A taxon that is pending, absent or not in the cache adds nothing.

The four messages are in `src/app/messages/en.ts`: `hostNow` and `hostSplitWithin` as functions of their parts, so word order is the translator's, and `hostSplit` and `hostNoLongerUsed` as plain strings. They say "names", the catalogue's word, and not "taxa", and "no longer used", not "retired". The API's record carries the current name, the family and the common name, as the listings do, and keeps back the rest of these fields (see `SAMPLE_PUBLISHED` in `src/app/api-read.ts`); the listings, their filters and the CSV are beeline-rfkj.4, and what else the exports say is beeline-rfkj.8's. **The common name is not shown; it is in the tooltip** (Peter, 2026-11-15: common names are not worth screen space). `TaxonName`'s optional `vernacular` prop (`src/app/views/components/taxon.tsx`) sets it as the `title` of the element that carries the scientific name, so it appears on hover and takes no space, and adds it after the name as visually hidden text (", woolly sunflower"), because screen readers do not announce a `title` reliably. The listings in beeline-rfkj.4 use the same prop, so there is one way to do it. The name is the current taxon's, so a replaced host shows its stored name with the replacement plant's common name in the tooltip, and "now *X* on iNaturalist" on the line below. A host with no common name has no tooltip; a split or retired host has none. The known limit is that phones and tablets do not show a `title`, so there a common name is reachable only through the host filter and the downloads. The rule and the reasons (why not brackets, why not quotation marks, case) are at `/design/names`, "English names".

**The listings** (beeline-rfkj.4; `hostMatches` and `nameHosts` in `src/app/listings.ts`). `/samples` and `/specimens` show the host as the record page does: the name as observed, then the common name in its tooltip, through `TaxonName`'s `vernacular` prop (the style guide's rule at `/design/names`), so the column is as wide as the scientific names and no wider. The filter hint says that the host box also finds the common name, which is why a row can match a name the page does not show. The listings leave out "now *X* on iNaturalist" and the split notes, which are the record page's, so that a row stays one or two lines; a person who wants them opens the record.

- **Filter.** The host box matches in part, in either case, the name as observed, what iNaturalist calls the host now, or its common name. The last two are read from `inat_taxon_current_named` as a set of stored taxon ids, in one subquery for the whole query, so a replaced host answers to its current taxon's names as well as to its own, and a host that is split, retired, pending, absent, or whose taxon the cache has not read, which has neither, is found by the name as observed alone (which is why that one is still in the filter). The subquery resolves the cache once, about 18 milliseconds, and only when the host box is used.
- **A trap's plant.** A sample whose method names a trap keeps its observation's plant, but never as a floral host (beeline-vjqy, Peter 2026-11-16): a trap does not say which flower any bee visited. `src/trap-method.ts` is the one test, on the method and not the sample's kind, which says only whether the sample spans days. The listings show the plant with "near the trap" under it, and the host box still finds it; the sample page calls it "Plant near the trap"; the taxon page's "off" and the determining page's "on" read "in a trap near" ("off or in a trap near" for a place where the person did both, since the listing that line links to cannot tell them apart); `associatedTaxa` reads `"near":"Ceanothus"`; and the occurrences file's `relationshipOfResource` reads `near` wherever the row writes a plant and the old record said "visits flowers of" or nothing, which the comparison rules wrong or filled ([The legacy-format export](the-legacy-format-export.md)). The 2026 vane-trap records hold a number in that column instead (10, 18, 6), which looks like a trap count and is left as it was. On the backup of 16 November 2026, 79 samples with a plant had a trap's method, all from settled seasons, and the occurrences file changed for 2,353 records.
- **Sort.** Still on the name as observed. The two other names would put a row where the volunteer's own label does not, and a replaced host's order would change when iNaturalist renames it.
- **Showing.** The page's query selects only the host's id. After it, `nameHosts` reads the hosts on the page, and the rows' names are not a join in the page's own query (which would resolve the whole cache for every row it sorts). A page needs only the common name, so a host that iNaturalist has not retired and has not said is absent, which is its own current taxon (standing `current` in `inat_taxon_current` is exactly that), is one lookup in `plant_common_name_cache` by its own id. Only a retired or absent host, which a page rarely has, goes through `inat_taxon_current_named`, because working out what it came to resolves the whole cache however few taxa are asked for. The pages ask for `"common"`. A download reads the whole view once, when its first page is asked for (`readHostNames`, `hostNamesOnce`), and gives the map to every page of the file (`hostNames` is that map), so a whole file is one snapshot of the names and does not pay for the view again with each page; the Darwin Core archives do the same for each archive. The API's listing, which is one page a request, reads the view for the hosts on its page (`"all"`, the default). A test holds that the pages and the downloads give the same names, including for an absent host. No reader needs the rank of the current name, so it is not read for the listings (the record page reads it, to set the name).
- **Downloads and the API's rows.** The name as observed stays in `associatedTaxa`, as Darwin Core's term asks. Four columns come **last**, after every column that was there before, so that a spreadsheet or a script that reads the old columns by position goes on working: `hostInatTaxonId` (the id the sample holds), `hostCurrentName`, `hostFamily` and `hostCommonName`; each is empty where the host has none (a host the cache has not read, a split or a retired taxon, which has no current name, and a name with no id that resolves to no taxon; a split's family is given where its parts share one). `hostInatTaxonId` is empty for every host with no id, including one read through the taxon its name comes to, whose other three columns are filled ([Reading a host by its name](#reading-a-host-by-its-name)). They are the last four columns of the samples download. On the API's specimen rows four more follow them, for loading an edited copy back ([Browsing](browsing-scope-filters-sort.md)). The Excel file of specimens does not carry the host columns: it holds the columns chosen for editing ([Loading an edited download](loading-an-edited-download.md)), of which the host's name as observed, `associatedTaxa`, is one. The Darwin Core archive keeps its own columns where they were and carries the first three after them, as nothing, as it does `hostRank`, and leaves out `hostCommonName`: the archive goes to Ecdysis and GBIF and carries scientific names only, while the samples CSV and the API carry the common name (Peter, 2026-11-14; `NOT_IN_ARCHIVE` in `src/app/dwc-archive.ts`). The family is in the archive too, by the default Peter's reviewer asked for; beeline-rfkj.8 keeps the question of what else the exports say. **No Darwin Core term exists for them**: `dwc:family` and `dwc:vernacularName` describe the identified organism, which here is the bee, and `associatedTaxa` is a list of names with no place for a second one, so naming a host's family or common name with either would say the bee's family was the plant's. The API's listings read the same header and row mapper (`SAMPLE_CSV_HEADER`, `sampleCsvRow`), so its rows gain the four fields too, and `GET /api/v1` describes them. The API's single record (`SAMPLE_PUBLISHED` in `src/app/api-read.ts`) carries `host_current_name`, `host_family` and `host_common_name` as well, so that `GET /api/v1/samples/<id>` and the listing agree; it still holds back the host's standing and the rest, which is beeline-rfkj.8's to decide. `hostCommonName` is the common name of the host's current taxon, which is the stored one unless iNaturalist has replaced it, and has three sources in this order: the plant list's entry for that taxon, else iNaturalist's name for Oregon, else the nearest coarser entry in the list.
- **Cost.** Measured with `pnpm bench:pages` on 2026-11-14 on a copy of production's store with the cache filled (5,686 taxa, 1,405 names looked up; 70,726 samples, 397,330 specimens), on the workstation with other sessions using it, so compare only within these numbers. The reads themselves: the host names of a page of 50 hosts take 2 milliseconds from the cache and 19 through the view (the whole view is 18 either way). Whole pages, median of 21 requests, two runs each way, before and after this change, as averages of the four medians in milliseconds: samples, all 380 and 403; specimens, all 388 and 389; samples, mine 338 and 334; specimens, mine 302 and 308, so the pages' differences are within the noise. The host filter is the one page that costs more: samples, all, by host name as observed went from 294 to 339 milliseconds (45 more). A page runs the filter's subquery twice, once for the rows and once for the count, and each run resolves the whole cache (about 18 milliseconds); that is the 45, with the two subquery evaluations and the wider match. Downloads, `samples.csv, all` and `specimens.csv, all`, each the median of 3 requests in two runs, with the view read once for the whole file (the final design) against once for each page (the first): samples 8.8 seconds before and 8.5 after, specimens 49.3 seconds before and 46.0 after (a download is pages of 5,000 rows, 80 of them for the specimens file, so 79 reads of the view are gone, at least 1.5 seconds; the runs vary by about a second, so the whole difference is only roughly that). The two downloads take about a minute together, so `pnpm bench:pages` runs them only when `--only` names them (`--only='csv, all' --n=3`); the sample-edit case likewise runs only without `--only` or with one that matches it.

## Running it

`pnpm inat:fetch-taxa [db]` by hand. In the nightly pipeline it is the step "fetch taxa", after the other store steps and before the check that fails the run over a refused history snapshot (`refreshInatTaxa` in `src/app/jobs/registry.ts`). It never fails the run, since a cache a night out of date costs a page its common name and nothing else, and it is capped at 60 requests (about two minutes) and at 8 minutes for the whole step, whatever the requests are doing, so that it cannot delay the 3am backup (the nightly starts at 2am and has taken from 36 seconds to 8 minutes). Taxa stored before the cap or the deadline stay stored. A cold fill on production, measured on a copy on 2026-11-13, is 111 requests and about 3 minutes, so it takes two nights.

`db:reseed` carries the four tables across, and the plant list's lookups too: `plant_name_lookup`, `plant_name_lookup_hit` and `plant_name_lookup_hit_replacement`, refusals included (`CARRIED_TABLES`), and loads the plant list from git, on the same terms as `inat_place`: they come from an outbound fetch nothing in the store can recompute. Production is never reseeded (ADR 0006), so this serves dev stores only. The migrations are `migrations/0090-inat-taxa.sql`, for what a host is today `migrations/0094-host-current-taxon.sql`, and for the hosts' names `migrations/0096-host-name-lookups.sql`, which changes views only. `plant_common_name_cache` is rebuilt from what is carried, by a refresh at the end of the reseed.

## Tests

`test/fetch-inat-taxa.test.ts` uses responses captured from the real API on 2026-11-13 (`test/fixtures/inat-taxa/`): 56861 (current), 322554 (retired, replaced by a species its stale parent is not), 887293 (a genus replaced by a section, 742759), 1415100 (the replacement of two retired names, 148304 and 78444), 1588297 (a species split into three, with its three replacements, `split.json`) and the 404 body for an id that returns nothing (`absent.json`). The fake API answers as the real one does: 200 with the ids it holds for several ids, and the captured 404 for a single unknown one. They are the shapes iNaturalist sends, which is what a parser tested only on strings we wrote would miss.

`test/inat-taxon-current.test.ts` covers every standing (current, replaced, a chain, a diamond, a loop, a split within a genus and across genera, a split with a dead end beside it, one active taxon beside a dead end, retired, pending, absent and how it ends, uncached, reinstated), a replacement iNaturalist does not have (cached or not), lineage through a retired genus or family, `is_plant` and `is_vascular`, a list entry whose taxon was replaced or split, the common name of a replaced host coming from its current taxon, and `sample_host`; `test/record.test.ts` renders each case on the sample page and the specimen page, down to the exact lines under the host (what the common name is, that "now X" comes before it, that a same-name replacement or a difference of case shows nothing, that a rename under the same id does, the genus in italics and the family upright). `test/plant-list.test.ts` looks up host names taken from production (the line break, the mangled hybrid sign, a family, `Grass cover crop`) with iNaturalist's answers captured on 2026-11-15 (`test/fixtures/plant-names/host-answers.json`, cut down to the fields the fetcher reads), and synthetic hosts for the cases production lacks (a doubtful tail, a common name typed as a host, a name the list shares). It also holds the refresh: a retry with the same file after a failed refresh, once at boot, and `thenRefreshPlantCommonNames` when the work, the refresh or both fail. The taxa are synthetic except where an id says otherwise (322554, 79294 and 1588297 are the captured real cases); the lineage around them is made up.
