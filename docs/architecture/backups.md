# Backups

Part of Beeline's architecture notes; the index is [README.md](README.md).

The `store-backup` job (`src/store-backup.ts`, beeline-elf, 3am Pacific, ahead of the Sunday sweep so it cannot be pushed past 5am) puts one archive a night in the Bee Line folder on the OSU shared drive, as a service account scoped to `drive.file`: a copy of the store, the authored CSVs, and a manifest of table counts and hashes. Until 2026-11-05 it also carried the private store, encrypted with that store's key; the store was retired then (beeline-4tdh), and `checkBackup` still reads archives from before, opening that copy only when given the key, since retention keeps a year of monthly copies. The copy is taken inside the app (ADR 0005) and is not `COPY FROM DATABASE`, which inserts tables in name order and so fails on the first foreign key; `src/store-snapshot.ts` copies the schema with `(SCHEMA)`, which carries the sequence's position, and fills tables parents first, a self-referencing table (`animal`) a level at a time, in one transaction. Nothing is trusted: the copies are reopened and their rows and schema counted against the store, Drive's MD5 of what it stored must match (an upload that does not is binned before the run fails), and only then does retention — two weeks of nights, the first copy of each month for a year — move old copies to the bin. Unconfigured in production, the job fails rather than succeeding at nothing; the sandbox, which gives production its folder at cutover because two apps' retention in one folder would bin each other's copies, says it backed nothing up (beeline-83b8.8). Restoring and the drill are [the runbook's](../runbooks/deploy-fly.md#backups).

**The copy kept for queries** (beeline-pnqr.4). It is read by `pnpm store:query` (`src/store-query.ts`), a command run on the machine over `fly ssh` while the app serves, which is what a lookup used to download a backup for; the app itself never opens the copy, and nothing reaches it over HTTP ([the runbook](../runbooks/deploy-fly.md#asking-the-store-a-question-while-the-app-runs)). After the snapshot is verified, and before the upload, the job also leaves that same copy for SQL queries to read: at `BEELINE_QUERY_COPY`, by default `query-copy/query-copy.duckdb` beside the store (`queryCopyPath` in `src/app/config.ts`; `data/query-copy/query-copy.duckdb` when `BEELINE_DB` is unset, the same default the job falls back to). It is a plain, unencrypted DuckDB file whatever the archive around the Drive upload is, about as large as the store (the snapshot is rebuilt compactly, so a little smaller than a store that has seen many updates), and there is exactly one. `keepQueryCopy` in `src/store-backup.ts` replaces it atomically: it creates `query-copy.duckdb.partial` with mode 0600, writes and fsyncs it, removes any `.wal`, `.wal.checkpoint` and `.wal.recovery` file beside the old copy and any older partial file, renames it over the old copy, and fsyncs the folder. The folder is mode 0500 and the file 0400 at rest; the folder is opened up only for that replacement and closed again in a `finally`. For a moment the volume holds the store, two copies, and the work directory's copy. The path is refused, in `config.ts` and again in `keepQueryCopy` (after resolving links), if it is the live store, a WAL beside it, or an authored file, because the rename would replace the open store. Because the folder is made read-only, it must also be the copy's own: a target in the folder of the live store or of any file the app writes is refused, as is a folder that already holds anything but the copy and its side files (`.partial`, `.wal`, `.wal.checkpoint`, `.wal.recovery`), before anything is touched. A copy that cannot be kept does not stop the archive: the job uploads and bins old copies, then fails, so /jobs shows `keep a copy for queries: ...`.

Why queries read the copy and not the live store: a SELECT on the live store can call `nextval` (a sequence does not go back when the statement is rolled back, so a query could use up the 32-bit `entity_id` sequence of a store that is never reseeded), and a write inside a WITH clause is typed SELECT. The data is therefore up to a day old (3am Pacific), and every result carries `copiedAt`, the modification time of the file the child actually opened (it stats the path before and after opening, and opens once more if the backup renamed a new copy in between), because a failed night leaves an older copy in place.

Why each query runs in a child process (`src/query-copy.ts` starts it, `src/query-copy-worker.ts` is it): review found what no DuckDB setting bounds. `SELECT len(range(400000000))` reached 16 GB under a 256 MB `memory_limit`; `levenshtein` of two 600,000-character strings ignored `interrupt` for over 30 seconds; and a statement of 50,000 nested subqueries crashed the process. So the app does not run the query. It starts a child (`child_process.fork`, under tsx as `src/label-pdf-worker.ts` is; a thread would share the address space and die with it), sends it one request, and waits. The parent kills the child with SIGKILL at the time limit (default 10 s, 100 ms to 60 s) and when its resident memory read from `/proc/<pid>/statm` every 50 ms passes 768 MB (no watchdog where there is no `/proc`); the child sets its own `oom_score_adj` to 1000 so the kernel kills it before the app. A child that ends without an answer is the error `timeout`, `memory` or `crashed`, and `busy` is cleared only when the child has exited, so one query runs at a time and a killed one cannot leave the module stuck. The child's environment is exactly `PATH`, `HOME`, `TZ`, `TMPDIR`, `NODE_ENV`, `NODE_OPTIONS` and `NODE_PATH` (not every `NODE_*`, which would include `NODE_AUTH_TOKEN`), so none of the app's secrets are in a process that runs someone's SQL (`HOME` because DuckDB finds its extensions under it). The child opens only the copy, read-only; it never opens the live store, so ADR 0005's one-writer rule is untouched. A process per query costs about 0.3 s on a workstation for `SELECT 1`.

What the child lets through: before spawning, the parent refuses a statement over 20,000 characters (a 6 MB one took 4.8 GB to parse), one with a NUL, and `maxRows` (1 to 50,000, default 5,000), `timeoutMs` and `maxBytes` that are not whole numbers in range. The child accepts exactly one statement, by DuckDB's own statement extraction, and only a statement typed SELECT; a plan is asked for with `explain: true`, which prefixes `EXPLAIN` (never `ANALYZE`) after the SELECT check and checks the result is still one EXPLAIN. `EXPLAIN ANALYZE` is refused because it runs what it wraps: `EXPLAIN ANALYZE COPY (...) TO '<the copy>'` overwrote the copy, and `... TO '<copy>.wal.recovery' (APPEND)` wrote 1.5 GB beside the store, since DuckDB keeps the database file and its `.wal*` paths open to statements with external access off. A PIVOT that lists its columns (`ON x IN (...)`) is a SELECT and only reads, so it is allowed; one that does not is several statements and is refused. The instance is read-only, has autoload and autoinstall of extensions off, external access off and its configuration locked (`openQueryCopy` in `src/db.ts`), runs on one thread with a 256 MB limit, and has a temporary directory it cannot create: DuckDB 2.0.0 does not enforce `max_temp_directory_size` on a read-only instance (a 1 MB limit let one query write 1 GB beside the copy), so a query that needs more memory than its limit fails with an error rather than spilling onto the store's volume. The result is read a chunk at a time and cut at `maxRows` or `maxBytes` of JSON (default 5 MB, counted in UTF-8 bytes), saying which; a text or blob value over 1 MB is replaced by a note giving its size, decided inside DuckDB (in bytes) before it is copied into Node. The statement is wrapped for that, and a scanner that knows strings, quoted names, dollar quoting and nested comments (`meaningfulEnd`) removes only a trailing semicolon and trailing comments. A result with a struct field named `__proto__` is refused (`not-allowed`, rename it in the query): the library drops that key, and carrying it as JSON text would round integers above 2^53. Values follow one rule, written at `jsonValue` in `src/query-copy-worker.ts`. One quirk remains: the open file itself is readable through `read_text` and `read_blob`, which shows nothing a SELECT on its tables does not.
