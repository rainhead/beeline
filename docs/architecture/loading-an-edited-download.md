# Loading an edited download

Part of Beeline's architecture notes; the index is [README.md](README.md).

People download the specimens CSV from `/specimens`, edit cells in a spreadsheet, and will upload the edited copy (beeline-kgyd, Peter, 2026-11-16). Mostly they will give determinations; staff will also correct a sample's method, dates and place. Beeline shows every difference and, in a later slice, records the changes.

**What exists so far is the first slice, and it writes nothing to any record.** Staff upload a file at `/uploads` (`src/app/views/uploads.tsx`, the routes in `src/app/server.tsx`) and read a preview at `/uploads/:id` that lists what differs from what Beeline says now and what is held, under a line saying that nothing has been changed and that **applying changes from a file is not built yet**. The routes are admin only and refused while impersonating, as the other staff writes are. The link is on `/specimens` beside the bulk actions and on `/exports`.

**The upload is kept before anything reads it.** `upload` (`schema/047`, an entity, never updated) says who sent the file, when, its name, its SHA-256, its size and how many rows it holds, and an optional `reference`: the request behind the file, an email's message id or an issue link, so that a later change can be traced to who asked for it (never an address or a name). The bytes go to `<uploadsDir>/<upload id>/upload.csv` (config `uploadsDir`, `BEELINE_UPLOADS`, default `data/uploads`; declared and refused under Vitest like `printRunsDir`), as `upload.csv`. A file that is refused is deleted again and no row is written. The preview reads the kept file and works the plan out again each time, so it always compares with what Beeline says now. The files are on the volume and are not in the nightly backup, which holds the store and the authored CSVs: only the `upload` rows are, so a restored store can name a file it no longer has, and the preview says so.

**The comparison is `src/app/upload-plan.ts`**, a function of the store and the file's bytes that returns a plan (`planUpload`, or `parseUpload` then `comparePlan`). Its decisions:

- **A row is found by `specimenId`**, never by field number, because a field number is not unique, may be absent, and is the cell a spreadsheet damages. A field number column is still read, as a check on the row's identity: a cell that is not the specimen's number holds the row (`number_disagrees`), a blank cell agrees with a specimen that has none, and two all-digit numbers that differ only by leading zeros agree, since dropping them is what a spreadsheet does.
- **A change is a cell that differs from what the download would say now**, and "now" is the download itself: `listSpecimens` (a new `ids` option restricts it to the named specimens, read 500 at a time as staff, scope all) through `specimenCsvRow`, so the comparison cannot drift from the file the person edited. Columns are found by name in any order, unknown ones are ignored, and a column the file lacks is never a difference. Neither is a cell beyond the end of a short row: that is a column the row lacks, not a blank, and a unit is built only from the columns that some row of its sample reaches. A column named twice refuses the file (`repeated_column`), since which one is meant cannot be told.
- **Both sides are normalised first**, because a spreadsheet rewrites dates, numbers and encodings without anyone editing the cell: text is made NFC, a non-breaking space becomes a space, it is trimmed, and the quote the download puts before a cell that would read as a formula is taken off (the inverse of `csvCell`). Sex, qualifier, caste and `identifiedByExpert` ignore case (a spreadsheet writes `TRUE`); coordinates and uncertainty compare as numbers within 1e-9. A date is read leniently and held only when it cannot be shown equal to what Beeline says: a slash date is read month first and day first, and is unchanged if either reading is what Beeline says; if neither is and both are possible days (`3/4/2025`) it is held (`date_ambiguous`); if only one is possible it is read that way. A date identified also takes a spreadsheet's month forms (`Jul-2026`, `July 2026`), and a two-digit year only where that reading equals what Beeline says, since it would otherwise guess a century. A cell that cannot be read is held (`number_unreadable`, `date_unreadable`), and a blank where Beeline has a value in a column that cannot be empty (the name, the collecting date) is held (`cannot_be_blank`) and is never a request to remove the value.
- **A fact is held or offered whole.** The units are a specimen's determination (name, qualifier, sex, caste, determiner, date identified), a specimen's disposition (disposition, remarks), and for a sample its method and dates, its place, and its coordinates (latitude, longitude, uncertainty). A plan offers a unit with every cell of it the file has and says which differ (`SpecimenChange`, `SampleChange`), so applying takes a unit, not a cell. If any cell of a unit is held for any reason, every differing cell of the unit is held with it and none is offered, and the held item lists each of those cells with what Beeline says and what the file says (`HeldItem.cells`), so the page shows that a name change is held along with the unreadable date that caused it: a new name offered with an unreadable date would put a name on record with the date it was made on lost. For a sample, a row whose cell is unreadable holds the unit for the whole sample, so its sample-mates' values are not offered either. Coordinates are one unit because a latitude alone is not a point; a file with only one of the two columns holds the unit (`column_missing`).
- **Each differing cell gets a kind by its column**: `determination`, `method_dates`, `place`, `coordinates`, `disposition`, and `not_applied` for everything else, which is listed apart and never offered.
- **`identifiedByExpert` is never read from a file.** The determination of record ranks expert determinations first (`schema/110`), so a flipped cell would outrank every other determination for good. It, the authorship, the rank and the host columns are listed apart, in a collapsed section, as differences that Beeline does not take from a file.
- **A file edited against something Beeline no longer says is held, not applied.** A specimen's determination and disposition are held (`specimen_changed_since`) when the row's `specimenVersion` is not the specimen's now, and a sample's units (`sample_changed_since`) when its `sampleVersion` is not the sample's now. A file lacking the column cannot say what it was edited against, so those are held as `column_missing`. The specimen's version is a hash of its changeable cells and not the determination's id, because an id does not change when a row is updated in place (a loader fills a sex, a caste or a date) or when a joined name is corrected, and the file would then look current when it is not.
- **A sample's change is one change, not one per row.** The file repeats a sample's cells on every specimen row. If the rows of one sample do not all say the same thing in a column where one differs from Beeline, nothing can tell which is meant, and the unit is held (`rows_disagree`); otherwise it is one change for the sample, carrying how many of the sample's specimens the file holds and has in all, and whether its labels are on paper (`printed_sample`), which a later slice needs to decide whether a change reaches a printed label.
- **A row is held and the rest of the file goes on; a whole file is refused only when it cannot be read**: over 20 MB, not UTF-8, no `specimenId` column, a column twice, a quotation mark that never closes (`malformed`: it would swallow the rows after it into one cell, which the plan could then offer as one specimen's remarks), no data rows, or more than 20,000 of them. A held row contributes no differences. Counts are split by active and settled season with `settled_sample` ([CONTEXT.md](../../CONTEXT.md), Season); a row naming no specimen has no season and is counted apart.

**The route enforces the 20 MB limit on the bytes it reads** (Hono's `bodyLimit`, a little over the file's size for the form around it), not on a declared length, which a client can leave out or lie about. The upload's own folder is made without `recursive`, so an id that an earlier upload already used (a store put back to an earlier copy can draw it again) fails the upload with the generic failure page and a log line, writing no row and touching no file. The file is kept as `upload.csv` whatever it was called, so a name never reaches the file system, and the preview checks the kept file's SHA-256 against `upload.sha256` before reading it and shows a failure page if it differs. `upload` carries CHECKs (`byte_size > 0`, `row_count > 0`, a 64-character hash) because a deployed store can never gain one (ADR 0006).

The parser is small and lives in the module (`parseCsvRecords`): RFC 4180, a BOM stripped, `\n`, `\r\n` or a lone `\r`, blank lines skipped. The tests (`test/upload-plan.test.ts`, `test/uploads-app.test.ts`) build their input from the app's own `/specimens.csv?scope=all`, so an unedited file compares as no differences at all, including after a round trip that adds a BOM and carriage returns.

Not built yet: applying anything, recording who changed what and on whose request, and the determination and sample paths a plan would feed. The preview's `kind` and `held` names are what those slices will read.
