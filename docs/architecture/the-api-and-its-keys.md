# The API and its keys

Part of Beeline's architecture notes; the index is [README.md](README.md).

Beeline has an API under `/api/v1/` for programs: a script, an AI assistant, an agent working on the code (`src/app/api.ts`, beeline-pnqr). Every request carries a **personal API key** as a bearer header, and every answer is JSON, errors included. The first endpoint is `GET /api/v1/me`, which says whose key it is and what it may do.

**A key** (`src/app/api-keys.ts`, the `api_key` table in `schema/012`) is made by a person on their own page, `/keys`, reached from the account menu. They name it, choose what it may do and how long it lasts, and see it once: the store keeps only its SHA-256, as it does for a session, so a copy of the table lets nobody in. The key starts with `beeline_` so that one pasted in the wrong place can be recognised. Its first 12 hex digits of the hash are its reference, which the person's list shows and which is safe to record. Like a session, a key is held against the iNat user and resolved through `inat_account` on every request.

**What a key may do** is chosen when it is made, and is a ceiling, not a grant: `read` sees what its person sees, `edit` also corrects its person's own samples, and `staff` does what its person may do as staff. The scopes a person may give are decided in one place (`offeredScopes`) for both the form and the check on what it posts: `read` for anyone signed in, and `edit` and `staff` only for someone who is staff now. (Until 2026-11-13 `edit` was offered to everyone. Narrowing it stops anyone making an `edit` key from now on and does not touch one already made, which still works for its person.) A person may have ten working keys. A staff key acts as one only while its person holds a `person_admin` row, which is asked on every request, so taking the rights away stops the key at once. A key acts as its own person and nobody else: there is no acting for someone and no impersonation through one, and a key cannot be made or revoked while acting for someone, because a key signs its holder in as its owner and a delegation does not hand that over.

**A key stops working** when it expires (7, 30 or 90 days, the longest being the most a session can last; a key has no idle limit and no signing out), when its person or a staff member revokes it, or when their iNat account is unlinked: the unlink on `/people` revokes the account's keys where it ends its sessions (as soon as the store has changed, before the change log is written, so a failure after that cannot leave them standing; a key is also made inside the queue that runs account changes one at a time, and only if the person's account is still the iNat user their session was issued to, so none can be made between an unlink and its revocation or by a session the change ended; saving an account without changing it revokes nothing), and the nightly `session-purge` job revokes the keys of an account that went some other way. Without that, linking the account to a different person would bring the key back as them. A row is kept after its key stops working, so what the key did can still be traced to it.

**Two credentials, two places.** The API is mounted ahead of the session gate and never calls it, so a session cookie means nothing under `/api/v1/`; no page reads a bearer header, so a key means nothing anywhere else. `test/api-keys.test.ts` holds both. The CSRF check does not apply to the API for the same reason: it protects a credential a browser sends by itself.

**The old Beeline's redirect.** Until the old Beeline closes, `/api/*` is redirected to it ([the app process](the-app-process-and-its-gate.md)). `/api/v1/` is registered ahead of that, and a request that carries an `Authorization` header to any other address those redirects answer, the old interface's pages included, is answered 401 and not redirected, because some HTTP clients resend that header when a redirect stays within the site, and one mistyped path would hand the key to another server.

**Limits.** One key may make 120 requests a minute, counted in memory and before the key is looked up, so a key over its limit costs the store nothing; past that it is answered 429 with `Retry-After`. The machine's CPU allowance is small, and a script in a loop should be slowed before the pages are. The last-used time is written at most every five minutes and is allowed to lose a write conflict, as a session's slide is.

**Jobs** (beeline-pnqr.5). A staff key can do what the Jobs page shows staff and its Run button does:

| Request | Answer |
| --- | --- |
| `GET /api/v1/jobs` | every registered job with its schedule and latest run, and which job is running |
| `GET /api/v1/jobs/runs?job=<name>&limit=<n>` | recent runs, newest first |
| `GET /api/v1/jobs/runs/<id>` | one run: its status, its detail, and the steps a night job recorded |
| `POST /api/v1/jobs/<name>` | starts the job now; 202 with the run to watch, as soon as the run is recorded |

Starting a job takes no arguments: it is the registered job, run now, as the button runs it. One job runs at a time ([Ingestion, jobs, and elevation](ingestion-jobs-and-elevation.md)), so a start while another runs is answered 409 naming what is running, and a name nobody registered 404; the scheduler's `startRun` tells the two apart and returns the run's id, which the page's `start` never needed. A run's status is `succeeded` or `failed` as recorded, `running` for the one run the scheduler has in hand, and `unfinished` for a run the process stopped under, which nothing will complete. A program may treat `unfinished` as final, so the answer has to be right at the moment a run ends: the scheduler names the run it has in hand by id (`runningRun`), set as the run's row is inserted and cleared only after its outcome is written, the API asks it on both sides of reading the rows, and a run with no outcome that neither answer names is read once more before it is called unfinished. These are for staff keys only, as the page is for staff only: a run's detail is whatever the job or its error said, and that can name people. Who started a run is written to the log (`[api] <login> started job ...`), since `job_run` has no column for it yet (beeline-pnqr.7). The commands that still need maintenance mode are not jobs and cannot be started this way; moving them is beeline-pnqr.7.

**Who can see and revoke which keys** (beeline-pnqr.9). Anyone signed in may open `/keys`, see their own keys and revoke them, so that someone who has lost their staff rights can still end a key that goes on working for reading. Anyone signed in may also make a `read` key, and the account menu links to `/keys` for everyone signed in. (Until 2026-11-13 making keys was staff only, and the link was shown to staff and to anyone who had made a key, which cost a lookup in the store on every page for a person who was not staff; with the page open to all, that lookup is gone.) While viewing Beeline as someone else `/keys` is refused and the link is not shown; while acting for someone under a grant the list is still the signed-in person's and nothing can be changed. Staff also see another person's keys on that person's page, `/people/:id`, only when they have made one: name, what it allows, made, expires, last used, reference and whether it is revoked or expired, never the key. Each working key has a Revoke button posting to `/people/:id/keys/:ref/revoke`, staff only and refused while viewing as someone. The person in the URL must be the key's owner, so a reference taken from another page revokes nothing. Only a working key (not revoked and not expired) is touched, so a second revoke changes nothing and keeps the first one's record. The page lists the keys of the person's account in two parts, under separate headings. The first is the keys made while the account has stayed with this person, with a Revoke button on each working one. The second, "Made before this account was linked to this person", is the keys made before the account was unlinked or moved, with no buttons, since all of them have ended, and with who revoked them and why. Staff see those names because they may need to trace a key, and the heading says plainly that they are not this person's.

**What is recorded when a key is revoked.** Three columns on `api_key`: `revoked_by`, the iNat login of whoever did it (the owner's own login when the owner did), and `revoked_reason`, one of `owner` (on `/keys`, or staff ending their own key from their own page), `staff` (on the person's page), `account_changed` (staff unlinked or changed the account on `/people`; `revoked_by` is that staff member) and `account_gone` (the nightly `session-purge` job; `revoked_by` is empty). A key revoked before the columns existed has both empty. The third column, `account_changed_at`, says whose keys these are: when staff unlink an account or link it to someone else (`revokeKeysFor`), or the nightly job finds it linked to nobody (`revokeOrphanedKeys`), every key of the account that is not yet marked is stamped with that moment, whether it was working, revoked or expired. Only the working ones are revoked and given a reason, so an expired or already revoked key keeps its own story. A stamped key belongs to whoever held the account before: the account's new holder does not see it on `/keys`, the account menu does not offer them the link because of it (`hasKeys` and the owner's list read only keys with no stamp), and the person page shows it to staff under the separate heading. A person unlinked and then linked again to the same account therefore starts with no keys of their own on `/keys`, and the keys they had made show to staff under that heading; a key made after the relink is theirs. Revoking by staff is refused while acting for someone as well as while viewing as someone, as on `/keys`. The owner's list says who and why only when it was not the owner ("Revoked 12 Nov by samstaff", "Revoked 12 Nov by samstaff: the iNaturalist account changed"); the staff list on the person's page always says who, "by its owner" included. A key with neither column set says only the date. Staff revoking a key is not written to the person change log ([ADR 0007](../adr/0007-authored-changes-are-events.md), `src/person-change.ts`): that log records differences in a person's state, a key is not part of that state, and an entry would have to pretend otherwise. The two columns are the record.

**Who may make which key** (the owner's decision, 2026-11-13). Collectors may make `read` keys and staff may make all three, so a collector can point their own program or AI assistant at the records they can see, and nothing more: a read key changes nothing, and an `edit` key writes to samples, which the owner has not opened to collectors. `offeredScopes` is the one rule, used by the form's choices and by the check on what `POST /keys` posts, so a volunteer who posts `edit` or `staff` by hand gets a 400 and no key is made. Everything else about making a key is as before: refused while viewing Beeline as someone else and while acting for someone, at most ten working keys, the three lifetimes, made inside the queue that runs account changes and only for the account the session was issued to.

**Sample corrections** (beeline-pnqr.6). A key can make the corrections the pages already allow and no others, by calling the same functions as the forms ([Editing and corrections](editing-and-corrections.md#where-the-rules-for-a-correction-live)), so the rules, the overlay each one writes and the history entry are the page's. Each is a `POST` with a JSON body under `/api/v1/samples/<id>/`:

| Request | Body | The page's equivalent | Who |
| --- | --- | --- | --- |
| `edit` | `values` (an object of field to text, from `locality`, `country`, `state_province`, `county`, `protocol`), `note`, `dry_run` | the collector's edit form | the sample's collector, for a sample with no observation |
| `locality` | `locality` | the place editor: an offered name is adopted, an empty name follows iNaturalist again, any other name is staff only | a collector for their own sample; staff for any |
| `coordinates` | `latitude`, `longitude`, `uncertainty`, `remove`, `note` | the staff coordinates form | staff |
| `take-observation-location` | `note` | "Use iNaturalist's location" | staff |
| `hold` | `lift`, `note` | the hold on the flags card | staff |
| `waiver` | `rule`, `remove`, `note` | the waiver on the flags card | staff |

For `edit`, a program sends only the fields it means to change, and a value equal to what the sample holds now is not a change: the answer is `unchanged` and nothing is written. That holds for `edit` and for a `locality` equal to the sample's own. The other corrections answer what their writer reports, and not all of them compare first: the same `coordinates` sent twice is saved twice, the second time rewriting the same point. (The page's form also sends `bases`, the values it was drawn with, so that a stale tab cannot undo a newer save; the API does not offer them, because a program has no stale form, and a `bases` field is refused as unknown.) `dry_run: true` on `edit` goes through the same rules in the same turn of the sample's queue and answers with the fields that would change, from what they are now to what they would be, and writes nothing: no corrections file, no change to the sample, no history entry. It answers `would_save`, and a repeat without `dry_run` saves exactly that. The other corrections have no step between working out a change and writing it, so there is no dry run for them, and a `dry_run` sent to one is refused with 400 and does nothing. Every endpoint also takes an optional `reference`, described under the record of use below.

*What it takes.* Each body is a JSON object of at most 64 KB. A field the endpoint does not take is a 400 naming it, and only the endpoint's own fields count (`toString` and `__proto__` are unknown like any other). Text ends up on printed labels and in the history, so a string with a control character (anything below U+0020, or U+007F, a line break and a tab included) is refused, a `values` string may be at most 500 characters and a note at most 2,000, and the 400 names the field. The same limits apply to every other string the endpoints take.

*Who acts.* A `read` key corrects nothing: it is refused 403 before the body is read or any sample is loaded. An `edit` key acts as its person with no staff rights, so it reaches that person's own samples and the staff endpoints answer 403. A `staff` key acts as staff for as long as its person is staff, asked on every request as for any staff key. It never acts for another person and never impersonates. Everything that decides who may make a correction is in the function, so a rule changed there changes the pages and the API together.

*Answers.* A correction that was made answers 200 with `sample_id`, `outcome` (`saved`, `removed` or `unchanged`, as the writer reported it; the pages ignore it), and where the function returns them `settled` (whether the county and state are now the point's) and, for `edit`, `changes`. A refusal is answered with `error` (its name) and `message` (a sentence): `not_found` and `not_editable` 404; `not_admin` 403; `printed`, `set_by_other`, `not_yours`, `only_offered`, `changed`, `busy`, `not_moved`, `no_staging`, `no_observation` and `unresolved` 409; `invalid` 422 with the problem; `unavailable` 503. The sentences are in one table in `src/app/api-corrections.ts`, and the switch over refusals ends in `unreachable`, so a refusal added to a function fails the typecheck until the API answers it. A body that is not a JSON object, a field the endpoint does not take (named in the answer, so a misspelt field is never taken for an absent one) or a field of the wrong type is 400, and a body over 64 KB 413. *Busy.* While the nightly run or the weekly sweep runs, the API takes no correction at all: all six are answered 409 `busy`, before the correction is called, and nothing is done. Those two jobs rewrite samples wholesale and are the main source of write conflicts. This rule is the API's. The pages are as they were, and the one `busy` the functions make (for a point) is unchanged.

*A write conflict.* A correction writes its file first (the corrections file for the collector's edit; the sample overlay for the other five) and then applies it to the store. A save does not retry on a write conflict ([Ingestion, jobs, and elevation](ingestion-jobs-and-elevation.md)). If the store write loses one anyway, the file already holds the change, and the next promotion applies it ([Editing and corrections](editing-and-corrections.md)). So the answer is 409 `recorded_not_applied`: the change is recorded, it is not yet visible, it will be applied the next time Beeline brings its records up to date (nightly), and sending the same request again applies it now without recording it twice. That is tested for each of the six: after a forced conflict and a second send, the store has the change, the file has one row for it and not two, and the history has one entry, under the key's person. What the repeat is not is conditional: like any correction it replaces what the sample holds when it arrives, so if someone else corrected the same field in between, the repeat puts the earlier value back over theirs. The API has no way to say "only if nothing changed" (the page's `bases` do that for a form, and the API does not take them), so a program that cannot rule that out should leave the change to the nightly, which applies the file as it then stands, the later correction included. (A conflict while the county and elevation of a moved point are being worked out comes after the point is stored; the same advice holds, the repeat finishing the derivation.)

*Order.* A program that needs two corrections applied in order waits for the first answer before it sends the second. Requests sent together may be applied in either order: each looks its key up in the store before it reaches the correction, and how long that takes varies, as the network's own ordering does. (An earlier version queued one key's requests to hide this; that made unrelated requests wait for each other, and a request whose body never arrived held up the key's next one, so it was removed.)

*The history.* A change made through the API is entered in the sample's history with the source `api`, credited to the key's person as an author, as a page's is to the signed-in person. The record page shows the author with "through the API" beneath. (The source labels are in the record page's message catalogue; the log file's header is unchanged, since a source is a value in a column and not a column.) The locality and take-location corrections store a reason built from the message catalogue, in one place both the pages and the API call (`src/app/correction-reasons.ts`), so the wording stored does not depend on the door.

**Which key did it** (`api_key_use`, `schema/012`). One row for each request under `/api/v1/` that is not a `GET` or `HEAD` and that a route answered, written by one middleware once the request has been answered: when, the key's SHA-256 (the `api_key` table's key, so a row traces to a key even after it is revoked), the method, the route pattern (never the path), a `subject` (the sample's id for a route under `/samples/<id>`, the job's name for `POST /jobs/<name>`), the `outcome`, the `reference` and the status. The `outcome` is what the handler answered, in its own words (`saved`, `removed`, `unchanged`, `would_save`, a refusal's name such as `printed` or `busy`, `invalid_request`, `recorded_not_applied`, `started`): a dry run, a save and a request that changed nothing leave the same status, and this tells them apart. It is empty where no handler said, such as a request that ended in a 500. The row is written whatever the answer was, so a refused request is traced too, but only for a request whose key worked: a request with no key, a key that does not work, one over its limit, or one to a path no route answers has nothing to record. Failing to write the row never fails the request; it is logged, a write conflict included, since a missing row is a gap in the trace. The rows are kept for good with no purge, as the sign-in records are: this is the trace from a change to a key, and it is one small row for each write request by a handful of key holders. A reseed carries them, with the `subject` of a sample route set to empty, because a reseed redraws sample ids and the number would name another sample (a job's name is kept).

**A reference to the request behind a change.** Each of the six endpoints, and `POST /api/v1/jobs/<name>`, takes an optional `reference` in its JSON body (the job start's body may be missing or empty, as before, and holds nothing else): a string of 1 to 500 characters once trimmed, with no control character; an empty one is none; anything else is a 400 naming the field. It is recorded in `api_key_use.reference`, a dry run and a refused request included, and goes nowhere else: the correction never sees it, it is not in the overlay or the corrections file, no page shows it, and the history entry's reason stays what it was. The trace is from the history entry (who, when, source "through the API") to the row for the same key, sample and moment, which says why. A good reference points at the request and is not it: the id of the message that asked for the change (`gmail:18c2f0a1b2`), or a link to the issue (`https://github.com/oregon-bee-project/beeline/issues/7`). Never an address or a person's name, since comments and exports of this store are public.

**Not in the API.** Reading samples and records (beeline-pnqr.2). Asking the store a question in SQL is deliberately not part of the API (Peter, 2026-11-13): it is a command on the machine, `pnpm store:query`, over `fly ssh` ([Backups](backups.md), beeline-pnqr.4), because a server that accepts SQL from the internet has one key between a stranger and a copy of everything, and the only people who need it already have a shell there.
