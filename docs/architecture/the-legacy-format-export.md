# The legacy-format export

Part of Beeline's architecture notes; the index is [README.md](README.md).

Reporting built on the legacy system's occurrences file — Andony's R comparison, the taxonomists' Ecdysis uploads — keeps working because Beeline writes that file too (`src/legacy-export.ts`, beeline-6q8, GitHub #107): every specimen, the legacy template's 63 columns in its order and then one of Beeline's own, `occurrenceRemarks`, the inventory's remark on the specimen where there is one (`specimen_disposition`, beeline-fud5; Andony's own 2025 master file carries the column under that name, and the comparison below rules it `expected`), csv-stringify's conventions (BOM, header, `\n`, quote only when needed, blank as nothing) and its composite_sort row order. The `legacy-export` job writes it nightly at 4am Pacific into `exportsDir`, and admins download it from `/exports`; DuckDB writes it with `COPY` because the corpus is ~160 MB. **Where a value comes from is a rule, not a column-by-column choice**: anything Beeline can change comes from the model — collectors, dates, places, coordinates, determinations, printing — so the file follows staff edits and Ecdysis determinations; what Beeline does not model at all (the legacy error flags, catalog numbers, resource links) is carried from the staged record of an imported specimen exactly, blanks included, and a Beeline-originated specimen gets the model's value where it holds the fact and a blank where it does not. **The rule of the file** (Peter, 2026-11-21): a specimen's record stays faithful to its old record unless the sample's data and judgment improve it. Tidying a specimen's record is fine; making the old sample records themselves clean is not the file's work. **The plant is the sample's for every specimen** (beeline-qpys, Peter, 2026-11-20): its floral host as the store holds it, whether it followed the sample's observation or staff set it, and whether or not old Beeline held the specimen, except in the two cases below where that would overwrite a truer specimen record. Old Beeline's own values stop being refreshed when it closes on 31 December 2026, while the store's keep changing, so the old record cannot be the usual source. The aim is to match the legacy file exactly (Peter, 2026-10-04), so a row describes one point: where it carries its own imported coordinates it carries that row's elevation and uncertainty too, never the sample's, since a sample that merged legacy rows taken at different points has one location and its elevation belongs to another place (beeline-en7i); a row likewise carries its own method, end date and place by name wherever the legacy rows of its sample disagree about them, since a sample holds one of each and one collector's sample 1 of 25 April 2019 was two specimens netted that day and three from pan traps emptied the next — read from the corrected rows, so a staff edit, which corrects every row of its sample, brings the model's value back (the method and dates, and the country, state and county staff correct, beeline-kgyd.4.3, which the comparison calls `staff_correction`; the collectors come from the model anyway, and where staff put another first collector on a record, beeline-kgyd.4.5, decided by person (the sample's first collector against whom promotion read the record's names as, so a renamed first collector is the same one), its login and user id are only the new first collector's, never the old record's own, which was the old one's; the comparison calls the name columns and initials that a collector correction moved `staff_correction`, and the login and user id too where the first collector changed), as does a locality override set on the sample, and a staff point on it for the country, state and county that went with the point (`sample_location_override`, beeline-kgyd.4.2; the comparison names those differences `staff_point`); where Beeline holds no volunteer identification, the volunteer columns are the legacy row's, and where it holds no expert one, the expert columns are (a determiner with no name, `L.R.Best` on 88 records, has no determination to live on); sex and caste are the expert's, so where no expert determination states them the old record's are carried only where it names an expert identification, because from 2023 the old Beeline wrote "male" on records nobody had identified as an entry default (24,434 on the store of 15 November 2026, of which experts in Ecdysis have since found half female; Peter, 2026-11-15, beeline-eznn); and while the legacy determination is still the record its subgenus is the legacy row's, since the tree files a species under its genus and the subgenus the determiner stated is held nowhere else (Peter, 2026-10-04). Legacy vocabulary is kept where it differs from the model's: `CA`/`NZ` rather than ISO alpha-3, several collectors joined with `" | "` in the name columns as the register wrote a shared login, a qualifier inside `scientificName`. `pnpm legacy:compare-export` is the done-test: on the 2026-09-27 corpus the open season differs in a few hundred values per column out of 61,400 records, and the settled seasons mostly where Beeline normalised (Roman-numeral months, `Male`) or filled what older records left blank (the higher taxonomy of 158,669 identified specimens). During the parallel run it is also the list of what nobody has explained yet (beeline-en7i): each difference gets a kind from its two values alone (`filled`, `case`, `date_form`, `country_code`, `subgenus_form`, `authorship`, … or `changed`), or from what the store knows where the values cannot say it — `collector_alias` (the legacy spelling of a collector that `ingest/collector-aliases.csv` corrects), `taxon_alias` (the same for a genus or epithet and `ingest/taxon-aliases.csv`), `subgenus_form` again where a genus column holds only `(Peponapis)` and the tree files it under the genus exported, `staff_correction` (the legacy row as staff corrected it, and the columns written from a date they corrected), `newer_determination` (an expert identification from Ecdysis or Beeline, and for sex and caste the newest expert determination that states one), `newer_volunteer_determination` (the same for a volunteer's, from a worksheet or made in Beeline), `sex_caste_vocabulary` (sex and caste as promotion reads the old pair: `Male` is male, a worker is female, Queen a gyne), `second_print` (an identification carried from the specimen's other old record, which the one-time repair tied to it), `repair_placed` (a held-back record the repair placed in its sample, whose values it takes), `reprinted` (a label printed again, whose print date is the newest printing's), `unidentified_sex_dropped` (the old default sex on a record no expert identified, no longer carried), `subgenus_dropped` and `coarser_determination` (what a newer expert identification lost: the old subgenus, or a species where the newest names a genus), `label_name`, `initial_from_surname`, `collector_order_contradicted` (a record whose recordedBy and name columns list its pair in opposite orders), `login_renamed` (the same iNaturalist user id under another login), `sample_disagreement` (promotion found the legacy rows merged into this specimen's sample disagreeing about that place field), the plant kinds described below, a record only one side holds is a difference about the whole record kinded by why — the blocking promotion finding that stopped it, or whether Beeline minted its number — and `ingest/legacy-export-rulings.csv`, written by hand and reviewed in git, says which are explained: by column, by kind, or one record by field number, or with no column for a kind wherever it occurs, the most specific ruling winning, with the outcome (`expected`, `reference-wrong`, `beeline-wrong`, `known-gap`), why, and where the call was made. The outcome follows one rule (Peter, 2026-11-15): the old Beeline is wrong (`reference-wrong`) where its value is false, a misspelling, a lower-case genus, an obscured observation's hiding point printed as its real one, a default sex; and it is `expected` where its value is true written another way, a capital in a login or a name, an initial without its full stop, a Roman month, a three-letter country code. A `beeline-wrong` ruling that matches nothing any more reports itself retired, so a fixed defect never hides behind a stale ruling. The legacy side is the staged pull, which Beeline also imports from, so this measures what Beeline does to the legacy records rather than two independent systems, and the report names the pull by a fingerprint of its rows; it runs from a workstation whenever someone asks, and nightly as the `legacy-changes` job (below), with no gate. Every difference, with the ruling that explains it, goes to `data/exports/legacy-export-differences.csv` for anyone auditing it — under `data/` because it names people. **It is now the ledger of what new Beeline does to the old records** (beeline-eznn): Lincoln Best kept his own list of corrections, never applied before cutover, so a three-way merge of the old records, new Beeline and his list is coming, and this is the second side of it. Audited against the production backup of 15 November 2026, it matched 396,307 records and found 1,371,180 differing values, every one ruled. Until then 7,281 records whose sex went from male to female had been put down to the sex vocabulary, and 7,270 of them were an expert's identification from Ecdysis since cutover; the vocabulary now has a kind of its own, applied only where promotion's reading of the old pair is what new Beeline wrote, and sex and caste follow the newest expert determination that states them. An independent review of the ledger then found most of those 2025 "male" values were an entry default (above), which the export stopped carrying, and that a newer identification's losses had been ruled as nothing more than newer: 2,420 subgenera and 6 species, now known gaps for the taxonomists to see. With those, the backup's 1,385,256 differing values are every one ruled.

**The plant** (beeline-qpys). Every specimen's plant columns are written from its sample's floral host as the store holds it: `genusPlant`, `speciesPlant` and `taxonRankPlant` from `sample.host_name_as_observed` and `host_rank`, and `familyPlant`, `orderPlant` and `phylumPlant` from the host's lineage in the taxon cache ([plant taxa](plant-taxa.md)), read from the host's current taxon and its ancestors in `inat_taxon_ancestor`. The form follows old Beeline's own, which `getPlantAncestry` in OBP-Server's `PlantTaxaService.js` built by keeping the ancestor named at each of five ranks (phylum, order, family, genus, species) and then the taxon itself at its own rank: a variety is `Nemophila menziesii atomaria` with no rank marker, a hybrid `Osmanthus × burkwoodii`, a host at genus rank has a genus and an empty species, a host at family or tribe rank has its family, order and phylum and no genus, and the genus of a section, complex, subgenus or subsection comes from the lineage. **Which taxon each column reads.** Genus, species and rank are the taxon as the sample stores it (the name as observed), and family, order and phylum are the lineage of its *current* taxon, so a host iNaturalist has since replaced writes its old name beside today's family (`Mahonia aquifolium` in Berberidaceae). A host that is only a name is read through the taxon the plant name lookups resolve it to (`sample_host`), and has a lineage when that taxon does. Where the cache cannot give the lineage (the host's taxon, or an ancestor of it, has not been read yet, it has no current taxon, or the host is only a name nothing resolves) the old record's family, order and phylum stand in, but only where the old record names the same plant, by the lowest rank it gives, so that a whole name in its genus column or an epithet alone in its species column still counts; otherwise they are blank, never one plant's genus beside another's family. `relationshipOfResource` is `near` for a trap with a host, as before; otherwise a value the old record gave stays (the numbers on the 2026 vane-trap records), except that an old `visits flowers of` or `near` is blank where the sample has no host, and a blank one is `visits flowers of` where the sample has a host. `resourceID`, `relatedResourceID` and `relationshipRemarks` stay the old record's, since the store does not hold them. **Where the old record's plant stands** (Peter, 2026-11-21). Two cases are no improvement, and the six plant columns are the old record's: (1) where the old rows promotion merged into a sample name different plants, each row writes its own old record's six plant columns and its own `relationshipOfResource`, by the rule above for method, end date and place (the plant each row names by its lowest rank, so two spellings of one plant's lineage are not a disagreement, and a row that names the sample's own plant in another form keeps the store's form of it); (2) where the old record names the same plant by name and the store holds it at a broader rank than the old record gave (a tribe, section or variety held as a family, genus or species, because promotion takes the rank of a host that does not follow an observation from whichever old column was filled) or has lost that it is a hybrid, the old record's plant is written; an old rank of a dash or blank says nothing finer, so the store's stands. In both a host staff set, or one that follows the sample's observation, wins. On the backup of 21 November 2026 that is 230 specimens: 189 of the first, 39 of the second and 2 hybrids. The comparison gives a plant difference the first of these kinds that fits: `staff_host` (staff set the sample's host, or said it has none); `not_a_plant` (the old record's phylum is not Tracheophyta, so its plant is not a vascular plant, a person, another animal, a moss or a fungus, and the store holds no host; on the backup of 20 November 2026 all 1,360 specimens of it were Homo sapiens); `taxonomy_moved` (the same plant in another family, order or phylum); `plant_form` (the same plant written another way, or the old rank blank); `host_follows_observation` (the sample holds the very taxon its observation names, and the file writes a plant: a plant that is gone, or a family, order or phylum that went blank, is not explained by this and stays unexplained); for the relationship, `visit_stated` (a blank filled from the host) and `claim_without_plant` (an old value of exactly `visits flowers of` or `near` with no host on the sample, which the file leaves blank; the old record claimed a visit and named no plant). A plant the old record named and the store dropped for some other reason stays unexplained, which is how a lost plant shows. On the production backup of 20 November 2026 the old records' Homo sapiens (1,360 specimens of 30 samples) were the only plants the store held none of.

**Staff read the ledger at `/exports/changes`** (`src/legacy-changes.ts`, beeline-eznn), written for Linc rather than for whoever maintains the comparison. Each difference goes on one line that says what new Beeline did, in a taxonomist's words ("Subgenus no longer given after a newer identification", "Two collectors written one way"), chosen by its kind and its column. The lines sit under seven headings: identifications, corrections staff made, what new Beeline cannot hold yet, names, specimens, collectors, and places, dates and other forms. Where an expert identification differs from a name old Beeline gave, it has a line apart from one that fills a blank (2,856 records against 17,118 on the backup of 15 November 2026), because new Beeline shows the identification it received last rather than the one made last: a name a taxonomist corrected in old Beeline after the earlier one reached Ecdysis shows as the earlier one, and those are the records a list of corrections must be checked against. The page also says when the export it compared was written, and how many field numbers it could not pair because one side holds them twice (one on that backup). Every line gives its records by program (below), the outcome of its rulings in plain words, three records to look at (each the first record of one of the line's commonest changes, linked to its specimen), and a CSV of every value it changed. The CSVs are one per line, not one per heading, because the higher classification filled in from the name is a million values (200 MB) and would bury the rest of the names. The line of records not carried over has no file of its own: new Beeline holds no value of theirs, so each row would say only that old Beeline had the record, and its button is the held-back page's download instead, with every column old Beeline held and why. The second records of a pin download as a map instead, each old field number beside the field number of the specimen it is tied to, since a correction naming the old number belongs to that specimen; and the specimens new Beeline numbered have no download, since no correction to old Beeline can name one. A test holds the lines to taking no kind in the same column twice, and to placing every kind and column found on the production backup of 15 November 2026 on a line that describes it. A difference no ruling explains goes on a line of its own, and one that no line describes goes on an `other` line, so nothing drops off the page. The comparison takes 25 to 90 seconds and about 1.6 GB of memory on one thread (it completes with DuckDB held to 768 MB, spilling to disk), so the page never runs it. The `legacy-changes` job runs it each night after the export, on one thread, and writes the CSVs into a new folder of the night's own under `<exportsDir>/changes/` and then `summary.json`, which names that folder and which the page reads, so the counts on the page and a file downloaded from it are always one night's, even after a night that fails part-way; each download link names its night, and the job keeps the night before's folder for anyone who loaded the page before the run, removing only older folders named as it names a night. Building the page also corrected the ledger: a second print that the one-time repair tied to a specimen still carries promotion's blocking finding, so the comparison had counted all 235 of them as held back. It now gives them a kind of their own, `tied_second_record`, which leaves 188 field numbers held back: the 99 records the held-back page lists, and the 89 field numbers of its 177 bare records.

**The same rows go back into the old Beeline** (`src/legacy-copy.ts`, beeline-83b8.18). The old Beeline stays open at old.melittologist.org for volunteer determinations through December 2026, and its screens show only its own master list, so the `legacy-copy` job copies there, nightly at 4am Pacific, every specimen a print run here printed and that was not imported from the old system, which holds those already (one, reprinted here under its old number, it holds under its own record). The determinations volunteers enter for them come back by beeline-c43w. Each copy is the export's row for the specimen, its 63 template columns: on the store of 7 November 2026 that filled every column the old system's own printed 2026 records fill except those Beeline does not hold (the OSAC `occurrenceID` and `resourceID`, the observation's UUID in `relatedResourceID`, and, until beeline-qpys, the plant's phylum, order and family, which the copy now fills from the host's lineage where the taxon cache holds it), none of which its determination screens read. It goes **through the old system's API, not its database**: `POST /api/occurrences` as an admin upserts each record by `_id` and sets only the fields it is given, and the old server's repository computes on every write the `composite_sort` and `date` fields its screens sort and filter by, which a direct Mongo write would have to copy exactly; the API is also reached over HTTPS with a login, where Mongo needs a root SSH key to the old host. Its working-file upload is no alternative, since reading that file in deletes every occurrence first. A copy is keyed `beeline-specimen-<entity_id>` rather than by the old system's hash of sample, specimen, date and link, so a corrected date or a duplicate repair's second field number updates the same record, and so beeline-c43w can tell a record that started here from one the old system made. Whether a record is new is read from the old system before each batch, by the field number it holds now and the one last copied (`legacy_copy`, schema/035), and **the five volunteer columns are written only where the old record has none**, so a volunteer's entry there is never overwritten; an update sends only volunteer values that say something, since a volunteer can save between that read and the write, and a blank sent then would erase their entry. Each batch is read back and a specimen recorded in `legacy_copy` only when the old system holds what was sent, since the old server's reply counts go null whenever a batch makes a new record; an unchanged row is not sent again, and a field number the old system holds under another record is not sent at all and fails the night. Batches stop at fifty records or 80 kB because the old server reads JSON bodies up to Express's default 100 kB. The copy compares Beeline's row with what it last sent, not with what the old system holds, so a record the old system rewrites itself is put right only by `--all`. **The legacy-format export must never be uploaded into the old Beeline**: its upload keys each row by its own hash, and would make a second record beside the copy under the same field number. `pnpm legacy:copy [db] [--dry-run] [--all]` runs the same from a workstation; the login is `OLD_BEELINE_USERNAME` and `OLD_BEELINE_PASSWORD` ([deploy-fly.md](../runbooks/deploy-fly.md)), and without it the job fails in production. **Since beeline-qpys that copy sends the plant too.** A row whose content changed is sent whole, apart from the volunteers' five columns (above), so the next copy after the change updates every specimen minted in new Beeline whose sample has a host: at most 2,180 specimens in 388 samples, all in the active season, on production's copy of 2026-11-20. A lineage the taxon cache holds incompletely for a night (a taxon or an ancestor not read yet) blanks the family, order and phylum of those rows in the old Beeline for that night, and the next copy writes them back.

**The volunteers' determinations come back** (`src/legacy-volunteer-import.ts`, beeline-c43w). The only thing that changes in the old Beeline until it closes is its five volunteer columns, so the `legacy-volunteer-import` job reads them nightly at 1am Pacific, through the same API and admin login as the copy, and records each change as a `legacy_import` determination made by the person promotion read the old record's own names as, who is whom promotion credited, and for a copy the specimen's first collector: read from the record and not from the sample's collectors as they stand, so a first collector staff corrected since (beeline-kgyd.4.5) does not take the credit (on production's store of 18 November 2026 the two give the same person for all 72,918 records with a volunteer determination; the record's own login would have moved the credit of 2,426 of them, which are filed under someone else's login); the night it was read is its `recorded_at`, since the old system keeps no time of change, and a determination made the same day in each Beeline is ordered arbitrarily (Peter, 2026-10-31). It runs in production rather than on a workstation over SSH (Peter, 2026-11-09): the import has to run where the store is held anyway, and production already holds the login. The API selects records whose column is non-empty, so it reads only the 73,000 records naming a volunteer family, genus or species, in three selections that do not overlap; a record naming only a sex could not become a determination. Each record's columns come apart by promotion's own rules, the macros of `ingest/parse-names.sql` and the sex and caste words of `ingest/promote-determinations.sql`, which promotion left in the store; the views that apply them read the staged rows by name, so their few lines of CASE are repeated, and a test holds the two to the same answer on every one of the 372 combinations of the five columns the old system held at cutover. A record is matched to its specimen by its `_id`: through `legacy_specimen_map` for a record the old system made, through `legacy_duplicate_record` for a second print the repair below tied to its specimen, and through the specimen id in the key for a `beeline-specimen-` copy. It is compared with the newest `legacy_import` volunteer determination of the specimen, not the newest of any kind, so the old record, which still says what it said, never overrules a determination made since in this Beeline. A copy needs one more rule, because the copy writes this Beeline's own volunteer determination into an old record that has none: a value read back from a copy is new only if Beeline holds no volunteer determination saying the same of that specimen, which misses only a volunteer going back in the old Beeline to a name they had given here. Names the tree lacks, specimens two old records describe differently, records promotion did not take (108 of them on the store of 9 November 2026, all but one of them second prints, before the repair below) and determinations cleared in the old Beeline, which no determination can say, are listed in the run and not recorded; a night on which more than one in a hundred of the old system's volunteer determinations seem to have vanished records nothing and fails, as the old system answering wrongly. Fed the old system's records as they stood at cutover, a dry run against the production backup of 9 November 2026 recorded nothing and matched all 72,918 legacy volunteer determinations, in half a second. `pnpm legacy:volunteer-import [db] [--dry-run]` runs the same from a workstation.

**What promotion set aside was repaired once, on the live store** (`src/repair-legacy-skipped.ts`, beeline-iuva). Promotion takes two old records with the same collector, date, sample and specimen number for one pin printed twice and keeps the later print, or, when both claim the same print date (most say 31 December), the higher field number; on the store of 9 November 2026 that had often kept the record nobody identified. But the test looks at nothing else, and many such pairs are not one pin: one collector's sample 1 of 8 August 2019 was both netted (1925139 onward) and pan-trapped (2121499 onward), and the expert identified 1925139 as a drone and 2121499 as a worker (found by an independent review of the repair). So the repair acts only on a pair that looks like a reprint, the same method, recorded within a kilometre, no sex or caste stated on both that differs, and no two experts who named different bees; on its first run that left 144 of 258 pairs tied to nothing (but see below). The last rule once made the set-aside record of such a pair a specimen of its own, until it was found to add a fourth bee to sample 103780, whose observation says it holds the three Beeline has. Since production is never rebuilt, `pnpm legacy:repair-skipped [db] [--dry-run]` mends the rest in one transaction: each set-aside second print of a reprint gives its specimen the expert or volunteer identification the specimen lacks, read by promotion's own name rules (its views are copied for the transaction, reading the set-aside records), and is recorded in `legacy_duplicate_record` (schema/040) rather than `legacy_specimen_number`, which the export reads as one record per specimen and would print the specimen twice; and a record refused only for its date, on an iNaturalist observation that is a sample, and the only one, with no specimens and the same collector, becomes a specimen of that sample, whose date is the observation's. On that store the repair ties 114 records and carries 18 expert and 6 volunteer identifications, and gives the net sample of observation 56359335 (2 August 2020; its old records say 2 August to 1 August) its 34 specimens. Which of a pair's field numbers is on the pin it does not decide, since that takes somebody looking at the pins. A second run finds nothing to do, and a store promoted afresh, which only a development store can be since production has printed, needs it run again. A specimen with more than one set-aside record would stop the repair before it wrote anything, since two identifications could then disagree with nothing to say which stands; none had.

**What the repair could not settle, it says on the specimen** (GitHub #303). The 144 pairs, the reprints whose identifications were entered under the other number, and 82 records refused for a missing collector, sample number, specimen number or date went to Andony as questions, and his answer was to say what is in doubt where a taxonomist will read it and move on. A second run of the repair, after its first on production, does that, and two things an independent review found on 12 November changed what it ties first. A different method is not a difference where the kept record cites an iNaturalist observation whose own method is the set-aside record's and whose count is both no more than Beeline holds and exactly the number of set-aside records of that method, a whole second printing of the sample: the old Beeline wrote "aerial net" on every print it made from an observation, and Pat Wheeler's six pan- and vane-trap samples of 2021 were each printed twice, once that way and once with the trap and the identifications (sample 26 of 16 April 2021: observation 93297897 says pan trap and 9 bees, 2127318 to 2127326 say aerial net, 2127003 to 2127011 pan traps, at the same coordinates). So 98 of the 144 are reprints after all, tied and carried. A second independent review then found that coordinates differing only where one record gives a whole degree are one place, not two: Mark Gorman's 2039536 says 44.227, -121 where 2040640 says 44.227, -121.452, "36 km" away, and his 2039541 rounds -122.854 to -123. Peter decided these are reprints too, which ties his 10 pairs and Andony Melathopoulos's 4. And a refused record that names its collector and leads to exactly one sample, through its observation or through records Beeline holds of the same collector and sample number on one of its dates (or in its year and month, where its date is incomplete), is either a second record of a specimen of that sample, tied and carried like a set-aside print, or a specimen of it. It is a second record when its specimen number, or failing one the last part of a 2017–2018 field number such as `Nicole_Sanchez:17.006.006`, is one a record of the sample already carries; nine 2018 entries of Nicole Sanchez's 2017 specimens are that, five of them the only place the expert's identification was entered, and because such an entry is bare (no method, place or coordinates) it is tied unless it contradicts the specimen's record, rather than only if it agrees. It becomes a new specimen when its number is free, or, with no number, when records of the same collector and sample number lead to the sample and it counts more specimens than Beeline holds; an observation alone does not place a record with no number, since three of the four it led to were bees later printed under another sample Beeline holds (1905675 is 1924481, its month mistyped).

The remark, in `specimen_disposition` and so in every export as occurrenceRemarks, is credited to Beeline rather than to a person, and is one of three kinds. On a specimen whose old records include another with its numbers that may be a second bee, it names that record's field number, how they differ and what it was identified as. On a reprint, where the identifications were entered under the number Beeline does not use, the method differs, or the coordinates differ by a whole degree, it names both numbers and says which: the other record's method and dates where the observation agreed with them, since the sample Beeline holds still says what the kept copy said (Pat Wheeler's six samples, which Beeline published as netted on one day, are corrected by staff from the sample page's Method row, beeline-p8y1, [Editing and corrections](editing-and-corrections.md)); the two points where they differ by a whole degree; and that the identified number is probably on the pin. On a second entry of a refused record it says only that the identification was entered there. On a placed record it says which detail was missing and what was assumed. On the store of 12 November 2026 the run ties 121 (98 trap reprints, 14 whole-degree reprints, 9 second entries), carries 91 expert and 95 volunteer identifications, places 7, remarks on 184 specimens (144 reprints and second entries, among them 8 of Mark Gorman's tied on the first run whose coordinates differ by a whole degree; 33 that may be a second bee, one of them the refused 2010834; and 7 placed), and leaves out 65 of the 82 refused records #303 listed, 10 of them identified, eight of those because their iNaturalist observation never became a sample in Beeline. A specimen that already has a remark from elsewhere, such as the 2025 inventory, is left as it is and named in the output, and `pnpm disposition:load` holds an inventory row rather than replace one of these remarks.

**What is still held back is listed for staff** at `/exports/held-back` (`src/app/held-back.ts`, beeline-cel0), because Lincoln Best asked to see which old records were not carried over and why. A staged record is carried over when it has a number in a sample (`legacy_specimen_number`, which the repair writes too for the records it placed) or is tied to a specimen (`legacy_duplicate_record`); every other record is held back, and its reasons are its blocking rows in `legacy_promotion_finding`. The page reads the table rather than `legacy_specimen_map`, which joins it to `specimen` by number and would lose a record whose specimen was renumbered. Where the repair wrote a remark naming the record by its field number, the page shows that specimen and its remark beside it: on the production store of 13 November 2026 that is every one of the 32 records held back as a second print, each of which the repair judged may be a second bee. That store held back 276 records, all from settled seasons: 177 hold nothing but a field number (25100000 to 25100089, most staged twice), which the page counts rather than lists, and 23 of the rest carry an identification. A record is called a second print only where a record that was carried over has its collector, sample, date and specimen number, because promotion also ranks records with blank numbers against each other, and so had called every bare record a second print of another. Where a record cites an iNaturalist observation that is a sample in Beeline, the page names the sample with the count it states and the specimens it holds: on that store 29 records did, and 7 of their samples hold fewer specimens than they count, which is where such a record may belong. The counts are by program, not by season, and the records are listed under a heading for each program in field-number order. A CSV carries every held-back record with all its staged columns, the reasons in the page's words, the note, the sample and `beeline_program`. The page reads the store in one pass, 0.6 seconds on that store, and says so plainly on a store with no staging, since the views it reads are promotion's and not the schema's.

**A record a correction in git makes whole is carried over** (`src/carry-over-legacy.ts`, `pnpm legacy:carry-over [db] [--dry-run]`, beeline-n7gt). Promotion reads `ingest/legacy-corrections.csv` only when it builds a store, and production is never promoted again, so a correction added to the file since cutover would never reach it. The command, run like the repair above against a store the app is not holding, does in one transaction what promotion would: it adds to the store's `legacy_correction` table every row of the file the table lacks (a record and field an in-app edit already corrects is left alone, the app winning as in promotion), and then makes a sample of every held-back record no blocking finding holds back any more, grouped by collector, sample number and start day, with the record's place, method, dates, point and elevation as `legacy_import`, the atlas of its state, its collectors through the curated aliases, its field number as printed and its `legacy_specimen_number` row. It refuses a group, and says why, where it would have to decide something promotion decided with more evidence: a sample of that collector, number and day already exists, another record of the sample is still held back, a field number is already a specimen's, the records disagree, a record cites an iNaturalist observation, names a plant or carries an identification (none of them carried over yet), or a collector has no person in Beeline. A row of the file for a record already carried over is listed and not added, since that record is corrected on its sample's page. A test holds what it makes to what promotion makes of the same corrected records. It was written for two groups whose end date was written before the start (Peter, 2026-11-15): Lincoln Best's trap sample OBAS-01087, 18 records written 19/8/2018 to 23/7/2018 at the point of Big Lake where his LRB19S-14 ran 19 to 23 August, so the month is mistyped; and Paul Moschetti's sample 13, 2 records written 17/6/2019 to 8/6/2019, whose other trap samples that year ran one or two days and whose samples are numbered in date order (12 on 17 June, 14 on 28 June), so the end is 18 June. Either reading can be corrected afterwards on the sample page, since staff correct the dates of a sample without an observation there ([Editing and corrections](editing-and-corrections.md)). A dry run against the production backup of 15 November 2026 adds the 20 corrections and makes the two samples with their 20 specimens.

Each program's Data tab (`/programs/<code>/data`, beeline-q8di; [programs.md](programs.md) says who may open it) lists a Darwin Core archive for each of its calendar years, and `/exports` links to every program's tab (`src/app/dwc-archive.ts` the format, `src/app/program-archives.ts` the writer, beeline-rvun): the specimens CSV's columns with a column list of its own (`ARCHIVE_DWC_COLUMNS`, so a change for Ecdysis and GBIF never moves a column in a download that people load back), tab-separated behind a `meta.xml` that declares only the terms. **Its numbers follow Darwin Core's definitions, which the download's do not** (Peter, 2026-11-18): `fieldNumber` is the sample's number, `recordNumber` is the specimen within the sample as `<sample>.<specimen>` (as Joel Gardner's uploads write it), and `catalogNumber` is the one Ecdysis reported, else the program's catalog prefix from `ECDYSIS_COLLECTIONS` (`src/fetch-ecdysis.ts`) followed by the label number, else empty; a specimen with no label number gets no made-up catalog number. That fallback is the archive's guess at the number the museum will assign; `specimen_catalog_number` still holds only what Ecdysis reported. The label number is therefore not written under its own name in the archive; `sampleNumber` and `specimenNumber` stay as undeclared columns. **`geodeticDatum` is `WGS84` for every point**, in the download too, because GBIF's parser rejects `unknown`. **The occurrence row carries the higher classification** (kingdom, phylum, class, order, family, genus and, where the tree has one, subgenus, from `classificationsByAnimal`: one recursive query over the animal tree, made once per run of the job and looked up by the animal id of each specimen's determination of record, which the listing's row carries; beeline-t54r) **and the determination of record's `caste` beside its `sex`**, both declared; `identification.txt` declares each determination's own `sex` and `caste` too (Peter, 2026-11-20: they are part of an identification), and only `identifiedByExpert` is left undeclared there. Every determination of each specimen in the Identification extension — the history `determination_of_record` flattens — with Symbiota's `identificationIsCurrent` (1 or 0) on each, since without it Symbiota imports every identification as not current. The `dwc-archives` job writes them nightly at 4am Pacific into `<exportsDir>/dwca/` beside a `manifest.json`, **every program-year with specimens, so staff can download and review them** (Peter, 2026-10-23; until then one was written only when its program had both a licence and a privacy policy in force for it, which with no policy yet meant none was). A year is the calendar year a sample was collected in, by its first day, because that is how the taxonomists count (Peter, 2026-10-23); since beeline-rxn8 that is also what a season is (CONTEXT.md), so an archive holds one season. Until then the season ran from 1 March and was judged by a sample's last day, and 266 samples on the dev store fell in different years in the archives and everywhere else. A year is ready to *publish* only when its program has both, and the page says how far each has got. Those are decisions curated in git, `ingest/program-licenses.csv` and `ingest/program-privacy-policies.csv` (`src/program-governance.ts`): each row holds from its year (`from_year`) until the program's next row and the latest holds indefinitely — Peter's presumption that a program continues with the licence it last used — so ranges cannot overlap, and a year before a program's first row has none. Licences are the three GBIF accepts, written into `meta.xml` as a constant `dcterms:license` where one is in force and left out where none is; the seeded rows are the licences each atlas's records were last published under on GBIF, with the dataset as the source. The privacy-policy file starts empty, so for now no year is ready to publish. The program's Data tab lists every program-year the last nightly run wrote (the years and counts are the manifest's, so a year that first gets specimens today appears after tonight's run) with its licence and policy, which are read live from the decisions as they stand, and a download of its archive; the upload to Ecdysis on the same tab reads its years live; an archive whose year no longer has specimens is removed at the next run, and a manifest from before the archives were cut by year is read as no manifest. Which specimens are a program's follows CONTEXT.md's rule with no collecting events yet: an atlas's are those collected on its ground, Master Melittology's those no atlas covers. **The BLM surveys get no archive, and must never get one by geography**: their samples will arrive through their own pipeline (field entry, and the collecting event that says whose day it was), so a BLM sample from New Mexico is BLM's, not the New Mexico Bee Atlas's — when that lands, the archives select by the sample's program rather than by where it fell. The page says not to upload them: which identifier Oregon's records are published under, OSAC's or none (beeline-1kb.22; Beeline mints no `occurrenceID`, per ADR 0008's second amendment), and how Beeline holds a publication embargo on particular records (beeline-bqvp) are undecided. The archives, like the other files staff download and send on, carry true coordinates, a rare host plant's included, until an atlas says otherwise (Peter, 2026-11-20). A year is the grain Beeline produces and checks at, not the grain to publish: a program should publish one dataset that grows, since a dataset per year is republished by the next cumulative one — every record of Oregon's 2018 and 2019 datasets is on GBIF twice — and GBIF gives a dataset one licence ([docs/research/program-governance-for-exports.md](../research/program-governance-for-exports.md), which also holds what a privacy policy must answer and how others record an embargo). Which volunteer determinations go downstream is not among them: each atlas's staff decide that after downloading, outside Beeline (beeline-pyr). **Beside each program's years is its checklist** (`src/app/dwc-checklist.ts`, beeline-024a), every year together: Darwin Core has no Taxon extension for an occurrence archive to carry, so the names are a second archive with Taxon as its core, one per program because a checklist says what somebody recorded (Peter, 2026-10-26). It holds the names the program's specimens are identified to by determination of record, the identification the occurrence archive carries, with their ancestors so the classification is whole, in `/taxonomy`'s order and with kingdom to genus on each row; `taxonID` and `parentNameUsageID` are `entity_id`s, by the occurrence archives' rule. Ecdysis's id, its standing and the name it files a synonym under are Beeline's own columns rather than `taxonomicStatus`, since the tree is the program's classification and a name Ecdysis calls a synonym is still the name the specimens carry; so are the program's specimens at and below each name, how many of them an expert identified, and the first and last year. It states no licence, because licences are decided a year at a time and a checklist spans every year. **And each program has an archive of every year together** (`<code>-all.zip`, beeline-9bnm), for whoever wants the whole record in one download rather than one per year (Lincoln Best, 2026-11-13): the same format as a year's, written by the same job after the years. Because licences are decided a year at a time, it states a licence only where every year it holds has the same one in force (`sharedLicense`), and none where they differ or any year has none; on the decisions of 13 November 2026 that is Oregon's (CC BY-NC 4.0 from 2017) but not British Columbia's or Washington's, whose early years have no licence. The page reads that from the decisions as they stand, as it does for the years, and says where the file states another. It roughly doubles the job's writing, since every specimen is written twice. Its `id` is the specimen's `entity_id`, which joins the two files and which Symbiota keeps as the record's key; a rebuild redraws it, but only the sandbox is rebuilt, and no archive the sandbox writes will be uploaded anywhere (Peter, 2026-10-10).

**Both pages count by program, not by season** (`src/legacy-program.ts`, beeline-z0pi; Peter, 2026-11-20). This is a deliberate exception to the rule that every check count is split by season (AGENTS.md, [reporting-counts.md](../agents/reporting-counts.md)): the pages describe old Beeline's records as they stood at cutover, and no season was in progress then, so an active/settled split tells the reader nothing ("these features pertain only to cutover. The current season is not 'in progress', so it is not special", Peter). A record new Beeline carried over is in the program its sample files under (`sample_atlas`), reached through the specimen with its field number; a second record tied to a specimen is in that specimen's. A record new Beeline does not hold is in the program of the sample its iNaturalist observation is in Beeline, else of the atlas `atlas_region` assigns to the `stateProvince` it wrote. Under no atlas is At large, the word the listings use; a record that writes no state and has no sample is in a group of its own, No state written, which a page shows only where it has records. Programs are named by `program_abbreviation` (WABA, where the code is WaBA) and ordered as the program table is, then At large, then No state written. The comparison (`src/compare-legacy-export.ts`) carries a `program` column beside its `active_season` one, which its own command-line report still reads; the pages read only `program`. `summary.json` names its `programs` and gives each count as a map from program to records; a summary written in the old shape names none, so it is read as missing until the next night's job writes a new one. Each line's CSV has a `program` column where it had `season`.
