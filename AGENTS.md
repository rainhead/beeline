# Project Instructions for AI Agents

This file provides instructions and context for AI coding agents working on this project. (CLAUDE.md is a symlink to this file.)

## Build & Test

```bash
pnpm install
pnpm test                      # vitest, against in-memory DuckDB
pnpm typecheck
pnpm db:build [target.duckdb]  # blow away and rebuild from schema/*.sql
pnpm db:migrate [--status|--check|--baseline] [db]  # bring a deployed store forward (ADR 0006)
pnpm db:reseed <old.duckdb> <new.duckdb>  # re-derive a deployed store: fresh schema + its staging, then re-promote
pnpm app:dev                   # web app: tsx watch + vite build --watch (islands)
pnpm app:build && pnpm app:start  # web app, production shape
pnpm bench:pages [store]       # page latency against a copy of a store; --compare=<result.json> (bench/README.md)
pnpm bench:contention [store]  # pages, edits and the nightly overlapping: latency, and conflicts counted apart
```

Populating a fresh database end to end (production access = `beeline` in
`~/.ssh/config`; iNat access = dev OAuth credentials in `data/secrets/`):

```bash
pnpm legacy:fetch && pnpm legacy:load && pnpm legacy:promote  # production Mongo → model
pnpm inat:login                             # OAuth sign-in; mints the 24h JWT sync reads
pnpm inat:sync <projectId> [d1] [d2]        # observation window → append-only loads
pnpm inat:promote                           # current observation state → samples
pnpm inat:backfill-accounts                 # resolve legacy logins → iNat accounts
pnpm elevation:fetch && pnpm elevation:derive  # DEM tiles (SRTM 1-arc-second, Copernicus GLO-30 where SRTM does not reach) → missing elevations
pnpm itis:fetch && pnpm itis:load            # ITIS release (224 MB) → the insects in data/itis/ → itis_taxon, every animal node matched
pnpm taxon:fetch-sheet <sheet-id> [dir]      # a taxonomist's worksheet, every tab as CSV, to data/taxon-decisions/<modified instant>/ — to be read, not parsed
pnpm taxon:decide <kind> <rank> "<name>" --by … --reason …   # record one decision (or --batch file.csv): the ITIS facts filled from the store, the row validated, the file merged
pnpm taxon:apply [db]                        # replay ingest/taxon-curation.csv onto a store: the program's departures from ITIS, and what a new release moved from under
pnpm legacy:export [db] [out.csv]            # every specimen as the legacy occurrences file (the app writes it nightly)
pnpm legacy:compare-export [db] [export.csv] # how far that file is from the staged legacy records, by column and kind, by season, less what ingest/legacy-export-rulings.csv explains
```

## Architecture Overview

### Store and schema

The schema **is** the `schema/*.sql` files, applied in filename order (0xx tables, 1xx derived views). Databases are blown away and rebuilt before cutover ([docs/roadmap.md](docs/roadmap.md)); the ones that can't be — the sandbox, production later — catch up through `migrations/NNNN-slug.sql` and `pnpm db:migrate`, recorded in `schema_migration` and stamped (never run) on a fresh build ([ADR 0006](docs/adr/0006-migrations-for-deployed-stores.md)). QC rules, printability, and determination-of-record are SQL views, not app code. Engine: DuckDB behind dialect-neutral SQL — [ADR 0001](docs/adr/0001-duckdb-first-with-portable-sql.md).

### The app process, and its gate

The web app (`src/app/`) is the process that owns the database — [ADR 0005](docs/adr/0005-app-process-owns-the-store.md): Hono with `hono/jsx` SSR views, Lit light-DOM islands built by Vite, MD3 color tokens generated from a seed (`src/app/theme/tokens.ts`), every route session-gated by construction — and the gate remembers the URL it refused, so signing in lands you on the page you asked for rather than home (same-site GET paths only, carried in a short-lived cookie beside the OAuth state, beeline-2c3.31); `/design` is the design system (component library in `src/app/views/components/`, stylesheets split `elements`/`layout`/`components` under `src/app/static/`, every section rendering live from the real tokens), offered only to admins but not gated — it reads no records, so walling a curious volunteer out of it protects nothing; the reason it is not offered to them is that it is not their tool — and `/glossary` is its volunteer-facing counterpart. The header nav carries only the records people work through, `/samples` and `/specimens`; everything else a person can open — the glossary, the taxonomy, the staff tools — lives in the menu left of the brand, grouped by what it is for rather than by who may use it, and each item is shown only to whoever may open it (beeline-45v.5); on a phone the records collapse into it too. Beside it, in the header itself and never in a menu, is "Send feedback": a mailto to `BEELINE_FEEDBACK_EMAIL` (no address, no link) pre-filled with the page, the time, the browser and the session — the session as the first 12 hex digits of its id's SHA-256, since the id is the bearer credential and an email carrying it would let whoever read it sign in; `sha256(id)` in the private store finds the row. The account menu is for the person signed in and their own things — signing out, acting for someone, and later their mailing address — and never a place to find pages. Every response carries a Content-Security-Policy and its companion headers from one middleware registered first (`src/app/security-headers.ts`, beeline-m9o): same-origin scripts, styles, fetches and forms, iNaturalist's static host for the avatar, no framing, and inline `style=` attributes allowed while inline `<style>` and script are not; the Referrer-Policy keeps a same-origin referrer because the error page's way back reads it. Auth is iNat OAuth; sessions and sign-in records (`inat_sign_in`, which held volunteers' OAuth tokens until those were dropped and is kept with no purge, beeline-cj6/zg4) live in the attached private store ([ADR 0003](docs/adr/0003-private-data-store.md)), whose schema is `schema/private/*.sql`, applied by the app at boot when missing — a renamed table is renamed in place before that, and every `COMMENT ON` that differs from the DDL is rewritten, since applying a file only to a missing table never carried a corrected comment to a deployed store.

### Browsing: scope, filters, sort

Browsing lives at `/samples` and `/specimens` (`src/app/listings.ts` + `src/app/views/listings.tsx`, beeline-2c3.21): the same paged table at two grains, with scope, filters, search, sort and page all in the query string so a filtered listing is a shareable URL, and a CSV of exactly what the filters select — in Darwin Core terms wherever one exists (the pin's number is `catalogNumber` per ADR 0008, the sample number `fieldNumber`), UTF-8 with a BOM, `\n` line endings, and streamed whole a page at a time, so it has no cap and no line that is not a record; a numeric cell is never formula-guarded, since a guarded longitude is `'-123.26`, text. Reshaped with Peter and Nora on the sandbox (2026-09-16): each column heading opens a menu holding that column's two sort orders and its filter — a listing *describes* its columns as `TableColumn` specs and `DataTable` draws them, through the one `ColumnMenu` in the component library (the header's `<details class="menu">` with the panel fixed so the wrapper's sideways scroll cannot clip it), so every menu wears the same chevron, the order in force is a separate arrow with `aria-sort` on the heading cell, and no screen can draw a heading differently from the next; it was written out twice at first, for the listings and for People, and the two had drifted within a day (Peter, 2026-09-17) — whose form carries the rest of the query as hidden inputs (`listingParams` is the one place the query becomes a query string, so hidden inputs and hrefs agree); what is in force reads off a row of dismissable pills, not off ten controls. Above the table sit the search box and, for staff, a three-way toggle — my records, my atlas's (from `person_membership`), all — with other atlases and the ground outside them reached through the Atlas column and shown as a pill. There is no season filter: the dashboard's link to settled seasons names a date, the day before `season.started_on`. A record's number is a pill, the iNaturalist link is the wordmark, the host plant is a column on both listings, the specimens listing also carries the date the determination of record was made — an order and no filter, since "what came back from the taxonomist this winter" is asked by sorting, and a dash where the source gave no date, which is most legacy determinations — and on a wide screen the heading row is sticky — which needs the wrapper to stop being a scroll container, since sticky positions against the nearest one, so `main > .table-scroll` is `overflow: visible` from 64rem up. A session is keyed by `inat_user_id`, never by `person.entity_id`: that is a per-store sequence draw a rebuild or `db:reseed` redraws, so a session holding one resolved to whoever inherited the number and a volunteer browsed as somebody else under the `mine` scope forced for them (beeline-ten). The person is resolved through `inat_account` per request, which also makes unbinding an account end its sessions and rebinding move them. A private store predating that change is repaired at boot — it outlives the blow-away era, so its schema changes are patched in `src/app/db.ts` rather than by rebuild, per table rather than all-or-nothing, because a store that holds some of its tables and not others is a state that patch itself can create. Resolution failing is not revocation: an unbound session stops sliding its `last_seen_at` so the idle cutoff never reaches it, and rebinding that iNat user would revive every cookie ever issued for it as whoever now holds the account — so `endSessionsFor` runs on both sides of an account change and the idle purge collects orphans. Scope is `mine` (the only one a volunteer has, forced at parse time), one atlas, `outside` (collected where no member atlas reaches), or all of them — staff being the admin allowlist until a per-atlas role exists. Scope asks where a sample fell; a separate staff-only `member` filter asks where its collector belongs, and the two genuinely disagree — most records from outside the atlases are members travelling (beeline-lcl). Exports carry coordinates with their provenance and geoprivacy beside them: the open per-atlas question ([docs/questions.md](docs/questions.md)) is about revealing taxon-obscured coordinates *downstream* — on labels, to Ecdysis and GBIF — not about showing a participant their own data, and CONTEXT.md's stance is that anyone trusted with this store is trusted with them. Dashboards scope to the open season: from 1 March the previous season is settled (`season`/`settled_sample`), still flagged and still fixable but no longer asking.

### The front page

`/` is one table (`src/app/dashboard.ts` + `src/app/views/qc.tsx`, reshaped with Peter and Nora on the sandbox, 2026-09-16): the person's samples that want something — a flag to fix, labels still to print — and the observations they numbered but left at 0 specimens, which minting refuses (`observation_sample_candidate`) and which are on the page for exactly that reason: a placeholder made in the field is what a volunteer forgets to fill in. Beside those are the observations in the project with their sample number left blank (`observation_unnumbered`, `schema/109`, beeline-a04): the three synced projects require `sampleId` to join and accept it empty, so `observation_field.sample_number_field_attached` keeps "attached but blank" apart from "absent", which `sample_number_raw` cannot. Their notes are quoted back, since some volunteers wrote the number there, and are never parsed for one: '1C red cuckoo' is why. Below the table, advisory, is the list of days whose run of sample numbers skips one (`sample_number_gap`, beeline-virz), each linked to everything the volunteer observed on iNaturalist that day, in the project or not. Numbers restart every collecting day, so a gap is judged per day, and only for collectors who number that way. A jump of more than three starts a second run (`1, 2, 3, 101, 102`) rather than counting as missed samples. A day whose unnumbered observations account for its missing numbers is left out. A flag names the column it is about — sample, place, coordinates, host plant, specimens — and that cell is marked, with the flag's words on a full-width line under the row; `DASHBOARD_RULES` is the list of rules a volunteer sees here and the column each maps to, and a rule absent from it is not this page's business (a count that fell after printing means labels to discard, not a job; beeline-69t reviews the rest). The page never says "sync": it states the schedule — every morning at 2am Pacific — and not the last run's timestamp, which the sandbox printed in UTC as 9am and which is `/jobs`'s concern. Settled seasons stay off it and are counted (beeline-2c3.24); a settled sample waiting on labels stays, since a season's end does not cancel a print job. The heading is the brand with a lede for a new volunteer, not a worklist title; the summary — "2 samples need attention" — is the second heading, since it is what the volunteer came for, and the schedule note sits under the table. Where the person belongs to an atlas (`person_membership`, never where their samples fell), the header ends in that atlas's mark, as it does on their `/people` page; the marks and colorways live in one table, `ATLAS_IDENTITY` (`src/app/theme/atlas.ts`), and are for now the 216px JPEGs the program distributes on Canvas, cropped to their circle and drawn small until the vector artwork arrives (beeline-2c3.13).

### One record

`/samples/:id` and `/specimens/:id` (`src/app/record.ts` + `src/app/views/record.tsx`, beeline-2c3.34) are the two record pages, and the specimen one exists because `determination` is append-only and `determination_of_record` is a view: a correction is a newer event and an expert never overwrites a volunteer, and the specimen listing gave that whole history one cell. The page is the events — who, when, through which channel, expert or not, the qualifier, `verbatim_identification`, which row is the record — newest first and with the record *marked* rather than hoisted, because hoisting it rebuilds the flattened read this replaces. The record is frequently not the newest (61,102 specimens on the dev store), so where they differ the page says why. The grain split follows the data: QC findings are keyed to the sample, so "why will this not print" is answered on the sample's page, which also carries the coordinates with their `source` provenance and the observation's geoprivacy beside them, the elevation with its `elevation_source`, and a paged list of its specimens — the largest trap sample holds 2,252. Each page carries the whole of the other's sample block, through the same components, because a determination read without where and when the insect was collected is not a record of anything. Reachability is the listings' rule with the filters gone — a volunteer reaches their own, staff reach everything, `mine` follows the acting-for switch — and unreachable is answered as 404 rather than 403, so a URL cannot be probed. A record is addressed by `entity_id`, which a rebuild redraws; there is no better handle, since a field number is nullable and, across the four identifier eras, not unique.

### Printing

A print run (`schema/035`, its meaning in `schema/155`, the writers in `src/print-run.ts`, beeline-1kb.2) is the batch act of printing and the moment specimens come to exist: **preparing a run is the freeze**. It takes every pending sample in scope — `pending_print_sample`, narrowed to `print_scope_sample` for an unscoped run, which means every atlas without an `atlas_printing` row plus samples outside any atlas, since Oregon prints for the whole program — and a run scoped to one atlas is refused unless that atlas has the row, since the rest are the program's to print (Peter, 2026-09-21; the flag is a satellite row, like `person_admin`, because DuckDB cannot add a NOT NULL column to a referenced table by migration) — creates their specimen rows, mints a field number and a UUID v7 `occurrence_id` for each, composes the six label strings (`src/label-text.ts`, the reference implementation's formats so a Beeline label reads like every label already pinned, the collector line included: `P.Abrahamsen`, set tight with no space after the initial, as every label in the drawers reads — decided in the room on 2026-09-18, screens keep `labelName()`'s `P. Abrahamsen` — and both names for a pair, `M.&D.O'Loughlin`; a county prints as its name alone, never with iNaturalist's `, US, WA` suffix, which `countyName` refuses even if the store still held one, since 172 labels in the first run anyone prepared said `Franklin County, US, WACo`, beeline-gr7) and lays them out in sheet order — the collector line, then the primary collector's id to keep two people whose lines read the same apart, then date, sample number (natural order) and specimen number — a blank cell between collectors, 250 to a sheet, so one collector's numbers run together. A pending sample with no single primary collector stops the run rather than being skipped by the join (`sample_primary_collector_invalid` is checked first, as the location row is checked after). The snapshot is `printed_label`, one row per label per run: the six strings *and* the values they were rendered from, so the sheet re-renders byte-identical and beeline-1kb.17 can compare an iNaturalist edit against what actually printed. The mint is the INSERT into `minted_field_number`, whose PRIMARY KEY is the uniqueness guarantee (ADR 0008 §5); `specimen.field_number` is written beside it because it is the column every read uses, and `specimen_field_number_stale` asserts the two agree. The number continues the eight-digit `YY` form, seeded one past the highest eight-digit number in the **imported corpus and the registry together**, floored at `YY000001` — the registry alone would have started a rebuilt 2026 store at `26000001`, inside the imported block whose ceiling is `26072091` (`minted_field_number_collision` is the check). State is derived from timestamps, never a column: prepared → approved → printed → mailed, or canceled while unprinted, each a guarded UPDATE behind one in-process lock, and the freeze runs on a connection of its own because the app's shared connection cannot hold two transactions at once. Two runs can be open together and cannot collide: the freeze is what takes a sample out of pending. **Printed is the moment that matters, not the freeze** (Peter, 2026-09-14): `printed_sample` — a specimen with a label in a printed run, or an imported specimen with no run at all, since the legacy labels are on pins too — is what `promote-observations.sql` and `mint-samples.sql` read to stop the coordinates and the locality following iNaturalist; dates never followed. **Cancelling destroys nothing**, and not by preference: DuckDB will not delete a referenced row in the transaction that removed its references, and a cancel that half-succeeded leaves specimens no run holds, which read as printed. So the labels stay as the record of what was prepared, the specimens keep their rows with the number cleared, the numbers stay burned (`specimen_id` NULL), `individuated_specimen` (`schema/117`) takes those rows out of the count that `pending_print_sample` and `qc_rule_count_below_printed` read, and the next freeze re-adopts them — same row, same `occurrence_id`, a fresh number. Every author column after `prepared_by` is a plain INTEGER, because a foreign key is an index and an indexed column on a row the labels reference could never be updated (duckdb/duckdb#20246). `db:reseed` carries none of it and says how much it left behind: the sandbox is the only store that reseeds, and a deployed store is migrated (ADR 0006). The sheets are `src/label-pdf.ts` (beeline-1kb.4): pdf-lib, the reference implementation's geometry verbatim — 25×10 on US Letter, 0.666"×0.311" labels, its six text boxes and shrink-to-fit rule, an 8×18 DataMatrix of the digits stood on end — because Arthur asked that the new sheet match the old one, and the vendored Oxygen Mono (`assets/fonts/`, OFL). Rendered from `printed_label` rows only, with the document dates set to `prepared_at` and no object streams, so two renders of a run are byte-identical (a test hashes them; `print_run.pdf_sha256` will record the first). The DataMatrix is vector: filled rectangles, one per run of dark modules, from bwip-js's module matrix. It was a 1-bit image first and came out blurry, because viewers and print drivers smooth a tiny bitmap when they scale it whatever its Interpolate flag says. Fits are remembered per render and found by bisection, since a sheet repeats the same strings down a column; with the freeze writing its three tables in multi-row statements rather than three statements a label, a 5,411-label run freezes in 1.6 s and renders in 2.9 s on a workstation, where the first version took 7.6 s and 7.2 s and minutes on the sandbox's two shared threads. A scanner reads the number, not a string, since only the digits are encoded, as the reference did. The render runs on a **worker thread** (`src/label-pdf-worker.ts`, beeline-1kb.19), because it is CPU-bound from end to end and Node would otherwise run it on the thread that serves every request — during the first demonstration Fly's health check failed mid-render, not at a deploy, the process alive and answering nothing. Measured on the production shape (`node --import tsx`, 5,000 labels): `/healthz` answered 2 probes at worst 3,996 ms while the sheets rendered in process, and 47 at worst 36 ms — its idle latency — with the worker, for about 7% more wall clock. The boundary is what makes it the cheap fix rather than rendering at approve time as a job: plain rows in, bytes out, nothing in between touching the store, and the renderer itself untouched so the sheets stay byte-identical. `runPdf` coalesces concurrent requests for one run's sheets, since two admins opening an unrendered run would otherwise start two workers on the same input. The freeze's own TypeScript half is the same shape of work and stays on the main thread: it runs inside the freeze's transaction, which cannot cross a thread. The screens are `/print-runs` (`src/app/print-runs.ts` + `src/app/views/print-runs.tsx`), admin-gated like `/jobs`: the list with a Prepare form whose scope picker says how many labels and samples each scope would take before anyone presses it, and the run page — the six strings per label in sheet order as the proofing surface, the labels to look at listed first, one button for the state's next step with a note, Cancel while unprinted, and the sheets at `/print-runs/:id/labels.pdf`, rendered on first request into `data/print-runs/` (config `printRunsDir`) with the hash recorded — and a cached file is served only when it hashes to what the run recorded, since a reseeded sandbox restarts ids while that directory survives; a canceled run serves no sheets at all, its numbers being burned. The writes go through the print connection (`printConn`, opened in `main.ts` beside the scheduler's) and refuse impersonation. What a volunteer sees: their front page keeps a sample until its labels are **mailed**, not until a run is prepared — the freeze takes a sample out of `pending_print_sample` at once, and the page listed only what was pending, so in the first demonstration a sample vanished from its collector's dashboard days before any envelope existed; `sample_label_in_progress` (`schema/155`) is what holds it there, reading "3 labels are being printed" and then "printed Sep 18, not mailed yet". Then a Label column on the sample page's specimen list — printing, printed, mailed, run canceled, or printed before Beeline, never blank — and a Labels block on the specimen page, one row per run with the number as it printed, which is also the proofing lookup's other half: a number that matches twice shows each specimen's labels beside their runs. A specimen with no number is two stories, told apart by whether it has a label row (beeline-1kb.21): one a canceled run had numbered reads "awaiting a number" on the listing and the sample page and names the burned number on its own page, since the registry has let go of it and `printed_label` is where it survives; one with no label row at all predates field numbering, and only that one says so.

### Determinations from Ecdysis

`pnpm ecdysis:load <archive-dir-or-export.csv> [db] [--prefix WSDA_] [--force]` (`src/load-ecdysis.ts`, beeline-9ut) is the `ecdysis_import` channel: expert determinations made in Ecdysis, Symbiota as WSUC deploys it, brought back as events. Two inputs, one row model — an unpacked Darwin Core archive (`occurrences.*` + `identifications.*`, the whole identification history with, usually, one row flagged current, each with a Symbiota `recordID` and the moment it was entered) or the flat occurrence export staff download today, read as one current identification per occurrence and keyed by the occurrence and its fields. The join is the catalog number under the collection's prefix; names resolve against `animal` by spelling; one the tree lacks but ITIS accepts is adopted from ITIS first, with whatever ancestors the tree also lacks, walked up `itis_taxon.admitted_parent_tsn` (`src/adopt-itis.ts`, beeline-45v.1.1: ITIS is the default, so taking its word is no taxonomist's claim — but never a homonym or a subspecies), and anything else is reported, never minted (curation, beeline-45v.1); determiners go through `ingest/determiner-aliases.csv`. **Ordering is what an import has to get right, and `dateIdentified` cannot help** — "s.d." on two thirds of Ecdysis's identifications, a bare year on the rest, kept as `determined_on` with `determined_on_precision` beside it and shown as the year. The identification Ecdysis calls current — the occurrence's own determination where an archive's history flags none, as 484 of Washington's occurrences do (beeline-9ut.6) — is recorded when it crosses into Beeline, so it supersedes what stood before (the legacy import's undated copy of the same assertion included, which is how a Washington record gains its year); a superseded one is recorded at the moment Ecdysis entered it, so history lands in the past and can never be the record, whichever export brings it. Idempotent twice over: by `recordID` (`ecdysis_identification`), and by adoption — an event on the specimen with the same node, qualifier and determiner that no `recordID` has claimed, recorded from a flat export that could not know the id, is linked to the archive's `recordID` rather than recorded again or skipped; skipping was the first version, and it skipped a superseded row for matching what happened to be current, so the next load recorded it. An older export loaded after a newer one would make since-revised rows current again, so the loader refuses it unless forced; the check is to the minute, since flat exports stamp to the minute and archives to the second. Measured on the dev store in date order — February flat 25,715 loaded, March flat 175, July archive 8,026 of 85,103 with 24,331 already recorded, and the archive again 0 — after which 30,465 of Washington's 30,995 expert records are the dated Ecdysis event. What the exports hold is [docs/research/ecdysis-integration.md](docs/research/ecdysis-integration.md). The `ecdysis-fetch` job (`src/fetch-ecdysis.ts`, beeline-9ut.1, 3am Pacific, between the sync and the legacy export) keeps Washington's archive current the way beeatlas does: it asks Ecdysis's public v2 API whether dataset 44 has moved since the last download — the total, and the count modified since a day before it — and signs in (`ECDYSIS_USERNAME`/`ECDYSIS_PASSWORD`; the bulk download answers 401 otherwise) to download only if it has, any doubt meaning download. Unchanged upstream still loads, from the archive it kept, because a reseed drops every Ecdysis event and the loader's idempotence makes the reload free; the collections it reads are `ECDYSIS_COLLECTIONS`, Washington's alone until beeline-9ut.2.

### Volunteers identifying their own specimens

`/determinations` (`src/app/determine.ts` + `src/app/views/determine.tsx`, the island `src/app/islands/determine/`, beeline-bcq) is where a volunteer says what their pinned specimens are: every specimen is already a row, so a number is typed only to *find* rows, never to enter a name; ticked rows are named all at once (a box is all *Bombus*, then three refined to species), and sex is one click — queen/worker/male where `animal_castes` (`schema/119`) says the taxon has castes, female/male elsewhere. Which taxa have castes is stated, not derived, in `animal_caste` (`schema/045`), nearest stated ancestor winning: the tree has no subgenus to say that cuckoo bumble bees have no workers, and the expert records cannot either (24 *B. flavidus* "workers" on the dev store). Two views over one grid: **by sample**, a season in collecting order (`sample_season`, `schema/160` — the 1 March line), and **the batch**, specimens gathered by field number in the order added, kept in `determination_batch` so a box can be worked over several sittings. Numbers are read by `src/determination-numbers.ts` — whole, a unique tail (`412`), or a range whose start may be a tail and whose end may be abbreviated (`9685-697`) — across **every** season, since a box sorted by genus mixes years and numbers before 2025 have seven digits; its problems are codes and the catalog says them, with the span of the person's numbers by length so a dropped digit shows. **Entry writes drafts, never determinations** (Peter, 2026-10-01): `determination_draft` holds one changeable row per specimen and determiner, nothing downstream reads it, and the `commit-determinations` job (1am Pacific, `src/commit-determinations.ts`) turns each into an `in_app` determination in one transaction — before the 4am legacy export, so the export carries the day's work — taking only drafts changed before it began and dropping any that say what the newest volunteer determination already says. That is CONTEXT.md's draft/commit boundary, with one consumer and no per-export bookkeeping; the screen says it as what it means to the person — undo is free until 1am, and after that a change is kept beside the earlier name. Reach is the listings' `mine`, following the acting-for switch; the determiner — and owner of drafts and batch — is whoever is signed in, since delegation grants reach and never credit; impersonation looks and cannot write; someone else's specimen answers 404. Expert determinations are deliberately absent from the screen so a volunteer determines rather than copies (beeline-bcq's anti-anchoring note); the listings and the specimen page still show them. `db:reseed` carries none of it and says how much it left behind, like print runs. The design was chosen from three variants on a prototype branch, `prototype/volunteer-determinations`.

### Determinations from worksheets

`pnpm worksheets:fetch <drive-folder-id> [dir]` then `pnpm worksheets:load [dir] [db] [--manifest path] [--dry-run]` (`src/fetch-worksheets.ts`, `src/load-worksheets.ts`, beeline-pbk) is the `worksheet_import` channel: the Google Sheets volunteers determined their 2025-season specimens in, one copy of a template per volunteer (OBA Number, Sex/Caste, Family, Genus, Species), awaiting a transcription into the old database that mostly never happened — 18,704 settled-season rows fall on specimens with no determination at all ([docs/research/volunteer-worksheets.md](docs/research/volunteer-worksheets.md)). Three rules, decided with Peter on 2026-10-01. **Who** is a decision per file, never inferred: a sheet names no determiner, households and helpers break "the collector of its specimens", and Drive's last editor is usually the staff member who made the copy; so `data/worksheet-files.csv` (gitignored — it is a list of names) is refreshed on every load with the collector of most of each file's specimens proposed, and a file loads only once somebody writes a person reference (the overlay's `name:`/`inat:`) or `skip` beside it. **Which version**: volunteers copied sheets and kept going, so one specimen can stand in several of a determiner's files; copies that agree are one entry, and copies that disagree are held naming each other until somebody marks the stale one `skip`, because no clock says which is later thinking — the first version took the most recently modified file, which was an old copy touched in January, and creation time is wrong on other pairs. The same holds against the old system, which had a Determinations page of its own and kept no date: a row that would contradict the determiner's identification there, say less than it, or change its sex is held, and one that refines it loads (Peter, 2026-10-04, beeline-wuwm; on the sandbox none of the old values appeared in any of 34 Drive revisions of the sheets that disagreed with them). **Stray numbers** — typed by hand with no validation — are held when they land on a specimen the determiner did not collect, unless the manifest marks the file as determining for others, and are listed in the export's `held.csv` with the numbers either side — as is every row of a file nobody has decided about, so that file is everything that did not load. Sex/Caste maps to in-app entry's vocabulary (queen is a female gyne; a caste on a taxon without castes goes to the notes); `determined_on` stays empty, since a sheet has no clock but the file's. Loading again records nothing it holds, nothing a newer file already gave, and nothing changed in Beeline since the sheet was last edited. A store built before the channel existed refuses it by CHECK, which DuckDB cannot change: the loader says so before reading a file, and the answer is a reseed (ADR 0006). Like the Ecdysis load, a reseed does not carry what it recorded — run it again after one.

### Copy

Volunteer-facing copy goes through the message catalog (`src/app/messages/` — en only; those views never carry literal prose); QC self-service instructions and the glossary live there, pinned by test to the `qc_rule` seed and to the rendered anchors. Staff screens (`/jobs`, `/people`, `/design*`) are English-only: `/design*` carries literal prose, `/jobs` and `/people` read from the catalog like everything else, since there is no reason for staff copy to be worse-kept than volunteer copy — only untranslated.

### A value that is not there

Absence is a component, `Absent` (`src/app/views/components/text.tsx`, proofed on `/design/components`), because the app drew it three ways — words on the record pages, a bare em dash on People and Jobs, an empty cell on the listings — and an empty cell is the worst of them: nobody can tell "there is none" from "it failed to load" (Nora, 2026-09-17). The rule: never blank; every absence carries its meaning as a `label` in the catalog's words, always read aloud; **spelled out** where the absence is the exception or tells the reader something ("not determined", "obscured", "No account", "outside"), and an **em dash** where the same absence repeats down a dense column and the words would be noise (a person with no membership recorded, a job that breached nothing, a name that is simply current in ITIS); secondary text either way, so it never reads as a value. A record page has the room and always spells. A count of 0 is a number, not an absence, and a links column with nothing to offer is `class="actions"` and may be empty, since it holds no value. **Do not type a "—" into a view or leave a nullable straight in a cell**: tests render each table against data with gaps in it and fail on any empty value cell.

### Determinations and names

Rank is reference data, not free text: `animal_rank` (`schema/020`) holds the ranks the store admits with an `ordinal` gapped by 10, because "species or finer" is the comparison the domain needs and a bare TEXT column cannot answer it — every caller was growing its own copy of the ladder instead (beeline-a2p, beeline-4zi). The numbers live in the table and callers join, which is the half of Symbiota's rank design worth copying without the ~150 bare `rankid > 220` literals that came with it. `TaxonName`'s `ITALIC_RANKS` stays a separate, deliberately wider list — it must do something sensible with a rank the store has never heard of — and a test pins the two to agree wherever they overlap. `determination_misplaced_qualifier` (`schema/115`) is the CHECK the engine cannot hold, since "species or finer" is a fact about `animal_rank` rather than about the determination row: a test asserts it empty, the same shape as `sample_elevation_stale` and for the same reason. A determination says which node and, since beeline-tgu, how sure: `determination.qualifier` holds the three open-nomenclature qualifiers that modify a species assertion (`cf.`, `aff.`, `nr.`) and cannot be expressed by dropping to genus, which would throw away the resemblance the determiner observed; `sp.`/`spp.` are deliberately absent, being what a genus-rank determination already means. `verbatim_identification` keeps the name as the source wrote it beside the node it resolved to, and a CHECK requires it, never blank, on every channel but `legacy_import`: not every name will resolve to an ITIS taxon, so the words are the one record of what was said (beeline-45v), while legacy import is exempt because 225,669 of its 256,161 determinations arrive as parted columns with no whole name to keep, and promotion invents none — except where a curated decision sends a determination to a node other than the one its own columns spell (a spelling alias, and next an adopted ITIS name), when the spelling the source used is kept here, since nothing else would say what was written (beeline-bph). Only `nr.` is attested in the legacy corpus (3 records, `Lasioglossum nr. tenax`, which used to land on the bare genus because `specificEpithet` is empty on those rows and nothing read the string); the glossary and `/design/names` teach all three. The curated taxonomy is based on ITIS (beeline-45v), and `animal.itis_tsn` is the TSN of the one ITIS name a node matches at its rank and spelling, a current name preferred over an outdated one — derived by `ingest/match-itis.sql` from `itis_taxon` and `itis_synonym` (`schema/025`), restated whenever ITIS is loaded and after legacy promotion, and checked by `animal_itis_stale`. ITIS arrives as an extract: `pnpm itis:fetch` downloads a release on a workstation and keeps every insect at the ranks `animal_rank` admits, each current name with its nearest ancestor at one of them (`admitted_parent_tsn`) — 337,419 names and 92,892 synonym links in the 2026-08-26 release, two CSVs of 27 MB against a 925 MB database — and `pnpm itis:load` replaces the tables wholesale in one transaction; `db:reseed` carries them, since promotion cannot recompute them. All insects rather than only what already matches, because bycatch arrives from any order and the curation layer has to look up names the store does not hold yet. `animal_itis` (`schema/118`) says what a node's TSN, or its absence, means: on the dev store 3,357 nodes are valid, 37 synonyms (kept on their own TSN, with what ITIS calls them now beside it), 4 homonyms (two ITIS names share the spelling and no node carries authorship to choose between them), and 169 absent — mostly bee names ITIS lags on and bee subgenera, which ITIS carries in no bee family but Colletidae. `not loaded` is its own answer, so a store without ITIS never reads as a taxonomy ITIS has never heard of; what the program does about a synonym or an absent name is `animal_curation` (`schema/022`, beeline-45v.1), replayed from `ingest/taxon-curation.csv` by `src/taxon-curation.ts` after the seed and before the match. ITIS is the default, so the file holds only the claims — an **addition** (a name ITIS lacks, kept), a **departure** (a name ITIS calls outdated, kept under the program's treatment, with what ITIS said recorded beside it) and a **homonym** resolution (which of two current ITIS names at one spelling is meant, by TSN, which the match then honours) — and every row names the taxonomist who decided and why, with a DOI or link where a paper is behind it, since the loader transcribes a decision and never makes one (Peter, 2026-10-02). A row whose node is not in the tree creates it under the parent its name implies, or under `parent_rank`/`parent_name` for a genus or family, which is what will let the seed stop minting a node for every spelling it meets once the decisions are in; one whose parent is missing is reported, never guessed. `animal_curation_stale` is the check of each later ITIS release against the decisions — an addition ITIS now carries, a departure ITIS has adopted (retire it) or renamed again, a homonym choice no longer on offer — empty while ITIS is not loaded. The decisions are asked for in a Google Sheet (built from the dev store on 2026-10-02 and sent to Lincoln Best), and **reading the answers is a person's or a model's job, never a script's** (Peter, 2026-10-03): an answer comes back as prose, a crossed-out proposal, a row added at the bottom, or an email saying "mostly fine, except…", and the first reader — which matched dropdown strings and prefix-matched "Keep…" — would have mapped those with a confidence no reviewer of a forty-row diff catches. So `pnpm taxon:fetch-sheet <sheet-id>` only writes the tabs to a dated snapshot under `data/taxon-decisions/`, the record of what was said; whoever reads it records each decision with `pnpm taxon:decide <kind> <rank> "<name>" --by "L. Best" --reason "<his words, and where from>" [--reference] [--tsn]`, or `--batch file.csv` for forty rows under one signature ("every proposal, as confirmed by email"), and that tool fills in what the reader must not type — the TSN, what ITIS calls the name instead, the release — refuses a decision the ITIS tables contradict (an addition of a name ITIS has, a departure from a name ITIS still accepts, a homonym choice not among the candidates), and merges the row into the file. The reason is the taxonomist's words verbatim; a paraphrase is the reader's. `pnpm taxon:apply [db]` replays the file onto an existing store; promotion does the same on every rebuild. On `/taxonomy` a decided name wears a chip in the decision's words ("Kept beyond ITIS", "Kept against ITIS", "Chosen") in place of the warning, with ITIS's view kept beneath; its own page says who decided, when, against which release and why, links the reference, and warns when the release now loaded has moved from under it; the index counts decisions and lists them through a `decided` filter, whose `moved` value is the curation worklist. Names are derived, never typed: `TaxonName` derives italics, subgenus brackets, and qualifier placement from rank, and `labelName()` (`src/person-name.ts`) derives a label's "P. Abrahamsen" from `person.given_name`/`family_name` — family names print whole, `label_name` overrides (`/design/names`). The tree itself is `/taxonomy` (`src/app/taxonomy.ts` + `src/app/views/taxonomy.tsx`, beeline-45v.5), readable by everyone like the glossary and the place curation will land: a name is addressed by rank and name — the table's own unique key, which a rebuild does not redraw, where the name alone is not a key — and its page shows where it is filed, how it stands in `animal_itis` (the current name for an outdated one, both ITIS authors for a homonym), and what is filed below it, counted by determination of record — and for staff each count links to the specimen listing at `scope=all`, naming it because a link that names no scope lands on whatever scope they last browsed, so a count of everyone's could open on their own; a volunteer, whose listing holds only their own, sees the count without a link. A name search or a standing filter turns the index into a flat list, which is the worklist curation grows into; browsing starts where the tree first branches, since Animalia, Arthropoda and Insecta each hold one thing. A row speaks about ITIS only when the name is not simply current there.

### The roster

Who is in the store, and who they are, is `/people` (`src/app/roster.ts` + `src/app/views/roster.tsx`, beeline-eft): the roster, admin-gated — a listing of people first and, after cutover, only. The account promotion picked for someone can be wrong, and a wrong one is invisible in any view that prints only the login, which is how one survived review; but checking them is a job that ends when the legacy records stop being the source, so it gets no column, no sort order, and no vocabulary of its own (beeline-eyk). A row says something only when something is wrong with it — a chip in the account cell, in the words anyone would use — with a count above the table, since the listing is ordered as a roster rather than as a worklist. It is a listing like the record listings (2026-09-16): a search box, a menu in each column heading with its two sort orders and its filter — active in the last twelve months by a sample or a visit (beeline-caa), where they belong, only admins, who leads which program, only accounts that look wrong — the filters in force as pills, the count set as a title beside a CSV download (`/people.csv`, the user id in it and off the screen, where it only made rows taller), and the heading row sticky. Two dates ask whether someone is still active and neither implies the other: `Last sample` reads from `sample_collector`, and `Last seen` from the private store, which a store opened without it simply has no answer for. `Last seen` answers from two sources of different strength and now says which it is using: a visit — a request they actually made, recorded in `person_activity` and throttled to an hour — prints plain, while a bare sign-in prints as one, because iNat tokens never expire and that date can be months behind somebody who has been here every week. It is a table rather than a column on `session` in either direction: the session's `last_seen_at` has to slide within minutes of the real last request for the 30-day expiry to mean anything, and it cannot serve as the person's activity because the idle cutoff is per credential — a phone in daily use would keep an abandoned laptop's cookie alive. Neither write may fail a request: DuckDB has no row locks, so the second of two overlapping updates to one row fails rather than waiting, and the slide used to run on every request — two tabs on one session was a 500 (beeline-cla). The slide is throttled to five minutes and both writes are allowed to lose, since whoever won just wrote the same value. Keyed on `inat_user_id`, so it outlives a rebuild; kept outside the session, so that destroying sessions — an expiry purge, a rebind, the beeline-ten rekey — no longer silently ages the column toward "less active" (beeline-dji). A person with no account whose records point at somebody else's is a household sharing one login (`inat_user_id` is unique, so only one of them can hold it): the row names the holder rather than leaving a blank, and squaring the model itself is beeline-oyl.

### The person's own page, and the overlay

The person's own page is where the work is done and so explains itself at length; a store with no legacy staging drops the apparatus entirely rather than explaining its absence. Staff act there too — rebind or unbind an account, grant or revoke admin, set where someone belongs (`person_membership`), say who may act for whom (`person_delegate`), say which programs someone leads (`program_lead`, beeline-7c1: whose work a program's is, never access — each atlas is a `program`, beside it Master Melittology `MM` and the BLM surveys `BLM`, and the overlay field `leads` names the whole set by code, semicolon-separated like `acts_for`), fix name parts — and every one of those writes goes to `data/person-overlay.csv` first and is applied from there (`src/person-overlay.ts`, `src/apply-person-overlay.ts`), so promotion replays it onto a rebuilt store. `create` asserts that a person exists at all: promotion mints people from records, so a staffer who collects nothing — an intern, a coordinator — has no other way into the store and therefore no way to sign in, since the approval gate is an account bound to a person. It names them `name:<display name>`, is applied before every other row so the account binding and the admin grant compose with it, is idempotent on replay, and refuses a name two people already share rather than minting a third (beeline-2c3.32); a hand-written INSERT would do the same thing once and be gone at the next `db:reseed`. Its one screen is the unknown collectors' (below), which admits somebody who has records; somebody who has none still goes through the file (beeline-2c3.33).

### Collectors Beeline doesn't know

`/unclaimed` (`src/app/unclaimed.ts` + `src/app/views/unclaimed.tsx`, beeline-e85, admin-gated) is where a collection record from an iNaturalist user no person is connected to stops being invisible. Minting never makes one — every sample has a primary collector, and a placeholder person is worse than a queue — so they wait in `observation_sample_unresolved`, and `unclaimed_record` (`schema/108`) routes each to a program by where it fell, as minting assigns an atlas: an atlas's state, else Master Melittology, which also takes a record with no state at all. The page lists observers, not records, grouped by program with the program's leads named (responsibility, never access: any admin acts), each program counting only its own records so the sections add up; one row per observer because both answers are about the person and clear every record at once. The answers are the overlay's: **connect** the account to somebody already here (refused for a name two people share, or somebody already connected — a person holds one account, and moving theirs belongs on their page), or **add** somebody new (`create`, the account, the name parts their labels need; refused for a name that would reach anybody already here, which `create` would otherwise read as that person, connecting the account to them and overwriting their name parts). Whether a name reaches somebody is asked of the overlay's own resolver, never of `person.display_name` alone: it reads every spelling legacy promotion recorded first, so "MaryJo Mosby" can name the Mary Jo Mosby already here. Both write through the same `commitDecisions` as `/people/:id`, and every decision about a person, from either screen, takes its turn behind one lock and reads its checks inside the turn, since two at once — two staff on one collector, or a rebind on `/people` racing an add — would both pass the checks and leave the loser's overlay row failing on every rebuild. The app's writes run on a connection of their own (`appConn` in `src/app/main.ts`), never the scheduler's: a single-statement write there during the 2am promotion landed inside its transaction, invisible to minting and rolled back with it on a retry. Suggestions — the legacy register listing the login under a person's name, or the iNaturalist profile name matching one — are offered and never acted on (beeline-eft). Then it **mints at once** rather than at 2am: the nightly's own promotion, on a connection of its own behind a lock, skipping only the `observation_field` refresh (only a sync changes that table, and it was most of the cost), ~0.7 s on the dev store. The same promotion and not a narrowed copy, because connecting a returning volunteer links their observations to legacy samples rather than minting beside them — 27 of the 79 records the dev store's suggestions would connect — and adding that person as new would have made 27 duplicates. What it changed is recorded by a full pass of the sample log afterwards, filed as the promotion it was and with no reason, since most of what a store-wide pass finds is not this connection's doing; a full pass because it runs the whole store's promotion and a pass narrowed to one observer records nothing for a sample it has no earlier row for — every sample just made. Who caused it is in the person log, against the decision.

### What happened to a person, and when

The overlay says what was decided; it cannot say what happened. One current row per (`person_ref`, field) means a later edit replaces the earlier one, so it answers "who last changed this, and why" and never when, what the value was before, that it changed twice, or who changed it the first time — and nothing displayed it at all. So there is a second artifact beside it, in the shape the project already settled for a correction to a determination (`schema/040`): authored changes are append-only events. `data/person-change.csv` (`src/person-change.ts`) holds one entry per (when, `person_ref`, field, old, new, author, source, reason), read on `/people/:id` as that person's history and on the unfiltered `/people` as the newest entries across everybody — filtered, the panel is dropped, since a search for one person answered with somebody else's history reads as a filter that leaked. A CSV rather than a table for the same reason the overlays are, and a sharper one: a history the blow-away erases answers "who changed this" with "nobody, we rebuilt it". That constraint dies at cutover and the natural home is then a table — [ADR 0007](docs/adr/0007-authored-changes-are-events.md), beeline-o22.

Every writer is covered, not just the screen — legacy promotion mints people and binds accounts wholesale, observation promotion rewrites `inat_account.login` whenever iNaturalist renames an account, and both used to leave no trace but the code that did it, which is exactly the class of change that bound three people to the wrong account (beeline-eft). Coverage does not depend on each writer remembering: entries are produced by comparing the store against what the log itself last said (`recordPersonChanges`, idempotent, run at the end of legacy promotion, after observation promotion, after the account backfill, and at boot), so a change made any other way is caught by the next pass and attributed to that pass rather than to a person — which is what `source` says and `author` deliberately does not. Both producers read one query (`PERSON_STATE_SQL`) and record **state** rather than the overlay's instructions, because a log minted from what a writer intended would differ from what a rebuild computes and report a change nobody made. The entries are keyed by the overlay's `person_ref` and never by `entity_id`, a per-store sequence draw a rebuild redraws (beeline-ten). A rename moves that reference and the log's own `display_name` entries follow it — forward only, in file order, never onto a name the log already knows somebody by, because treating a rename as evidence that two names *are* one person merges two people the moment their names swap or a vacated name is reused, and then reports the difference between them on every pass forever. A reference also moves when nothing has happened to the person — a namesake arriving pushes them off their own name onto their account, a rebuild that respells `MaryJo` as `Mary Jo` moves it with no rename recorded anywhere — so a pass matches the store's people against the log's in order of evidence: the reference itself, then the name the log last recorded (a name changes only when somebody changes it), then the account. Every claim is proposed before any is granted, because whether a claim is safe depends on what the other people in the store turn out to be — deciding one at a time is a different and wrong problem, and produced a fabricated rebinding in every review round that went looking. What cannot be attributed is recorded as **nothing** and counted (`contested`): two people reaching one history claim nothing, and a history whose account somebody else in the store now holds is nobody's to claim, since a newcomer taking over a respelled person's old name is identical in evidence to the person whose account was taken away and who is still standing there. That costs an account shuffle one of its two rebindings — silence is a gap somebody can look into, where a fabricated rebinding is a lie about the one thing this log exists to make visible (beeline-eft). A name the store still carries means its person is still here, so an account only recognises somebody whose last recorded name nobody answers to any more. A reference falling silent records **nothing**: it looks like a departure and is equally a name that became ambiguous or a store promoted from a smaller corpus, and the version that wrote departures made flat false statements about people standing right there. A page's history is addressed by the reference the **store** gives that person rather than by a name two of them might share. Read leniently where both overlays are read strictly — refusing a malformed row protects a file that gets rewritten wholesale, and this one is only ever appended to, so its own order is the order things were recorded and no timestamp can restate it.

### And to a sample

Samples get the same treatment (beeline-ewl, the second instance of [ADR 0007](docs/adr/0007-authored-changes-are-events.md)): `data/sample-change.csv` (`src/sample-change.ts`) is append-only events, produced by the same compare-against-what-was-last-said pass at the end of legacy promotion, after observation promotion, and at boot — so the nightly's coordinate rewrites, minting, free-linking, and a staff edit all leave a trace, and a writer that forgets is caught by the next pass. The edit screen runs a pass narrowed to its one sample, so the author is credited with their edit and nothing else. Where it deliberately differs from the person log: the baseline lives in `data/sample-state.csv` — one current row per sample, restated wholesale each pass — because the person log's in-log baseline over this corpus would be a million rows; the reference is the derived triple (collector as the overlay names them, number, start date), with the observation link recognising a sample across a corrected number or date and a triple collision (a live duplicate) recorded as nothing and counted. The record page reads it as the History panel on `/samples/:id`. Measured on the dev store: baseline 1.1 s and 11.2 MB, a steady pass ~2 s and zero entries, and a nightly-shaped 30 moves + 2 renumbers recording exactly 32. The snapshot is a statement about one store, and a full pass **refuses** one that mostly names samples the store does not hold — no entries, no restatement, and a message naming the file — because the vanishing rule records silence and a store that has never seen a sample records an arrival, so a scratch store pointed at the shared `data/` paths turns one boot into a million-row append on the next real pass (the screenshot fixture did exactly that on 2026-09-21, and the 1,085,665 rows appeared on 2026-09-23; beeline-hrw). Refusing rather than re-baselining is what makes the mistake cost nothing in either direction: the fixture's own boot leaves the real snapshot alone. A store that has genuinely replaced the snapshot's re-baselines by deleting the file, and a snapshot with no rows is read as no snapshot. On the nightly a refusal **fails the run**, after the elevation step so nothing the store needs waits on it, because a refusal is a standing condition that needs a person and a green `/healthz/jobs` over an unrecorded history would hide it; the CLIs and the boot pass warn. Start a scratch app with `BEELINE_SAMPLE_CHANGES`/`BEELINE_SAMPLE_STATE`/`BEELINE_PERSON_CHANGES` pointed away from `data/` regardless; the person log has no snapshot to protect and simply gains the fixture's people as arrivals.

### Delegation

Delegation exists because a household shares one iNat login and `inat_account` is 1:1 and stays that way (beeline-oyl): the partner who does not hold it cannot sign in, and since `mine` is forced for volunteers their samples are unreachable by the only person who can — 1,087 of the Pedersons' 2,233 are in that state. It grants reach and never credit; attribution and Master Melittology progress stay with whoever collected. Staff grant it rather than the person represented, because being unable to sign in is the whole reason the row exists. The `acts_for` overlay value names the **whole** set of people, semicolon-separated, since one row per (person_ref, field) with latest-wins cannot say "and also". Turning it on is an explicit switch rather than a widening: `mine` keeps meaning mine everywhere, and while the switch is on `mine` *is* the person being acted for — never both, since a page blending Gretchen's 1,146 samples with Robert's 1,087 leaves a volunteer unable to say whose work they are reading. The switch is a cookie (`src/app/acting.ts`) naming the person the way the overlay does — by display name, never by `entity_id`, since the cookie is client-held and no rebuild can reach it, so a delegate holding two grants whose numbers permuted would have had a stale cookie silently select the other one on a switch that gates writes. Deliberately not a query parameter like scope and the filters: those are questions about the records and travel fine in a pasted URL, this one is about who is asking and the recipient may hold no grant. The grant is re-read on every request, so a revocation takes effect at once and a forged cookie resolves to nothing. Every "mine" surface follows it — the QC home, both listings and their CSVs, and the collector gate on sample editing — while admin rights and a correction's recorded author stay with whoever is signed in.

Impersonation (beeline-jjt) is the same switch for staff, without a grant: from a person's page on `/people`, an admin views Beeline exactly as that person sees it, to help them over the phone or to check what they are being told. It is its own cookie, resolved only for an admin, so the delegation cookie keeps the property that a forged value resolves to nothing for everyone; a name two people share resolves to nobody, as it does for delegation. Three things distinguish it from delegation, and the routes enforce them rather than the module: it is **read-only** — the volunteer's edit form renders, since they would see it, and a save is refused; it **takes the admin flag away for the duration**, so `/people`, `/jobs`, the scope picker and staff reach on record pages all answer as they would for the volunteer, which is what makes the view faithful and is why stopping is not admin-gated; and turning it on **leaves a trace** in `private.impersonation` — who, whom, when — because "who looked at my records" is a question a volunteer is entitled to ask. The trace is a gate, not a courtesy: a store that cannot write it does not start the switch, and a shared display name is refused on the person's page before anything is recorded, since the cookie could only ever resolve it to nobody. The delegation grants are not carried across: they are the signed-in person's, and the view is meant to be the volunteer's.

### Membership

Membership has two shapes and one absence: a member atlas, or the umbrella program itself with no atlas — Master Melittology membership without a member atlas is real, so absence is reserved for "nobody has asked" (beeline-lcl; the overlay field stays `home_atlas` and takes `program` as a value). Samples answer the same question geographically through `atlas_region`, where a row with a NULL atlas says "known region, no atlas covers it" and no row at all is what `qc_rule_place_unrecognised` fires on.

### Addressing a person, and admin

A person is addressed in a URL by their login where they have one and their `entity_id` otherwise (`personHandle`), and both resolve — `/people/pandg` and `/people/722396` are the same page, matched case-insensitively, and an all-digit segment is always an id since no iNaturalist login is all digits. The login is preferred because an `entity_id` is a per-store sequence draw that a rebuild or a `db:reseed` redraws: `/people/722436` was Steve Lang in one promotion of the sandbox's data and Robert Pederson in the next. The overlay is a separate question and a stricter one — it names a person `name:<display_name>` or `inat:<user_id>` and **never** by `entity_id`, because it is replayed onto a store that does not exist yet. The admin roster itself now lives in `person_admin`; `config.adminLogins` is only the bootstrap seed, applied at boot **per person** — to anyone on the list who holds no row and whom the overlay has not revoked. Asked of the store instead of of the person, it locks people out: `db:reseed` does not carry `person_admin`, so a reseeded store rebuilds the roster from the overlay alone, and the one grant anyone had written (to a new staff member) was enough to make the table non-empty and the overlay non-silent — which disabled the bootstrap for the five people who had only ever been in it, with no way back because granting admin requires being an admin (beeline-2c3.38). Only a revocation of *this* person suppresses their seed, which is the property the guard was reaching for; someone else's grant is none of their business, and neither is already holding a row a reason to skip the rest of the list. Both overlays are read, since half the decisions are curated in git.

### Editing and corrections

Non-iNat samples are edited in-app (`/samples/:id/edit`, collector-gated): each save updates the live sample row and records correction events keyed by staging Mongo `_id` in `data/corrections.csv` (`src/corrections.ts` — outside the blow-away path), which legacy promotion reads union the git-curated `ingest/legacy-corrections.csv`, app rows winning ([ADR 0004](docs/adr/0004-correction-overlay.md), beeline-2c3.8). Staff set a sample's **locality** from its page (`/samples/:id`, admin-gated, refused while impersonating; `src/app/locality-override.ts`, beeline-649), because an unprinted iNat-linked sample's locality follows its observation on every promotion and nobody could edit one in the app, so a place name the observation cannot yield had nowhere to go. One form, two durable stores, since the two kinds of sample are named by different things a rebuild reproduces: a sample with an observation goes to `data/sample-overlay.csv` (`src/sample-overlay.ts`, the person overlay's shape plus a `base_value`, keyed `inat:<observation id>` — the link is the sample's identity, and `entity_id` is a per-store draw), applied as the satellite `sample_locality_override` (schema/030) by `src/apply-sample-overlay.ts` at the end of observation promotion and at once from the page; a sample with none goes through the corrections overlay as the collector's own edit would. The follow rule in `ingest/mint-samples.sql` skips overridden samples, `sample_locality_override_stale` asserts the row and the sample agree, and `sample_locality_override_diverged` (schema/175) names an observation that has since moved to a third value, which the page shows beside the override rather than resolving: a deliberate assertion beats an unreviewed upstream edit (ADR 0004). Removing the override hands an unprinted sample back to its observation at once; a printed one keeps what the label says. Promotion reads the file only when given its path, so a scratch promotion never reads the deployed store's decisions; the nightly reports rows that name no sample in the run's detail and goes on. The coordinates take the same form (beeline-942): a second field in the same file, `coordinates`, valued `<latitude> <longitude> [uncertainty m]`, applied as `sample_location_override` with `sample_location` written beside it as `staff_entry`, the provenance every read already carries — and the location upgrade in `ingest/promote-observations.sql`, which used to rewrite `sample_location` unconditionally and so erased a staff point on the next nightly, skips overridden samples. The base it records is the `sample_location` row as it stood, whatever its source, so removal hands an unprinted sample back exactly what it had, an imported point included, and a sample that had none goes back to none; the elevation is left for `sample_elevation_stale` to notice, never cleared by the writer. The observation's believed-true point is now the view `observation_location` (schema/105), which promotion's candidate table reads and the diverged view compares against, with `sample_elevation_stale`'s 5e-5° tolerance. The form appears on the coordinates block even where the sample has none, because that is the case it exists for: an obscured observation with no trusted access yields no coordinates and cannot print, and only a person can put the true point in. Offered only on samples with an observation: the corrections overlay would land an imported sample's point as `legacy_import`, misstating who said so.

### The legacy-format export

Reporting built on the legacy system's occurrences file — Andony's R comparison, the taxonomists' Ecdysis uploads — keeps working because Beeline writes that file too (`src/legacy-export.ts`, beeline-6q8, GitHub #107): every specimen, the legacy template's 63 columns in its order, csv-stringify's conventions (BOM, header, `\n`, quote only when needed, blank as nothing) and its composite_sort row order. The `legacy-export` job writes it nightly at 4am Pacific into `exportsDir`, and admins download it from `/exports`; DuckDB writes it with `COPY` because the corpus is ~160 MB. **Where a value comes from is a rule, not a column-by-column choice**: anything Beeline can change comes from the model — collectors, dates, places, coordinates, determinations, printing — so the file follows staff edits and Ecdysis determinations; what Beeline does not model at all (the legacy error flags, catalog numbers, resource links, the plant's higher taxonomy, sex on a specimen nobody has identified) is carried from the staged record of an imported specimen exactly, blanks included, and a Beeline-originated specimen gets the model's value where it holds the fact and a blank where it does not. The aim is to match the legacy file exactly (Peter, 2026-10-04), so a row describes one point: where it carries its own imported coordinates it carries that row's elevation and uncertainty too, never the sample's, since a sample that merged legacy rows taken at different points has one location and its elevation belongs to another place (beeline-en7i); a row likewise carries its own method, end date and place by name wherever the legacy rows of its sample disagree about them, since a sample holds one of each and one collector's sample 1 of 25 April 2019 was two specimens netted that day and three from pan traps emptied the next — read from the corrected rows, so a staff edit, which corrects every row of its sample, brings the model's value back, as does a locality override set on the sample; where Beeline holds no volunteer identification, the volunteer columns are the legacy row's, and where it holds no expert one, the expert columns are (a determiner with no name, `L.R.Best` on 88 records, has no determination to live on); and while the legacy determination is still the record its subgenus is the legacy row's, since the tree files a species under its genus and the subgenus the determiner stated is held nowhere else (Peter, 2026-10-04). Legacy vocabulary is kept where it differs from the model's: `CA`/`NZ` rather than ISO alpha-3, several collectors joined with `" | "` in the name columns as the register wrote a shared login, a qualifier inside `scientificName`. `pnpm legacy:compare-export` is the done-test: on the 2026-09-27 corpus the open season differs in a few hundred values per column out of 61,400 records, and the settled seasons mostly where Beeline normalised (Roman-numeral months, `Male`) or filled what older records left blank (the higher taxonomy of 158,669 identified specimens). During the parallel run it is also the list of what nobody has explained yet (beeline-en7i): each difference gets a kind from its two values alone (`filled`, `case`, `date_form`, `country_code`, `subgenus_form`, `authorship`, … or `changed`), or from what the store knows where the values cannot say it — `collector_alias` (the legacy spelling of a collector that `ingest/collector-aliases.csv` corrects), `taxon_alias` (the same for a genus or epithet and `ingest/taxon-aliases.csv`), `subgenus_form` again where a genus column holds only `(Peponapis)` and the tree files it under the genus exported, `staff_correction` (the legacy row as staff corrected it), `newer_determination` (an expert identification from Ecdysis or Beeline), `label_name`, `initial_from_surname`, `collector_order_contradicted` (a record whose recordedBy and name columns list its pair in opposite orders), `login_renamed` (the same iNaturalist user id under another login), `sample_disagreement` (promotion found the legacy rows merged into this specimen's sample disagreeing about that place field), a record only one side holds is a difference about the whole record kinded by why — the blocking promotion finding that stopped it, or whether Beeline minted its number — and `ingest/legacy-export-rulings.csv`, written by hand and reviewed in git, says which are explained: by column, by kind, or one record by field number, the most specific ruling winning, with the outcome (`expected`, `reference-wrong`, `beeline-wrong`, `known-gap`), why, and where the call was made. A `beeline-wrong` ruling that matches nothing any more reports itself retired, so a fixed defect never hides behind a stale ruling. The legacy side is the staged pull, which Beeline also imports from, so this measures what Beeline does to the legacy records rather than two independent systems, and the report names the pull by a fingerprint of its rows; it runs from a workstation after each pull, with no job and no gate, since the parallel run ends at cutover. Every difference, with the ruling that explains it, goes to `data/exports/legacy-export-differences.csv` for anyone auditing it — under `data/` because it names people.

`/exports` also lists a Darwin Core archive for each program and season (`src/app/dwc-archive.ts` the format, `src/app/program-archives.ts` the writer, beeline-rvun): the specimens CSV's columns, tab-separated behind a `meta.xml` that declares only the terms, and every determination of each specimen in the Identification extension — the history `determination_of_record` flattens — with Symbiota's `identificationIsCurrent` (1 or 0) on each, since without it Symbiota imports every identification as not current. The `dwc-archives` job writes them nightly at 4am Pacific into `<exportsDir>/dwca/` beside a `manifest.json`, and **a program-season is written only when its program has both a licence and a privacy policy in force for that season** (Peter, 2026-10-10). Those are decisions curated in git, `ingest/program-licenses.csv` and `ingest/program-privacy-policies.csv` (`src/program-governance.ts`): each row holds from its season until the program's next row and the latest holds indefinitely — Peter's presumption that a program continues with the licence it last used — so ranges cannot overlap, and a season before a program's first row has none. Licences are the three GBIF accepts, written into `meta.xml` as a constant `dcterms:license`; the seeded rows are the licences each atlas's records were last published under on GBIF, with the dataset as the source. The privacy-policy file starts empty, so for now every season is listed and withheld. Every program-season with specimens is listed with its count, licence and policy, read live rather than from the manifest, and the download re-reads the decisions too, so withdrawing one withdraws the download at once and the file at the next run. Which specimens are a program's follows CONTEXT.md's rule with no collecting events yet: an atlas's are those collected on its ground, Master Melittology's those no atlas covers, a season by `sample_season`'s 1 March line. **The BLM surveys get no archive, and must never get one by geography**: their samples will arrive through their own pipeline (field entry, and the collecting event that says whose day it was), so a BLM sample from New Mexico is BLM's, not the New Mexico Bee Atlas's — when that lands, the archives select by the sample's program rather than by where it fell. The page says not to upload them: which `occurrenceID` an imported specimen carries (ADR 0008), the catalog-number prefix Ecdysis matches on, each atlas's answer on taxon-obscured coordinates (beeline-1kb.7.1), and how Beeline holds a publication embargo on particular records (beeline-bqvp) are undecided. A season is the grain Beeline produces and checks at, not the grain to publish: a program should publish one dataset that grows, since a dataset per season is republished by the next cumulative one — every record of Oregon's 2018 and 2019 datasets is on GBIF twice — and GBIF gives a dataset one licence ([docs/research/program-governance-for-exports.md](docs/research/program-governance-for-exports.md), which also holds what a privacy policy must answer and how others record an embargo). Which volunteer determinations go downstream is not among them: each atlas's staff decide that after downloading, outside Beeline (beeline-pyr). Its `id` is the specimen's `entity_id`, which joins the two files and which Symbiota keeps as the record's key; a rebuild redraws it, but only the sandbox is rebuilt, and no archive the sandbox writes will be uploaded anywhere (Peter, 2026-10-10).

### Errors and logs

With `SENTRY_DSN` set, the app reports to Sentry (`src/app/error-reporting.ts`, beeline-8w6.1): a failed request with its route pattern and the signed-in login, a failed job with its name, the console as searchable logs, and every job run as a cron check-in built from its `Schedule`; unset, it reports nothing and behaves the same. The rule is `/healthz/jobs`'s — say which thing went wrong, never the record it went wrong on — so the SDK collects no request body, query string, cookie or local variable, and every message is passed through `redact`, which blanks anything quoted, any decimal of four or more places, tokens and email addresses. Two consequences for new code: log a string, never an object, since the log integration sends an object as JSON whose every quoted key is blanked; and put the value an error is about in quotes, as DuckDB already does, so redaction finds it. Listing requests are also counted, as the application metric `listing.view` (`src/app/usage.ts`), to see how people browse: the listing, the scope, the sort and whether it was changed, a page band, and which filters are in use — each free-text filter reduced to whether it was used, since a listing search is how somebody finds a person or a place — with the viewer's role and never their identity. Every request's latency is the metric `request.duration` by route pattern, method and status, and one over a second also logs a `[request] slow:` line naming the route and the login (`src/app/request-timing.ts`, the outermost middleware): until it, a page that answered in eight seconds was invisible except to the person waiting. A listing's CSV does its work after its response has gone, so `csvStream` reports its pages' time in the store separately, as `csv.generation`. Neither writes anything to the store. The runbook's section is [Errors, logs and job check-ins](docs/runbooks/deploy-fly.md#errors-logs-and-job-check-ins). The `resource-budget` job (`src/fly-usage.ts`) reads the last day of the machine's CPU, memory, swap and disk from Fly's metrics and fails when a limit was crossed, the CPU burst balance being the one heavy batch work actually reaches; Fly counts CPU in clock ticks, not seconds ([the machine's budget](docs/runbooks/deploy-fly.md#the-machines-budget)).

What the person sees is a page, never bare text (`errorResponse` in `src/app/server.tsx`, `src/app/views/error-page.tsx`, beeline-0kj): a thrown error and an address nothing answers both render inside the ordinary layout, so the header, the menu and Send feedback survive, with a way back to the same-site page that linked there and a way home. A failure gets an eight-hex-digit **reference** (`reportAppError`), in the log line and as a Sentry tag, and the feedback email the page starts carries it — so "it broke" arrives with what finds it. It never says *what* failed, since DuckDB's errors quote the values they choke on; development alone shows the error, with a hint where it reads like a store behind its migrations. Not-found never says whether a record is missing or not the person's to see: the record pages answer both with the same page — identical but for the feedback email's note of the address asked for — and a test holds them to it. A page that knows more and leaks nothing by saying it — the taxonomy, print runs, people — passes its own sentence. Signed out, everything is still the sign-in page. A caller that asked for JSON gets `{error, reference}`, and if the layout itself cannot render, a static page that depends on nothing answers instead. **New code answers a 404 with `errorResponse(c, "notFound")`, not `c.text`.**

### Ingestion, jobs, and elevation

Ingestion runs as in-process scheduled jobs (`src/app/jobs/`, history in `job_run`, page at `/jobs`): interactive-window jobs chunk work into SLA-timed steps, the nightly pipeline (updated_since incremental sync → promote → elevation; `BEELINE_SYNC_PROJECTS`/`BEELINE_SWEEP_DAYS`) runs in the 2am-Pacific night carve-out, and a Sunday full sweep of the trailing year is the presence proof deletion detection reads (beeline-3hj). Promotion is one idempotent transaction and DuckDB has no row locks, so a small write committed to a row it rewrites makes it lose rather than wait; it runs again after 1, 5 and 15 seconds before failing (stopping at once if the job is aborted), and the run's detail says when it had to (`src/write-conflict.ts`, beeline-lpx). A sample edit does **not** retry: its new values are computed before any wait, so a retry would overwrite an edit saved meanwhile and leave the live row disagreeing with the corrections overlay, and the samples it edits are ones promotion does not rewrite. Shutdown settles the running job before the store is closed (beeline-fth): `scheduler.stop()` waits a minute for it, then aborts the context's `signal` — which `step()` checks at each boundary and the sync's paging loop checks before every page — and interrupts the DuckDB connection so an in-flight transaction rolls back, and only then does `main.ts` checkpoint both catalogs and close, on a path that is reached whatever threw before it. The version that closed a busy connection from an async callback could lose the checkpoint to an unhandled rejection, which is the unopenable-store state of beeline-c1b. An elevation is a statement about a point, so `sample_location` records the point it was read at (`elevation_latitude`/`elevation_longitude`, CHECK-paired with `elevation_m`) and `schema/170_views_elevation.sql` states the rule once: `sample_elevation_stale` is an elevation about somewhere else, `sample_elevation_pending` is what the derive job selects. A coordinate too vague to place gets no elevation at all: `elevation_derivation_limit` states the threshold once (100 m, tighter than the 250 m at which `qc_rule_coordinate_uncertainty` blocks printing, because an elevation is a stricter claim than a locality string), `sample_elevation_pending` drops those rows so they are never a standing backlog, and the derive job counts them separately so a shrinking gap count is not mistaken for progress. `sample_elevation_unsupportable` names the ones already in the store — 1,558 on the dev store, 744 of them on records that still print, and 1,546 from iNaturalist rather than the legacy import — and removes none of them, because that is a decision rather than a consequence (beeline-6vc). **Do not add a clear-the-elevation rule to a new coordinate writer** — the pending view already covers it, so a move self-heals on the next derive run rather than depending on the writer having remembered; observation promotion clears eagerly only so the intervening state reads "unknown" rather than "confidently wrong", and it does so by naming the view, not by restating its tolerance (beeline-x5c). Observations reach the model through one stored projection: `observation_field` (`schema/060`) is the materialisation of `observation_current_fields` (`schema/105`), which stays the definition and is now also what the table is refreshed from and checked against. It is the one place a view's output is kept, licensed by an input nothing but a sync writes — where a *finding* also depends on `sample`, which the in-app editor writes while promising the flags update immediately, and on `specimen`, which printing will write, so findings stay derived (`schema/050`). Shredding 63k JSON projections costs ~200 ms and three QC rules read it, which is why scanning `qc_finding` cost ~670 ms and the QC home, both listings, printability and the record pages each paid it; storing it took the union to ~205 ms, and replacing `qc_rule_locality_format`'s nineteen `LIKE` passes with one regular expression took it the rest of the way to ~25 ms (beeline-2c3.36, beeline-2c3.37). `refreshObservationFields` runs inside the sync run's own transaction — so loads and their shredded form agree at every commit boundary — and again at the head of promotion, which is how a reseeded or hand-staged store gets one at all; `observation_field_stale` names the disagreement, the way `sample_elevation_stale` does, because an unrefreshed table is not a visibly broken one: the rules simply report nothing and printability calls every sample clean. Two things that projection did not read until beeline-2yt, both needed before an observation can become a sample: `sampleId` is the 2019-onwards sample-number field and the 2018 season used one named `sample id` — not a stray, since 1,054 of its 1,532 usable values match a sample already in the store on (collector, number, date) — so `sample_number_raw` coalesces them, `sampleId` winning, with `observation_sample_number_conflict` there to name a disagreement — empty as it stands, since of the 31 observations carrying both fields the 17 with a value in each all agree; and `OBA Collection Method` (`collection_method_raw`) is the only controlled vocabulary the source offers for how a bee was caught, four values over 10,178 observations. The observer's own free text arrived later still and by a different route (`notes`, beeline-hza): it was missing not because the projection skipped it but because **the sync's `fields` whitelist IS the projection** (`src/sync-inat.ts`) and never asked — so all 64,227 loads on the dev store carry no `description` at all, and no view could have recovered it. Adding the field is what makes it exist; notes then arrive as observations are re-fetched, which for anything outside the Sunday sweep's trailing year means a one-off full sync. 31 of 100 sampled observations carry notes, median 9 characters and longest 151 — mostly the plant's condition, the weather, or a locality detail `place_guess` never had (`Wallowa Mountain Loop (NF-39), along Gumboot Creek`). Stored verbatim — markdown, HTML and leading whitespace alike, with `trim()` used to decide whether there is anything there and never as the stored value — because rewriting it would make the store disagree with iNaturalist about what the collector said; the renderer escapes it, and `/samples/:id` shows it as a row that is simply absent where there are none. A new column on that table goes **last**, always: the refresh inserts positionally and `observation_field_stale` compares with `EXCEPT`, so a `TEXT` column added in the middle swaps silently with its neighbour and the alarm built for exactly that cannot see it — which is also why the two migrations that fill the table name their columns instead of `SELECT *`, a delta being pinned to its moment while the view it reads keeps growing.

Where an observation *is* comes from `place_ids`, never `place_guess`: that field is free text a volunteer typed ("Leach Botanical Garden", "3334 NW Covey Run, Corvallis, OR 97330, USA") and only a state can be read from an id. So `inat_place` (`schema/065`) caches what an id means — filled by the nightly pipeline's fetch-places step between sync and promote, or by `pnpm inat:fetch-places` by hand, unauthenticated because a place has no private projection, incremental against `inat_place_uncached` so "missing" is defined once; the step never fails the run, since a stale cache is fine and a skipped promotion is not, and the fill-only atlas refresh repairs anything minted meanwhile. An id iNaturalist answers with 200 and no result is a place merged or deleted upstream (three on the corpus, one of them on 4,127 observations), recorded in `inat_place_absent` and subtracted from the view, so "uncached" means "not yet tried" and the view can actually be empty (beeline-0oj) — and `observation_place` (`schema/107`) reads country/state/county off `admin_level` 0/10/20, preferring `private_place_ids` exactly as the coordinate rule prefers `private_geojson`, since iNat withholds place ids on a private observation too. `atlas_region` gains the place id of every region, which is the only route from an observation to the two-letter code and so to an atlas; the ids were derived twice and agreed — iNat's autocomplete, and independently the place that actually appears on the observations behind the samples already filed under each code. Verified before it shipped: the derived state agrees with the legacy import on 57,241 of 57,278 linked samples, every observation carrying any place ids resolves to a state (the 82 that do not carry none at all, 60 of them because geoprivacy is `private`), and `observation_place_ambiguous` — the alarm on the lowest-id tie-break — is empty. Of the 37 disagreements at least one is the *legacy* record being wrong, and in a way `qc_rule_place_unrecognised`'s own comment predicted: two Utah samples carrying `CAN`. `inat_place` is in `db:reseed`'s `CARRIED_TABLES` because it is the one carried table promotion cannot recompute — it comes from an outbound fetch, and leaving it out would silently give a reseeded store no atlases at all.

An observation becomes a sample in `ingest/mint-samples.sql`, and until beeline-oyq nothing did: observation promotion started every join from a sample the legacy dump had already supplied, so it was a provenance upgrade and never a source of records — which at cutover, when the legacy import freezes and iNaturalist becomes the only entry point, would have made a whole season invisible rather than visibly broken. Promotion is now three files in one transaction and **the order is the point**: `harvest-inat-accounts.sql` first, because minting resolves an observer to a person through `inat_account` and minting ahead of the harvest would mint fewer samples on every pass; `mint-samples.sql` second; then `promote-observations.sql`, which keys on the `inat_observation_id` minting has just set, so a sample minted on this pass is located on this pass. A collection record is `observation_sample_candidate` (`schema/108`) — a sample number, a positive count, a date, count zero being the project's own signal that nothing was collected — shared with beeline-e85's unclaimed screen so both agree. An observer the store cannot resolve is never minted, since every sample has a primary collector and a placeholder person is worse than a queue (324 records, `observation_sample_unresolved`). **The reconcile key is a date RANGE, not `date_start`**: a trap sample spans a range and its observation is dated on the END, and keying on the start turned 20 free links into duplicate collecting events that `qc_rule_duplicate_sample_number` could not see, because it groups on `date_start` too. Once an observation is linked *the link is the identity*, which is what stops an upstream edit to a `sampleId` minting a second sample — the reference implementation's sha256-primary-key bug. A group matching two existing samples is neither linked nor minted but named (`sample_mint_ambiguous`, 3 on the dev store, all pre-existing duplicates); `kind` and `protocol` are the constants `net`/`aerial net` and never derived from `OBA Collection Method` (`schema/060` says why); the observer is the primary collector, making minting the second writer the head-of-list invariant (`sample_primary_collector_invalid`, schema/116) was waiting for. Measured on the dev store: 1,421 samples minted, 1,113 existing ones free-linked, `pending_print_sample` non-empty for the first time at 962.

Minting **never rewrites** an existing sample's date or count, or a printed sample's number — `inat_observation_id` stays scalar and there is no `sample_observation` list, which is what makes that guarantee cheap and what protects a staff edit to any field minting writes; `sample_observation_number_mismatch` and `sample_multi_observation` are the cost of it, named rather than argued away (the 633 disagreements on the dev store are all pre-existing legacy links, 57 of them a bare zero-padding difference). **One observation is one sample**: several claiming one sample number is a collector error, not one collecting event recorded twice (Peter, 2026-10-04, beeline-0199). Both writers merged them, on the very key `duplicate_sample_number` grouped by, so that rule, counting samples, never fired once; now neither does. Minting makes one sample per observation, so two observations carrying one number are two samples with that number, each with its own count, and an unprinted sample's **number follows its observation** as its locality does — which is how the volunteer's renumbering on iNaturalist clears it on the next nightly. It mints beside an unprinted sample citing another observation, which is the collision showing before anything prints, and never beside a printed one or one citing nothing: those may hold the specimens on pins already, and minting would label them twice. Legacy promotion splits a group of records by observation whenever they name more than one (`legacy_row_observation`) — 434 groups on the 2026-10-04 corpus, every row linked — and so ranks reprints within an observation, never across: each observation numbers its own specimens from 1, and treating specimen 1 of one and specimen 1 of the other as one pin printed twice had refused 2,467 real specimens, 701 of them from the open season (beeline-bib1) — so each is the sample its pins describe, and it writes each sample's observations to `sample_legacy_observation`, which minting will not mint again. `sample_claiming_observation` (`schema/108`) still names any sample more than one observation claims — a cited one since renumbered claims it no longer, and an observation another sample cites claims nothing here, so a household sharing a login or a trap whose range takes in another day's net sample is two samples, not a conflict. Either shape is a `sample_number_conflict` (`schema/120`); `qc_rule_sample_number` flags it as `duplicate_sample_number`, blocking, only where the sample is not yet printed, and a printed one is named there and **flagged nowhere** (Peter, 2026-10-04): its pins carry the number for good and there is nothing left to do. `printed_sample` lives in `schema/101` for that reason, ahead of minting and the rules. The inverse, one observation cited by several samples, is not a cost of that design but legacy residue minting cannot produce, and is named the same way rather than constrained: `sample_shared_observation` (beeline-15k), each group labelled by the shape that decides its repair — different collectors, a collector unknown, same date, same number, duplicate. Descriptive fields are the exception and they are a **fill-only refresh**, with one exception of their own: an unprinted sample's `locality` — one with no specimen rows yet — **follows** its observation on every promotion, because until the labels print it is the volunteer's to fix on iNaturalist and nobody can edit an iNat-linked sample in the app (beeline-kza). `inat_place` is network-fetched, so a reseeded store that promotes before `pnpm inat:fetch-places` has run would otherwise mint samples whose geography no later fetch could repair. Fill-only is what makes it safe to run over every iNat-linked sample rather than only over minted ones — it writes where the store says nothing and so cannot reach a value the legacy import stated or a staffer typed, which is just as well, since by design there is no way to tell a minted sample from an imported one. Verified: across 66,293 existing samples it filled 26 localities and 2 counties and overwrote nothing, on any field. The host's iNaturalist taxon id joins it on one extra condition, that the sample's host name agrees with the observation's, since a legacy name was typed apart from the observation and an id beside the wrong plant is worse than none (beeline-z9j). The atlas joins that refresh too, and could not until beeline-6e9: DuckDB will not update an **indexed** column on a row an incoming foreign key references (duckdb/duckdb#20246, pinned by test), every sample has a `sample_collector` row, and the atlas was a column on `sample` — set at INSERT or never, with `sample_atlas_unfilled` naming permanent damage and the reseed recipe fetching places first to prevent it. The same freeze made reassigning a collector impossible, which is most of what the staff override screen is for. The fix is structural: the atlas lives in `sample_atlas` (a satellite nothing references, so it stays writable; no row = outside, a NULL atlas with `assigned_by` set = a human stating "belongs to none", which the refresh never overwrites), `sample.collector_id` is gone with the primary collector defined as `sample_collector` position 1 (read through `sample_primary_collector`, schema/100), and `sample_atlas_unfilled` is now the worklist the refresh drains on every promotion — fetch-places-first is tidy but no longer load-bearing. Reseed-only per ADR 0006: no migration can rebuild `sample`, so migrations 0001–0023 are the pre-reseed epoch and a store shaped before it is caught by `db:migrate --check`. A minted sample's `locality` is the first comma-separated component of its (private-preferred) `place_guess` that reads like a place name — at least 2 characters, no street suffix, no postcode (US, Canadian or plus code), no house number, not the observation's own state or country — which beats the reference implementation's exactly-three-parts rule (86% against 68% on the 2026 set). It has no upper length: a name too long for a label is minted as written and flagged by `qc_rule_locality_format`, because the 18-character cap it used to carry skipped to the next component, which for 113 observations was a postal town and in the case that surfaced it one 12.3 km from the trail the bees came off (beeline-kza). That flag is clearable only because the unprinted locality follows its observation; the price is the urban cases, where the substitute town was right, which now ask the volunteer too. The street-suffix predicate lives once, in the `locality_street_suffix_pattern` macro, because that rule and this one both read it — and it says *where* the word sits, not only that it is there (beeline-4dt): `st` is Saint and the abbreviation for State as well as Street, so an unanchored list told 168 samples that "St Helens" looked like a street address and ~70 more the same about "Cottonwood Canyon St Prk", which is the one kind of QC finding that damages data, since the only way to satisfy it is to write the locality wrongly. A Saint or a State precedes the rest of the name and a Street ends it, so the word must end its comma-separated phrase, give or take a trailing directional or road number — a fact about English addresses rather than a list of exemptions to keep. It is a deliberate divergence from the reference implementation, which has the same defect. 310 samples lose the street flag on the dev store, 283 of them correctly and 27 backcountry road references with the number in the middle, all of it in the settled seasons; the fill-only refresh gives 114 observations the locality the list had been refusing them, with no backfill. On the minting side the anchor took away the accident by which `lane` refused `Lane Co.`, and the accident turned out to be covering a larger hole (beeline-bev): only the long spelling `Wheeler County` was ever refused, so 583 observations read `Deschutes Co.` where the guess also said `Bend` — the rule takes the first usable component and the county comes first. `observation_locality` now names the county in its administrative clause beside the state and the country, data-driven off `observation_place.county_name`; 116 observations carrying a bare county and nothing else get no locality at all, which is the documented outcome for a guess too coarse to use, and existing samples keep what they have because the refresh is fill-only. A **macro** and not the one-row view a shared constant would otherwise be, and that is a measurement rather than a taste: DuckDB compiles a regex once for a literal pattern and once per row for anything else, so reading it out of a view cost 1.1 s over 67,304 localities against 18 ms — the whole `qc_finding` union 1.1 s against 34 ms, which every QC read in the app pays. A threshold in a one-row view (`elevation_derivation_limit`) costs nothing because nothing is compiled; a pattern is different in kind, and it is [ADR 0001](docs/adr/0001-duckdb-first-with-portable-sql.md)'s third named exception (beeline-5bm).

## Conventions & Patterns

- Build only what the current roadmap phase needs; the fuller domain sketch waits in [docs/schema-sketch.md](docs/schema-sketch.md) and is re-reviewed when its phase arrives.
- Keep DDL dialect-neutral per ADR 0001: `TEXT` + `CHECK` for enum-ish columns, `concat()`/`concat_ws()` over `||`, no partial unique indexes. Three exceptions are named and taken deliberately — the iNaturalist JSON shredding (`schema/105`), the street-suffix predicate in `qc_rule_locality_format` (`schema/120`), and that predicate's pattern as a `MACRO` rather than a one-row view (`schema/108`, because DuckDB recompiles a regex per row unless the pattern is a literal) — each marked in place with what a port must rewrite, and each with a measurement behind it rather than a preference. **Never `~`**: DuckDB's is `regexp_full_match` and Postgres's is a partial match, the one construct found so far that answers differently in the two engines without erroring.
- Collecting is often a pair (two thirds of legacy trap specimens), so collectors are a list: `sample_collector` in `recordedBy` order, position 1 **being** the primary — whose sample numbering it is. There is no `sample.collector_id`: the column was the same fact written twice, needed a view to police the copy, and could never be UPDATEd (beeline-6e9), so `sample_primary_collector` (`schema/100`) is the one definition every primary-collector read joins, and every "my samples" query reads the list (beeline-77j). What the engine cannot hold is now exactly one head per sample — `(sample_id, person_id)` stops neither a headless list nor two collectors both at position 1 — and `sample_primary_collector_invalid` (`schema/116`) names both, asserted empty after each promotion (beeline-daa). That list comes from the rows a sample is made of, never from everything its `(firstName, lastName)` pair ever recorded — one stray name on one row used to collect 1,675 samples. Person identity is the recordedBy name folded to letters and digits, so typography cannot split a human in two, and the display name is the spelling used **last** — a name changes only when somebody corrects it — but only where the later spelling *succeeds* the earlier rather than interleaving with it, since a single stray row is a keystroke and not a change of name; spellings that fold apart but name one human (`Barrett Barrett`, `Emily Hoskins`) are curated in `ingest/collector-aliases.csv`, and the worklist they are curated from is `legacy_collector_duplicate_candidate` — person records filing under one iNat login, minus the ones who collect together (beeline-eyk). The legacy system's own hand-curated name register (`shared/data/usernames.csv`, fetched by `pnpm legacy:fetch` into gitignored `data/legacy/`) is a second opinion and not an authority over any of this: it fills no missing name part — the people who have none have no iNat login for it to match on, which `legacy_register_unreached` is the view of — and of the 414 people it does reach it disagrees about 25. A few it has right in a way promotion cannot see (`MaryJo`→`Mary Jo`), several it has plainly wrong (`Herrmann`→`Hermann`, against a login of `mherrmann` and an iNat profile of `Mady Herrmann`), some are a nickname against a formal name in both directions (Kim/Kimberly, but also William/Bill), some are its own bad rows, and one is a shared household login that would hand Tom Robertson the name Julie Biddle. The login is the cheap adjudicator wherever it says anything at all; where it says nothing the person gets asked rather than picked for. So it lands as `legacy_register_name_conflict`, which is a **report and not a worklist** (Peter, 2026-08-28): staff fix names on `/people/:id`, which writes the overlay and applies immediately, so a name nobody has complained about is not worth a curation session in git. The view stays because "what does the register think about this person" is a fair question to be able to ask; nothing graduates from it on a schedule. Its email and mailing-address columns are never staged into the store at all — that satellite does not exist yet (beeline-8t8, beeline-1kb.6).
- Scientific names come apart in exactly one place, `ingest/parse-names.sql`, which runs before anything reads them apart: `legacy_det_taxa` names the outcome (genus, subgenus, epithet, authorship, trinomial) and `legacy_name_parse` is the survey of what those rules do to every distinct verbatim string, because a parser is a pile of assumptions about strings nobody here wrote and the only way to know which hold is to run it over all of them and read the residue (beeline-qcd). All three sources that write names in columns come apart there — the expert columns, the volunteer ones (`legacy_vol_det_taxa`), and the staff taxonomy list — by rules that are facts about zoological names rather than a list: a genus is capitalised and an epithet never is, and a bracketed name is a subgenus wherever it was written, which the subgenus column (`Andrena (Andrena)` on 2,888 rows, once minted as `Andrena (Andrena (Andrena))`), the epithet column, the volunteer genus column and the staff list all do (beeline-45v.2). What no rule can recognise is misspelling (`Agopostemon`), curated in `ingest/taxon-aliases.csv` with `legacy_taxon_alias_unused` beside it — spelling only, since a gender ending or a name ITIS lacks is a taxonomic choice and belongs to the curation layer (beeline-45v.1). Two rules were wrong until it did: authorship was "whatever follows the binomial", which on a trinomial is the third epithet — `Osmia montana` authored *montana*, `Bembix americana` *spinolae* — and authorship prints on a label, which is permanent; and a subspecies was recognised from `taxonRank`, which calls two of the corpus's five trinomials a species. So authorship must look like one (`(` or a capital) and must have had a binomial to follow, and a trinomial is this row's own genus and epithet plus one more bare epithet, anchored on the parted columns rather than the string's shape — which read `Not a bee` as a subspecies of *Not a*. `test/legacy-name-parse.test.ts` runs the real parser over strings lifted from production staging, near-exhaustively by category, since the corpus is only 727 distinct names. What the model still cannot say is in `legacy_name_flattened`: 25 morphospecies (`Melissodes sp.1` and `sp.5` are one node, beeline-8g7) and one `nr.` (beeline-tgu) — nobody typed those wrong and no volunteer can fix them, so they are a view rather than a flag. `legacy_verbatim_shape` surveys the other parsed fields the same way, and its answers are what license their rules: `recordedBy` uses `|` and nothing else — no `&`, no comma — so splitting on the pipe is complete; 1,731 records spell the month in Roman numerals, which `legacy_month` already takes; and of the URLs the observation id is read off, five point at an iNat *taxon* page and correctly yield nothing.

Identity per [ADR 0002](docs/adr/0002-entities.md): entity tables have an `entity_id` PK drawn from the global `entity_id_seq`; facet tables (1:1 satellites) are keyed by their parent's id; only global-identity columns are named `entity_id`.
- Document tables and columns with `COMMENT ON` (queryable in-database); reserve `--` comments for design rationale spanning statements.
- **Report every check count split by season** (Peter, 2026-08-29): the open season against the settled ones, never one number. A defect in current-practice data says the workflow is broken now; the same defect before it is residue from the wild west, and a combined figure cannot tell you which — nor whether a number that looks stable is actually a live problem growing under a historical one. The line is the store's own, `season.started_on` / `settled_sample` (`schema/160`), judged on `date_end` for a sample and `observed_on` for an observation; not a hand-rolled 1 January, which puts the first two months of a season on the wrong side. It changed the reading of minting's own numbers: `non_tracheophyte_host` is 0 against 40, so host plants are a solved problem; a missing locality is 14% of the open season against 34% before it; but `obscured_no_true_coordinates` is 50 against 21, which is the one that *inverts* — obscured-without-trust is a live and growing gap, not a historical one, and only the split says so.
- Tests run against in-memory DuckDB built from the real `schema/*.sql` (`createMemoryDb`), so a schema mistake fails a test rather than a review — the load-bearing half being *from the real schema*, not *in memory*. Where being file-backed is itself what is under test, `createFileDb` (`test/helpers.ts`) applies the same schema to a file: the default catalog is then named after the file rather than `memory`, which is where beeline-d34 lived, invisible to a suite in which every test paired a file-backed private store with an in-memory main one. It is slower, and reaching for it anywhere else is a mistake. `insertCleanSample` (`test/helpers.ts`) is the fixture that makes a sample nothing is wrong with, and a test that wants something wrong says which. Assert against strings the source actually produced rather than invented ones — `test/legacy-name-parse.test.ts` is the pattern, its corpus lifted from production staging and its few synthetic cases labelled as such, because a parser tested only on strings we wrote is a parser tested on our assumptions.
- `src/model.ts` (Kysely types) follows the SQL by hand — update it with any schema change.
- Kysely is pinned to 0.28.x until `kysely-duckdb` supports 0.29.

## Non-Interactive Shell Commands

**ALWAYS use non-interactive flags** with file operations to avoid hanging on confirmation prompts.

Shell commands like `cp`, `mv`, and `rm` may be aliased to include `-i` (interactive) mode on some systems, causing the agent to hang indefinitely waiting for y/n input.

**Use these forms instead:**
```bash
# Force overwrite without prompting
cp -f source dest           # NOT: cp source dest
mv -f source dest           # NOT: mv source dest
rm -f file                  # NOT: rm file

# For recursive operations
rm -rf directory            # NOT: rm -r directory
cp -rf source dest          # NOT: cp -r source dest
```

**Other commands that may prompt:**
- `scp` - use `-o BatchMode=yes` for non-interactive
- `ssh` - use `-o BatchMode=yes` to fail instead of prompting
- `apt-get` - use `-y` flag
- `brew` - use `HOMEBREW_NO_AUTO_UPDATE=1` env var

## Git Authority

**This repository authorizes agents to commit and push without asking, and
work lands as a pull request** (2026-08-28). Branch, commit, push, open it with
`gh pr create`; close the beads you finished when it merges. No approval is
needed to open one, or to merge a green one — the review, not the asking, is
the point. **Do not commit or push to `main` directly**: nothing gets reviewed
on the way in that way, which is the whole reason for the branch.

**Beads are the exception** (Peter, 2026-08-28). Issue work syncs with `bd
dolt push`, and the `.beads/*.jsonl` exports it changes are committed straight
to `main`. They are a passive export of a store that has already been synced —
there is nothing in them for a reviewer to read, and wrapping them in a pull
request spends a review cycle on a machine-written file.

This is the "repository profile" the Beads block below defers to, and it
overrides that block's conservative default — stated here, outside the managed
markers, so `bd setup` cannot regenerate it away.

Committing straight to `main` was the stance until CodeRabbit began reviewing
every pull request, and the reason to change was empirical rather than
procedural: on beeline-o22 it found a real defect that four rounds of
adversarial design review had missed — an identity shortcut on the sibling code
path of one already fixed. It is good at exactly what design review is worst
at. Since 2026-10-04 it reads Peter's branches locally, through the CodeRabbit
CLI, before the pull request is opened, so findings become ordinary edits rather
than push-and-wait round trips; the PR bot skips his PRs (`.coderabbit.yaml`)
and still reviews everyone else's. Triage what it says: fix what is real, and
give the reason in the PR when declining. The branch still earns its keep: CI
runs on it, and the pull request records what landed and why.

Why the commit authority itself is broad is the era, not the tooling:
pre-cutover the store is blown away and rebuilt at will, nothing downstream
consumes it, and no volunteer sees it, so a bad commit costs a revert and
nothing else. **Revisit at cutover (December 2026)**, when minted field numbers
become permanent and backups become mandatory — the blow-away era ending is
what makes this stance expire, and is when a PR will want a human approving it
rather than only a bot reading it.

Still true regardless: don't commit someone else's uncommitted work, don't
rewrite published history, and keep documentation current in the same commit as
the change it describes.
