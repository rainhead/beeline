# And to a sample

Part of Beeline's architecture notes; the index is in [AGENTS.md](../../AGENTS.md#architecture-overview).

Samples get the same treatment (beeline-ewl, the second instance of [ADR 0007](../adr/0007-authored-changes-are-events.md)): `data/sample-change.csv` (`src/sample-change.ts`) is append-only events, produced by the same compare-against-what-was-last-said pass at the end of legacy promotion, after observation promotion, and at boot — so the nightly's coordinate rewrites, minting, free-linking, and a staff edit all leave a trace, and a writer that forgets is caught by the next pass. The edit screen runs a pass narrowed to its one sample, so the author is credited with their edit and nothing else. Where it deliberately differs from the person log: the baseline lives in `data/sample-state.csv` — one current row per sample, restated wholesale each pass — because the person log's in-log baseline over this corpus would be a million rows; the reference is the derived triple (collector as the overlay names them, number, start date), with the observation link recognising a sample across a corrected number or date — and outranking the triple where a sample carries a different observation from the one recorded and another sample now carries that one, which is what splitting two observations that shared a number leaves (a renumbered sample, and a newcomer on its old number) — and a triple collision (a live duplicate) recorded as nothing and counted. The record page reads it as the History panel on `/samples/:id`, from a parse the app takes at boot and extends with its own appends, since the log is 15 MB on the sandbox and re-parsing it after every nightly cost the day's first sample page about 1.5 s. Measured on the dev store: baseline 1.1 s and 11.2 MB, a steady pass ~2 s and zero entries, and a nightly-shaped 30 moves + 2 renumbers recording exactly 32. The snapshot is a statement about one store, and a full pass **refuses** one that mostly names samples the store does not hold — no entries, no restatement, and a message naming the file — because the vanishing rule records silence and a store that has never seen a sample records an arrival, so a scratch store pointed at the shared `data/` paths turns one boot into a million-row append on the next real pass (the screenshot fixture did exactly that on 2026-09-21, and the 1,085,665 rows appeared on 2026-09-23; beeline-hrw). Refusing rather than re-baselining is what makes the mistake cost nothing in either direction: the fixture's own boot leaves the real snapshot alone. A store that has genuinely replaced the snapshot's re-baselines by deleting the file, and a snapshot with no rows is read as no snapshot. On the nightly a refusal **fails the run**, after the elevation step so nothing the store needs waits on it, because a refusal is a standing condition that needs a person and a green `/healthz/jobs` over an unrecorded history would hide it; the CLIs and the boot pass warn. Start a scratch app with `BEELINE_SAMPLE_CHANGES`/`BEELINE_SAMPLE_STATE`/`BEELINE_PERSON_CHANGES` pointed away from `data/` regardless; the person log has no snapshot to protect and simply gains the fixture's people as arrivals.
